Pi 选型建议与实践路线

推荐原则：如果你重视模型中立、运行时可塑性、透明 Session 与 TypeScript 嵌入，并愿意自行承担安全边界和工程治理，优先试 Pi；如果你想直接获得成熟的 MCP、多 Agent、企业策略或内置 Sandbox，应先试更匹配的成品。

决策方式：先做可逆、低风险的短期 PoC，用真实任务和硬指标验证；不要从“功能列表喜欢”直接跳到全团队标准化。

快速阅读： 结论 · 决策树 · 场景 · 风险 · PoC · 验收 · 资料

核心结论

  1. Pi 是“自建 Agent 产品”的良好底座，不一定是“零配置团队工具”的首选。它把 Provider、Agent Loop、TUI、Session、Extension、SDK 暴露得清楚，同时故意不内置大量上层工作流。
  2. 最大选型风险不是模型质量，而是安全与长期维护。Pi 无内置权限系统；自定义 Extension 与 Package 又拥有完整进程权限。没有容器/账号隔离、版本固定、代码审查和维护人时，不应扩大使用。
  3. 个人采用和平台采用要分开决策。个人 TUI 试用只需验证工作效率与可恢复性；嵌入产品还要验证并发、Session 隔离、取消、协议兼容、观测、成本和故障恢复。
  4. 竞品不是替代名单，而是需求探针。需要 Claude 原厂工作流看 Claude Code；需要内置 Sandbox 看 Codex CLI；需要 HTTP client/server 看 OpenCode；需要 Git 精细编辑看 Aider；需要 MCP 通用自动化看 Goose。
  5. 选型必须预留退出。提示、Skills、评测任务、业务工具 schema 和结果数据应保持 Harness 无关；不要让关键流程只存在于某个 Session 或私有 Extension API。

决策树

强内置治理？是 → Codex / Claude / OpenCode
多模型 + 深定制？是 → Pi PoC
只要 Git 结对？是 → 对照 Aider
量化验收通过采用；不通过退出

每个分支都应带同一组真实任务验证。决策树负责缩小候选，不替代 PoC。

第一问：安全边界必须由工具内置吗？

  • 必须内置 workspace Sandbox、审批与集中策略：先验证 Codex CLI；若组织已深度使用 Claude，再评估 Claude Code managed permission。
  • 已有容器、短命工作区、最小权限账号与网络策略：Pi 的“宿主负责隔离”可能更简单，继续下一问。
  • 目前没有任何隔离，也不准备建设：不要让 Pi 处理生产凭据、公司主仓库或可发布环境。

第二问：你真正需要哪种扩展？

需求优先候选判断依据
TypeScript 进程内注册工具、拦截事件、定制 TUIPiExtensionAPI 与 SDK 直接，开发反馈快
大量现成 MCP、Skills、Subagent、团队插件Claude Code / OpenCode / Goose / Codex这些能力是一等产品面，不必自建桥接
稳定 HTTP API，多客户端共享后端OpenCodeServer + OpenAPI + generated SDK 是核心架构
跨语言但只需本地子进程Pi RPC / Codex exec / Goose run比较 framing、事件、Session、取消和稳定性
文件级 Git 编辑与自动 lint/testAiderrepo map、编辑格式、commit/undo 是主线设计

第三问：你要控制力还是成品能力？

如果团队愿意维护 Prompt、Skill、Extension、安全容器和评测，Pi 的留白是优势。如果团队只想安装后立即获得 plan、权限、MCP、Subagent、IDE 与企业策略，留白就是成本。不能把“未来可以用 Extension 实现”算作“今天已经具备”。

场景建议

场景建议起步方式主要警戒线
个人学习 Agent 原理优先试 Pi读五核心包；做一个只读 Tool；观察 JSONL tree不要把 demo Extension 当生产安全机制
个人日常编码Pi、Aider、Codex CLI 三选一对照固定模型跑 10 个真实小任务误改率、恢复成本和每任务费用
多 Provider 成本路由Pi 或 OpenCode固定 2～3 个已验证模型；做 fallback 演练工具语义和推理块跨 Provider 不一致

CI 自动修复/评审可用 Pi print/JSON，但先比较 Codex exec/Goose run只读或最小工具；短命容器；输出 schema无交互 trust、无限 turn、凭据和网络
嵌入内部 TypeScript 工具Pi SDK 值得 PoCadapter 隔离 API；一请求一 Session/工作区共享进程权限、取消、内存、版本漂移
跨语言桌面/IDE 集成Pi RPC 可试；OpenCode Server 通常更自然先做进程监督与 JSONL contract test半帧、背压、进程崩溃、重连
高合规企业统一部署默认不从 Pi 起步先列 SSO、审计、策略、数据留存、Sandbox 硬要求自建治理成本可能远高于许可证
面向外部客户的多租户 Agent SaaS不要直接暴露 Pi RPC独立身份、工作区、队列、配额、审计和密钥代理跨租户泄漏与远程命令执行

何时优先试 Pi

  • 要同时支持多家模型，并愿意为每个模型维护能力测试。
  • 需要 TypeScript SDK 或进程内 Extension，而不是只调用一个黑盒 CLI。
  • 希望 Session 使用可读 JSONL、能够研究 tree/compaction/context transformation。
  • 已有外部 Sandbox/容器平台，或任务本来就在一次性受限环境中运行。
  • 团队有明确维护人，能跟踪 Earendil 包的快速演进与迁移。

何时不要选择 Pi

  • 不要选择 Pi，如果“内置审批 + 强 Sandbox + 企业集中策略”是不可妥协的上线门槛，而你不准备自建外部控制。
  • 不要选择 Pi，如果业务依赖大量现成 MCP、复杂 Subagent/Agent Teams、后台任务，却不愿维护对应 Extension。
  • 不要选择 Pi，如果团队需要一个有 SLA、商业支持、统一身份与合规合同的完整成品。
  • 不要选择 Pi，如果唯一需求是小步修改 Git 文件；Aider 可能更简单，成熟产品也可能更省运维。
  • 不要选择 Pi，如果无法固定版本、测试 Extension 或为快速 API 演进预留升级预算。
  • 不要选择 Pi，如果计划把 RPC 直接暴露公网，或让不同租户共享进程、cwd、Session 与凭据。

采用风险

风险早期信号缓解措施停止条件
宿主权限过大Agent 可读主目录、SSH、云凭据或仓库外文件短命容器、只挂工作区、最小环境变量、网络 allowlist无法证明租户/凭据隔离
Extension 供应链安装 latest、隐式依赖、项目一信任即执行固定 commit/version、源码审查、lockfile、禁 lifecycle script、内部镜像扩展来源不可追溯
API/协议漂移升级后类型、事件或 RPC 字段改变adapter、contract test、canary、双版本回退关键流程无兼容窗口
模型差异换 Provider 后工具参数错误、结果质量骤降模型 allowlist、每模型 eval、fallback 降级规则核心任务成功率低于基线
上下文有损Compaction 后忘记约束、重复操作短 Session、外部事实文件、摘要验收、保留原 JSONL关键决策无法审计复原
成本失控工具循环、上下文增长、重试放大turn/token/时间/费用预算，终止工具，Provider 限额单位任务成本超过人工或替代方案阈值
自动化不可取消abort 后子进程/请求仍在运行全链路 AbortSignal、进程组清理、超时分级取消不能在 SLA 内收敛
维护人缺失没人负责升级、安全公告和失败复盘明确 owner、月度升级窗、运行手册连续两个升级周期无人维护

最低安全基线

  1. Pi 进程使用专用非管理员账号；容器只挂载目标工作区，不挂主目录和宿主 Docker socket。
  2. 凭据按任务注入，只给所需 Provider/服务；不把通用云凭据、SSH Agent、浏览器 profile 暴露给进程。
  3. 第一次运行只启用 read/grep/find/ls；写入和 Bash 按任务逐步开放。
  4. 项目 Extension、Package、Skill 脚本必须经过代码审查；Project Trust 记录不等于安全审计。
  5. 禁用自动 push/deploy/merge；发布动作由独立、有审批的流水线执行。
  6. Session、日志和 Telemetry 先做数据分类、留存与脱敏；分享前人工审查。

两周短期 PoC 实践路线

目标不是“学会所有命令”，而是回答三个问题：Pi 是否提高真实任务完成率？安全与维护成本是否可接受？相对第二候选是否有足够优势？建议同时选一个对照工具，避免单臂试验。

第 0 天：冻结实验条件

  • 挑选 12 个历史真实任务：4 个只读定位、4 个小修复、4 个跨模块任务；移除敏感数据。
  • 记录初始 commit、测试命令和人工完成基线；定义成功、部分成功和失败。
  • 固定 Pi 版本、Provider/model、thinking level、工具集合、系统提示和最大预算。
  • 建立一次性容器或受限账号；确认工作区外文件、网络和凭据不可访问。

第 1～2 天：只读理解

pi --tools read,grep,find,ls \
  "只读分析仓库：定位入口、测试命令和指定故障路径；引用文件证据。"

git status --short

记录定位准确率、读文件数量、Token、耗时和错误假设。若只读阶段就频繁幻觉文件或无法使用目标模型，不要急着开放写权限。

第 3～5 天：交互式小修改

  1. 每个任务使用独立分支和命名 Session。
  2. 要求先复现或补测试，再做最小修改；完成后由外部脚本验证。
  3. 测试 /tree、resume、abort 和 Compaction；记录恢复失败。
  4. 同一任务用对照工具和同模型重复，至少交换先后顺序，减少学习偏差。

第 6～8 天：一个最小 Extension

只实现一个真实痛点，例如内部只读查询、测试结果格式化或禁止直接 push。扩展必须包含参数校验、取消、输出限制、错误标记、状态恢复和自动测试。若一个简单需求就需要大范围覆盖内置工具，说明 Pi 的扩展模型可能不匹配你的治理方式。

第 9～10 天：SDK 或 RPC 自动化

  • TypeScript 产品选 SDK；其他语言/故障隔离选 RPC，二者不必同时做。
  • 实现 timeout、abort、进程/Session cleanup、结构化终态和一条只读 CI 工作流。
  • 注入 Provider 429、网络超时、工具异常、畸形 JSONL 和进程退出。
  • 验证同时两个任务不会共享 cwd、Session、Extension state 或凭据。

第 11～14 天：对照与决策

  1. 用 Pi 和第二候选完成剩余任务，不临时改变评分权重。
  2. 审查所有 diff、测试证据、Session、成本和人工干预记录。
  3. 做一次版本升级演练和回退；做一次容器/凭据边界攻击测试。
  4. 输出采用、限定采用或退出结论；限定采用要写清任务类型、模型、工具和数据范围。

验收标准

类别建议门槛证据
任务质量小任务一次通过率不低于现有流程；跨模块任务无未解释回归固定测试、人工 review、任务日志
人工效率中位有效工时有明确下降；审批/纠错次数可接受计时与干预计数，不用主观“感觉快”
可恢复误改可用 Git 恢复；Session resume/tree 可复现关键上下文故障演练录像/记录
安全不能读取未挂载目录/未注入密钥；不能绕过发布边界负面权限测试
取消abort 后在约定秒数内停止模型、工具和子进程进程表、网络和临时文件检查
成本单位成功任务成本在预算内，异常循环有硬上限Provider usage + 嵌套 Tool usage
兼容固定版本可复现；升级 contract test 全过且可回退锁文件、镜像、CI 报告
运维有 owner、告警、日志脱敏、Session 清理和故障手册责任表与 runbook

三档决策

  • 采用：质量、效率、安全和维护全部过线；先限制到 PoC 验证过的任务与模型，再逐步扩展。
  • 限定采用：只读分析、个人开发或受限容器中过线，但自动化/多租户未过线；明确禁止超范围使用。
  • 不采用：安全边界、可恢复性或成本任一硬门槛失败；不要用“后续提示词优化”掩盖基础设施缺口。

退出策略

  1. 固定最后可用版本。保留 package lock、安装包/镜像、配置 schema 和已验证模型列表，确保过渡期可运行。
  2. 导出数据。Session 为 JSONL，先备份并按数据政策脱敏；把关键决策转成普通文档/issue，而非只留在会话。
  3. 隔离适配层。业务侧只依赖自定义的 AgentRequest/AgentEvent/ToolResult，由 adapter 映射 Pi SDK/RPC，便于替换。
  4. 保持资产可移植。优先使用标准 AGENTS.md、Agent Skills、JSON Schema 和独立 CLI/MCP 服务；Pi Extension 只做薄胶水。
  5. 建立双跑窗口。退出前让 Pi 与替代工具同时跑代表任务，比较结果与成本，再迁移流量。
  6. 撤销权限。删除 Provider token、Package、Extension、容器镜像、缓存和不再需要的 Session；检查外部分享/Gist。

最终建议

对学习和可控的个人工程实验，Pi 值得优先投入：代码小而不玩具，能从统一 LLM API 一路看到 Agent Loop、TUI、Session 和嵌入接口。对团队生产采用，则应把它看成“需要自己完成最后一公里的平台组件”。只有当这份自主权带来的价值超过安全、运维和升级成本时，Pi 才是正确选择。
