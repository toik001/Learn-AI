Pi 源码架构与运行机制

一句话：Pi 把“模型协议、Agent 循环、编码会话、终端渲染、遥测和远程协议”拆成独立 package；一次交互由 AgentSession 做应用编排，Agent/agentLoop 执行模型—工具循环，事件同时驱动 TUI、Extension 和 JSONL Session Tree。

源码快照：本文检查 2026-08-10 下载的 earendil-works/pi 主分支，package 版本字段为 0.84.1。主分支可能领先正式 release，因此版本号属于仓库观察。

快速阅读： 核心结论 · Package · 请求路径 · Loop · 事件 · 会话 · 资料

核心结论

  1. 分层边界清晰：pi-ai 只负责模型与 Provider，pi-agent-core 负责通用 Agent 状态和 Loop，pi-coding-agent 负责编码领域的资源、工具、会话和模式。
  2. AgentSession 是应用编排核心：它处理 Extension 输入拦截、Skill/Prompt 展开、模型认证、Compaction、队列和持久化，再调用通用 Agent。
  3. 事件是内部主干：同一组 agent/message/tool/turn 事件被 AgentSession 转发给 Extension、TUI 订阅者和 SessionManager，减少 UI、存储与 Loop 的直接耦合。
  4. Session 是树而不是线性聊天：JSONL entry 使用 id/parentId；/tree 改变当前叶节点即可分叉，无需复制整个文件。
  5. 当前仓库正在演进远程架构：protocol/client/server/session backend 已存在，但根 README 仍只把五个 package 列为公开核心，server README 明确标为 experimental。

一次请求的完整路径

1. InputInteractiveMode / SDK / RPC
2. AgentSession命令、资源展开、认证、Compaction
3. Agent状态、队列、transformContext
4. pi-aiProvider stream 与增量事件
5. Tools校验、preflight、并行/顺序执行
6. EventsExtension、TUI、JSONL Session

一次“用户消息”可能包含多个 LLM turn：每当模型返回 tool call，结果会成为 toolResult 消息，Loop 再次调用模型；直到没有工具、发生错误/取消，或 termination hook 停止。

阶段一：AgentSession 预处理

  1. InteractiveMode 把普通输入交给 session.prompt()；若正在 streaming，则指定 steer 或 followUp 进入不同队列。
  2. AgentSession.prompt() 先尝试 Extension command，再触发 Extension input 事件，允许 handled 或 transform。
  3. 展开 /skill:name 和 Prompt Template；随后检查 model、认证和可能需要的 Compaction。
  4. 构造 user message，并触发 before_agent_start，Extension 可以注入 custom message 或临时修改 system prompt。
  5. 最终调用内部 _runAgentPrompt()，把消息交给 Agent；上层错误重试、context overflow 恢复和 auto-compaction 仍由 AgentSession 管理。

阶段二：Agent 到 Provider

Agent 持有 system prompt、model、thinking level、tools 和 messages。每个 turn 先执行可选的 transformContext()，再由 convertToLlm() 把允许包含自定义消息的 AgentMessage[] 转成 Provider 可识别的 user/assistant/toolResult。

createAgentSession() 注入的 stream function 最终调用 ModelRuntime.streamSimple()，同时应用 timeout、Provider retry、header transform、Extension 的 provider request/response hook 和 session ID。pi-ai 再根据 model 所属 Provider 选择真实 wire protocol。

阶段三：工具执行与回灌

模型生成 tool call 后，Agent Core 查找同名工具、使用 schema 校验参数，再调用 beforeToolCall。Hook 可以阻止执行并产生错误结果；通过后执行工具，并以 AbortSignal 传播取消。

当前默认 tool execution 为 parallel：先按模型输出顺序做 preflight，允许的调用并发执行；完成事件可按真实完成顺序出现，但写入上下文的 toolResult 仍按模型原始顺序排列。只要批次中有工具声明 sequential，整个批次改为顺序执行。afterToolCall 可以修改结果、错误状态或终止提示。

Agent Loop

// 教学化伪代码：对应 packages/agent/src/agent-loop.ts
emit("agent_start");
emitUserMessages();

while (true) {
  emit("turn_start");
  const assistant = await streamAssistantResponse(context, streamFn);
  const calls = assistant.content.filter(block => block.type === "toolCall");

  if (assistant.stopReason === "error" || assistant.stopReason === "aborted") break;
  const results = calls.length ? await executeToolCalls(calls) : [];
  context.messages.push(...results);
  emit("turn_end", { assistant, results });

  if (shouldStopAfterTurn?.(...) || (calls.length === 0 && noQueuedMessages())) break;
}

emit("agent_end");

上面省略了 steering/follow-up 两层队列：内部循环处理工具与 steering；当模型原本准备结束时，外层循环检查 follow-up，再决定是否开启下一轮。

停止并不只有“模型没调用工具”

条件发生位置结果
模型无 tool call，且无队列消息Agent Loop正常 agent_end
Provider error 或 AbortAssistant stream结束本轮；AgentSession 可根据策略 retry/恢复
所有 tool result 都带 terminate: true工具批次跳过自动 follow-up LLM call
shouldStopAfterTurn 返回 trueturn_end 后在下一次模型调用前优雅停止
Context overflowProvider/AgentSession可能触发 overflow recovery 与 Compaction 后重试
用户 steering/follow-up消息队列原本要结束的 Agent 继续运行

TypeScript 实现要点

  • Discriminated union：event.type 和 content block 的 type 让 switch 分支获得类型收窄，新增事件时可做穷尽检查。
  • Async stream：EventStream 同时支持 for await 增量消费和 result() 最终结果；UI 不需要等完整消息。
  • AbortSignal：模型 stream、transform、工具和 hook 共用取消信号，避免只停止界面却让副作用继续。
  • Declaration merging：AgentMessage 允许应用声明自定义消息类型；convertToLlm 是最终进入模型前的强制边界。

事件系统

Agent Core 事件既是 UI 协议，也是持久化和扩展的同步点。AgentSession 的处理顺序很关键：先向 Extension 发对应事件，再通知 session listener，随后在 message_end 把最终消息交给 SessionManager。Extension 在 message_end 返回替换消息时，Agent 状态、后续事件和最终持久化会保持同一对象语义。

事件含义TUI 行为持久化
agent_start/end一次 prompt/continue 运行边界开启/关闭 working 状态不直接写消息
turn_start/end一次 LLM call 加工具批次更新 footer、扩展状态消息通过 message_end 单独写入
message_startuser/assistant/toolResult 开始创建消息或流式组件尚未写入
message_updateassistant text/thinking/tool args 增量差分更新文本与工具卡片不写 partial，避免历史污染
message_end消息最终形态结束 streaming component写入 SessionMessageEntry
tool_execution_start/update/end工具生命周期创建、刷新、结束工具卡片最终 toolResult 作为消息写入

Telemetry 不等于 Session

pi-telemetry 使用显式传递的 TelemetryContext 和 callback-owned span，刻意不提供全局 current span 或内置 exporter。Span 是诊断数据；Session entry 是 Agent 历史与恢复数据。两者不能互相替代：关闭遥测不应改变任务结果，而删除 Session 会影响恢复和上下文。

会话模型

coding-agent 的 Session 默认保存在 ~/.pi/agent/sessions/，按工作目录组织。JSONL 第一部分包含 session header，后续 entry 通过 id 与 parentId 形成树；SessionManager 维护当前 leafId，追加消息就是把新 entry 挂在当前叶子并推进叶子。

{"type":"session","version":...,"id":"...","cwd":"..."}
{"type":"message","id":"a1","parentId":null,"message":{"role":"user",...}}
{"type":"message","id":"a2","parentId":"a1","message":{"role":"assistant",...}}
{"type":"message","id":"b1","parentId":"a1","message":{"role":"user",...}}
// a2 与 b1 是从同一用户消息出发的两个分支
Entry 类型记录内容为什么不是普通 message
messageuser、assistant、toolResult、custom/Bash 消息直接参与或展示会话
model_changeProvider 与 model ID恢复时需要重建选择，不应伪装成聊天文本
thinking_level_change推理强度属于运行配置历史
compaction摘要、保留边界、压缩前 Token 和 details替代旧上下文的结构化检查点
branch_summary跨分支切换时的摘要帮助新分支保留离开路径的上下文
custom/session_infoExtension 数据、session 名称可持久化但不必进入 LLM

树结构带来的三个结果

  1. 分支不复制文件：/tree 选择旧 entry 后继续追加即可形成新路径；/fork 才创建新的 session 文件。
  2. 完整历史与当前上下文分离：JSONL 保留完整 entry；构造 LLM context 时只取当前分支并应用 compaction/转换。
  3. Extension 能持久化自己的状态：custom entry 不必污染模型消息，但开发者要负责 schema 版本和兼容。

架构风险清单

  • 不要把根 README 未列出的 experimental server/protocol 当作稳定远程平台承诺。
  • 不要在 message_update 就写业务副作用；partial tool arguments 可能继续变化。
  • 并行工具完成顺序不稳定；任何有先后依赖的工具必须声明 sequential 或在外部串行编排。
  • Session 保存了提示、代码片段和工具结果，必须按敏感开发数据管理；/share 前先审查。
  • Project Trust 控制项目资源加载，不提供文件系统、网络或命令沙箱。
