DSH 开发使用与 Codex 协作指南

一句话：DSH 的正确用法不是“选一个最强模式”，而是把入口形态、Agent 预设、会话模式、权限模式四层分开组合。日常开发优先“标准模式 + 工作区可写 + 按次审批”；与 Codex 协作优先做共享上下文，再把 Codex 作为一次性子代理，最后才考虑双向嵌套调用。

版本前提：本文以本机 Desktop 0.2.1-rc.2（2026-10-17 发布）为主，参考官方 master 文档；本机另有一个 0.1.5-rc.2 的 CLI 源码 checkout。RC 版本细节可能随小版本变化，升级前先备份 ~/.dsh。

快速阅读： 结论 · 四层模式 · 场景组合 · 预设 · 插件 · Codex 协作 · Java 落地 · 常见坑 · 资料

核心结论

  1. 默认就用“标准模式 + 工作区可写 + 审批 ask”。这是功能、可见性、爆炸半径三者最平衡的组合；90% 的 Java 功能开发不需要切到完全访问。
  2. Plan 是设计门，Goal 是长跑器，PTC 是批处理模式。三者解决不同问题：Plan 先想清楚再动手，Goal 让一个目标跨多轮自动推进，PTC 用 run_code 减少往返。不要用 PTC 替代日常开发，也不要用 Goal 做开放式探索。
  3. 插件按“共享上下文 → 按需能力 → 自动化”三层加，不要按“功能列表”加。AGENTS.md 和 skills 的收益最高、风险最低；MCP 和 hooks 是能力扩展；Codex/Claude Code 子代理是“第二意见”。
  4. 与 Codex 协作，第一优先级不是互相调用，而是共用一份项目宪法。项目根 AGENTS.md、.agents/skills/、MCP 工具命名 mcp__server__tool 都是现成的共享层；先做这层，再谈子代理。
  5. Codex 子代理适合“一次性、自包含、结果可验收”的任务。它看不到当前对话、只回最终答案、会在同一工作区里真实执行；不要把它当多轮结对，也不要在你正在改文件时并发运行。
  6. 同一工作区只让一个 Agent 写。并行研究可以开子代理；并行写代码请用 git worktree + 分支隔离。两个 Agent 同时改同一目录，冲突和“谁覆盖了谁”比模型犯错更难查。
如果你只记 5 句话对应动作
日常开发标准模式；工作区可写；审批 ask；多文件改动先 Plan
只读审查只读模式；子代理并行；Codex 子代理做第二意见
批量机械改动PTC 模式；干净 git 工作区；先小批量验证再放大
长任务Goal + 明确验收标准 + 轮数上限；每轮看 diff

先分清四层“模式”

“DSH 用什么模式”这个问题，答案取决于你说的是哪一层。四层互相独立，可以组合；把它们混在一起，就会得到“我明明选了只读，为什么它还能写文件”这类误判。

流程图只负责缩小组合；真正的安全边界仍由权限模式和工作区隔离决定。

入口形态怎么选

  • Desktop / Web：日常开发主入口。能多轮、能看 diff、能审批、能管理会话；Desktop 还负责工作区选择和应用级配置。
  • Headless：dsh --profile headless "任务"，跑完打印最终答案并退出，退出码 0/1。适合 CI、批处理、一次性报告；没有交互式追问，审批请求无人应答时会 fail closed。
  • ACP：dsh --profile acp 以 ACP stdio 服务编辑器等客户端；适合 Zed 一类支持 ACP 的编辑器，不是给 Codex CLI 用的。
  • SDK：dsh --profile sdk 通过 JSON-RPC 嵌入自有系统；适合平台化，不是个人开发首选。

Agent 预设怎么选

预设不是“聪明程度”，而是工具面和提示词的组合。当前 0.2.1 的 Web/Desktop 提供四个预设；预设只能在空会话切换，权限则可以随时切。

预设能力面适合不适合主要代价
标准模式 文件读写、Shell、搜索、Skills、Plan、Goal、子代理、Workflow、Web、Present 日常开发、重构、审查、学习 需要单工具批处理或运行时自省的场景 工具多、每步往返多；长会话需要 compaction
PTC 模式 标准能力 + 以 run_code 为主的编排面；工具结果由程序筛选后输出 批量文件分析、确定性流水线、把多步工具调用压成一次程序 需要逐步审批每个工具调用的高风险改动 审计粒度粗；只看到你打印的内容；程序内异常要自己处理
创造模式 标准能力 + 运行时检查、插件实验、preset 创作指导；plugin_manager 默认开启 写自定义 preset、调试插件、检查运行时组合 普通业务开发 权限大、容易把运行时改坏；必须单独工作区/分支
极简模式 持久 Shell 单工具；固定训练/评测配置 评测、教学、最小化对照实验 真实项目开发 没有文件编辑、搜索、子代理等能力

PTC 的正确打开方式

PTC 的价值不是“更聪明”，而是把 N 次工具往返压成 1 段 TypeScript 程序。适合做“读很多文件、按规则筛选、输出一张表”的工作；不适合做“每改一处都需要人确认”的工作。

// 典型只读批处理：扫描所有模块的 pom.xml，输出 Java 版本与 Spring Boot 版本
const files = await tools.glob({ pattern: "**/pom.xml", path: "." });
const rows = [];
for (const f of files.paths) {
  const r = await tools.read({ file_path: f, limit: 120 });
  const text = r.lines.map((l) => l.text).join("\n");
  const java = text.match(/<java.version>([^<]+)<\/java.version>/)?.[1] ?? "-";
  const boot = text.match(/<spring-boot.version>([^<]+)<\/spring-boot.version>/)?.[1] ?? "-";
  rows.push({ module: f, java, boot });
}
console.log(JSON.stringify(rows, null, 2));

三条纪律：只打印筛选后的结果，不要把整份日志倒进上下文；写操作前先在 1 个模块试跑；程序里仍然受权限策略约束，不要假设 run_code 能绕过沙箱。

Plan 模式与 Goal 模式

Plan：先出决策完整的方案

Plan 模式会禁止写入和改动，只允许读、搜、静态分析和检查；最终必须通过 exit_plan_mode 提交计划，由你批准后才进入实现。它不是“先随便聊聊”，而是“把设计决策一次性补齐”。

  • 该用：改动跨 2 个以上文件、涉及公共 API/数据库 schema、需求有歧义、需要先做影响面分析、框架升级。
  • 不该用：改一个拼写、加一行日志、已经明确到可以直接执行的小修。
  • 判断标准：计划里应该写清目标与验收、按子系统分组的改动、公共 API/数据流变化、边界与失败模式、测试与假设；如果计划还需要实现者做设计决策，说明没写完。
  • 常见误解：你在对话里说“可以，开始吧”不等于批准；必须在 Plan 的审批通道里批准，或者手动切出 Plan。

Goal：让一个目标跨多轮自动推进

Goal 适合“一个明确目标 + 需要很多轮才能完成”的任务，例如“把订单模块所有失败测试修到通过”“把 Spring Boot 2.x 迁移到 3.x 并保持 API 兼容”。它会自动续轮，直到你标记完成、暂停或达到轮数上限。

  • 先写验收：目标里带可执行验收命令（./mvnw -pl order-api test）和不可接受的结果（改测试断言、删功能、跳过失败用例）。
  • 设上限：给 max_goal_rounds 一个预算；每轮结束看 diff 和测试，不要让它无限“再试一次”。
  • 配 checkpoint：开始前提交或建 worktree；每轮通过测试就提交一次，失败可回滚。
  • 该停就停：连续两轮没有实质进展、开始改测试或扩大范围，立即暂停，回到 Plan 重新分解。
任务形态建议原因
需求清楚、改动小普通模式直接做Plan 的探索成本大于收益
需求模糊、跨模块Plan → 批准 → 普通模式先把设计决策补齐，避免边写边改
目标明确、轮次多Plan 定验收 → Goal 执行Goal 负责推进，Plan 负责定义“什么算完成”
开放式研究普通模式 + 只读子代理Goal 会把“探索”误当“收敛”，容易烧 token

权限与安全：三种模式，两个开关

DSH 把“文件边界”和“审批策略”拆成两个独立开关，再用三个预设把它们打包。理解这一点，比记住三个名字更重要。

权限预设沙箱审批实际含义适用
只读read-onlyask能读、搜、分析；写入会被拒绝；需要越界的命令会请求审批第三方仓库、代码审查、依赖升级影响面分析
工作区可写workspace-writeask工作区内可写；越界/高风险操作请求审批日常开发默认
完全访问danger-full-accessnever无沙箱、无审批；命令能碰网络、凭据和系统文件一次性容器/虚拟机；绝不用于公司主仓库

ask 与 never 的真实差别

  • ask：需要越界或高风险操作时弹审批；没有审批通道时 fail closed。这是 headless 最容易踩的坑：没人点“允许”，任务就卡住或失败。
  • never：从不询问；能做的直接做，做不了的失败。它不会“自动批准”，只是把审批环节去掉。
  • 完全访问 + never 才是真正的“无边界”；工作区可写 + never 仍然是工作区沙箱，只是不弹窗。

工作区可写不等于“只改代码”

工作区内的 .env、测试数据、构建脚本、.git 配置都在可写范围内。Agent 可能为了“让测试通过”修改断言、跳过用例、改配置。把以下规则写进 AGENTS.md，并在 review 时检查：

  • 禁止修改测试断言来“制造通过”；测试失败先定位实现。
  • 禁止提交密钥、token、生产连接串；示例配置用占位符。
  • 禁止对生产数据库执行迁移；本地用 Testcontainers 或一次性库。
  • 禁止 git push --force、改写历史、删除分支；这些操作必须人工执行。

威胁模型：插件、MCP、hooks 都是代码

  • 插件在宿主进程内运行，不受工作区沙箱保护；安装插件等于授予它进程权限。只用可信来源，升级前看 diff。
  • MCP server 是外部程序，可能读环境变量、访问网络；stdio server 还会在启动时跑一个探测进程。先接一个只读 server，确认行为再扩。
  • hooks 是可执行命令，会在会话/工具前后运行；hooks-codex 只支持同步命令 hook，失败会记录但不会中止 Agent。
  • 仓库内容不可信：AGENTS.md、README、issue、网页都可能包含提示注入。第三方仓库先用只读模式，不要让 Agent 执行 curl | bash 或安装未知依赖。

插件取舍：默认、按需、别装

0.2.1 的插件面比 0.1.x 更“产品化”：侧边栏有 Plugins 页，可以启用/停用 Bundle、选择已安装 Bundle、安装外部 Bundle；设置里的插件列表仍是只读清单。官方“按需插件”目录截至 2026-10-20 只有两个：Codex 子代理和 Claude Code 子代理。

怎么装 Codex 子代理

  1. 打开侧边栏 Plugins，找到 Official 区域的 Codex subagent。
  2. 启用。它会为当前 DSH 安装装入匹配的原生 Codex payload，并把 subagent_codex 注册为全局工具；启用本身不会启动 Codex 进程。
  3. 如果界面提示需要重启，重启 DSH；之后在新会话里就能看到 subagent_codex。
  4. 停用只会取消选择层，包仍留在本机；“移除”是另一个操作。

桌面端注意：desktop 是 Electron 保留的 Profile 名，CLI 会拒绝针对它的 dsh plugin 管理。桌面端优先用 Plugins 页；要在 CLI 里装插件，请用 web、headless 等非保留 Profile。

MCP：复用 Codex 的 server，但别照搬全部

DSH 的 MCP 工具命名与 Codex/Claude Code 一致（mcp__<server>__<tool>），所以提示词和权限规则可以复用；但配置文件格式不同：Codex 是 ~/.codex/config.toml 的 [mcp_servers]，DSH 是 YAML 行。手工映射一个最小 server 即可：

- id: mcp-docs
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: docs
    transport: streamable-http
    url: https://developers.openai.com/mcp
    toolCallTimeoutMs: 60000
    failOnStartupError: false

不要照搬的例子：Codex 的 node_repl 是它自己的浏览器/计算机使用服务，依赖 CODEX_HOME 和一堆私有环境变量；搬到 DSH 既没有收益，也会把 Codex 的私有运行时带进来。先接“读文档/查 issue/查数据库只读视图”这类边界清晰的 server。

Hooks：把 Codex 的护栏搬过来

hooks-codex 支持五个点：SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop。它只运行同步命令 hook；async: true 或非命令 hook 会被跳过并告警；配置读取失败时不会阻止 Agent 启动。它属于实验包，适合“已经有 Codex hooks，且只想复用命令门禁”的团队。

Skills 比插件更值得投入

Skill 是“按需加载的操作手册”，不是插件：目录和 frontmatter 常驻，正文只在模型决定使用时加载。DSH 的扫描根按优先级是：

优先级来源路径用途
100项目 DSH<projectRoot>/.dsh/skills项目私有、可提交
200项目 Agents<projectRoot>/.agents/skills与 Codex 共享的首选
300自定义customSkillDirs团队/外部目录
400用户 DSH~/.dsh/skills个人全局
500用户 Agents~/.agents/skills与 Codex 共享的个人全局

注意两个限制：只发现顶层的 <name>/SKILL.md 或 <name>.md，不会递归扫 **/SKILL.md；frontmatter 必须有 name 和 description。本会话已经加载了 ~/.agents/skills 下的 Lark 系列技能，说明共享目录是生效的。

与 Codex 协作：四种由浅到深的方式

先给结论：方式 A（共享上下文）应该先做，而且长期保留；方式 B（Codex 子代理）按需开；方式 C（双向嵌套）只适合少量稳定流程；方式 D（编辑器/协议）是团队工具链问题。

方式 A：共享“项目宪法”

这是成本最低、收益最大的一层。两个工具都读项目根 AGENTS.md，都能用 .agents/skills/，MCP 工具命名也一致。

共享物CodexDSH怎么做
项目指令项目根 AGENTS.md项目根 AGENTS.md（+ CLAUDE.md）只维护一份；DSH 会从项目根一路加载到 cwd
用户级指令~/.codex/AGENTS.md~/.dsh/AGENTS.md用软链或共享源文件；不要维护两份会漂移的规则
Skills~/.agents/skills / 项目 .agents/skills同左（另有 .dsh/skills）优先放 .agents/skills，两边都能用
MCP~/.codex/config.tomlYAML 行手工映射；工具名一致，提示词可复用
Hookshooks.jsondsh-hooks-codex已有 hooks 才复用；只支持同步命令 hook

一份好的 AGENTS.md 写什么

DSH 对 AGENTS.md 的总预算是 64KB，加载顺序是“用户级 → 项目根 → 更深目录”，宽泛文件先被省略，最具体的文件最后截断。所以：越靠近根，越写“稳定规则”；越靠近子目录，越写“局部约定”。

# 项目：order-platform

## 环境
- JDK 21（不要用 17 编译）；Maven Wrapper：./mvnw
- 本地启动：./mvnw -pl order-api spring-boot:run -Dspring-boot.run.profiles=local
- 测试：./mvnw -pl order-api test；集成测试用 Testcontainers，不要连生产库

## 模块边界
- order-api：REST + 应用服务；不直接依赖 order-infra 的 JPA 实体
- order-domain：纯领域模型；禁止引入 Spring 注解
- order-infra：持久化/消息；对外暴露端口实现

## 约定
- 公共 API 变更必须同步 OpenAPI 与契约测试
- 数据库变更用 Flyway；一次迁移只做一件事
- 不修改测试断言来制造通过；不提交密钥/生产连接串
- 生成代码目录（target/generated-sources）只读

## 完成标准
- ./mvnw -pl order-api test 通过
- 新增/修改的公共方法有单元测试
- 输出变更摘要：改了什么、为什么、如何验证

不该写进 AGENTS.md 的：长流程、几十行命令清单、某个框架的完整教程。这些放 Skills；AGENTS.md 只留“每次都要遵守”的约束和入口命令。

方式 B：把 Codex 当一次性子代理

启用后，DSH 会多一个全局工具 subagent_codex。它的行为很明确：

  • 一次性：每次委派新建一个隔离的 Codex thread，只完成一个自包含任务，返回最终答案或失败诊断；不能多轮追问。
  • 同工作区：Codex 在父会话的工作区里真实执行，可能读写文件；不是“只读沙箱”。
  • 原生配置：Codex 的认证、模型、provider 配置仍以本机 Codex 为准；DSH 只负责发起和收取结果。
  • 权限模式：默认 never（Codex 不询问，沙箱按 Codex 原生配置）；可选 approve-for-me（Codex 自动审查 + workspace-write）；dangerously-bypass-approvals-and-sandbox 必须显式选择，不要在日常仓库用。
适合交给 Codex 子代理不适合
只读代码审查、找根因、给第二意见需要你来回追问的结对调试
独立、自包含的小任务（补一组测试、审查一个 diff）依赖当前对话隐含上下文的任务
在独立 worktree 里做一次性重构/实验和你同时改同一目录
用不同模型/不同产品交叉验证结论需要看到中间工具调用与逐步推理的合规审查

提示词要“自包含”：它看不到 DSH 的对话历史，所以把目标、约束、文件、验收命令、输出格式一次给全。

你是独立审查者，只读，不要修改任何文件。

背景：这是 Java 21 + Spring Boot 的订单模块，改动在 git diff 中。
目标：找出会导致线上故障或数据不一致的问题，而不是风格问题。

请按以下格式输出：
1. 结论：通过 / 有阻塞问题 / 信息不足
2. 问题列表：文件:行号 | 严重级别（P0/P1/P2）| 问题 | 具体修复建议
3. 你实际检查过的文件和命令
4. 不确定项

约束：
- 不要修改文件、不要提交、不要运行会写数据的命令
- 不要泛泛而谈；没有证据的猜测标为“待验证”
- 如果 diff 不足以判断，明确说缺什么

本机注意：你的 Codex 走本地代理（~/.codex/config.toml 里的 openai_base_url 指向本地端口）。启用子代理前先确认代理在运行，并用一个最小任务验证：让 Codex 只回 OK；如果失败，先查 codex login status 和代理端口，再查 DSH 日志。子代理的模型/计费与 DSH 主模型是两套，别把成本算混。

方式 C：让 DSH 给 Codex 打下手

反过来也可以：Codex 通过 Shell 调 dsh --profile headless "任务"，拿 stdout 的最终答案和退出码。适合“离线批处理、生成报告、跑固定检查”，不适合紧密的多轮循环。

  • 优点：DSH 的权限、沙箱、插件、技能都能用；headless 不开端口、跑完退出。
  • 缺点：没有交互追问；审批请求无人应答会 fail closed；每次都是新会话，上下文要自包含；嵌套 Agent 的耗时和费用会叠加。
  • 更稳的做法：不要让两个 Agent 互相“聊天”，让它们通过仓库产物交接：spec、计划、diff、测试报告、review 结论。

方式 D：接力协议（推荐给真实项目）

把协作变成“有版本、可 review 的产物流”，而不是“把聊天记录贴来贴去”：

SpecCodex/OpenSpec 写清目标与验收
PlanDSH Plan 出决策完整方案
ImplementDSH 在独立 worktree 实现
Verify跑测试、生成变更摘要
ReviewCodex 只读审查 → 人工合并

关键不是“谁更强”，而是“每一步都有可验收的产物，且同一时刻只有一个写者”。

  • Spec：目标、非目标、验收命令、受影响模块、数据迁移策略；用 OpenSpec/Superpowers 的现成模板即可。
  • Plan：DSH 的 Plan 输出按子系统分组、列公共 API/数据流变化、边界与测试；它本身就是给 Codex 审查的输入。
  • Implement：一个 worktree 只给一个 Agent 写；提交信息写“为什么”，不要只写“改了什么”。
  • Review：Codex 只读审查 diff，输出 file:line + 严重级别 + 修复建议；一轮足够，不要开无限 review 循环。
  • Merge：人工决定；CI 必须绿；不让 Agent 直接合并主分支。

同一仓库并行：用 worktree，不要用“两个窗口”

DSH 的 subagent/subagent_fork 默认在同一进程、同一工作区；Codex 子代理也在父会话工作区。它们适合并行读，不适合并行写。要并行写，先隔离目录：

# 为每个任务建独立 worktree（示例）
git worktree add ../order-platform-review -b review/order-api
git worktree add ../order-platform-refactor -b refactor/order-api

# 每个 worktree 只开一个写入 Agent
cd ../order-platform-review
dsh web   # 或 Desktop 里把该目录添加为工作区

# 合并前
git -C ../order-platform-review status
git -C ../order-platform-review diff --stat
./mvnw -pl order-api test
  • 构建目录：Maven 的 target/、Gradle 的 build/ 都在各自 worktree 内，避免互相覆盖。
  • 本地仓库：~/.m2 是共享读缓存，通常没问题；如果同时跑会写本地仓库的工具，给每个任务单独的 -Dmaven.repo.local。
  • 端口/数据库：两个集成测试不要抢同一个端口或同一个本地库；用随机端口和 Testcontainers。
  • 子代理：只读调研可以并行开 2–3 个；写任务串行，或每个 worktree 一个。

上下文与成本：把 token 花在证据上

  • 本机模型窗口 200k，但不是免费。长会话靠 compaction 续命，压缩会丢细节；关键结论（计划、决策、测试结果）写进文件，不要只留在对话里。
  • AGENTS.md 是常驻成本，Skills 是按需成本。把“每次都要遵守”的短规则放 AGENTS.md；把长流程、命令清单、框架教程放 Skills。
  • MCP 的工具 schema 是常驻成本。每接一个 server，模型每次请求都要看它的工具定义；接 5 个 server 可能比接 1 个多花很多 token，还增加启动失败面。
  • 子代理是上下文隔离器。让子代理读 50 个文件、只回 20 行结论，比父会话自己读 50 个文件便宜得多；但子代理的 token 也要算总账。
  • PTC 减少往返，不减少工作量。它适合确定性流水线；如果程序里把大段日志 console.log 出来，反而更贵。
  • 一个会话一个任务。任务结束就新开会话；不要在一个会话里混三个不相关的重构，compaction 会把它们搅在一起。

当前最现实的版本风险

这台机器上有两个版本：Desktop 是 0.2.1-rc.2，而 ~/.dsh/profiles/node_modules/@deepseek-ai/dsh 软链到源码 checkout（0.1.5-rc.2）。如果你用旧 checkout 启动 CLI，却和 Desktop 共用同一个 ~/.dsh，就可能遇到插件 API、会话格式、配置字段不一致的问题。建议：要么把 checkout 更新到与 Desktop 一致的版本，要么给 CLI 用独立的 DSH_HOME；不要把两个版本混在同一个 Profile 里。

建议的落地路线

阶段做什么验收
第 1 天 标准模式 + 工作区可写 + ask；写项目 AGENTS.md；用一个真实小任务跑通；对一次多文件改动使用 Plan 能稳定完成 1 个真实任务；计划被批准后能按计划实现；diff 可读
第 1 周 写 3 个 Skills（接口、迁移、测试）；用只读子代理做一次跨模块调研；记录 token/时间/返工 同类任务第二次明显更快；子代理结论可复核；没有越权写入
第 2 周 启用 Codex 子代理；定义 spec→plan→implement→review 接力；用 worktree 做一次并行任务 Codex 审查能发现真实问题；两个 worktree 互不污染；合并前 CI 绿
第 3–4 周 按需接 1 个 MCP server；试一次 headless CI；做安全复盘（密钥、权限、插件来源） MCP 有明确收益；headless 任务可重复；没有高危权限常开

验收指标

  • 任务成功率：同类任务 10 次里有多少次一次通过测试，而不是“看起来改了”。
  • 返工率：多少 diff 需要人工重写；返工集中在需求理解、边界处理还是风格。
  • 安全性：有没有越界写入、密钥泄露、测试被篡改、生产命令被执行。
  • 可复现性：换一个会话/换一个 Agent，是否还能按 AGENTS.md 和 Skills 得到同样结果。
  • 成本：每个成功任务的 token、时间、审批次数；不要只看单次响应速度。
