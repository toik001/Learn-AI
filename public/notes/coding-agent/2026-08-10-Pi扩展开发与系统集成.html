Pi 扩展开发与系统集成

先做路径选择：只复用文字流程用 Prompt；需要可发现、按需加载的知识与脚本用 Skill；需要事件拦截、工具或 TUI 用 Extension；需要分发一组资源用 Pi Package；同一 Node.js 进程嵌入用 SDK；跨语言或进程隔离用 RPC。

版本基线：本文使用迁移后的 @earendil-works/* 包名和 2026-08-10 主分支 API，不沿用旧 @mariozechner/* 示例。

快速阅读： 结论 · 选路径 · Extension · 工具 · Prompt/Skill · SDK · RPC · 资料

核心结论

  1. 从最小机制开始。能用 Markdown 表达的流程不应先写可执行 Extension；能力越强，安装、审查、测试和故障面越大。
  2. Extension 不是沙箱插件。它与 Pi 同进程运行，拥有启动用户可用的文件、网络、环境变量和子进程权限；项目 Extension 只有在 Project Trust 通过后才自动加载，但信任并不限制其权限。
  3. 并发是工具作者必须处理的事实。当前 Agent Loop 默认可并行执行工具；文件修改工具要进入 withFileMutationQueue()，长操作要响应 AbortSignal。
  4. SDK 与 RPC 解决不同边界。SDK 类型完整、事件直接、开销小，但与宿主共享进程；RPC 允许任何语言接入并隔离崩溃，但必须管理子进程、JSONL framing、背压、取消和版本兼容。
  5. 集成验收不能只看“能回复”。还应验证工具 allowlist、超时与取消、进程退出、凭据隔离、Session 留存、并发请求、协议异常和升级回滚。

Extension：改变运行时行为

Extension 默认导出一个接收 ExtensionAPI 的 factory。Pi 会等待异步 factory 完成，再进入 session_start。factory 只适合一次性初始化；进程、Socket、Watcher 等长生命周期资源应在 session 启动或首次使用时创建，并在幂等的 session_shutdown 中释放。

最小可运行 Extension

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.on("session_start", async (_event, ctx) => {
    ctx.ui.notify("team-guard 已加载", "info");
  });

  pi.on("tool_call", async (event) => {
    if (event.toolName !== "bash") return;
    const command = String(event.input.command ?? "");
    if (/\bgit\s+push\b/.test(command)) {
      return { block: true, reason: "团队规则：push 必须由操作者显式执行" };
    }
  });

  pi.registerCommand("guard-status", {
    description: "显示当前保护策略",
    handler: async (_args, ctx) => {
      ctx.ui.notify("git push：阻止；其他命令：未修改", "info");
    },
  });
}
# 临时验证
pi -e ./team-guard.ts
# 在交互界面执行
/guard-status

这个例子展示拦截点，而不是完整命令安全策略。正则黑名单容易被 shell 包装、别名、脚本和间接调用绕过。高风险环境应在容器、操作系统权限和网络层实施强制控制；Extension 更适合额外提示、审计或业务规则。

状态与恢复

需要跟随 Session 保存的状态，应通过 pi.appendEntry() 或工具结果的 details 持久化，再在 session 启动时遍历当前 branch 重建。不要只放在模块全局变量中：/reload、Session 切换、分支导航和进程重启都会暴露这种设计的缺陷。

自定义工具：给模型增加确定性操作

工具定义包含名称、面向模型的描述、TypeBox 参数 schema、执行函数和可选渲染。描述决定模型何时调用，schema 决定入口结构，execute 决定真实权限，因此三者都需要测试。

只读工具示例

import { readFile } from "node:fs/promises";
import { resolve, relative } from "node:path";
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  pi.registerTool({
    name: "read_project_text",
    label: "Read project text",
    description: "Read one UTF-8 text file inside the current project",
    promptSnippet: "Read a UTF-8 text file constrained to the current project",
    promptGuidelines: [
      "Use read_project_text only for text files under the current project root."
    ],
    parameters: Type.Object({
      path: Type.String({ description: "Project-relative path" }),
    }),

    async execute(_id, params, signal, _onUpdate, ctx) {
      if (signal?.aborted) throw new Error("Cancelled");
      const root = resolve(ctx.cwd);
      const target = resolve(root, params.path.replace(/^@/, ""));
      const inside = relative(root, target);
      if (inside.startsWith("..") || inside === "") {
        throw new Error("Path must name a file inside the project");
      }
      const text = await readFile(target, "utf8");
      return {
        content: [{ type: "text", text: text.slice(0, 50_000) }],
        details: { path: inside, truncated: text.length > 50_000 },
      };
    },
  });
}

示例只是教学最小值。真实实现还要处理符号链接逃逸、特殊文件、体积限制、编码、访问日志和读取过程中的取消。失败必须 throw 才会被标记为工具错误；返回带 error 文本的普通结果不会设置 isError。

工具并发与写入

  • 当前 Tool Call 默认可能并行；若工具声明需要顺序执行，整个 batch 会顺序运行。
  • 修改文件时，用当前包导出的 withFileMutationQueue(absolutePath, callback) 包围完整的读—改—写窗口，避免与内置 edit/write 丢更新。
  • 用 signal 取消外部命令、HTTP 和耗时循环；用 onUpdate 流式报告进度。
  • String enum 应使用 StringEnum（来自 @earendil-works/pi-ai）以保持 Google API 兼容。
  • 若嵌套调用模型，返回 usage，这样 Session、RPC 和页脚成本统计才完整。
  • 返回 terminate: true 只是结束提示；只有同一 batch 的全部最终工具结果都终止，才跳过自动 follow-up。

工具测试清单

  1. 合法、缺失、额外、旧版兼容参数是否按 schema 处理。
  2. 绝对路径、..、符号链接和以 @ 开头的路径是否越界。
  3. 两个相同目标的并发调用是否丢失修改。
  4. 执行中 abort 是否终止子进程/请求且不留下半成品。
  5. 输出是否有限长、可渲染且不泄露密钥。
  6. Extension reload、Session resume/tree/fork 后状态是否一致。

Prompt 与 Skill：先用声明式扩展

Prompt Template

---
description: 评审指定文件，不执行修改
argument-hint: <path> [focus]
---
只读评审 `$1`，重点关注 `${2:-正确性与安全性}`。
先说明证据，再列问题；不要修改文件或执行发布命令。

保存为项目的 .pi/prompts/review.md，信任项目后通过 /review src/example.ts security 使用。模板支持 $1、$@、默认值和切片，适合把团队话术变成可审查文件；它不能强制工具权限，需结合 --tools 或 Extension。

Skill

---
name: release-check

# Release Check

Pi 对 Agent Skills 标准采取宽容加载：启动时主要把名称和描述放入上下文，模型选择后再读取完整 SKILL.md，因此 Skill 比无条件注入长提示更节省上下文。用户也可用 /skill:release-check 显式调用。

Package 是分发约定，不是权限容器。官方建议把 Pi 核心包放在 peerDependencies 并使用 *，让运行时类型和实例保持一致；包自己的运行依赖必须位于 dependencies，因为生产安装会省略 devDependencies。

SDK：在 Node.js/TypeScript 进程内嵌入

SDK 主入口是 createAgentSession()。它返回 AgentSession，负责消息、模型、Compaction、事件和取消。只做单个临时任务可使用内存 Session；需要切换/恢复/分支 Session 的完整 UI，应使用 AgentSessionRuntime，因为替换后 runtime.session 会变化，订阅也必须重新绑定。

最小 SDK 示例

import {
  createAgentSession,
  ModelRuntime,
  SessionManager,
} from "@earendil-works/pi-coding-agent";

const modelRuntime = await ModelRuntime.create();
const { session } = await createAgentSession({
  cwd: process.cwd(),
  tools: ["read", "grep", "find", "ls"],
  sessionManager: SessionManager.inMemory(process.cwd()),
  modelRuntime,
});

const unsubscribe = session.subscribe((event) => {
  if (event.type === "message_update" &&
      event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("只读解释这个项目的入口与测试方式");
} finally {
  unsubscribe();
  session.dispose();
}

生产宿主还应显式选择 Provider/model、ResourceLoader、认证来源、工具集合、cwd 和 SessionManager。不要让多租户请求共享可变 Session、工作目录或凭据；一个 Session 的 prompt 也不应被当作任意并发请求队列。

SDK 适用与限制

  • 优势：TypeScript 类型、直接事件订阅、无协议序列化、可注入 customTools/Extension factory。
  • 代价：Agent 的异常、CPU/内存、环境变量和文件权限与宿主共域；SDK 升级可能带来编译期或行为变化。
  • 建议：用固定版本和 contract test 包装 Pi API；把业务对象与 Pi 事件模型隔离在 adapter 后；对 session 创建、prompt、abort、dispose 做结构化日志。

RPC：跨进程与跨语言集成

启动 pi --mode rpc 后，宿主向 stdin 写一行一个 JSON command；Pi 在 stdout 交错输出 command response 与 Agent events。每个请求应带 id 做关联，但 prompt 的 success 只代表被接受/排队/立即处理，后续模型或工具失败仍通过事件流报告。

协议示例

# 宿主启动子进程
pi --mode rpc --no-session --no-approve --provider anthropic --model "claude-*"

# stdin：每条记录必须以 LF 结束
{"id":"state-1","type":"get_state"}
{"id":"prompt-1","type":"prompt","message":"只读解释当前目录"}
{"id":"abort-1","type":"abort"}

# stdout：response 与 event 交错出现
{"id":"prompt-1","type":"response","command":"prompt","success":true}
{"type":"agent_start",...}
{"type":"message_update",...}
{"type":"agent_end",...}

Framing 陷阱：协议只以 LF（\n）分隔记录；输入可接受 CRLF 并去掉末尾 CR。不要使用会把 Unicode U+2028/U+2029 也当换行的通用 reader。官方明确指出 Node.js readline 对此协议不合规，应按字节缓冲并只搜索 0x0A。

RPC 工程清单

问题最低处理失败表现
关联每个 command 唯一 id；response 与 event 分流把“已接受”误判为“任务成功”
Framing按 LF 拆帧；限制单帧和缓冲大小Unicode 文本截断、内存无限增长
背压等待 stdin drain；消费 stdout/stderr双方管道塞满后死锁

生命周期监听 exit/error，拒绝 pending promise请求永久悬挂

选择 SDK 还是 RPC

  • 宿主是 TypeScript、需要深度类型集成、信任域一致：优先 SDK。
  • 宿主是其他语言、需要独立升级/重启、希望限制 Agent 进程权限：优先 RPC。
  • 需要远程多租户服务：不要直接把裸 RPC 暴露到网络；在前面增加身份认证、租户隔离、队列、配额、审计和会话映射。
  • pi-server 当前官方 README 标为 experimental，可能变化或移除；不应仅因名称像服务端就默认作为稳定生产 API。

集成验收

  1. 功能：固定输入能得到可解析输出；工具调用、Session 恢复和模型切换行为明确。
  2. 安全：未知项目默认不加载项目 Extension；Agent 进程看不到不必要的密钥和目录；发布命令由基础设施限制。
  3. 可靠性：模拟 Provider 超时、429、工具失败、进程崩溃、畸形 JSON、半帧和超大帧。
  4. 取消：用户取消后模型流、工具、子进程和文件临时状态全部收敛。
  5. 可观测：记录版本、sessionId、request id、model、工具名称、耗时、Token/成本和终态，但对提示、输出和环境变量脱敏。
  6. 升级：在 canary 中同时跑旧/新版本 contract test，可一键回退包版本和 Session 读取路径。
