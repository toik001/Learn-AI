#DSH 模式全解：Agent 预设、权限模式与 Plan 怎么用

一句话：DSH 里的“模式”不是一条从弱到强的档位，而是三层可以自由组合的开关——Agent 预设决定模型看到哪些工具和提示词，权限模式决定文件写入边界和审批策略，Plan 决定先评审方案还是直接执行。把这三层混成一个“聪明程度”，就会出现“我明明选了只读，为什么它还能写文件”这类误判。

版本前提：本文基于本地 deepseek-harness checkout 的 0.2.1-rc.2（2026-10-23 阅读），界面名称取自随包中文 locale。DSH 仍在快速迭代，升级后请以实际界面和源码为准。

范围：只讨论会影响任务行为的模式；Desktop / Web / headless / ACP / SDK 属于“入口形态”，不是模式，文末单独说明。

快速阅读： 核心结论 · 三层模式 · Agent 预设 · 权限模式 · Plan 模式 · 易混淆开关 · 场景组合 · Java 落地 · 扩展与自定义 · 常见误区 · 参考资料

#核心结论

  1. 默认组合：标准模式 + 工作区内修改 + 普通执行。这是功能、可见性和爆炸半径最平衡的组合，适合 90% 的 Java 日常开发。
  2. 多文件、跨模块、改 API/数据库的活，先 /plan。让 Agent 只读探索并交出一份可评审的计划，批准后再切到可写权限执行。
  3. 只读审查就选“仅可查看”。它挡的是文件写入，不是网络和进程；对不可信仓库仍要用容器或独立环境。
  4. PTC 是“工具调用组织方式”，不是更强的模型。适合批量读取、筛选、去重、统计；不适合每一步都要人确认的高风险改动。
  5. Plan 是软约束，权限才是硬边界。Plan 激活时所有工具仍然可用；真正保证“不乱写”的是沙箱模式。
  6. 极简模式是评测基线，不是安全模式。它没有文件编辑工具，但仍然可以通过持久 Shell 读写文件。
  7. 完全权限只应出现在一次性容器/VM。Auto review 是实验性的概率审查，不能替代沙箱；它默认关闭，也不进入新会话默认设置。

#先分清三层模式，再看底层两个旋钮

DSH 把“Agent 能做什么”“文件能写到哪里”“先想还是先做”拆成了三个独立维度。它们可以任意组合，而且修改时机不同。

层选项决定什么什么时候改

界面叫“模式”		 标准模式 / PTC 模式 / 极简模式 / 创造模式（以及自定义预设） 模型看到的工具目录、系统提示词、技能与运行时上下文；直接决定它“能做什么” 新任务开始时选定，任务进行中固定；默认值可在设置里改

界面叫“权限/访问模式”		 仅可查看 / 工作区内修改 / 完全权限 / 自动审查（实验） 文件沙箱边界 + 审批策略；决定它“最多能碰到哪里” 当前会话随时切换；设置里的默认值只影响之后新建的会话
会话模式 普通 / Plan（计划模式）；Goal 属于会话级目标，不是模式 先探索并提交计划，还是直接执行 随时 /plan 进入、/plan off 离开；批准计划也会离开

权限模式本身又是两个更底层的旋钮打包出来的：沙箱模式（read-only / workspace-write / danger-full-access）和审批策略（ask / never）。理解这两个旋钮，才能理解四个权限模式为什么长得不一样。

#Agent 预设：四个内置模式各自解决什么问题

预设不是“模型智商档位”，而是工具面 + 提示词 + 技能目录的组合。它决定模型能不能直接改文件、能不能跑命令、能不能开子代理、能不能创建插件。当前 Web/Desktop 自带四个预设，按界面顺序如下。

预设模型看到的工具面最适合不适合 / 主要代价
标准模式
standard		 最完整：文件读写与搜索、Bash/Pwsh、后台任务、计划、Goal、Skills、子代理（fresh/fork）、Workflow、Web、todo、ask_user、present、上下文压缩 日常功能开发、重构、代码审查、资料整理；绝大多数任务从这里开始 工具多、每一步往返多；长会话依赖压缩；需要你在提示词里把验收标准说清楚
PTC 模式
ptc		 标准能力 + 以 run_code 为主的编排面：模型写 TypeScript 程序，通过生成的 SDK 调用工具；当前预设关闭了 Workflow 批量读取/校验/聚合：扫描所有 pom.xml、汇总 Surefire 报告、按规则筛日志、生成 CSV 不适合需要逐步人工确认的高风险改动；程序内异常要自己处理；只把筛选后的输出交给模型，审计粒度更粗
极简模式
minimal		 一个持久 Shell + read_image + 上下文压缩；固定系统提示词，不注入标准运行时上下文；没有文件读写工具、搜索、Skills、Plan、Goal、子代理、Web、todo 模型/提示词对比实验、教学基线、最小能力验证 不是真实项目开发环境；仍然可以通过 Shell 读写文件，所以不是安全边界；读图需要支持图片输入的模型
创造模式
cordis		 标准能力 + 只读运行时检查（cordis_inspect_*）+ 插件管理（plugin_manager、plugin_market）+ 编写 Cordis 插件与 Agent 预设的 Skills 扩展 DSH：写插件、加 UI、调试运行时组合、基于标准模式定制自己的“代码审查模式”等 权限大、容易把 profile 改坏；插件在宿主进程内运行，等于可信代码；安装可能要求完全权限或逐次批准，且可能需要重启

#标准模式：默认答案

标准模式直接向模型暴露各个工具：读文件、写文件、搜代码、跑命令、开后台任务、开子代理、维护 todo、查网页。它适合“描述目标 + 指出相关文件 + 给出验收方式”的常规开发任务。对 Java 项目，典型提示词是：

“先读 OrderService 和它的测试，定位重复提交导致结果消失的原因；做最小修复；运行 mvn -q -pl order-service test；最后说明根因、改动和测试结果。”

标准模式的代价是工具多、上下文长。长任务要依赖压缩，复杂改动要配合 Plan，否则容易出现“边改边猜”的返工。

#PTC 模式：把 N 次工具往返压成一段程序

PTC 是 Programmatic Tool Calling。模型不是逐个调用工具，而是写一段 TypeScript 程序，通过 tools.* 调用工具，在程序里做循环、条件、错误处理、并发和聚合，最后只打印或返回需要给模型看的结果。例如批量检查配置：

const files = await tools.glob({ pattern: "**/pom.xml", path: "." })
const rows = []
for (const file of files.paths) {
  const result = await tools.read({ file_path: file, limit: 120 })
  const text = result.lines.map(line => line.text).join("\n")
  rows.push({
    module: file,
    java: text.match(/<java.version>([^<]+)<\/java.version>/)?.[1] ?? "-",
    springBoot: text.match(/<spring-boot.version>([^<]+)<\/spring-boot.version>/)?.[1] ?? "-",
  })
}
console.log(JSON.stringify(rows, null, 2))

三条纪律：

  • 只输出筛选后的结果。不要把整份日志或整批文件倒进上下文，否则 PTC 的收益会被上下文成本吃掉。
  • 先在 1 个样本上试跑。批量写操作、批量重命名、批量迁移尤其要先小范围验证。
  • PTC 不能绕过权限。程序里的嵌套工具调用仍会被记录、仍受工具权限和沙箱约束；run_code 本身也可以请求一次性升权，但需要批准。

如果任务是“每改一处都要停下来问人”，不要用 PTC；它是批处理和确定性流水线的工具，不是高风险交互式改动的加速器。

#极简模式：对照组，不是“新手模式”

极简模式把工具面压到最小：一个持久 Shell、一个 read_image、上下文压缩，加上固定系统提示词。它的用途是做受控对比：固定模型、权限、输入和工作区起始状态，比较标准模式与极简模式在同一个 Bug 修复任务上的完成情况、工具调用次数和最终 diff。

注意两点：

  • 它没有文件编辑工具，但 Shell 仍然能 sed、cat、重定向写文件；所以“工具少”不等于“权限小”。
  • 它不是更容易上手的模式。缺少 Plan、Skills、子代理和结构化文件工具，长任务反而更难管理。

#创造模式：把 DSH 本身当作可编程对象

创造模式在标准能力之上增加了三样东西：

  • 只读运行时检查：查看已注册的服务、工具、事件、Slot 树等，先搞清楚现状再写代码。
  • 插件管理：列出、启用/禁用、安装、移除当前 profile 的插件或 bundle；变更会影响该 profile 的所有会话。
  • 创作 Skills：Cordis 插件、Agent 预设、UI 扩展的编写规则。

典型任务不是“帮我写业务代码”，而是“给侧栏加一个项目笔记入口并验证能打开”“基于标准模式创建一个代码审查模式”“把某个工具封装成插件”。插件可能热加载，也可能需要重启；安装插件可能要求 danger-full-access 或本次调用的批准，批准本身不会改变会话权限模式。第三方插件是宿主进程内的代码，必须当可信代码对待。

预设只能在新任务开始时选择；任务开始后头部会固定显示当前预设，运行中不能切换。想换预设，新开一个任务。

#权限模式：四个选项，两个底层旋钮

权限模式把“文件边界”和“审批策略”打包成一个选择器。先看底层：

旋钮取值含义
沙箱模式
SandboxMode		 read-only / workspace-write / danger-full-access 只管文件系统的“写效果”。read-only 拒绝写入；workspace-write 允许写会话工作区和后端承诺的临时区域；danger-full-access 完全绕过隔离。网络和进程可见性不在这个旋钮里。
审批策略

#ask 与 never 的真实差别

很多人把 ask 理解成“每个命令都弹窗”，把 never 理解成“自动批准”。都不准确。

  • ask 只在有工具主动请求批准时才介入。普通的工作区写入由沙箱直接执行，不会弹窗。会主动请求批准的主要是：Bash/文件工具/PTC 显式请求 sandbox_permissions 升权；Auto review 拒绝某个调用；实验性 hooks 返回 ask 决策。
  • never 不是“自动允许”，而是“从不询问”。所有审批请求确定性地返回拒绝。它和完全权限组合时，因为已经没有需要申请的事，看起来像“畅通无阻”；但 workspace-write + never 仍然是工作区沙箱，只是不弹窗。
  • 没有审批通道时，ask 会 fail closed。headless、CI、无人值守场景最容易踩这个坑：不是“默认放行”，而是“没人回答就拒绝”。

#一次性升权：只读/工作区可写并不是死墙

Bash、文件写入/编辑、PTC 的 run_code 都暴露了两个参数：sandbox_permissions 和 justification。模型可以在被沙箱拒绝后，请求一个严格更宽的模式，并说明理由；审批通过后只对当次调用生效，不会改变会话的权限模式。

这带来两个实际后果：

  • “仅可查看”下仍然可能发生一次写入，只要模型申请、你批准。所以它是“默认拒绝 + 可审计的例外”，不是绝对只读。
  • “工作区内修改”下可以临时申请完全访问，用于确实需要写工作区外的操作；批准记录会进入会话日志。

子代理是例外：委派出去的 child 会固定 never 审批策略，沙箱范围在委派时确定，不能从子会话内部升权。需要更大权限时，必须由父级在委派前设置好。

#沙箱到底管什么、不管什么

DSH 的文件沙箱只负责文件效果。这不等于完整安全隔离：

  • 网络不受限。只读模式下的命令仍然可以访问网络；不要把“只读”当成防数据外泄的沙箱。
  • 进程可见性不受限（视平台后端）。沙箱限制的是文件写入，不是“看不到其他进程”。
  • 强制执行可能是 partial。Windows ACL 后端和较旧的 Landlock ABI 会报告部分强制执行；需要绝对边界时，用容器或远程执行器。
  • 插件、MCP、hooks 不受工作区沙箱保护。它们在宿主进程或外部进程中运行，安装/启用前要确认来源可信。
  • 工作区内的敏感文件仍然可写。.env、测试数据、构建脚本、.git/config 都在可写范围；Agent 可能为了“让测试通过”改断言或配置。用 AGENTS.md 明确禁止，并在 review 时检查 diff。

#自动审查：概率性的第二道判断

Auto review 是随包提供但默认关闭的实验层。启用后，它在每个受支持调用执行前，用当前 Agent 的同一模型评估“这个动作该不该放行”：

  • 低风险（普通项目内操作、精确清理本会话创建的对象）直接放行；
  • 中风险（不可逆删除既有对象、生产操作、外部写入、安全控制变更）需要人（或直接父级）明确授权；
  • 高风险（跨信任边界泄露敏感信息）始终拒绝；效果不明确或授权冲突未解决时也拒绝。
  • 被拒绝的调用会按 ask 策略请求你批准；你拒绝或取消，调用就不执行。reviewer 响应不合法或技术失败时，调用失败且不执行。

代价和边界：

  • 每个受支持调用额外产生一次模型请求，消耗额外 token；不缓存、不重试、不压缩。
  • 分类可能出错，可能误放行，也可能误拒绝。
  • 没有文件沙箱；外层 run_code 和 PTC 程序里的直接 Node 效果不经过内层工具审查。
  • 只出现在当前会话选择器里，不进入通用设置和新会话默认值；需要先在插件页启用实验层。

结论：Auto review 适合“本地、可信仓库、想减少弹窗”的场景；不适合不可信代码、生产环境和需要确定性边界的任务。

#怎么切换，什么时候生效

  • 当前会话：点权限选择器，或输入 /permission 查看当前预设与所有可用项；/permission workspace-write 切过去。切换会写会话日志，沙箱模式在下一次受限调用时生效。
  • 未来会话：设置里的“权限”只写 defaultPreset，只影响之后新建的会话，不会改写当前会话。
  • 完全权限/自动审查：切换时会出现风险确认对话框，需要明确勾选“我已了解风险”。

#Plan 模式：先评审方案，再动手

Plan 模式是一个逐 Agent、可持久化的协作状态。激活期间，每次模型请求都会额外带上一段部署定义的 plan:policy 指引，要求 Agent 先探索、设计，再通过 exit_plan_mode 提交完整计划。

#它是什么，不是什么

它是它不是
提示词层面的软约束：要求先只读探索、不要改文件、不要跑会重写文件的格式化/代码生成 权限边界：Plan 激活时所有工具仍然注册、仍然可调用；模型如果无视指引，仍可能尝试修改（然后被权限模式拦住）
一个评审门：Agent 调用 exit_plan_mode 提交 Markdown 计划，你选择批准或继续规划 逐动作审批：它不会为每个 Bash 命令弹窗；那仍然由权限模式和审批策略负责
可恢复状态：plan/mode 只写日志，恢复、fork、压缩后都能还原 “更聪明的模型”或“更保守的沙箱”：它只改变工作流，不改变模型能力和文件边界

#完整使用流程

  1. 进入：输入 /plan，或 /plan 帮我设计订单重复提交的修复方案；可以附带图片和文件，按选择顺序随指令提交。
  2. 探索：Agent 应使用只读读取、搜索、静态分析、检查来把计划落到真实代码上；不编辑、不写文件、不提交、不跑会改文件的生成器。
  3. 提交：Agent 调用 exit_plan_mode，传一份以 # 标题开头的完整 Markdown 计划；该调用应是当前回复中唯一且最后的工具调用。
  4. 评审：界面展示计划原文。选 Approve 离开 Plan 并继续执行；选 Keep planning（可附反馈）让 Agent 修订后再次提交；直接关闭评审去打字，则结束当前轮，Plan 保持激活。
  5. 离开：/plan off 可以随时手动退出；批准评审也会在下一步骤自动退出。

一个好的计划应该“决策完整”：目标与验收标准、按子系统分组的改动、公开 API/Schema/数据流变化、边界条件与失败模式、测试与验收方式、明确假设。计划要足够详细，让另一个工程师不需要再做设计决策就能实施。

#推荐组合：只读 + Plan → 批准 → 可写执行

Plan 本身不阻止写入，所以对“不熟悉的仓库”或“跨模块重构”，最稳的组合是：

新任务：标准模式 + 仅可查看 + /plan <目标>
  → Agent 只读探索，提交计划
  → 你 Approve
  → /permission workspace-write（或点权限选择器）
  → Agent 按计划执行、跑测试
  → 你 review diff

这个流程把“设计评审”和“执行授权”分成两个明确的人工决策点，比“一上来就让它改”更容易控制爆炸半径。

#已知限制

  • 不是强制隔离。指引说“不要改”，但工具仍在；真正的保证来自权限模式。
  • 需要交互评审通道。没有用户交互通道时，exit_plan_mode 会失败；此时只能用 /plan off 手动退出。
  • 退出是“待生效”的。批准后会记录一个静默的待生效退出，由下一个被接受的轮内 pre-step 追加；当前这批工具调用剩余部分仍保留计划指引。
  • 别用 todo_write 代替计划。todo 跟踪的是批准后的实施，计划本身应放在 exit_plan_mode 里。

#容易和“模式”混淆的四个开关

#Goal：跨轮持久目标，不是模式

Goal 是会话级的一个持久完成目标（每会话最多一个），跨轮、恢复、fork 和进程重启都存在；可选的续行驱动器会让进行中的目标连续跑多个 Round。你可以用 /goal 检查或控制它，模型也可以用 create_goal/update_goal。它适合“修完所有失败测试”“完成一次迁移”这种长跑目标，不适合开放式探索。它不改变工具面，也不改变文件边界，所以不是模式；但常和 Plan 组合：先 Plan 定方案，再把执行挂到一个 Goal 上。

#native 与 PTC：底层工具呈现方式

PTC 预设背后是“工具呈现方式”这个开关：native 把每个工具 schema 直接给模型；ptc 只给 run_code 和生成的 SDK。它按 Agent 预设声明，同一进程里可以同时存在 native agent 和 PTC agent。部署级默认由 dsh-tools 的 mode 决定，临时可以用 DSH_TOOLS_MODE=native|ptc 让整个进程切换。这是给扩展开发者看的旋钮，普通用户只需要选 PTC 预设。

#子代理：fresh 与 fork 是上下文模式

标准/创造/PTC 预设都提供两种委派：

  • subagent（fresh）：全新上下文，只看到你写的任务；提示词必须自包含，适合独立研究、并行审查、一次性实现。
  • subagent_fork：继承当前会话已完成的轮次（不包含正在进行的这一轮），适合“基于刚才的讨论继续分析/评审”，不用重复交代背景。

两者都共享同一文件系统，子代理的审批策略固定为 never，沙箱范围在委派时确定，不能从内部升权。所以：并行只读研究可以放心开；并行写代码必须用 git worktree + 分支隔离，并且一个文件范围只让一个 Agent 写。

更重的多 Agent 协作（Team Lead + 持久 teammate + 共享任务板）属于 Agent Teams 能力，不是本文所说的“模式”，但同样遵循“父级权限是天花板、子级不能升权”的规则。

#入口形态：Desktop / Web / headless / ACP / SDK

这些是“从哪里运行 DSH”，不是任务模式，但会影响模式可用性：

  • Desktop / Web：日常主入口，有权限选择器、Plan 评审、diff 和审批弹窗。
  • headless：跑完打印结果并退出，适合 CI/批处理；没有交互式审批通道，ask 的升权请求会 fail closed。
  • ACP：以 stdio 服务编辑器等客户端；SDK：通过 JSON-RPC 嵌入自有系统。两者都需要部署方自己补齐审批与权限策略。

所以 CI 里要么用 workspace-write 做只改工作区的任务，要么在一次性容器里用完全权限；不要指望 headless 里有人点“允许”。

#开发中怎么组合：九个可直接套用的场景

下面这张表是“任务 → 预设 / 权限 / 会话模式”的速查。默认从标准模式 + 工作区内修改开始；只有明确需要时才升级或降级。

#1. 日常开发：默认组合

标准模式 + 工作区内修改 + 普通。把任务写成“目标 + 证据 + 约束”：

“在 order-service 里修复重复提交导致结果消失的问题。先读 OrderController、OrderService 和对应测试；做最小修改；运行 mvn -q -pl order-service test；不要改测试断言来制造通过；最后给出根因、diff 摘要和测试输出。”

如果改动涉及 3 个以上文件、公共 API、数据库 schema 或并发语义，先加 /plan，不要直接让它动手。

#2. 只读审查：把“只读”用于审查，不用于安全隔离

标准模式 + 仅可查看。适合 PR 审查、依赖升级影响面分析、代码考古。要求 Agent 输出“结论 + 文件/行号 + 风险等级 + 建议”，不要只说“看起来没问题”。

提醒：只读模式仍然可以访问网络、读取环境变量、运行命令；对来源不明的仓库，应该用容器/独立用户，而不是只靠“仅可查看”。

#3. 大改：只读 Plan → 批准 → 可写执行

这是最值得养成的习惯。步骤：

  1. 新任务选标准模式；权限先设“仅可查看”。
  2. /plan 设计把订单状态机从枚举迁移到状态表的方案，包含数据迁移、兼容层、测试和回滚。
  3. 评审计划：重点看 API/Schema 变化、边界条件、测试覆盖、是否漏了调用方。
  4. Approve 后，/permission workspace-write。
  5. 让 Agent 按计划分阶段执行；每阶段跑测试、看 diff；不要一次性“全都改完”。

#4. 批量处理：PTC 的边界

PTC 模式 + 工作区内修改。适合“读很多文件 → 按规则筛选/聚合 → 输出一张表/一份报告”。提示词里写清楚输入、规则、输出格式和失败处理：

“检查 configs/ 下所有 JSON，按 schema.json 找出缺失字段和非法值；每个问题写 CSV 一行；读取失败的文件也记入报告，继续检查其余文件；不要修改原文件。”

不要用 PTC 做“每个文件都要人工确认”的高风险批量改写；那种任务用标准模式 + 小步执行更稳。

#5. 对比评测：极简模式

固定模型、权限、输入、起始 commit 和工作区状态，分别用标准模式和极简模式跑同一个任务，比较完成情况、工具调用次数、最终 diff 和耗时。极简模式的 Shell 仍能读写，所以“工具少”不会自动更安全，也不会自动更便宜。

#6. 扩展 DSH：创造模式

典型流程：

  1. 先让 Agent 用 cordis_inspect_* 查看现有服务、工具、Slot；不要凭猜测写插件。
  2. 描述“能力 + 出现位置 + 验证方式”，例如“侧栏加项目笔记入口，能列出并预览 Markdown”。
  3. 要求“安装并验证”，不要只生成源码；插件可能热加载，也可能需要重启。
  4. 自定义预设基于标准模式复制，改提示词/工具白名单；新任务开始时才能选。

#7. 完全权限：只在一次性环境

完全权限的价值是“没有边界摩擦”，代价是“没有边界”。适用：一次性容器、临时 VM、专门为某任务克隆的 checkout。不要在主仓库、生产凭据所在环境、共享开发机上用。切换时界面会要求确认风险，这个确认不是形式。

#8. CI / 无人值守

headless 没有审批应答者，ask 的升权请求会失败。可行策略：

  • 任务只需要改工作区：用 workspace-write，预先准备好依赖缓存（见 Java 落地一节）。
  • 任务需要更大范围：在一次性容器里用完全权限，任务结束销毁容器。
  • 不要指望“自动批准”；如果必须无人值守，显式选择 never 并接受“需要审批的操作会被拒绝”。

#9. 长跑：Goal 是目标，不是模式

当任务需要跨多轮持续推进（修完所有失败测试、完成迁移、清理所有 lint 告警），用 Goal 记录完成目标，让续行驱动器跨轮推进。每轮要有可验证的进展，完成要有证据；同一阻塞条件持续存在时应该 blocked，而不是无限重试。Goal 不改变工具面和权限，所以仍要单独设置权限模式。

#Java 项目落地：权限边界与构建缓存的冲突

Java 开发者最容易踩的坑不是模型能力，而是“Maven/Gradle 要写工作区外的缓存目录”。

#1. Maven / Gradle 缓存

workspace-write 只允许写会话工作区和平台临时区域。~/.m2/repository、~/.gradle 在工作区外，首次下载依赖时会被沙箱拒绝。三种处理方式：

  • 预热缓存：在进入 DSH 前先跑一次完整构建，把依赖放进本地仓库；之后 DSH 只读缓存，通常能正常编译/测试。
  • 把缓存放进工作区：Maven 用 -Dmaven.repo.local=$PWD/.m2repo，Gradle 用 GRADLE_USER_HOME=$PWD/.gradle；记得把目录加入 .gitignore。
  • 一次性容器 + 完全权限：让容器内的 HOME 可写，任务结束销毁；适合 CI 或干净环境。

#2. 常用命令与验收

# 单模块测试，减少输出
mvn -q -pl order-service -am test

# 指定工作区内的本地仓库，避免写 ~/.m2
mvn -q -Dmaven.repo.local="$PWD/.m2repo" -pl order-service test

# Gradle 缓存放进工作区
GRADLE_USER_HOME="$PWD/.gradle" ./gradlew :order-service:test

让 Agent 把验收写成可执行命令，而不是“看起来对了”。测试报告、target/、build/ 都在工作区内，通常可写；如果测试需要 Docker/Testcontainers，先验证当前环境是否可用，再让它批量跑。

#3. 写进 AGENTS.md 的硬规则

- 测试失败先定位实现，禁止修改断言、跳过用例或删除测试来“制造通过”。
- 禁止提交密钥、token、生产连接串；示例配置用占位符。
- 禁止对生产数据库执行迁移；本地用 Testcontainers 或一次性库。
- 禁止 git push --force、改写历史、删除远程分支；这些操作由人执行。
- 改动后至少运行相关模块测试；报告失败时附命令和关键输出。

#4. 并行与隔离

同一工作区只让一个 Agent 写。需要并行时用 git worktree 给每个 Agent 一个独立 checkout 和分支；只读研究可以共享工作区并行开子代理。合并前由 Lead 统一 review diff、跑测试。不要用“两个窗口同时改同一目录”来提速。

#扩展与自定义：什么时候该动哪一层

如果你要“造一个自己的模式”，先判断需求属于哪一层，不要把所有东西都塞进提示词。

你想改变应该扩展典型做法
模型能用哪些工具、用什么人设/提示词Agent 预设新增 @deepseek-ai/dsh-agent-preset 行，组合 persona、工具、Skills；通过 bundle patch 安装
文件写入边界、审批行为权限预设 / 沙箱策略配置 @deepseek-ai/dsh-permission-presets 的 presets 表；或直接改 sandbox-policy 默认模式
先规划再执行的工作流Plan 模式配置 section 引导；用 ctx.planMode 驱动；保留 exit_plan_mode
工具呈现方式（逐个 schema vs run_code）工具呈现@deepseek-ai/dsh-agent-tool-presentation 的 mode: native|ptc
新能力、新 UI、服务连接Cordis 插件创造模式编写/安装；插件在宿主进程内运行，按可信代码管理

#自定义权限预设

- name: '@deepseek-ai/dsh-permission-presets'
  config:
    presets:
      read-only:
        sandbox: read-only
        approval: ask
      workspace-write:
        sandbox: workspace-write
        approval: ask
      danger-full-access:
        sandbox: danger-full-access
        approval: never
    defaultPreset: workspace-write

custom 和 auto 是保留名，不能出现在配置表里。挂载这个服务需要“会报告 sandboxMode 的 bash 执行器”和审批服务；只有配置预设会进入通用设置和未来会话默认值。

#Plan 模式的配置与服务

- name: '@deepseek-ai/dsh-plan-mode'
  config:
    section: |
      You are in plan mode. Explore and design before presenting the complete
      plan through exit_plan_mode.

服务侧只有两个核心方法：ctx.planMode.set(agent, active) 返回 committed/queued/cancelled/noop；ctx.planMode.get(agent) 返回 { active, pending? }。状态是只写日志的 plan/mode 事件，恢复和 fork 都能回放。

#部署级默认值

  • DSH_PERMISSION_MODE=read-only|workspace-write|danger-full-access：部署的默认权限模式（还会联动审批策略的默认值）。
  • DSH_TOOLS_MODE=native|ptc：临时让整个进程切换工具呈现方式；这是过渡用的环境开关，不等同于用户级预设。

#常见误区

  1. “只读 = 安全隔离。”只挡文件写入；网络、进程、环境变量读取都不在文件沙箱里。不可信代码要用容器。
  2. “工作区可写 = 只改代码。”.env、测试数据、构建脚本、.git/config 都在范围内；必须用 AGENTS.md 和 diff review 补规则。
  3. “完全权限 + never = 自动批准。”never 是拒绝所有审批请求；完全权限是根本没有沙箱。两者叠加是“无边界”，不是“自动审批”。
  4. “Plan 会限制工具。”不会。工具目录保持不变；它只是提示词层的软约束，硬限制仍靠权限模式。
  5. “PTC 更聪明/更省 token。”它改变工具调用组织方式；是否省取决于任务和程序如何筛选结果，简单任务反而多一层开销。
  6. “极简模式更安全。”它只是工具少；持久 Shell 仍能读写文件，不是安全边界。
  7. “预设可以中途换。”Agent 预设固定在任务开始时；权限模式可以随时切换。
  8. “Auto review 可以替代沙箱。”它是概率性审查、没有文件沙箱、会误判、额外耗 token；只能作为本地可信场景的补充。
  9. “子代理可以自己升权。”子代理固定 never，沙箱范围在委派时确定；父级必须先设置好权限。
  10. “插件/MCP/hooks 受工作区沙箱保护。”它们通常在宿主或外部进程运行，不受工作区文件沙箱约束；安装即信任。

#开工前 30 秒检查清单

  1. 任务要写文件吗？不写 → 仅可查看；写 → 工作区内修改。
  2. 改动跨模块/改 API/改数据吗？是 → /plan 先出方案；否 → 普通执行。
  3. 任务是否批量、可程序化？是 → PTC；否 → 标准。
  4. 要扩展 DSH 本身吗？是 → 创造模式；否 → 标准。
  5. 是否一次性环境？是 → 完全权限；否 → 不要用完全权限。
  6. 是否需要跨多轮推进？是 → 加 Goal；否 → 普通。
  7. 构建缓存是否在工作区内？Maven/Gradle 尤其要检查，否则先预热或改缓存目录。
