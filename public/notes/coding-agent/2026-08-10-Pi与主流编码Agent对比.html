Pi 与主流编码 Agent 对比

一句话结论：Pi 的核心优势是“可读、可改、可嵌入的极简 Agent Harness”，不是功能数量；Claude Code 与 Codex CLI 更像集成度高的完整产品，OpenCode 是多界面、client/server 型开源平台，Aider 是 Git 与编辑格式驱动的专注型结对工具，Goose 是以 MCP 为中心的通用自动化 Agent。

不要把模型质量当成 Harness 质量。同一模型在不同工具中的上下文选择、编辑协议、提示、工具、重试和权限路径不同；不同模型的结果更不能直接归因于 CLI。

快速阅读： 结论 · 方法 · 矩阵 · 分析 · 场景 · 局限 · 资料

核心结论

  1. 想研究或塑造 Agent Runtime：Pi 的五个核心包、Extension、SDK 和 JSONL Session 很适合阅读与二次开发；代价是权限治理、MCP、多 Agent 等要自己组合。
  2. 想要厂商整合的完整工作流：Claude Code 的 Skills、Hooks、MCP、Subagent/Agent Teams、插件和多端面最丰富，但主 CLI 是 Anthropic 商业许可，模型范围围绕 Claude。
  3. 想要开源 CLI + 强安全执行边界：Codex CLI 将审批与 read-only/workspace-write/danger-full-access Sandbox 作为一等能力，并提供 MCP、插件、SDK、App Server 与非交互模式；主要体验围绕 OpenAI 模型，另有 Ollama/LM Studio 本地 OSS 路径。
  4. 想要多 Provider、多客户端与可服务化架构：OpenCode 的 TUI、桌面、IDE、HTTP Server/OpenAPI SDK、Agent 和 MCP 形成完整平台；能力面较大，也意味着配置与版本演进面更大。
  5. 想要可预测的 Git 结对编辑：Aider 的 repo map、编辑格式、自动提交、undo、lint/test 仍然独特；它不像另外几项那样以通用工具生态和长期 Agent 编排为中心。
  6. 想要 MCP 优先的通用本地自动化：Goose 同时提供桌面、CLI、API、Recipe、权限模式和大量 MCP Extension；但默认 Autonomous，需要先调整安全配置。

比较方法

本文只比较“本地/终端 Agent Harness”这一重叠面。Claude Code 与 Codex 还有云端、桌面和企业功能，Goose 也定位为通用 Agent；这些非对称能力会单独标明，不用来制造总分。

逐项分析

1. 设计中心：Harness、产品、平台还是编辑器

  • Pi：提供可组合 primitive。核心保持小，特殊流程由 Extension/Skill/SDK 构建。它适合“我要决定 Agent 应该长什么样”。
  • Claude Code：提供一致的成品工作区，从代码理解延伸到插件、团队、后台任务和企业治理。它适合“我接受 Claude 生态，想直接获得完整能力”。
  • Codex CLI：把本地 Agent、安全执行、OpenAI 模型和多 Codex 客户端连接起来。它适合“我要可审计开源 CLI，同时要内置 Sandbox 与自动化接口”。
  • OpenCode：TUI 本身就是本地 Server 的客户端，OpenAPI 再生成 SDK，天然适合多 UI 和服务化。它更像一套 coding-agent platform。
  • Aider：核心心智模型仍是“选择文件 → 提供 repo map → 让模型生成特定编辑格式 → 应用变更 → Git 记录”。它是专注的 AI pair programmer。
  • Goose：开发工具只是默认 Developer Extension 之一；MCP、Recipe、桌面自动化、研究和数据工作同属一套通用 Agent。

2. 模型中立性的三种层次

层次代表含义边界
原生多 ProviderPi、OpenCode、Aider、Goose一套 Harness 面向多家 API/本地模型模型工具语义、推理块和编辑质量仍不等价
单模型家族、多部署渠道Claude CodeClaude 可经 Anthropic 或公有云企业渠道使用不是任意第三方模型 Harness
主生态 + 本地 OSS 通道Codex CLI主线使用 OpenAI/ChatGPT；--oss 可接 Ollama/LM Studio不能据此推断所有 Provider 都有同等官方支持

如果组织要求按地区、成本或数据政策动态路由多家模型，优先评估 Pi/OpenCode/Goose/Aider。如果首要目标是某一厂商模型的最佳集成，原厂 Harness 往往能更快采用专用能力。

3. 权限、安全与默认值

  • Pi：默认继承启动进程的全部可用权限。工具 allowlist 能减少模型看到的工具，但不是文件系统强隔离；官方列出 OpenShell、Gondolin 和 Docker 方案。
  • Claude Code：default/acceptEdits/plan/auto/dontAsk/bypassPermissions 面向不同监督强度，配合 deny/ask/allow 与 PreToolUse Hook。bypass 明确只适合隔离环境。
  • Codex CLI：审批策略与 Sandbox policy 分离；workspace-write 可把写入约束在工作区，danger-full-access 才放宽系统边界。--yolo 同时绕过审批和 Sandbox，风险语义清晰。
  • OpenCode：Permission 可按工具、命令 pattern、Agent 和 MCP tool 配置，适合声明式团队策略；部署 Server 时还要单独设置认证与网络边界。
  • Aider：Git 自动提交和 /undo 对可恢复性很有价值，ask/dry-run 能减少写入，但 Git 回滚不等于阻止命令、网络或仓库外访问。
  • Goose：官方明确 Autonomous 是默认；首次用于敏感仓库应切到 approve/smart_approve/chat 并设置 Tool Permissions。官方也说明读写分类包含 LLM/best-effort 判断。

4. 上下文与会话策略

  • Pi：透明 JSONL Tree，entry 有 id/parentId，可在同一会话树导航、分支与 Compaction；适合研究 Harness 和审计原始历史。
  • Aider：显式把文件加入/移出 chat，repo map 用图排序在有限 Token 中展示跨仓库关键符号；控制感强，特别适合代码编辑。
  • Claude Code：CLAUDE.md、Rules、Skill 描述按需加载、MCP Tool Search、独立 Subagent context 和 Compaction 共同管理上下文，自动化层次更多。
  • Codex CLI：AGENTS.md、Skill、Compaction、resume/fork/archive 以及多 Agent/工作区机制联动；本地与桌面/云端面需要区分数据边界。
  • OpenCode：Session 是 Server API 的一等资源，TUI 可 sessions/undo/redo/share；适合不同 client 使用同一后端抽象。
  • Goose：named session、resume、no-session、Recipe 与结构化输出适合重复工作流；Chat Recall、Memory 等通过平台 Extension 增强。

Pi 进程内 Extension 的优势是低摩擦和深度控制，缺点是 API 耦合与同权限域。MCP 的优势是语言/进程边界和可复用生态，缺点是连接、认证、schema/token、故障恢复和供应链面更大。两者不是简单的先进/落后关系。

6. 自动化与系统集成

  • Pi 提供 print、JSON event、严格 LF JSONL RPC 和同进程 SDK；底层自由度高，但调用方要自己做版本适配和治理。
  • Claude Code 提供 -p headless 与 Agent SDK，适合围绕 Claude 构建定制 Agent；商业条款和数据路径需要组织审查。
  • Codex 的稳定 codex exec 可输出 JSONL/恢复 Session；另有 SDK、experimental App Server 与自身 MCP Server，适合脚本到客户端集成的渐进路线。
  • OpenCode 的 TUI 即 Server client；opencode serve 暴露 OpenAPI 3.1 并生成 SDK，是六项中最明确的 HTTP client/server 架构。
  • Aider 的 --message/--message-file 和 Python 使用方式适合批处理；它不是以长驻多客户端 Agent Server 为首要定位。
  • Goose 的 goose run 支持 text/file/Recipe、no-session、JSON/stream-json，goose serve 需要 secret，适合本地自动化与 MCP 工作流。

不应这样比较

  • 只跑一次提示就宣布胜负；随机性、缓存、仓库状态和模型版本都会影响结果。
  • 拿一个工具的最新旗舰模型对另一个工具的廉价模型，再把差异归因于 Harness。
  • 把 Git undo 当 Sandbox，或把审批弹窗当权限隔离。
  • 用 GitHub star、功能数量或 Provider 数量代替维护质量和真实需求匹配。
  • 忽略云端订阅、API 计费、遥测、Session 留存和企业条款，只比较安装命令。

比较局限

  1. 时间截面：六个项目都在快速更新；尤其 experimental server、Agent teams、插件与安全模式可能变化。
  2. 文档口径：“Provider 支持”可能只是能发请求，不代表工具调用、推理块、缓存、图像和编辑质量均被完整适配。
  3. 未做效果基准：本文没有声称 Pi 或任何竞争者在代码正确率、Token 成本、延迟上领先。
  4. 企业能力不对称：Claude Code/Codex 的云端和管理面、OpenCode/Goose 的服务面、Aider 的专注编辑面都无法压成一个公平总分。
  5. 安全需实测：文档中的 mode、permission、sandbox、trust 含义不同；实际部署应做越权、Prompt Injection、网络和凭据泄漏测试。

建议的本地对照实验

  1. 选一个有测试、20～50 个源文件、无敏感信息的仓库，固定初始 commit。
  2. 尽量使用同一模型/温度/思考强度；无法同模型时明确把模型作为独立变量。
  3. 准备三类任务：只读定位、带测试的小修复、跨模块功能；每类至少重复 3 次。
  4. 记录一次成功率、人工干预数、误改文件、测试结果、Token/成本、耗时和恢复难度。
  5. 单独做权限实验：仓库外文件、敏感环境变量、网络、危险命令、未信任项目配置。
  6. 最后按团队权重评分，而不是直接套用网上榜单。
