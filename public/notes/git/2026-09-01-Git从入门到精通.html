Git 从入门到精通

一句话心法：Git 不是“文件备份工具”，而是一个用不可变对象保存项目快照、用引用给提交命名、用有向无环图组织历史的分布式版本控制系统。

适用读者：零基础开发者，以及会用 add/commit/push、但仍害怕分支、冲突、rebase、reset 和 worktree 的 Java 全栈开发者。示例默认使用现代 Git 2.x 命令，并以 Spring Boot 仓库作为工程语境。

资料范围：内容检索并核对于 2026-09-01，主要依据 Git、GitHub 与 GitLab 官方文档。平台套餐、权限和界面会变化，实际采用前应复核对应官方页面。

快速阅读： 核心结论 · 原理 · 安装 · 分支 · 合并 · Rebase · Worktree · GitHub/GitLab · 练习

核心结论

  1. 提交是快照，不是“保存按钮”。一次提交包含根 tree、父提交、作者、提交者、时间和说明；提交 ID 由内容计算而来，修改历史会产生新的 ID。
  2. 分支只是可移动的提交引用。新建分支很轻，HEAD 表示当前检出的分支或提交；合并、变基和 cherry-pick 本质上都在改变提交图或引用。
  3. 先分清三个区域。工作区是你正在编辑的文件，暂存区（index）是“下一次提交的候选快照”，仓库保存对象和引用。大多数 Git 困惑都来自混淆这三个区域。
  4. 共享历史优先追加，个人历史可以整理。已经推送并被他人基于其开发的提交，通常用 revert 反做；尚未共享的个人提交可以用交互式 rebase、amend 或 reset 整理。
  5. 合并与变基都能整合分支，但表达不同。merge 保留真实分叉并可能生成双亲提交；rebase 重放提交，形成更线性的历史，也会生成新的提交 ID。
  6. worktree 是同一仓库的多个工作目录。它们共享大部分对象与引用，但各自有工作区、index 和 HEAD，适合同时开发、紧急修复、并行测试和多个编码 Agent。
  7. GitHub/GitLab 不是 Git。Git 是本地版本控制引擎；两者是在 Git 之上提供远程托管、代码评审、权限、Issue、CI/CD、制品和安全能力的平台。

学习地图：从命令记忆到提交图思维

阶段应该掌握验收标准
入门安装、配置、init/clone、status、add、commit、log能独立创建仓库并解释一次提交保存了什么
熟练branch、switch、merge、冲突、remote、fetch/pull/push能走完功能分支与代码评审流程
进阶rebase、cherry-pick、reset、restore、revert、reflog、stash能为不同撤销/整合场景选择安全命令
精通对象、引用、DAG、worktree、bisect、签名、团队策略能从提交图推导命令效果，并设计可审计的团队工作流

学习时不要背“神奇命令”。每次操作前回答四个问题：我在哪个分支？工作区是否干净？哪个引用会移动？是否会重写已经共享的提交？

Git 的历史：为什么它生来就是分布式的

早期 Linux 内核开发主要通过补丁和归档文件协作；2002 年开始使用专有分布式版本控制系统 BitKeeper。2005 年合作关系变化后，免费使用安排终止，Linus Torvalds 和 Linux 社区开始设计 Git。初始目标包括速度、简单设计、强大的非线性开发、完全分布式，以及高效处理 Linux 内核这类大型项目。Pro Git：A Short History of Git

时代/模式代表形态核心问题Git 的回答
本地版本控制复制目录、补丁文件、本地数据库难协作、易覆盖、不可审计完整提交历史与内容寻址对象
集中式 VCSCVS、Subversion强依赖中央服务器；离线能力有限每个 clone 都有完整仓库，可离线提交与查看历史
分布式 VCSGit、Mercurial需要高效同步、合并和并行开发轻量分支、对象传输、远程引用与多种工作流

“分布式”不等于“没有中心”。团队仍可约定 GitHub 或 GitLab 上的仓库为权威来源，但技术上你的本地仓库不只是客户端缓存：它拥有对象数据库、提交图和引用，可以离线提交、分支、合并、回退和查询历史。

Git 原理：对象、引用与三个区域

三个区域：工作区、暂存区、仓库

工作区正在编辑的文件
git add挑选下一提交内容
暂存区 / index候选快照
git commit生成不可变对象
本地仓库对象 + 引用 + 历史

暂存区不是“临时文件夹”，而是一份索引：它记录下一次提交要包含的路径、模式和 blob。正因为有 index，你可以只提交当前文件的一部分改动：git add -p。

四类核心对象

对象保存什么不保存什么查看方式
blob文件内容文件名、目录路径git cat-file -p <id>
tree目录结构：名称、模式、blob/tree ID作者、提交说明git ls-tree <commit>
commit根 tree、父提交、作者、提交者、时间、说明“分支名”本身git show --format=raw <id>
annotated tag目标对象、标签者、说明、可选签名自动移动能力git show <tag>

Git 官方将其核心描述为内容寻址文件系统：数据写入对象数据库后，会得到由内容计算出的键。高层的 git add 和 git commit 会创建 blob、更新 index、写 tree，再写指向 tree 和父提交的 commit。Pro Git：Git Objects

# 在练习仓库中观察对象，不要依赖 find 的目录结构猜类型
git rev-parse HEAD
git cat-file -t HEAD
git cat-file -p HEAD
git ls-tree -r HEAD
git count-objects -v

初始理解可把 commit 看成完整快照。为节省空间和加速传输，Git 后续会把对象打包（packfile）并使用增量压缩；“逻辑模型是快照”和“物理存储会压缩”并不矛盾。

引用、分支与 HEAD

refs/heads/main              # 本地分支引用
refs/remotes/origin/main     # 上次 fetch 后看到的远程跟踪引用
refs/tags/v1.0.0             # 标签引用
HEAD                         # 当前分支的符号引用，或直接指向提交（detached HEAD）

分支通常只是 refs/heads/* 下指向某个提交的名字。提交后，当前分支引用向新提交前进；其他分支不动。HEAD 通常指向当前分支，因此 Git 知道“下一次提交让谁前进”。这就是 Git 分支创建和切换非常轻量的根本原因。Pro Git：Branches in a Nutshell

提交图与可达性

          C---D  feature/order-export
         /
A---B---E---F    main
         \
          H      hotfix/payment

每个提交通过 parent 指向过去，因此历史是有向无环图（DAG）。分支、标签和远程跟踪分支是图上的入口。所谓“删除分支”，只是删除一个引用；只要某提交仍可从其他引用或 reflog 到达，对象通常仍可恢复。Git 的许多动作都可归结为三类：移动引用、创建新提交、更新工作区/index。

身份、默认分支与编辑器

# 作者身份会写入后续提交；使用工作邮箱还是个人邮箱取决于组织政策
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# 新仓库默认分支名
git config --global init.defaultBranch main

# 任选熟悉的编辑器；下面以 IntelliJ IDEA 的命令行启动器为例
git config --global core.editor "idea --wait"

# 查看最终值来自哪个配置文件
git config --list --show-origin
git config --get user.email

配置按 system、global、local 等层级覆盖。公司仓库可以在仓库内用不带 --global 的配置覆盖个人默认值。作者身份并不是平台登录凭据；是否能 push 由 HTTPS token、SSH key、SSO 和平台权限决定。Pro Git：First-Time Git Setup

换行符与凭据安全

  • 优先用仓库中的 .gitattributes 统一文本规则，例如 * text=auto，不要只依赖每个人不同的 core.autocrlf。
  • 不要把访问令牌写进 remote URL、脚本、IDE 配置示例或仓库文件；优先使用系统凭据管理器或 SSH agent。
  • 提交前检查 git diff --cached；一旦秘密进入提交，即使后来删除，仍可能存在于历史和平台缓存中，应先吊销凭据，再按组织流程清理历史。

第一个仓库：从文件到可审计提交

init 与 clone

# 把现有 Spring Boot 项目变成仓库
cd order-service
git init
git status

# 或复制一个已有远程仓库（获得工作区 + 完整本地仓库 + origin）
git clone git@github.com:example/order-service.git
cd order-service
git remote -v

git init 不会自动提交现有文件；git clone 则会创建远程配置、下载对象、建立远程跟踪引用并检出默认分支。二者都只影响当前目录，不会自动把代码发布到互联网。

一次规范提交

git status --short
git diff                          # 工作区 vs 暂存区
git add src/main/java/com/example/order/Order.java
git add -p                        # 按 hunk 挑选
git diff --cached                 # 暂存区 vs HEAD
git commit -m "feat(order): validate order total"
git log --oneline --decorate --graph --all -10

一次提交只表达一个可解释、可测试的逻辑变化。不要把代码格式化、依赖升级、功能修改和无关文件混进同一提交。提交信息重点回答“为什么改”，diff 已经展示“改了什么”。

# Maven / Gradle 输出

# IDE 用户状态（团队共享配置需单独讨论）
.idea/workspace.xml

.gitignore 只影响尚未被跟踪的文件。已经入库的文件要先用 git rm --cached <path> 从 index 移除，再提交；这不会自动从旧历史删除它。

Git 分支：轻量引用，不是目录副本

创建、切换、查看与删除

git branch                              # 列出本地分支
git branch -avv                         # 本地、远程跟踪、upstream 与领先/落后
git switch -c feature/order-export      # 创建并切换
git switch main                         # 切换已有分支
git switch -                            # 回到上一个分支
git branch -m feature/export-orders     # 重命名当前分支
git branch -d feature/export-orders     # 仅删除已合并分支
git branch -D abandoned-experiment      # 强制删除；先确认提交有其他引用或无需保留

旧教程常写 git checkout -b feature/x 和 git checkout main；现代 Git 更推荐用职责清晰的 switch 切分支、restore 恢复文件。checkout 仍常见，但同时承担多种职责，初学者更容易误用。

本地分支、远程跟踪引用与 upstream

名称含义谁会移动它
main本地分支本地 commit、merge、rebase、reset 等
origin/main本地记录的“最近一次 fetch 时远端 main 的位置”fetch 或成功的网络同步
origin远程仓库的别名git remote 配置
upstream当前分支默认 pull/push/比较的上游分支push -u 或 branch -u
git fetch origin
git switch -c feature/order-export --track origin/feature/order-export
git push -u origin feature/order-export
git branch -vv

origin/main 不是服务器上的实时指针，断网时也能查看；只有 fetch 等操作后才更新。先 fetch、再比较 main..origin/main，比把所有行为都藏在 pull 中更容易学习和排错。

分支策略怎么选

策略适合优势代价
Trunk-based / 短分支持续交付、成熟自动化测试集成频繁、分叉时间短依赖特性开关、快速评审和可靠流水线
GitHub FlowWeb/SaaS 与经常部署的团队规则少：分支 → PR → 检查 → 合并复杂版本线需补充发布策略
Release branches同时维护多个生产版本便于补丁回移和独立发布需要明确 backport 和生命周期
Git Flow严格版本发布、低频上线的特定场景角色分支明确分支多、合并多；不应因“经典”而默认采用

分支间合并：fast-forward、三方合并与冲突

先确认方向：把谁合并到谁

# 目标：把 feature/order-export 合入 main
git status --short                 # 工作区应干净
git switch main                    # 先站到“接收方”
git fetch origin
git merge --ff-only origin/main    # 先安全更新本地 main
git merge feature/order-export     # 再把功能分支合进当前分支
git log --oneline --graph --decorate --all -15

git merge X 的主语是“当前分支”：把 X 可达而当前分支不可达的历史整合进当前分支。执行前先说完整句子“我在 main，要把 feature 合进来”，能避免绝大多数方向错误。

三种常见结果

结果何时发生提交图效果常用命令
Fast-forward当前分支是来源分支的祖先仅向前移动当前分支引用，不创建合并提交git merge --ff-only feature/x
Three-way merge双方从共同祖先后都产生提交创建有两个父提交的 merge commitgit merge --no-ff feature/x
Squash merge只想保留最终改动，不保留来源分支拓扑把差异放入 index，随后创建一个普通提交git merge --squash feature/x

三方合并使用两个分支尖端和共同祖先计算结果；产生的 merge commit 有两个父提交。Pro Git：Basic Branching and Merging

冲突处理的完整闭环

git status
git diff --name-only --diff-filter=U

# 打开冲突文件，理解两边业务意图后编辑；不要机械删除标记
# <<<<<<< HEAD
# 当前分支内容
# =======
# 被合入分支内容
# >>>>>>> feature/order-export

git add src/main/java/com/example/order/OrderService.java
mvn -q -DskipTests=false test
git diff --cached
git commit                          # 结束 merge

# 如果发现方向或时机不对
git merge --abort
  1. 用 status 确认正在进行的是 merge、rebase、cherry-pick 还是 revert；不同流程的继续/中止命令不同。
  2. 理解两边为何修改同一区域；冲突标记只展示文本，不告诉你业务上正确的组合。
  3. 编辑后用 git add 标记已解决；删除标记不等于 Git 已知冲突解决。
  4. 运行测试和静态检查，再结束操作；“能合并”不等于“业务正确”。

Rebase：重放提交，让基线前移

# 在尚未共享的 feature 分支上同步最新 main
git switch feature/order-export
git fetch origin
git rebase origin/main

# 冲突时：编辑 → add → 继续；或完整放弃
git add <resolved-files>
git rebase --continue
git rebase --abort

# 整理个人提交：改顺序、改说明、合并或拆分
git rebase -i origin/main

rebase 会找出当前分支相对 upstream 独有的提交，把分支临时放到新基线，再逐个重放这些改动，最后更新分支引用。因此结果中的提交虽然改动意图相似，但父提交、时间或元数据不同，ID 也会变化。Git 官方手册：git-rebase

选择优点风险建议
merge main into feature不改已有提交 ID，保留真实整合点频繁同步会产生较多 merge commits共享功能分支、多人同时开发时更稳妥
rebase feature onto main历史线性，便于逐提交审查和 bisect重写提交；冲突可能逐个提交出现个人、短期、尚未共享的分支适合

黄金规则：不要擅自 rebase 已被他人基于其开发的共享提交。如果团队明确允许重写 PR/MR 分支，推送时使用 git push --force-with-lease，它会在远端引用与本地预期不符时拒绝覆盖；不要习惯性使用无保护的 --force。

跨分支与撤销动作：如何选择正确工具

目标工具改变什么是否适合共享历史
整合整个分支并保留拓扑merge移动引用或创建 merge commit是
把一串提交重放到新基线rebase创建新提交并移动分支通常否；除非团队协调
移植少数特定提交cherry-pick在当前分支创建等效的新提交可以，但要记录来源和避免重复合并
反做一个已共享的坏提交revert追加一个反向提交是，首选
移动本地分支并调整 index/工作区reset移动引用，按模式更新区域不应直接用于重写共享历史
恢复文件内容或取消暂存restore更新工作区和/或 index，不移动分支与提交历史无关，但可能丢未提交改动
临时收起未完成修改stash创建 stash 引用并清理选定区域本地临时用途

Cherry-pick：移植特定修复

# 把 main 上已验证的修复回移到 release/2.4
git switch release/2.4
git cherry-pick -x a1b2c3d

# 冲突处理
git add <resolved-files>
git cherry-pick --continue
git cherry-pick --abort

cherry-pick 应用某提交引入的变化，并在当前分支记录新提交；-x 会在说明中记录来源 ID，适合公开分支之间的 backport 审计。Git 官方手册：git-cherry-pick

Reset、restore 与 revert

# 取消暂存，保留工作区修改
git restore --staged src/main/java/com/example/order/Order.java

# 丢弃某文件未提交修改（危险：先 diff）
git restore src/main/java/com/example/order/Order.java

# 本地撤销最后一次提交，保留修改和暂存状态
git reset --soft HEAD~1

# 本地撤销最后一次提交，保留工作区修改但取消暂存
git reset --mixed HEAD~1

# 为已共享提交创建反向提交
git revert a1b2c3d

理解 reset 的“三棵树”：--soft 只移动分支引用；默认的 --mixed 再更新 index；--hard 还覆盖工作区。未提交内容可能因此不可恢复，所以本文不把 reset --hard 当日常清理命令。Pro Git：Reset Demystified；共享历史的撤销应优先使用会记录新提交的 git-revert。

Stash：短期切换上下文，不是长期仓库

git stash push -u -m "wip: order export validation"
git stash list
git stash show -p stash@{0}
git stash apply stash@{0}     # 保留 stash，适合先验证
git stash drop stash@{0}

# 或一步应用并删除；有冲突时仍需手工处理
git stash pop

默认 stash 不包含未跟踪文件，-u 才包含；ignored 文件需要更强的选项，使用前先确认范围。重要工作不要长期只放在 stash 中，最好在明确命名的 WIP 分支提交。官方文档推荐使用 git stash push，旧的 save 形式已被弃用。Git 官方手册：git-stash

远程协作：fetch、pull、push 与评审

git remote -v
git remote get-url origin
git fetch --prune origin
git log --oneline --left-right --graph main...origin/main

# 明确只允许快进，避免 pull 意外生成合并提交
git pull --ff-only

# 首次发布功能分支并设置 upstream
git push -u origin feature/order-export

# 删除远程功能分支
git push origin --delete feature/order-export
命令网络行为本地行为学习建议
fetch下载对象与远程引用通常不改当前工作区/本地分支最适合先观察，再决定 merge/rebase
pull先 fetch随后按配置 merge 或 rebase团队应显式约定 --ff-only 或 --rebase
push上传对象并请求更新远端引用成功后更新相应远程跟踪状态非快进通常会被拒绝，这是数据保护信号

Pull Request / Merge Request 不是 Git 对象，而是平台上的协作记录：它把来源分支、目标分支、diff、评论、审批、检查结果与合并动作组织起来。Git 提交应保持可构建、可审查；平台规则应保护默认分支，要求必要检查通过再合并。

Worktree：一个仓库，多套工作目录

核心概念

普通 clone 创建一个主 worktree。git worktree add 可以给同一仓库增加 linked worktree，使你同时检出多个分支。它们共享大部分对象库和引用，因此比重复 clone 更节省空间、创建更快；每个 worktree 又有独立的工作区、index 和 HEAD，修改不会直接覆盖另一个目录。官方定义与管理命令见 git-worktree 手册。

order-service/                 # main worktree，当前在 main
../order-service-export/      # linked worktree，feature/order-export
../order-service-hotfix/      # linked worktree，hotfix/payment-timeout

# 三个目录共享提交对象与大多数 refs，但工作区/index/HEAD 独立

创建、查看、移动与删除

# 从当前 HEAD 创建新分支，并在新目录检出
git worktree add -b feature/order-export ../order-service-export

# 把已有但当前未被其他 worktree 检出的分支放到新目录
git worktree add ../order-service-hotfix hotfix/payment-timeout

# 临时实验：detached HEAD，不创建分支
git worktree add --detach ../order-service-benchmark HEAD

git worktree list --porcelain
git worktree move ../order-service-benchmark ../bench-order-service
git worktree lock --reason "external disk" ../bench-order-service
git worktree unlock ../bench-order-service

# 先确认目标目录没有需要保留的修改，再从任意 worktree 执行
git worktree remove ../order-service-export
git worktree prune --dry-run
git worktree prune

适用场景与边界

场景为什么适合 worktree注意
主功能开发中插入生产 hotfix无需 stash 或污染当前工作区hotfix 合并后，功能分支仍需同步修复
同时维护 main 与 release两个 IDE 窗口、两套构建目录可并行本地服务端口、数据库 schema 和环境变量要隔离
多个编码 Agent 并行任务每个 Agent 有独立工作区和分支，diff 边界清楚不要让不同 Agent 编辑同一 worktree；合并仍需人工/测试验证
跨版本性能对比两个提交可同时构建运行Maven 本地仓库共享，项目输出目录各自独立
仅想节省一次 clone共享对象库节省空间不是权限或故障隔离；对象库损坏会影响所有 worktree
  • Git 默认拒绝把同一个分支同时检出到多个 worktree，这是防止两个工作区竞争移动同一引用的保护。
  • 不要直接用文件管理器移动或删除 linked worktree。优先用 worktree move/remove；误移动后使用 worktree repair。
  • 可移动磁盘或不常挂载路径可 lock，避免管理信息被 prune。
  • 官方手册仍提示多 worktree 对 submodule 的支持不完整；含 submodule 的超级项目使用前应在练习仓库验证。
  • 删除 worktree 不等于删除分支；两者按需分别执行，避免误以为历史已清理。

GitHub 与 GitLab：同用 Git，不是同一个产品

先分清 Git 与托管平台

能力Git 本身GitHub / GitLab
本地提交、分支、合并、变基提供调用/展示 Git 能力
远程仓库协议提供 SSH/HTTP 等传输机制托管服务器、账号、权限和审计
代码评审没有 PR/MR 对象Pull Request / Merge Request、评论、审批、规则
项目管理不提供 Issue/看板Issue、里程碑、项目/工作项等
CI/CD可用 hook 触发外部系统GitHub Actions / GitLab CI/CD 与 runner
制品与安全不直接提供依套餐和部署形态提供包、容器、安全扫描等

GitHub 与 GitLab 对比

维度GitHubGitLab选择建议
评审术语Pull Request（PR）Merge Request（MR）核心目的相同：提议、讨论、检查并合并分支
常见工作流GitHub Flow 强调轻量、短分支和经常部署常见受保护分支或 fork + MR 流程先按团队交付模型选流程，不要被名称绑架
CI/CD 配置.github/workflows/*.yml，GitHub Actions默认根目录 .gitlab-ci.yml，GitLab CI/CD比较 runner、缓存、合规、复用方式和现有生态
部署形态GitHub.com 与 GitHub Enterprise 等形态GitLab.com、Self-Managed、Dedicated强自托管/内网需求要评估运维成本与合规要求
生态侧重开源社区、Marketplace、Actions 与广泛第三方集成强项目、MR、CI/CD、制品、安全与部署链路高度集成对现有组织工具做 PoC，不用单一功能下结论
迁移成本Git 对象和分支通常可迁移，但 Issue、评审评论、权限、流水线、密钥、制品与审计记录需要专门迁移把“能 mirror 仓库”与“完整平台迁移”分开评估

GitHub 官方把 GitHub Flow 定义为适合经常部署团队的轻量、基于分支的工作流；PR 将独立分支上的变化提交给他人评审。GitHub Docs：Git workflows、Pull request quickstart。GitHub Actions 可在 GitHub 托管或自托管 runner 上执行 CI。GitHub Docs：Continuous integration

GitLab 把 repository 作为 project 的组成部分，并在 project 中组合 Issue、MR、CI/CD 等能力；MR 集中展示代码变化、讨论、流水线、可合并性和提交。GitLab CI/CD 默认以根目录的 .gitlab-ci.yml 定义 stage 与 job，再由 runner 执行。GitLab Docs：Projects、Merge requests、GitLab CI/CD

同一套本地 Git，两个平台只改远程与评审入口

# GitHub
git remote add origin git@github.com:acme/order-service.git

# GitLab（自托管域名示例）
git remote add origin git@gitlab.example.com:acme/order-service.git

# 后续本地动作一致
git switch -c feature/order-export
git add -p
git commit -m "feat(order): export orders"
git push -u origin feature/order-export

# 然后分别在平台创建 PR 或 MR，等待检查与评审

Java 团队完整实战：从 Issue 到上线

  1. 定义变更。Issue 明确订单导出 API 的验收标准、权限、数据量与兼容性。
  2. 同步基线。git switch main && git pull --ff-only，确认测试通过。
  3. 隔离工作。git switch -c feature/order-export；若主工作区还有别的任务，用 worktree 新建目录。
  4. 小步提交。按“接口契约 → 领域逻辑 → 持久化 → 测试/文档”拆分，每步运行 Maven 最小相关测试。
  5. 发布分支。git push -u origin feature/order-export，创建 PR/MR，关联 Issue。
  6. 自动检查。编译、单元/集成测试、格式、静态分析、依赖与秘密扫描；不要把“流水线通过”等同于业务评审完成。
  7. 处理反馈。个人分支可 amend/rebase 整理；多人共享分支优先追加提交，避免突然改写他人基线。
  8. 合并。按仓库规则选择 merge、squash 或 rebase merge；平台保护 main 并要求必要审批。
  9. 上线与追踪。部署应记录 commit/tag；故障时才能确定运行的是哪份源码，并选择 revert 或 hotfix。
  10. 清理。删除已合并远程/本地功能分支和不用的 linked worktree；保留 release tag 与审计记录。

恢复与排错：先停止扩大损失

现象第一步恢复思路
提交到了错误分支记录提交 ID，确认是否已 push在正确分支 cherry-pick；错误分支未共享可 reset，已共享则 revert
误删本地分支git reflog --all找到尖端提交后 git branch recovered/<name> <id>
rebase 结果不对进行中用 rebase --abort完成后查 reflog，给旧尖端建恢复分支，再比较
push 被 non-fast-forward 拒绝git fetch 后画图比较判断是需要 merge/rebase，还是远端被意外改写；不要直接 force
合并冲突太复杂保存现场并看 status必要时 abort，缩小分支差异、补测试后重新合并
不知道哪个提交引入问题准备可重复的好/坏判定命令用 git bisect 二分定位，再验证因果
# reflog 记录本地引用变化，是误 reset/rebase 后的第一救援入口
git reflog --date=iso
git show <suspected-id>
git branch recovered/pre-rebase <old-id>

# 二分定位回归；脚本返回 0 表示 good，非 0 表示 bad
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run mvn -q -Dtest=OrderExportTest test
git bisect reset

恢复原则：先创建恢复分支或 tag 固定仍可找到的提交，再尝试修改；不要在慌乱时连续执行 reset、clean、force push。reflog 主要是本地记录，不是跨机器备份，也有过期和垃圾回收边界。

精通阶段的高价值工具

工具用途示例
精确日志按路径、作者、时间和图查询历史git log --graph --decorate --oneline --all
内容搜索搜索当前或历史版本中的文本git grep "OrderStatus"
追溯行找到某行最后一次修改，作为调查入口git blame -L 40,70 -- OrderService.java
范围比较比较分支独有提交或共同祖先后的差异git log main..feature、git diff main...feature
交互暂存把混杂工作区拆成原子提交git add -p
签名让平台验证提交/tag 的签名身份git commit -S；需先配置并保护密钥
维护优化对象存储并检查仓库git maintenance run、git fsck

blame 只告诉你最后修改者，不自动等于缺陷责任人；应结合 commit、PR/MR、需求和后续重构理解上下文。bisect 的结论也依赖判定测试是否稳定。

推荐的团队安全基线

  • 保护默认分支：禁止直接 push，要求 PR/MR、必要审批和 CI 检查。
  • 明确合并策略：仓库统一使用 merge、squash 或 rebase merge，不让每个人临时决定。
  • 分支短生命周期、命名含目的；长期 release 分支明确负责人、支持期限和回移规则。
  • 禁止无审计 force push；确需改写功能分支时使用 --force-with-lease 并通知协作者。
  • 提交前本地运行最小相关测试；合并前由 CI 运行团队定义的完整门禁。
  • 秘密不入库，大文件评估 Git LFS 或制品仓库；构建产物和 IDE 用户状态通常忽略。
  • 发布使用不可变 commit ID 或 annotated tag；版本、制品和部署记录应能互相追溯。
  • 为 hotfix、revert、灾难恢复和 worktree 清理编写团队 runbook，并定期演练。

四阶段实践路线与验收

第一阶段：30 分钟建立对象感

  1. 创建临时仓库，提交两个版本的 Order.java。
  2. 用 cat-file、ls-tree 找到 commit → tree → blob 的关系。
  3. 用 restore --staged 和 add -p 操作 index，并解释三种 diff。

验收：不用背命令，能画出工作区、index、HEAD commit 和当前分支引用。

第二阶段：60 分钟掌握分支整合

  1. 制造一次 fast-forward、一次 --no-ff 三方合并。
  2. 让两个分支修改同一行，完整解决冲突并运行测试。
  3. 重复场景改用 rebase，对比提交 ID 与图结构。

验收：看到提交图就能预测 merge/rebase 后哪些引用移动、是否产生新提交。

第三阶段：60 分钟练习恢复

  1. 在练习仓库误删分支，用 reflog 恢复。
  2. 分别用 restore、reset --soft、reset --mixed、revert 完成指定撤销。
  3. 把修复 cherry-pick 到 release 分支，制造并解决一次冲突。

验收：能说明为什么共享分支选择 revert，而不是 reset 后强推。

第四阶段：90 分钟模拟团队交付

  1. 用两个 worktree 同时检出 feature 与 hotfix，分别运行 Spring Boot 测试。
  2. 在 GitHub 或 GitLab 建立受保护默认分支、评审和 CI 门禁。
  3. 走完 Issue → 分支 → 小步提交 → PR/MR → 冲突 → 合并 → tag → 清理。

验收：提交图可解释、流水线通过、评审记录完整、worktree 和临时分支已安全清理，并能从 tag 追溯发布源码。

常见问题

问题简短回答
commit 后文件是否上传了？没有。commit 只写本地仓库；push 才尝试更新远端。
branch 会复制整个项目吗？不会。分支本质上是提交引用；切换时 Git 更新 index 和工作区。
pull 等于下载代码吗？不止。它通常是 fetch 后再 merge 或 rebase，行为应由参数/配置明确。
merge 后能删功能分支吗？通常可以；提交仍可从目标分支到达。先确认合并策略、远端状态和未合入提交。
rebase 会丢代码吗？正常重放不会故意丢代码，但错误解决冲突或跳过提交会改变结果；用测试、range-diff 和 reflog 验证。
worktree 与 clone 有何区别？worktree 共享同一仓库的大部分对象/引用；clone 是独立仓库，有独立对象库和远程状态。
GitHub 和 GitLab 能互相 push 吗？Git 仓库可配置多个 remote；但 PR/MR、Issue、权限、CI/CD 等平台数据不会随 Git push 自动同步。
GUI/IDE 能替代命令行吗？能覆盖大部分日常动作，但仍应理解提交图、三个区域和危险操作；发生复杂冲突与恢复时原理比界面更重要。
