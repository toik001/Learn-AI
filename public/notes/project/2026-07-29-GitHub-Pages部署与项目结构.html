#GitHub Pages 部署与项目结构

整理日期：2026-07-29
目标：保持 public/ 作为唯一发布根目录，通过 GitHub Actions 在部署前完成确定性校验，再发布到项目级 GitHub Pages。

#核心结论

Learn-AI 不改成 Jekyll，也不维护 gh-pages 生成分支。main 中的 public/ 就是完整静态站点；GitHub Actions 负责校验、打包 Pages artifact，并通过受限的部署 job 发布。GitHub 官方把“自定义 Actions workflow”列为不希望维护专用编译分支时的推荐方式。GitHub Pages：配置发布来源

默认线上地址是 https://toik001.github.io/Learn-AI/。因为这是项目站点，仓库名会成为 URL 子路径；所有站内链接和资源必须保持相对 URL，不能写成以 / 开头的根路径。GitHub 对项目站点与用户站点的地址差异有明确说明。GitHub Pages：站点类型

#迁移方案对比

方案对当前仓库的影响发布前校验结论
Actions 上传 public/保留现有内容边界可运行全部 Node.js 校验采用
main/docs 分支来源必须移动 public/，并处理内部 docs/ 冲突Pages 发布前缺少自定义门禁不采用
独立 gh-pages 分支维护第二份生成结果仍需脚本或 Actions 同步不采用

从分支发布并非不可行，但 GitHub Pages 的分支来源只允许分支根目录或 /docs。当前项目的发布目录是 /public，直接上传 artifact 能避免目录迁移和重复状态。GitHub Pages：从分支或 Actions 发布

#项目结构

text
.
├── .github/
│   └── workflows/
│       └── pages.yml             # 校验、上传 artifact、部署
├── AGENTS.md                     # 项目持久规则
├── README.md                     # 仓库使用入口
├── public/                       # 唯一公开网站根目录
│   ├── index.html
│   ├── manifest.json
│   ├── assets/
│   │   ├── style.css
│   │   └── app.js
│   └── notes/<category>/
│       └── YYYY-MM-DD-主题.html
└── scripts/
    ├── build-html-index.mjs      # 生成导航和清单
    ├── verify-site.mjs           # 校验链接、锚点与结构
    └── test-*.mjs                # 回归测试

actions/upload-pages-artifact 的 path 明确设置为 public，因此工作流、README、规则和测试不会进入站点 artifact。GitHub 要求 Actions 模式下 artifact 根部包含小写 index.html。GitHub Pages：404 排查

#完整 GitHub Actions 工作流

yaml
name: Deploy knowledge base to GitHub Pages

on:
  push:
    branches:
      - main
  workflow_dispatch:

permissions: {}

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Checkout repository
        uses: actions/checkout@v6

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: 24
          package-manager-cache: false

      - name: Verify entry files and JavaScript syntax
        run: |
          test -s public/index.html
          node --check scripts/build-html-index.mjs
          node --check scripts/verify-site.mjs
          node --check public/assets/app.js

      - name: Run content regression tests
        run: |
          set -euo pipefail
          for test_file in scripts/test-*.mjs; do
            node "$test_file"
          done

      - name: Verify static site integrity
        run: node scripts/verify-site.mjs

      - name: Verify generated navigation is committed
        run: |
          node scripts/build-html-index.mjs
          git diff --exit-code -- public

      - name: Upload GitHub Pages artifact
        uses: actions/upload-pages-artifact@v5
        with:
          path: public

  deploy:
    needs: build
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Configure GitHub Pages
        uses: actions/configure-pages@v6

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v5

#为什么拆成 build 与 deploy

  1. build：只有 contents: read，负责检出、校验和上传 artifact；内容测试失败时不会进入部署。
  2. deploy：通过 needs: build 等待唯一合格 artifact，仅授予 pages: write 与 id-token: write。
  3. environment：github-pages 保存部署状态和页面 URL，也可以设置仅允许 main 部署的保护规则。
  4. OIDC：id-token: write 用于证明部署来自允许的 workflow/ref；不是仓库内容写权限，也不需要个人访问令牌。

deploy-pages 官方说明部署 job 至少需要 Pages 写权限和 OIDC token，并建议使用 github-pages environment。actions/deploy-pages

#Action 版本基线

GitHub Docs、starter workflow 和各 action release 的更新节奏可能不同。本项目以 2026-07-29 各官方仓库已经发布的最新主版本为准：

  • actions/checkout@v6 与 actions/setup-node@v6；显式选择 Node.js 24。
  • actions/configure-pages@v6：Node.js 24 运行时版本。
  • actions/upload-pages-artifact@v5：内部使用新版 artifact 上传能力。
  • actions/deploy-pages@v5：Node.js 24 运行时版本。

升级主版本前应重新查看 release notes，尤其关注 Actions Runner 最低版本和 artifact 兼容性。GitHub.com 托管 runner 会由平台维护；自托管 runner 则需要管理员升级。

#发布数据流

text
git push main
   │
   ▼
GitHub Actions build
   ├─ 语法与内容回归
   ├─ 链接、资源、锚点、元数据校验
   ├─ 索引可重复生成校验
   └─ 上传 public/ → github-pages artifact
   │
   ▼ needs: build
GitHub Actions deploy
   ├─ OIDC 验证 workflow/ref
   ├─ 创建 Pages deployment
   └─ 输出 page_url
   │
   ▼
https://toik001.github.io/Learn-AI/

artifact 是某次 workflow run 的静态打包结果；Pages deployment 是平台面向访问者的部署记录。部署 job 不重新检出或改写内容，从而保证发布物就是 build job 已校验的同一份 artifact。

#项目子路径与相对链接

仓库名是 Learn-AI，所以项目站点位于 /Learn-AI/。页面中的 ../../assets/style.css、../../index.html 等相对地址会从当前页面位置解析，既适合 GitHub Pages 子路径，也能直接从本地文件系统或本地静态服务器阅读。

不要把链接写成 /assets/style.css 或 /notes/...：浏览器会把它们解析到 toik001.github.io 域名根部，绕过 /Learn-AI/。scripts/verify-site.mjs 会在提交前拒绝这种根路径引用。

#首次启用 GitHub Pages

  1. 进入仓库 Settings → Pages。
  2. 在 Build and deployment 的 Source 中选择 GitHub Actions。
  3. 推送包含 .github/workflows/pages.yml 的 main，或在 Actions 页面手动执行 Deploy knowledge base to GitHub Pages。
  4. 等待 build 和 deploy 均成功，再从 deployment 的 page_url 打开站点。

Pages Source 是仓库级外部设置，无法只靠提交文件保证。GitHub 官方说明已有自定义 workflow 时可以跳过模板创建，但仍需把发布来源选择为 GitHub Actions。GitHub Pages：选择 Actions 来源

#本地维护与验证

bash
node scripts/build-html-index.mjs
test -s public/index.html
node --check scripts/build-html-index.mjs
node --check scripts/verify-site.mjs
node --check public/assets/app.js
for test_file in scripts/test-*.mjs; do node "$test_file"; done
node scripts/verify-site.mjs
node scripts/build-html-index.mjs
git diff --exit-code -- public
git diff --check

CI 会重跑生成器，但不会替开发者提交生成结果。如果重跑后 public/ 有差异，build 直接失败；应在本地重建、审查并提交，而不是让流水线静默修改发布物。

verify-site.mjs 会校验 artifact 根入口、本地链接和资源、片段锚点、重复 ID、标题 ID、知识页元数据、语义标签、外部链接安全属性、路径越界和根路径引用。

#常见失败与排查

现象原因处理
git diff --exit-code -- public 失败索引、侧栏或 manifest 未提交本地运行生成器并审查变化
完整性校验失败坏链接、未知锚点、重复 ID 或根路径按文件级诊断修复源 HTML
deploy 未开始build 失败或 artifact 未上传先修复 build 的第一个失败步骤
deploy 报权限错误Pages Source、workflow 权限或 environment 保护不匹配检查 Settings、job permissions 与 environment 规则
首页 404Pages 未启用或 artifact 根部缺少 index.html选择 GitHub Actions Source 并检查上传路径
首页正常、资源 404使用了域名根路径改为相对 URL 并运行完整性校验

GitHub 建议从 workflow run 定位构建和部署错误；Actions 模式下 artifact 根目录和小写 index.html 是 404 排查重点。GitHub Pages：Troubleshooting 404 errors

#安全与边界

  • public/ 中的所有文件都应视为公开内容，不得包含密钥、内网地址或私有数据。
  • 不使用个人 PAT。部署通过仓库的 GITHUB_TOKEN 与 OIDC 完成。
  • build job 没有 Pages 写权限；deploy job 不检出源码，也没有 contents 写权限。
  • 外部链接统一使用 target="_blank"、rel="noopener noreferrer"。
  • GitHub Pages 只提供静态文件，不能运行 Java、数据库或服务端 API；动态能力需要独立后端。
