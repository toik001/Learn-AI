#GitLab Pages 极简部署与项目结构

整理日期：2026-07-24
主题：使用零依赖、无构建步骤的纯静态结构部署学习知识库，并规定后续 HTML 文档的固定位置和发布流程。

#核心结论

本项目直接把可发布网站提交到 public/。GitLab CI 不生成页面、不安装依赖，只确认入口存在，然后将整个目录交给 GitLab Pages。

GitLab 官方文档说明，Pages 支持纯 HTML、CSS 和 JavaScript，默认发布目录是 public，发布目录根部必须包含非空 index.html。GitLab Pages

#项目结构

text
.
├── .gitlab-ci.yml             # GitLab Pages 部署
├── .gitignore
├── AGENTS.md                  # Codex 持久规则，不对外发布
├── public/                    # GitLab Pages 网站根目录
│   ├── index.html             # 知识库总入口
│   ├── manifest.json          # 页面清单
│   ├── assets/
│   │   ├── style.css
│   │   └── app.js
│   └── notes/
│       ├── codex/
│       ├── project/
│       ├── llm/
│       ├── papers/
│       └── tools/
└── scripts/
    └── build-html-index.mjs   # 重建入口和站内导航

public/ 之外的内容不会被 Pages 发布。这样可以让规则、脚本和 CI 配置留在仓库中，同时只公开真正需要浏览的静态文件。

#极简 CI 配置

yaml
pages:
  stage: deploy
  tags:
    - page-build-zhao
  script:
    - test -s public/index.html
  artifacts:
    paths:
      - public
  only:
    - main

tags: page-build-zhao 将该作业定向交给项目中配置了同名标签的 Runner。目标自建 GitLab 对 job 级 pages: true 报出 unknown keys: pages，说明它尚未支持新版 Pages job 关键字。因此这里使用兼容旧版本的语法：把 job 直接命名为 pages，并通过 artifacts.paths: public 指定发布内容。

only: main 只允许 main 分支触发 Pages。GitLab 新版文档已将 job 名称方式标记为弃用，但在该自建实例上它是实际支持的部署接口；升级 GitLab 后再考虑迁移到自定义 job 名称和 pages: true。GitLab CI/CD YAML：pages

#后续文档生成规则

  1. 直接创建 public/notes/<category>/YYYY-MM-DD-主题关键词.html。
  2. 页面使用共享的 public/assets/style.css 和 public/assets/app.js。
  3. 页面必须提供摘要、分类、整理日期、稳定标题锚点、页内目录和参考资料。
  4. 所有站内链接和资源使用相对路径，避免部署在 GitLab 项目子路径后失效。
  5. 完成页面后运行 node scripts/build-html-index.mjs，自动更新首页、侧栏、上一篇/下一篇和清单。
  6. 提交并推送默认分支，由 GitLab CI 自动发布。

#本地验证

bash
node scripts/build-html-index.mjs
test -s public/index.html
node --check scripts/build-html-index.mjs
node --check public/assets/app.js

知识库没有 npm、Java 或静态站点生成器依赖，可以直接双击 public/index.html 离线浏览。

#自建 GitLab 前置条件

代码推送成功不代表 Pages 一定已经启用。自建 GitLab 还需要管理员配置 Pages 域名，并为项目提供可运行 CI 的 GitLab Runner。若流水线成功但没有 Pages 地址，应先检查实例和项目的 Pages 设置。GitLab Pages settings

#部署位置与工作原理

#先回答：部署到哪里

Pages 不会把整个 Git 仓库检出后长期放在 Runner 上，也通常不会复制到普通 Nginx 的 /var/www。当前项目真正被发布的是 public/ 目录，它先作为 CI job artifact 上传给 GitLab，再由 GitLab 建立 Pages deployment。当前 GitLab Pages 的底层发布格式是“每个部署一个 ZIP 归档”，每次更新站点都会产生一个新归档。GitLab Pages：ZIP storage

对象典型位置作用
Git 仓库Gitaly repository storage保存源码和提交历史，不直接作为网站目录
Runner 工作目录Runner 主机、容器或 Pod 的临时构建目录检出代码并运行 test -s public/index.html；作业结束后不承担网站访问
CI job artifactLinux package 默认 /var/opt/gitlab/gitlab-rails/shared/artifacts，或 S3 兼容对象存储保存 Runner 上传的 public/ 归档
Pages deploymentLinux package 通常位于 /var/opt/gitlab/gitlab-rails/shared/pages，也可以位于对象存储或共享网络存储保存 Pages 服务实际读取的站点 ZIP
对外服务GitLab Pages daemon，可与 GitLab 同机或独立部署根据域名和路径找到部署并返回 HTML、CSS、JavaScript 等静态文件

上表中的路径是 Linux package 的常见默认值，不等于当前 code.dding.net 实例一定采用这些路径。如果 GitLab 使用 Docker，宿主机位置由 volume 映射决定；如果启用了对象存储，文件可能在 MinIO、AWS S3 或其他 S3 兼容 bucket 中；如果 Pages 独立部署，还可能通过共享卷或对象存储访问归档。

#从 git push 到浏览器的完整链路

  1. 推送源码：git push 把提交写入 GitLab 的 Git 仓库；这时还没有新网站部署。
  2. 创建流水线：GitLab 解析 .gitlab-ci.yml，发现名为 pages 的旧式 Pages job，并把它放入调度队列。
  3. Runner 执行：拥有 page-build-zhao 标签的 Runner 领取作业，在临时工作目录检出仓库并验证 public/index.html。
  4. 上传 artifact：Runner 根据 artifacts.paths: public 压缩并上传整个 public/。官方说明，大部分 artifact 都由 Runner 压缩后发送给 GitLab coordinator。GitLab：Storing job artifacts
  5. 建立 Pages deployment：GitLab 后台识别成功的 Pages job，记录部署元数据并保存新的 Pages ZIP。新部署就绪后成为当前站点版本，旧部署按实例和版本策略保留或清理。
  6. 域名路由：浏览器请求 Pages 域名；DNS 将请求导向 Pages 入口，通常先经过 Pages NGINX，再转给 GitLab Pages daemon。
  7. 定位项目：Pages daemon 根据 Host、namespace 和 project slug 查询 GitLab 内部 API，确定应读取哪个项目、哪个部署以及它位于本地还是对象存储。域名信息会被缓存。GitLab Pages：Domain source configuration
  8. 返回静态文件：Pages daemon 从部署 ZIP 中读取对应的 index.html、CSS 或 JavaScript 并返回。对象存储场景下，Pages 可以直接从 ZIP 提供内容，并使用内存缓存提高访问性能。
text
git push
   │
   ▼
GitLab 仓库（Gitaly）
   │ 创建 pipeline
   ▼
page-build-zhao Runner（临时检出与校验）
   │ 上传 public/ artifact
   ▼
GitLab Rails / Workhorse / Sidekiq
   │ 创建 Pages deployment ZIP
   ▼
本地 pages_path / 共享存储 / S3 兼容对象存储
   ▲
   │ 按域名和路径读取
GitLab Pages daemon ◀── Pages NGINX / DNS ◀── 浏览器

#Artifact 与 Pages deployment 的区别

两者相关但不是同一个概念：

  • Job artifact 属于某次 CI job，可以在 Build → Artifacts 查看或下载，保留时间受 artifact 策略控制。
  • Pages deployment 属于站点发布记录，可以在 Deploy → Pages 查看；Pages daemon 服务的是部署归档，而不是 Runner 的工作目录。
  • GitLab 版本不同，artifact 到 Pages deployment 的内部转换细节可能不同，但“Runner 生产并上传，GitLab 保存部署，Pages daemon 对外服务”的职责边界不变。

#管理员如何确认当前实例的真实位置

仅凭仓库配置无法得知 code.dding.net 的宿主机路径。管理员应查看 /etc/gitlab/gitlab.rb 或实际部署清单中的以下设置：

  • gitlab_rails['artifacts_path']：CI artifact 的本地路径。
  • gitlab_rails['pages_path']：Pages 本地或网络存储路径。
  • gitlab_rails['pages_object_store_enabled'] 以及 Pages object-store 配置：是否写入对象存储及对应 bucket。
  • pages_external_url：对外 Pages 根域名，不是文件存储位置。

在 Linux package 默认配置下，job artifacts 位于 /var/opt/gitlab/gitlab-rails/shared/artifacts；GitLab 官方也明确 Pages deployment ZIP 可以位于本地或对象存储。管理员可以查询 pages_deployments.file_store，其中 1 表示文件系统，2 表示对象存储。Pages deployment storage verification

#CI 长期 In progress 排查

#当前项目的判断

当前流水线只有一个 pages 作业，使用 page-build-zhao 标签匹配 Runner，实际脚本只有 test -s public/index.html。入口文件已经存在，该命令正常情况下会在一秒内结束；没有依赖下载、页面构建、网络访问或循环。因此，流水线长时间显示 In progress 时，优先检查该 Runner 是否在线、是否拥有同名标签以及是否允许当前分支作业，而不是怀疑知识库代码卡住。

最常见情况是作业处于 pending：GitLab 已创建作业，但没有合适的 Runner 来领取。GitLab 官方将 pending 定义为“在队列中等待 Runner”，将 running 定义为“已经在 Runner 上执行”。GitLab Jobs API：Job status values

#先看 pages 作业的精确状态

进入项目的 Build → Pipelines，打开最新流水线，再点击 pages 作业。不要只依据流水线顶部的聚合状态，按下表定位：

页面状态或日志停止位置含义处理方向
pending、stuck，没有 Runner 名称作业还未开始执行检查 page-build-zhao 标签是否存在且 Runner 在线
preparing / Preparing environmentRunner 已领取任务，但执行器环境没有准备好检查 Docker、Kubernetes 或 Shell executor 及 Runner 日志
Getting source from Git repositoryRunner 无法顺利拉取仓库检查 Runner 到 GitLab 的网络、DNS、证书和磁盘
Uploading artifacts脚本已完成，卡在上传 public/检查 GitLab artifact 本地存储或对象存储
pages 已成功，但 Deploy → Pages 仍进行中CI 已结束，Pages 后台部署尚未完成由管理员检查 Sidekiq、Pages daemon 和 Pages 存储

#最可能的修复：Runner

  1. 进入 Settings → CI/CD → Runners。
  2. 确认至少一个项目、群组或实例 Runner 为 online，没有暂停，并且已对当前项目启用。官方说明中，online 表示 Runner 最近仍在联系 GitLab，offline 表示当前不可用。GitLab Runner statuses
  3. 当前 pages job 已配置 page-build-zhao 标签；Runner 必须拥有完全相同的标签。Runner 的显示名称不能代替 Runner Tag。
  4. 如果 GitLab 页面中的 page-build-zhao 只是 Runner 名称或描述，需要在该 Runner 的 Tags 配置里再添加 page-build-zhao。
  5. 如果 Runner 被标记为 Protected，它只能领取受保护分支产生的作业；确认 main 的保护状态与 Runner 设置匹配。
yaml
pages:
  stage: deploy
  tags:
    - page-build-zhao
  script:
    - test -s public/index.html
  artifacts:
    paths:
      - public
  only:
    - main

GitLab 调度作业时会综合匹配 Runner 类型、状态、容量、标签和受保护分支设置；带标签的作业必须被拥有全部对应标签的 Runner 领取。GitLab Runners

#如果 pages job 已经成功

如果 pages 作业已经绿色成功，问题就不在 .gitlab-ci.yml。自建 GitLab 管理员应检查 Pages 后台和存储：

bash
sudo gitlab-ctl status
sudo gitlab-ctl tail sidekiq
sudo gitlab-ctl tail gitlab-pages
sudo gitlab-ctl tail gitlab-rails

重点搜索部署任务失败、artifact 读取失败、对象存储配置错误、Pages daemon 无法访问 GitLab API 等信息。GitLab 官方的自建 Pages 排障文档也建议从 Pages、NGINX 和 Rails 日志按请求链路定位。Troubleshooting GitLab Pages administration

#本项目推荐的排查顺序

  1. 打开最新流水线的 pages job，确认是 pending 还是 running。
  2. 若为 pending：检查 Runner 在线状态、Run untagged jobs、标签和 Protected 设置。
  3. 若为 running：看日志最后一行，区分环境准备、拉取代码或上传 artifact。
  4. 若 job 已成功：转到 Deploy → Pages；持续进行中需要 GitLab 管理员检查 Sidekiq 和 Pages 服务。
  5. 修复基础设施后重试原 job，不必反复修改或提交相同的 .gitlab-ci.yml。

#易错点与局限

  • 不要把密钥、内部配置或不希望公开的文件放进 public/。
  • 不要使用以 / 开头的站内绝对路径，否则项目级 Pages 子路径可能加载失败。
  • GitLab Pages 只能提供静态内容，不能运行 Java、PHP 或其他服务端程序。
  • 知识库首页由索引脚本维护，不应手工复制页面卡片。
  • 当前实例已经确认不识别 job 级 pages: true，不要在未升级 GitLab 前切回新语法。
