#Superpowers 大型 Java 微服务 Monorepo 使用指南

整理日期：2026-07-24
项目画像：一人长期维护、10+ 微服务、Monorepo、代码量 10 万行以上；普通功能平均涉及 2～3 个服务；同时存在 HTTP、消息与共享数据库，并已有接口或消息契约。
本文目标：不引入 OpenSpec 或 Spec Kit，以 Superpowers 作为唯一开发编排器，建立足够可靠的项目 Harness。

#核心结论

这个项目可以由 Superpowers + 分层 AGENTS.md + 契约 + 自动化测试 + CI + 轻量设计记录 支撑。Superpowers 负责需求澄清、设计、计划、TDD、调试、评审和完成验证；长期系统事实仍由代码、服务边界、契约、数据库迁移、架构决策和 CI 承担。

不要把 Superpowers 理解成一个安装后自动解决所有工程问题的插件。它是一套实现纪律，必须运行在清晰的 Harness 之中：

text
用户目标
   │
   ├─ 模糊需求 → Brainstorming → 设计确认
   ├─ 已知 Bug → Systematic Debugging → 根因确认
   │
   ▼
Implementation Plan
   │
   ▼
逐任务 RED → GREEN → REFACTOR
   │
   ├─ 规格符合性评审
   ├─ 代码质量评审
   └─ 完成前验证
   │
   ▼
契约检查 + 受影响服务测试 + CI
   │
   ▼
人工合并与发布判断

#适用边界

当前条件产生的影响工作流要求
单人维护协作冲突较少，但长期记忆和自我复核压力大设计必须落盘，关键判断不能只留在聊天里
Monorepo一次变更可以统一搜索、分支、评审和验证使用一份跨服务设计和一份任务计划
10+ 微服务上下文无法长期靠记忆维持根级规则只放全局事实，服务规则下沉
功能平均涉及 2～3 服务跨服务范围可控按契约和依赖顺序拆任务
HTTP、消息和共享数据库并存存在显式契约和隐式数据耦合重点约束数据所有权、幂等、版本兼容和发布顺序
已有契约接口结构和兼容性已有机器真相Superpowers 设计引用契约，不复制一套平行定义

#分层 AGENTS.md

Codex 从仓库根目录向当前工作目录逐层加载 AGENTS.md，越靠近当前目录的规则越晚加载，因此可以覆盖根级规则。官方默认合并上限为 32 KiB，10+ 服务的所有细节不应集中在根文件。Codex AGENTS.md

#根级 AGENTS.md 示例

markdown
# Repository Instructions

## Stack
- Java 21, Spring Boot, Maven Wrapper.
- TypeScript frontend; respect the committed lockfile.
- This repository contains all services and cross-service tests.

## Development workflow
- Superpowers is the only development orchestrator.
- New or changed behavior starts with brainstorming and design approval.
- Bugs start with systematic debugging; no fixes before root cause.
- Implementation follows an approved plan and test-driven development.
- Do not claim completion without fresh verification evidence.

## Architecture
- Every table and event has one owning service.
- Do not write tables owned by another service.
- Prefer declared APIs or events over direct database coupling.
- Public API and event changes require compatibility tests.
- Cross-service changes must describe call flow, data ownership,
  idempotency, rollout order and rollback.

## Change levels
- Small local change: debugging/TDD → verification → CI.
- Standard cross-service change: brainstorming → saved design →
  implementation plan → TDD → review → CI.
- High-risk change: add migration, compatibility, rollout and rollback gates.

## Verification
- One service: ./scripts/verify-service.sh <service>
- Affected services: ./scripts/verify-affected.sh
- Contracts: ./scripts/verify-contracts.sh
- Full repository: ./scripts/verify-all.sh

## Safety
- Never commit secrets or production data.
- Do not silently change authentication, authorization, money,
  public contracts, schemas or destructive operations.
- Preserve unrelated user changes.

## Code Review Rules
- Check service ownership and forbidden cross-service database writes.
- Check HTTP timeout/retry behavior and event idempotency.
- Check backward compatibility and mixed-version deployment.
- Check migrations, observability and rollback evidence.

#服务级 AGENTS.md 示例

markdown
# Order Service

## Ownership
- Owns order lifecycle, order status and order tables.
- Does not directly update inventory or payment tables.
- Publishes OrderCreated, OrderCancelled and OrderCompleted.
- Consumes PaymentConfirmed and PaymentExpired.

## Implementation rules
- State transitions go through OrderStateMachine.
- Event publication uses the transactional outbox.
- Consumers must be idempotent by event id.
- Public errors follow the repository problem-details contract.

## Testing
- Pure state transitions: unit tests.
- Persistence and concurrency: Testcontainers integration tests.
- Event payloads: schema and consumer contract tests.
- Verify: ./mvnw -pl services/order-service -am verify

#Superpowers 技能地图

技能何时使用在本项目中的输出停止条件
brainstorming新增功能、行为变化、架构选择目标、非目标、跨服务设计、风险与验收人确认设计
using-git-worktrees需要隔离长期或并行工作独立工作树、干净基线基线测试通过
writing-plans设计已批准精确文件、任务、测试和验证顺序计划可逐项执行
test-driven-development功能、Bugfix、行为重构RED、GREEN、REFACTOR 证据当前行为和相关回归通过
systematic-debuggingBug、测试失败、性能或集成异常复现、边界证据、根因、单一假设根因已证实
executing-plans单人按批次执行已审计划分批实现与检查点当前批次验证完成
subagent-driven-development任务足够独立且需要更强审查逐任务实现、规格审查、质量审查任务通过两级审查
requesting-code-review任务或整个变更完成按严重度排序的发现重要问题处理完
verification-before-completion准备声称完成、提交或合并最新命令、退出码、报告所有必需证据为真
finishing-a-development-branch分支收尾合并、PR、保留或清理选择人决定下一步

Superpowers 官方基础流程依次强调 brainstorming、工作树、计划、执行、TDD、代码评审和分支收尾；systematic-debugging 另行规定“没有根因调查就不能修复”。Basic Workflow · Systematic Debugging

#四级工作模式

级别典型任务必用能力落盘要求
L0 探索方向不清、技术选型、可行性研究brainstorming只有形成长期决定时保存
L1 局部变更单服务 Bug、小重构、小型技术调整debugging 或 TDD、verification通常由测试和 Git 记录
L2 标准功能涉及 2～3 个服务的普通功能brainstorming、plan、TDD、review、verification必须保存设计和计划
L3 高风险变更权限、金额、共享表、状态机、迁移、分阶段发布L2 全部 + 明确人工 Gate设计、迁移、兼容、发布和回滚记录

#通用提示词模板

#探索模板

text
使用 Superpowers 的 brainstorming 技能探索这个问题。

先读取根级和相关服务的 AGENTS.md、服务目录、契约和现有代码。
本轮只做调查和方案比较：
- 不修改生产代码；
- 不创建实施计划；
- 不扩大到无关服务；
- 标出事实、假设和未知项；
- 比较至少两种可行方案；
- 给出推荐、反对理由、验证实验和 go/no-go 条件。

#标准功能模板

text
使用 Superpowers 的 brainstorming 技能设计这个功能。

已知涉及 <service-a>、<service-b> 和 <service-c>。
设计必须包含：
1. 目标、非目标和用户可观察行为；
2. 当前调用链和目标调用链；
3. HTTP、事件和数据库所有权；
4. 幂等、并发、失败和补偿；
5. 新旧版本兼容；
6. 测试层次；
7. 监控、发布顺序和回滚。

设计确认前不写代码。确认后将设计保存到 docs/plans/，
再使用 writing-plans 生成唯一实施计划。

#计划执行模板

text
按照已批准的 implementation plan 执行。

规则：
- plan 是唯一任务清单；
- 一次只处理一个可验证行为；
- 使用 test-driven-development；
- 必须展示旧代码上的失败测试；
- 只做让当前测试通过的最小实现；
- 每个任务后运行最小相关验证；
- 公共契约变化立即运行兼容检查；
- 实现与设计不一致时停止并修订设计；
- 不顺手重构无关代码；
- 完成后执行规格符合性和代码质量评审。

#Bugfix 模板

text
使用 Superpowers 的 systematic-debugging 技能调查这个问题。

要求：
- 先稳定复现；
- 沿 HTTP、消息和数据库边界收集证据；
- 找到错误数据最初产生的位置；
- 写出一个单一、可证伪的根因假设；
- 根因确认前不修改生产代码；
- 确认后写失败的回归测试；
- 只实施一个根因修复；
- 运行当前服务、受影响服务和跨服务验证；
- 使用 verification-before-completion 后才能声称修复。

#实例一：跨服务 Bugfix

问题：支付服务显示扣款成功，但少量订单仍停留在 PENDING_PAYMENT。涉及 payment-service、消息系统和 order-service。

#阶段一：收集边界证据

text
使用 systematic-debugging 调查：
“支付已成功，但订单偶发未更新”。

按边界收集同一个 paymentId/orderId 的证据：
1. payment-service 数据库事务结果；
2. outbox 记录；
3. broker 中的消息发布结果；
4. order-service 消费日志；
5. inbox/幂等记录；
6. OrderStateMachine 转换结果。

先给出证据表和故障边界，不要提出修复。

期望输出不是“可能是消息丢了”，而是类似：

边界输入输出结论
支付事务支付回调PAYMENT_SUCCESS正常
Outbox支付事务缺少对应事件首次异常点
BrokerOutbox无消息下游症状
订单消费者Broker未消费下游症状

#阶段二：回归测试

确认根因是“支付状态更新和 outbox 写入不在同一事务”后，要求：

text
使用 test-driven-development：
先增加 Testcontainers 集成测试，证明在事件持久化失败时，
支付状态不能单独提交。

必须先在旧实现上运行并展示失败；
然后把状态更新与 outbox 写入放入同一事务；
不重构无关支付代码。

#阶段三：验证

bash
./scripts/verify-service.sh payment-service
./scripts/verify-contracts.sh
./scripts/verify-affected.sh
codex review --base main

验证还应注入一次 outbox 写失败，确认支付事务回滚；随后恢复故障，确认重试只生成一条有效事件。

#实例二：标准跨服务功能

功能：支付超时后自动取消订单并释放库存，涉及 payment-service、order-service 和 inventory-service。

#阶段一：设计

text
使用 brainstorming 设计“支付超时自动取消订单”。

现状：
- payment-service 管理支付状态；
- order-service 拥有订单状态机；
- inventory-service 拥有库存预占；
- 服务通过事件通信；
- 功能开关控制上线。

设计必须回答：
- 谁判断支付超时；
- PaymentExpired 的 schema；
- order-service 如何保证状态转换幂等；
- 已发货、已支付、手工取消等竞态怎样处理；
- OrderCancelled 如何触发库存释放；
- 消息乱序、重复和积压怎样处理；
- 新旧消费者如何兼容；
- 发布和回滚顺序是什么。

设计确认前不修改文件。

#阶段二：设计结果应包含

text
PaymentExpired v1
  paymentId
  orderId
  expiredAt
  eventId
  schemaVersion

payment-service
  定时扫描 → 原子更新支付状态和写入 outbox

order-service
  幂等消费 → 检查当前状态 → 状态机取消 → 写入 OrderCancelled outbox

inventory-service
  幂等消费 OrderCancelled → 释放预占 → 记录处理结果

发布顺序
  1. 先发布兼容的新消费者
  2. 再发布 payment-service 生产者但关闭开关
  3. 观察指标
  4. 小流量打开
  5. 全量

回滚
  关闭生产者开关；消费者保持兼容，不回滚已完成的合法取消。

#阶段三：实施计划

使用 writing-plans 后，计划应按依赖顺序，而不是随意按服务顺序：

  1. 定义并验证 PaymentExpired 契约。
  2. 先实现 order-service 消费者和状态机测试。
  3. 实现 inventory-service 对 OrderCancelled 的幂等处理。
  4. 实现 payment-service 超时扫描和 outbox。
  5. 增加跨服务组合测试。
  6. 增加功能开关、指标、告警和运行手册。
  7. 验证混合版本部署和回滚。

#阶段四：任务执行

text
执行计划中的“order-service 消费 PaymentExpired”任务。

使用 test-driven-development：
1. 先写 PENDING_PAYMENT → CANCELLED 的失败测试；
2. 增加 PAID、SHIPPED 状态拒绝取消的测试；
3. 增加重复 eventId 的幂等测试；
4. 在旧代码上展示失败；
5. 写最小实现；
6. 运行 order-service；
7. 运行事件契约检查；
8. 更新计划中的当前任务；
9. 停止，不继续下一个服务。

#阶段五：完成验证

  • 重复和乱序消息不会造成重复取消或重复释放库存。
  • 订单已支付时，晚到的 PaymentExpired 不会覆盖合法状态。
  • 消费者先上线、生产者后上线时可兼容。
  • 关闭开关后不再产生新超时事件。
  • 指标可观察扫描量、事件量、取消成功、状态冲突、消费失败和积压。
  • 跨服务测试验证最终订单和库存状态。

#实例三：共享数据库迁移

场景：order-service 和 reporting-service 都读取 orders 表，需要把 cancel_reason 从自由文本演进为结构化代码，同时保持混合版本兼容。这属于 L3 高风险变更。

#阶段一：先调查依赖

text
使用 brainstorming 设计 cancel_reason 的兼容迁移。

开始前搜索：
- 所有 SQL、JPA Entity、MyBatis Mapper；
- 报表、ETL 和数据导出；
- 直接数据库读取者；
- API 和事件中的 cancelReason；
- 历史数据分布；
- 索引和约束。

给出 expand → migrate → contract 三阶段方案。
设计确认前不生成 migration，不修改实体。

#阶段二：三阶段迁移

阶段数据库应用验证
Expand新增 nullable cancel_reason_code新版本双写，读取优先新列并回退旧列旧应用仍能运行
Migrate批量回填并记录不可映射值监控新旧列一致性回填可重入、可暂停
Contract增加约束，后续删除旧列所有读取者已切换依赖扫描为零后执行

#阶段三：人工 Gate

Superpowers 不能替代生产迁移判断，应在以下位置停下来：

  1. 新增列前确认锁表、磁盘和备份策略。
  2. 回填前确认批量大小、限速、重试和监控。
  3. 停止双写前确认所有服务和报表已切换。
  4. 删除旧列前确认完整依赖扫描和回滚窗口。

#实例四：新功能探索

场景：计划增加统一通知编排，但不确定应该扩展 notification-service，还是建立新的 workflow-service。

text
使用 brainstorming 探索统一通知编排。

读取现有调用和事件，但不写生产代码。
比较：
1. 扩展 notification-service；
2. 建立 workflow-service；
3. 让各领域服务继续自行编排。

评价维度：
- 领域所有权；
- 服务耦合；
- 状态和重试；
- 幂等与补偿；
- 可观测性；
- 运维成本；
- 未来功能范围；
- 迁移路径。

最后输出：
- 当前事实；
- 三种方案；
- 推荐及反对理由；
- 仍需验证的假设；
- 最小 spike；
- go/no-go 条件。

本轮结束后停止，不生成 implementation plan。

如果需要 spike，应在独立分支或工作树中完成，并提前规定时间盒、测试数据和退出条件。实验代码默认不进入生产实现。

#Harness 与验证分层

对于 10+ 服务，不能让 Codex 每完成一个小任务都运行全仓库测试，也不能只跑当前单元测试。推荐五层反馈：

层级内容目标时间使用时机
V1单个测试类或包秒级TDD 每轮
V2当前服务 verify分钟级任务完成
V3公共契约兼容分钟级API、消息变化
V4受影响服务组合测试数分钟跨服务任务或功能完成
V5全仓库、端到端、安全和制品较长提交、MR、发布

#验证脚本约定

bash
# 当前服务
./scripts/verify-service.sh order-service

# 根据 Git diff、Maven 模块依赖和契约消费者计算范围
./scripts/verify-affected.sh origin/main

# OpenAPI、事件 Schema 和消费者契约
./scripts/verify-contracts.sh

# 合并前完整检查
./scripts/verify-all.sh

脚本必须由人和 CI 使用同一入口。不要让 AGENTS.md 写一套命令、Codex 猜一套命令、GitLab 再运行第三套命令。

#GitLab CI 示例

yaml
stages:
  - validate
  - test
  - integration
  - package

contracts:
  stage: validate
  image: maven:3.9-eclipse-temurin-21
  script:
    - ./scripts/verify-contracts.sh

unit-and-module-tests:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  script:
    - ./mvnw -B -ntp verify
  artifacts:
    when: always
    reports:
      junit:
        - "**/target/surefire-reports/TEST-*.xml"
        - "**/target/failsafe-reports/TEST-*.xml"

affected-services:
  stage: integration
  image: maven:3.9-eclipse-temurin-21
  services:
    - docker:dind
  script:
    - ./scripts/verify-affected.sh "${CI_MERGE_REQUEST_DIFF_BASE_SHA:-origin/main}"

package:
  stage: package
  image: maven:3.9-eclipse-temurin-21
  script:
    - ./mvnw -B -ntp -DskipTests package
  artifacts:
    paths:
      - "**/target/*.jar"
  needs:
    - contracts
    - unit-and-module-tests
    - affected-services

示例需要按 Runner 的 Docker 能力调整。共享数据库迁移还应增加“旧版本 Schema → 新版本 Schema”的升级测试；消息系统应增加重复、乱序和消费者混合版本测试。

#日常使用节奏

#开始任务

  1. 同步主分支并检查工作区。
  2. 运行相关服务基线测试。
  3. 判断 L0、L1、L2 或 L3。
  4. 让 Codex 读取根级和相关服务 AGENTS.md。
  5. L2/L3 先 brainstorming；L1 Bug 先 systematic-debugging。

#任务进行中

  1. 一次只推进一个可验证行为。
  2. 先运行 RED，再做最小 GREEN。
  3. 契约变化立即运行 V3。
  4. 跨服务边界变化立即检查所有权和发布顺序。
  5. 计划错误时先修订设计和计划，不要让代码静默漂移。

#准备完成

bash
git diff --check
./scripts/verify-affected.sh origin/main
./scripts/verify-contracts.sh
codex review --base main
./scripts/verify-all.sh

只有最新命令的实际输出可以作为完成证据。此前运行过、理论上应该通过、Codex 认为没有问题，都不算完成。

#从 AIDLC 切换后的使用约定

切换后只保留一套活动编排：

AIDLC 原能力现在由什么承担
Ideation / Inceptionbrainstorming + 保存设计
Unit of Work / Boltimplementation plan 中的小任务
Walking Skeleton计划中的第一条端到端切片
ConstructionTDD + executing-plans 或 subagent-driven-development
Reviewer规格符合性评审 + 代码质量评审
Phase Gate设计、第一条切片、合并/发布三个 Gate
State / Audit设计、计划、Git、MR、CI 和发布记录
OperationCI/CD、指标、告警、Runbook 和人工发布判断
Learning Loop把重复纠正写入 AGENTS.md、测试、脚本或 CI

AIDLC 历史产物保持只读，不再更新其 Intent、Stage 和 Audit 状态。新任务不得同时启动 AIDLC 和完整 Superpowers 工作流，避免两份设计、两份任务状态和重复 Reviewer。

#常见错误

错误后果修正
一开始就让 Codex 修改三个服务未经确认的架构假设被放大先 brainstorming，审完设计再写计划
设计只留在聊天记录新会话和未来自己无法恢复原因L2/L3 设计保存到仓库
所有服务规则都塞进根 AGENTS.md上下文拥挤、规则互相干扰根级写全局事实，服务级写局部细节
只跑当前服务单测契约和跨服务回归遗漏按 V1～V5 分层验证
HTTP 防重代替服务端幂等重试和消息重复仍会破坏状态在数据所有者侧实现幂等约束
直接修改其他服务拥有的共享表隐藏耦合继续扩大通过所有者 API/事件或显式迁移计划
TDD 只补成功路径并发、乱序和失败模式未验证从用户可观察行为和分布式失败写测试
测试失败时连续尝试多个修复无法证明哪个假设正确回到 systematic-debugging 的单一假设
使用 AIDLC 和 Superpowers 双编排两套计划和状态互相冲突Superpowers 是唯一活动编排器
让 Codex 自动决定生产发布业务和数据风险失去人工控制L3 发布和回滚保留人工 Gate

#完成定义

一个涉及 2～3 个服务的功能只有同时满足以下条件才算完成：

  • 设计中的目标和非目标没有被静默改变。
  • 任务计划全部完成，且没有隐藏待办。
  • 每个新增行为都有对应 RED 和 GREEN 证据。
  • 接口和消息契约兼容。
  • 数据库所有权、迁移和混合版本行为明确。
  • 重复、乱序、重试、超时和部分失败得到验证。
  • 相关服务、受影响组合和完整 CI 通过。
  • 代码评审没有未处理的重要发现。
  • 日志、指标和告警足以观察新行为。
  • 发布顺序、功能开关和回滚方式可执行。
