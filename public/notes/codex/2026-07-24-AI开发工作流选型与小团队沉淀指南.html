#AI 开发工作流选型与小团队沉淀指南

整理日期：2026-07-24
主题：除 AIDLC 与 Superpowers 外，还有哪些较完整的 AI 开发工作流，以及 2 人小团队是否值得沉淀自己的工作流
适用团队：2 人、每人主要负责一个项目、Java 全栈为主、使用 Codex 等 AI 编码智能体
说明：本文的“评分”是结合当前团队场景作出的定性判断，不是框架性能基准。

如果暂时不准备引入任何附加工作流，先使用Codex 官方原生项目开发最佳路径建立从任务到 PR 的最小可靠闭环；重复摩擦出现后再判断是否需要规格层或流程框架。

#核心结论

#直接回答

还有不少类似工作流，但它们并不处在同一层：

  • BMAD Method：最接近 AIDLC 的“项目级完整开发方法”，覆盖分析、规划、架构、实现、评审和复盘。
  • GSD（Get Shit Done）：更偏“单人拥有一个项目、按里程碑持续交付”的上下文工程与自治执行系统。
  • GitHub Spec Kit：成熟的规格驱动开发框架，核心链路是 Spec → Plan → Tasks → Implement，还支持工作流编排、状态持久化和人工门禁。
  • OpenSpec：较轻量的变更级规格工作流，适合存量项目和小团队，以 Proposal → Apply → Archive 管理一次变更。
  • Kiro Specs：Kiro 产品内置的 Requirements → Design → Tasks → Implement 工作流，体验完整，但平台绑定更强。
  • Ralph Loop：不是完整 SDLC，而是让智能体反复读取规格、任务列表和验证反馈的自治执行循环。
  • Superpowers：主要解决实现阶段的设计、计划、TDD、调试、评审和完成前验证，也不是完整的产品生命周期框架。

对当前 2 人团队，结论是：

有必要沉淀工作流，但没有必要从零开发一个新的工作流框架。

最合适的做法不是把 AIDLC、BMAD、GSD、Spec Kit、OpenSpec 和 Superpowers 全部安装，而是沉淀一套薄的团队交付协议：

  1. 用项目 AGENTS.md 固化项目规则、命令和验证要求。
  2. 规格层只选择 OpenSpec 或 Spec Kit 其中一个。
  3. 实现内循环使用 Superpowers 的设计、计划、TDD、调试、评审与验证方法。
  4. 用 Maven、前端构建、测试、静态检查和 CI 形成确定性反馈。
  5. 对高风险、新项目或跨系统变更，按需升级为轻量 AIDLC。
  6. 同一项目只保留一个顶层流程指挥者，避免多个框架同时争夺任务状态和文档真相源。

如果主要是已有 Java 全栈项目，默认更推荐：

text
OpenSpec（变更规格）
    ↓
Superpowers（实现内循环）
    ↓
Maven / 前端测试 / E2E / CI（确定性反馈）
    ↓
风险触发的人类交叉评审

如果主要是大型新项目、需求复杂或多人未来会共同开发，则可以把 OpenSpec 换成 Spec Kit；只有在项目风险和治理要求明显上升时，才启用 AIDLC 或 BMAD 的完整轨道。

#一、先区分四类“工作流”

“完整工作流”容易产生误解。一个工具拥有很多命令，并不代表它覆盖了完整的软件生命周期。

#1. 生命周期外循环

回答的是：

  • 为什么做？
  • 需求和范围是什么？
  • 架构如何决策？
  • 何时允许进入实现？
  • 如何发布、运营、复盘和沉淀？

代表：

  • AIDLC
  • BMAD Method

#2. 规格与变更管理层

回答的是：

  • 这次具体要改变什么？
  • 验收标准是什么？
  • 设计和任务如何从需求推导？
  • 规格与代码如何在 Git 中一起演进？

代表：

  • GitHub Spec Kit
  • OpenSpec
  • Kiro Specs

#3. 实现内循环

回答的是：

  • 如何理解现有代码？
  • 如何拆计划？
  • 如何用测试驱动实现？
  • 如何系统调试、代码评审和完成前验证？

代表：

  • Superpowers
  • Codex 原生的计划、实现、评审和验证操作模式

#4. 自治执行循环

回答的是：

  • 如何让智能体在多轮或多个新上下文中持续推进？
  • 每轮如何选一个任务？
  • 如何通过测试、编译和静态检查形成反馈？
  • 何时停止、回退或请求人工介入？

代表：

  • Ralph Loop
  • GSD 的自动执行部分
  • BMAD 的自动开发循环

#四层关系

text
生命周期外循环
  AIDLC / BMAD
        ↓ 产生目标、需求、架构和门禁
规格与变更层
  Spec Kit / OpenSpec / Kiro Specs
        ↓ 产生规格、设计和任务
实现内循环
  Superpowers / Codex
        ↓ 产生代码、测试和评审证据
自治执行循环
  Ralph / GSD Auto Loop
        ↺ 读取任务与验证反馈，继续下一轮

确定性 Harness 横贯所有层：
  编译 + 单测 + 集成测试 + E2E + 静态检查 + 安全扫描 + CI

因此，更合理的问题不是“哪个框架命令最多”，而是：

当前项目在哪一层缺少约束和反馈？

#“覆盖”不等于“质量”

一个框架声称覆盖从想法到部署，不代表：

  • 自动生成的需求就是正确需求；
  • 自动生成的架构经过了真实负载验证；
  • 测试覆盖了业务风险；
  • 部署具备回滚、监控和告警；
  • 人类可以不再进行风险判断。

完整性应该从以下证据判断：

维度最低可接受证据
需求明确目标、非目标、验收标准
设计关键技术决策、替代方案、风险
实现可审查的小步提交、无占位实现
测试单元、集成、契约或 E2E 的适当组合
安全权限、输入、凭证、依赖和数据边界检查
发布可重复构建、发布步骤、回滚方案
运行日志、指标、告警、Runbook
协作责任人、人工门禁、交接材料
追踪规格、代码、测试、PR 和发布之间可关联

#三、BMAD Method：最像 AIDLC 的替代方案

BMAD 官方工作流把项目分成四个主要阶段：

  1. Analysis：可选的问题探索、研究、产品简报等。
  2. Planning：PRD、UX 和规格。
  3. Solutioning：架构、Epic/Story 拆解和实现就绪检查。
  4. Implementation：Sprint、Story 实现、代码评审、调整和复盘。

小型且清晰的变更还可以使用 Quick Flow，跳过较重的前置阶段。

#优点

  • 从产品问题到代码实现的链路比较完整。
  • 每个阶段产生明确文档，适合在新上下文中继续工作。
  • 对 PRD、UX、架构和 Story 的关注比纯编码工具更完整。
  • 同时提供完整轨道和 Quick Flow，可按任务复杂度切换。
  • 适合需要产品探索、架构决策和长期规划的绿地项目。

#缺点

  • 角色、Agent、命令和文档数量较多。
  • 两个人若对所有需求都执行完整流程，容易出现“为维护流程而维护流程”。
  • 多个 AI 角色并不等于多个真正独立的领域专家，人类仍需检查同源模型带来的共同盲区。
  • 快速演进的框架需要额外承担升级、迁移和命令变化成本。
  • 对已稳定运行的存量 Java 项目，小变更可能显得过重。

#适合当前团队的使用方式

不要把 BMAD 作为两个项目的日常默认流程。可以在以下场景选择它：

  • 从零定义一个产品；
  • 用户体验和业务需求都不明确；
  • 需要 PRD、UX、架构和 Epic 连贯生成；
  • 一个项目未来会扩展到多人共同开发；
  • 项目负责人希望由 AI 主动推动需求澄清。

对 2 人团队，优先使用 BMAD Quick Flow；只有新项目或大功能才进入完整轨道。

#四、GSD：更适合“一人负责一个长期项目”

GSD 强调上下文工程、阶段计划、原子任务和持续验证。典型新项目会形成：

  • PROJECT.md
  • REQUIREMENTS.md
  • ROADMAP.md
  • STATE.md
  • 阶段研究、计划与验证材料

每个阶段通常经历讨论、研究、计划、执行和验证，并通过新上下文执行较小计划，降低长会话中的上下文退化。

#优点

  • 很贴合“一人主要拥有一个项目”的工作方式。
  • 项目目标、路线图、当前状态和阶段计划落盘，便于中断后恢复。
  • 强调小任务、原子提交和验证。
  • 比单纯 Ralph Loop 更有项目结构和里程碑意识。
  • 当前官方仓库提供 Codex 安装与 $gsd-* 技能入口。

#缺点

  • 命令面和工作流表面较大，仍需学习。
  • 自治执行和多轮上下文会产生较高 Token 与时间成本。
  • 项目状态文件可能与现有 Issue、看板、PR 或规格目录重复。
  • 主要强项是项目交付，不等同于生产运行治理。
  • 如果两个负责人采用不同配置，跨项目交接仍可能困难。

#适合当前团队的使用方式

如果每个项目：

  • 周期较长；
  • 负责人会独立连续开发；
  • 容易被其他工作打断；
  • 希望 AI 自动维护路线图和状态；
  • CI 已经能快速、可靠地反馈；

那么 GSD 值得在一个非核心项目试点。

但不建议同时让 GSD、AIDLC 或 BMAD共同维护顶层任务状态。应选择一个作为项目指挥者。

#五、GitHub Spec Kit：较强的规格驱动 Harness

Spec Kit 的核心流程是：

text
Spec → Plan → Tasks → Implement

官方文档还提供更完整的工作流能力：

  • 规格、计划、任务和实现命令；
  • 工作流 YAML；
  • 人工 gate；
  • 条件与循环；
  • 扇出/汇聚；
  • 状态、输入和日志持久化；
  • 暂停后恢复；
  • 多种编码智能体集成，包括 Codex。

#优点

  • 规格产物是 Markdown，适合 Git 评审和长期维护。
  • 比纯提示词更能建立稳定的变更上下文。
  • 支持从手动分阶段运行逐步升级到自动工作流。
  • 工作流状态和恢复能力适合长任务。
  • 可以通过预设、扩展和 Bundle 形成组织标准。
  • 既能用于绿地，也能通过扩展适配其他流程。

#缺点

  • 默认结构比 OpenSpec 更重。
  • 工作流编排能力很强，容易过早进入“开发流程平台”的诱惑。
  • 社区工作流不应默认视为可信代码，安装和执行前仍需审查。
  • 它能推动到实现，但生产发布、运行治理仍需团队补充。
  • 与其他顶层规格框架并用时，容易产生重复规格和任务状态。

#适合当前团队的使用方式

以下情况优先考虑 Spec Kit：

  • 新项目或大型跨模块功能；
  • 需求经常在实现前需要多轮澄清；
  • 希望规格、计划、任务间有更强的结构；
  • 需要人工门禁、暂停恢复或工作流自动化；
  • 未来可能让多人或多个 Agent 共同处理同一项目。

对日常一两天的小改动，不需要每次都运行全套工作流。

#六、OpenSpec：当前 2 人团队最值得试用的规格层

OpenSpec 的新工作流可以概括为：

text
Explore（可选）
   ↓
Propose
   ├─ proposal.md
   ├─ specs/
   ├─ design.md
   └─ tasks.md
   ↓
Apply
   ↓
Archive

其团队协作原则很适合当前模式：

  • OpenSpec 本身不代替 Git；
  • 规格和代码在同一分支/PR 中演进；
  • 一个变更由一个人负责；
  • 不同变更目录减少冲突；
  • 合并后归档变更，形成可追踪历史。

#优点

  • 轻量、Markdown 优先。
  • 对已有项目友好，不要求重建完整产品文档。
  • “一个变更一个负责人”与两人各自主导项目非常匹配。
  • 规格和代码一起评审，减少“文档在另一个系统里过期”。
  • 已提供 Codex 集成。
  • 比完整 AIDLC/BMAD 更容易形成团队习惯。

#缺点

  • 不负责完整的产品研究、组织治理和运行阶段。
  • 不会自动保证 TDD、系统调试或高质量代码评审。
  • 若每个微小修复都建立完整 Proposal，也会产生负担。
  • 归档后如何维护系统级架构知识，仍需 ADR 或架构文档补充。
  • 规格写得差时，流程只会更稳定地执行错误方向。

#为什么它适合当前团队

两人各负责一个项目时，最大的风险通常不是“缺少 30 个 Agent 角色”，而是：

  • 一个人离开后，另一个人不知道为何这样设计；
  • 需求只存在于聊天记录；
  • AI 修改范围不可控；
  • 验证命令不统一；
  • 发布前没有风险检查点。

OpenSpec 可以用较低成本补齐“这次为什么改、改什么、怎么验收”；Superpowers 和 CI 再补齐“怎么正确实现”。

#七、Kiro Specs：产品内体验完整，但不宜为流程而换平台

Kiro Specs 通常产生：

  • requirements.md，Bug 场景可能使用 bugfix.md；
  • design.md；
  • tasks.md；
  • 任务执行与 PR。

它还区分 Feature、Bug 和 Quick Plan，能针对不同任务选择更合适的规格入口。

#优点

  • 规格、任务执行和 PR 形成一体化体验。
  • Feature 与 Bug 使用不同产物，符合真实工程差异。
  • Quick Plan 可以降低小改动的仪式成本。
  • 对不熟悉规格驱动开发的团队，上手路径比较直观。

#缺点

  • 工作流与 Kiro 产品结合紧密。
  • 如果团队当前主力是 Codex，引入新平台会增加工具切换与配置成本。
  • 规格流程完整不代表生产 Harness 完整。
  • 跨工具迁移时仍要依赖 Markdown 产物，而非产品内状态。

#当前团队建议

把 Kiro Specs 当作可借鉴的模式，而不是必须引入的工具：

  • Feature：需求优先；
  • Bug：先根因分析与不变行为；
  • Quick Plan：低风险小变更。

除非两个人都准备长期使用 Kiro，否则无需为了获得该流程而迁移。

#八、Ralph Loop：是一种执行模式，不是完整工作流

Ralph 的原始思想非常简单：

text
读取规格与计划
    ↓
每轮选择一个最重要任务
    ↓
修改代码
    ↓
编译、测试、静态检查形成反压
    ↓
更新计划与学习
    ↓
新上下文继续下一轮

原始介绍明确强调：

  • Ralph 是一种技术，最纯粹的形式就是循环；
  • 一轮只做一件事；
  • 每轮重新读取规格和计划；
  • 测试、编译、类型系统、静态分析和安全扫描形成 backpressure；
  • 原作者更偏向将其用于绿地项目，并明确警告存量代码库风险。

#优点

  • 实现简单，适合长时间自治推进。
  • 新上下文能降低历史对话污染。
  • 任务列表和验证输出成为跨轮次的外部记忆。
  • 当规格清晰、测试快速、失败信号明确时，吞吐量可能较高。

#缺点

  • 不是需求、架构、协作、发布和运营方法。
  • 弱测试会导致智能体“错误地通过”。
  • 容易重复实现、修改无关代码或追逐局部指标。
  • 可能消耗大量 Token 和计算资源。
  • 需要明确的最大轮次、范围、预算、停止条件和人工升级规则。
  • 不适合对支付、权限、数据迁移、基础设施等高风险变化进行无人值守运行。

#当前团队建议

不要把 Ralph 作为默认开发方式。只有同时满足以下条件时才试用：

  • 任务有稳定且经评审的规格；
  • 工作被拆成可独立验证的小项；
  • 仓库可以在隔离分支或 Worktree 中运行；
  • ./mvnw verify、前端测试和必要 E2E 足够快；
  • 不涉及不可逆数据和外部生产操作；
  • 设置最大轮次、Token/时间预算和失败升级；
  • 所有提交仍需人工或独立 Agent 评审。

#九、当前团队到底要不要“自己沉淀工作流”

#要，但要先明确“沉淀”的含义

值得沉淀的是：

  • 反复出现的决策规则；
  • 项目真实命令；
  • 风险触发条件；
  • 验证证据；
  • 交接必需信息；
  • 已经重复验证有效的操作顺序。

不值得从零构建的是：

  • 新的多 Agent 调度引擎；
  • 一套与 Git/Issue/PR 重复的状态系统；
  • 数十个虚拟角色；
  • 尚未实际使用过的全生命周期模板；
  • 为了“自动化一切”而创建的大量 Hooks 和脚本。

#推荐的沉淀阶梯

#Level 1：团队交付协议

现在就应该做。

产物可以是：

text
AGENTS.md
docs/workflow/TEAM-WORKFLOW.md
docs/adr/
docs/runbooks/
openspec/changes/                 # 若选 OpenSpec
# 或
specs/ + .specify/                # 若选 Spec Kit
.github/pull_request_template.md
scripts/verify.sh

这一层解决“两个项目使用相同的最小质量标准”。

#Level 2：模板与确定性脚本

当相同步骤重复使用至少 3 次后再做。

适合沉淀：

  • 变更 Proposal 模板；
  • ADR 模板；
  • 发布检查表；
  • Java 后端与前端统一验证脚本；
  • 数据库迁移检查；
  • API 兼容性检查；
  • 依赖和安全扫描；
  • 日志、指标、告警的最低要求。

#Level 3：仓库级 Codex Skill

当工作流已经稳定、输入输出明确、两个项目都重复使用时再做。

Codex 官方建议将：

  • AGENTS.md 用于仓库约定；
  • Skill 用于可复用的任务工作流；
  • Plugin 用于分发多个 Skills 或连接器；
  • Hooks/linters 用于机械强制；
  • MCP 用于访问外部系统。

因此，团队不应一开始就开发 Plugin。先用 Markdown 和脚本跑通，再把稳定流程封装成 .agents/skills/<skill-name>/SKILL.md。

#Level 4：Plugin、复杂编排或组织平台

只有出现以下信号才考虑：

  • 多个团队需要安装同一套工作流；
  • 需要同时分发多个 Skills、MCP 或 Hooks；
  • 有明确版本管理、升级和兼容性需求；
  • 工作流维护已经成为独立产品职责。

2 人团队通常不需要到这一层。

#十、最推荐的 2 人团队工作流

#总体结构

text
任务进入
  ↓
风险分级
  ├─ 快速变更：简短意图 + 测试 + 验证
  ├─ 标准变更：Proposal/Spec + Plan + TDD + PR
  └─ 高风险变更：AIDLC-lite + 人工检查点 + 发布/回滚方案
  ↓
Codex / Superpowers 实现内循环
  ↓
统一 Harness
  ↓
风险触发的同伴评审
  ↓
发布、观察、沉淀学习

#模式 A：快速变更

适用条件：

  • 预计小于 2 小时；
  • 修改范围局部；
  • 不改变公共 API、数据结构、权限或部署；
  • 有明确测试可以覆盖。

最低流程：

  1. 用 3～5 行写清意图和验收条件。
  2. 先重现问题或编写失败测试。
  3. 做最小实现。
  4. 运行相关测试和完整快速验证。
  5. 提交时记录验证结果。

不必创建完整 Proposal、设计文档或 ADR。

#模式 B：标准变更

适用条件：

  • 半天到约 3 天；
  • 涉及多个文件或前后端联动；
  • 需要明确接口、状态或交互行为；
  • 风险可控且回滚简单。

推荐流程：

  1. OpenSpec Proposal，或 Spec Kit Spec。
  2. 明确目标、非目标、验收标准和边界。
  3. 必要时记录简短设计。
  4. 形成可独立验证的任务计划。
  5. 采用 TDD 或至少测试先行处理关键行为。
  6. 后端、前端、数据库和接口契约分别验证。
  7. AI 自评审后，由另一人按风险抽查。
  8. PR 合并后归档规格。

#模式 C：高风险变更

触发条件之一：

  • 数据库 Schema 迁移或数据回填；
  • 身份认证、权限、密钥或隐私数据；
  • 支付、库存、结算或不可逆业务动作；
  • 公共 API、事件 Schema 或跨服务契约；
  • CI/CD、容器、云资源或基础设施；
  • 大规模重构、性能关键路径；
  • 发布失败会影响生产可用性；
  • 预计超过 3 天或跨多个系统。

推荐流程：

  1. 使用 AIDLC-lite、Spec Kit 完整流程或 BMAD 的适当轨道。
  2. 需求/规格评审后再进入设计。
  3. 记录 ADR、兼容策略和回滚方案。
  4. 先完成 Walking Skeleton 或最小纵向切片。
  5. 第二人检查关键接口、数据与发布风险。
  6. CI、测试环境或灰度环境验证。
  7. 发布后检查日志、指标、告警和业务信号。
  8. 更新 Runbook 和知识记录。

#十一、两个人如何分工，而不制造评审瓶颈

#每个项目两个角色

角色职责
Owner需求澄清、规格、实现、验证和发布
Peer在风险检查点挑战假设，检查可接手性和发布风险

Owner 仍对结果负责。AI 不是第三个责任人，只是执行和分析能力。

#建议的三个人类检查点

#检查点 1：规格或设计

只在标准/高风险变更使用。

Peer 重点问：

  • 真正解决的用户或业务问题是什么？
  • 非目标是否明确？
  • 是否改变 API、数据和权限边界？
  • 验收条件能否自动验证？
  • 有没有更小的纵向切片？

#检查点 2：Walking Skeleton

仅用于大功能：

  • 后端接口是否真实连通？
  • 数据是否真实落库？
  • 前端是否真实调用？
  • 鉴权、错误处理和日志是否贯通？
  • 测试能否在 CI 中运行？

#检查点 3：发布

高风险变更必须进行：

  • 如何回滚？
  • 数据迁移能否重复执行或安全恢复？
  • 哪些指标说明发布成功？
  • 哪些信号触发停止或回滚？
  • 另一人能否只看文档完成应急处理？

#不要求所有 PR 都同步评审

可采用风险触发评审：

变更Peer 参与
文案、局部样式、低风险测试可只看 CI 与摘要
一般业务功能异步 PR 抽查
公共接口、数据库、权限必须评审
生产发布与基础设施必须评审
无人值守 Agent 循环产物必须评审

#十二、Java 全栈 Harness 的最低标准

AI 工作流最终必须落到确定性反馈。对 Java 全栈项目，可按项目实际情况统一为一个入口：

bash
./scripts/verify.sh

脚本内部可组合：

bash
./mvnw verify
npm run lint
npm run typecheck
npm run test
npm run build
npm run e2e

不要求每次本地都执行最慢的完整 E2E，但 CI 必须明确区分：

  • 快速检查：格式、编译、单元测试；
  • 标准检查：集成测试、前端构建；
  • 完整检查：E2E、契约测试、安全和依赖扫描；
  • 发布检查：镜像、迁移、配置、健康检查与回滚。

#Java 后端重点

  • Java 版本和 Maven/Gradle Wrapper 固定；
  • Spring Boot 配置分环境管理；
  • Controller、Service、Repository 边界清晰；
  • Testcontainers 或等效方式验证真实基础设施交互；
  • 数据迁移使用 Flyway/Liquibase 并检查向前/向后兼容；
  • API 契约、异常码、幂等性和事务边界有测试；
  • 日志不泄露 Token、密码和隐私数据；
  • Actuator、指标、Trace 和健康检查满足运行需要。

#前端重点

  • TypeScript 严格模式；
  • API 类型或契约可追踪；
  • Loading、Empty、Error 和权限状态完整；
  • 关键交互有组件测试或 E2E；
  • 构建产物、环境变量和后端版本兼容；
  • 不在浏览器暴露后端密钥。

#AI 功能重点

  • Prompt 与模型配置版本化；
  • 输出使用 Schema 或强约束解析；
  • 超时、重试、限流和熔断明确；
  • RAG 检索、引用和权限隔离可验证；
  • 建立少量稳定评测样例，不只人工“感觉不错”；
  • 记录 Token、延迟、错误率和业务质量；
  • 模型失败有降级路径。

#十三、避免框架互相打架

#单一指挥者原则

每个项目同一时间只选择一个顶层指挥者：

  • AIDLC；
  • BMAD；
  • GSD；
  • Spec Kit；
  • OpenSpec。

Superpowers 可以作为实现内循环，因为它不必维护项目级唯一状态；Ralph 只能作为受控执行器。

#推荐组合

组合评价
OpenSpec + Superpowers + CI当前团队默认推荐
Spec Kit + Superpowers + CI复杂新项目推荐
AIDLC-lite + Superpowers + CI高风险/治理场景推荐
BMAD Quick Flow + CI产品探索较多的小项目可用
GSD + 强 CI一人长期主导项目可试点
OpenSpec + Spec Kit不推荐，规格和任务可能重复
AIDLC + BMAD 全量不推荐，生命周期与角色重复
GSD + Ralph 无边界运行不推荐，自治层叠加且难以停止

#多框架共存时的真相源

如果确实要组合，必须约定：

信息唯一真相源
项目长期规则AGENTS.md
本次需求和验收OpenSpec 或 Spec Kit，二选一
架构决策ADR
实现任务状态所选顶层框架或 Issue，不重复
验证证据CI
合并与评审PR
发布和回滚Runbook/Release

#十四、30 天落地计划

#第 1 周：建立基线

  1. 两个人各选一个真实、风险适中的变更。
  2. 记录当前从需求到发布的实际步骤。
  3. 列出最常见的返工、遗漏和等待。
  4. 统一 Java、前端和 E2E 验证命令。
  5. 确定规格层：默认试点 OpenSpec；复杂绿地项目可选 Spec Kit。

验收：

  • 每个项目都有能运行的验证入口；
  • 能说清什么变更必须让另一个人参与；
  • 没有同时引入多个规格框架。

#第 2 周：在真实变更中试用

  1. Owner 写 Proposal/Spec。
  2. Peer 只评审目标、边界和风险。
  3. 使用 Superpowers 内循环实现。
  4. PR 记录规格链接与验证证据。
  5. 统计额外时间和避免的返工。

验收：

  • 规格能让另一人理解变更；
  • CI 能拒绝明显错误；
  • 流程没有让小变更停滞。

#第 3 周：提炼团队协议

只固化已经重复有效的内容：

  • 风险分级；
  • 三种工作模式；
  • 人工检查点；
  • 统一验证脚本；
  • PR 和 ADR 模板；
  • 发布与回滚最低要求。

将其写入：

  • 根目录 AGENTS.md；
  • docs/workflow/TEAM-WORKFLOW.md；
  • 必要的模板和脚本。

#第 4 周：复盘并决定是否封装 Skill

检查：

  • 周期时间是否变长或变短；
  • 返工是否减少；
  • 线上遗漏是否减少；
  • 另一人接手是否更快；
  • 哪些步骤总被跳过；
  • 哪些步骤只是形式。

只有当同一流程已经稳定重复至少 3 次，再创建仓库级 Codex Skill。

#十五、用什么指标判断工作流有效

不要以文档数量、Agent 数量或 Prompt 长度作为成功指标。

推荐观察：

指标希望看到的趋势
从需求确认到合并的周期稳定或下降
因需求误解产生的返工下降
CI 之后才发现的基础错误下降
生产逃逸缺陷下降
Peer 理解变更所需时间下降
Owner 不在时的接手时间下降
发布回滚和恢复时间下降
AI 宣称完成但验证失败的次数下降
维护流程文档所需时间保持低水平

#建议的复盘问题

每两周用 20～30 分钟回答：

  1. 哪个错误本可由规则、测试或脚本提前发现？
  2. 哪份文档实际帮助了接手、评审或调试？
  3. 哪个流程步骤没有提供决策价值？
  4. 哪个知识点已重复出现 3 次，值得写进 AGENTS.md 或 Skill？
  5. 哪条规则已经过时，应该删除？

#十六、何时升级到更重的工作流

出现以下信号时，从 OpenSpec + Superpowers 升级到 Spec Kit、AIDLC-lite 或 BMAD：

  • 两个人开始共同频繁修改同一个项目；
  • 需求方增多且需求经常冲突；
  • 项目包含多个服务、前端和数据管道；
  • 架构决策频繁影响多个后续功能；
  • 审计、合规、安全或发布审批成为硬要求；
  • 生产事故暴露出需求、设计与运行之间断裂；
  • AI 生成速度已明显超过人工评审能力；
  • 需要暂停、恢复和追踪长时间自动工作流；
  • 新成员难以通过现有文档接手。

如果这些信号都不存在，继续保持轻量。

#十七、最终选型建议

#当前团队的首选

text
项目级 AGENTS.md
        +
OpenSpec
        +
Superpowers
        +
统一 verify 脚本与 CI
        +
风险触发的 Peer 评审

理由：

  • 两人各负责一个项目，变更所有权清楚；
  • 需要的是低成本的规格、交接和验证，而不是复杂角色编排；
  • OpenSpec 补齐变更意图和可追踪性；
  • Superpowers 补齐工程实现纪律；
  • CI 提供不依赖模型判断的证据；
  • AIDLC 仍可作为高风险任务的升级路径。

#备选

如果是复杂绿地项目：

text
Spec Kit + Superpowers + CI

如果产品探索和 PRD/UX 工作很多：

text
BMAD（先 Quick Flow，必要时完整轨道）+ CI

如果负责人需要长期自治推进单一项目：

text
GSD + 强 Harness + 明确预算/停止条件

#不推荐

  • 同时全面启用 AIDLC、BMAD、GSD、Spec Kit 和 OpenSpec；
  • 为两人团队自研工作流引擎；
  • 把所有小修复都升级为完整生命周期；
  • 让 Ralph 或其他自治循环直接处理生产高风险变更；
  • 只写 Prompt，不建设测试与 CI；
  • 把 Agent 生成的“评审通过”当作真实验证证据。

#十八、下一步学习与实践建议

建议按下面顺序推进：

  1. 选择一个真实存量 Java 全栈项目试用 OpenSpec。
  2. 把该项目的构建、测试、启动和发布命令精简写入 AGENTS.md。
  3. 建立统一的 verify 入口。
  4. 用一个标准变更走完整的 Proposal → Plan → TDD → Review → Archive。
  5. 两周后复盘，再决定是否创建团队级 TEAM-WORKFLOW.md。
  6. 至少重复 3 次后，才考虑封装 Codex Skill。
