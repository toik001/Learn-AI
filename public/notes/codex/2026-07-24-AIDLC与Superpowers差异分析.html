#AIDLC 与 Superpowers 差异分析：生命周期治理与工程 Inner Loop

整理日期：2026-07-24
适用对象：使用 Codex 开发 Java、Spring Boot 和前端应用的个人与团队
对比对象：AWS awslabs/aidlc-workflows 与 obra/superpowers
结论性质：基于两个项目的官方仓库和官方文档进行架构与工作流分析，不是量化性能评测

前置阅读：AIDLC 详细介绍 · Superpowers 详细介绍 · Codex 全栈开发最佳实践

#核心结论

#一句话区别

text
AIDLC 管“从想法到生产如何完整交付”
Superpowers 管“进入开发后如何可靠地设计、编码、调试、审查和验证”

两者都自称软件开发方法论，也都包含设计、计划、实现、人类确认和多 Agent 协作，因此表面看起来相似。但它们解决的是不同层级的问题：

项目本质定位最强能力
AIDLCAI 驱动的端到端 Development Life Cycle 与 Harness生命周期编排、Scope、追踪、状态、审计、团队知识、Operation
Superpowers编码 Agent 的可组合工程 Skills 与强制 Inner LoopTDD、系统化调试、细粒度计划、双重代码审查、完成前验证

AIDLC 当前在线指南把工作组织为 5 个 Phase、32 个 Stage、9 种 Scope、3 种 Depth、3 种 Test Strategy，并维护 Intent 状态与审计。AIDLC Introduction

Superpowers 的基础工作流是：

text
brainstorming
→ using-git-worktrees
→ writing-plans
→ subagent-driven-development / executing-plans
→ test-driven-development
→ requesting-code-review
→ finishing-a-development-branch

它明确要求 Red-Green-Refactor、先查根因、用最新命令输出证明完成。Superpowers README

#选型结论

  • 小到中型代码任务、Bug、重构：优先 Superpowers。
  • 跨产品、架构、研发、测试和运维的生产项目：优先 AIDLC。
  • 需要合规、审计、跨会话恢复或多团队知识治理：AIDLC 更合适。
  • 最关注代码实现质量、严格 TDD 和系统调试：Superpowers 更强。
  • 典型 Java 全栈生产功能：AIDLC 做 Outer Loop，吸收 Superpowers 的 TDD、调试、审查和验证纪律。
  • 不要同时运行两个顶层 Orchestrator：一个负责下一步路由，另一个只能作为局部实践来源。

#一、为什么不能简单问“谁更好”

一个方法论是否更好，取决于它被放在哪个责任层。

text
产品与业务层
  ├── 是否值得做
  ├── 谁是利益相关者
  ├── 范围和成功指标
  └── Build vs Buy
          ↑ AIDLC 覆盖

系统与交付层
  ├── 需求、故事、架构、NFR
  ├── Unit、依赖、发布、运维
  └── 状态、审计、团队规则
          ↑ AIDLC 强项

实现 Inner Loop
  ├── 设计细化
  ├── 任务计划
  ├── Red-Green-Refactor
  ├── Debug、Review、Verify
  └── Git 分支收尾
          ↑ Superpowers 强项

如果只用 AIDLC 评价 TDD 纪律，它不如 Superpowers 严格；如果只用 Superpowers 评价完整生命周期，它又缺少 AIDLC 的 Ideation、Operation、状态和治理。正确比较方式是逐层看职责覆盖和控制机制。

#二、定位与目标差异

#AIDLC 的目标

AIDLC 试图重新安排人和 AI 在整个 SDLC 中的职责：

  • AI 主动制定计划、分析和生成产物。
  • AI 主动识别不确定项并提问。
  • 人类提供业务上下文和关键选择。
  • 人类在 Stage Gate 审批。
  • 需求、设计、代码、测试、部署和反馈保持追踪。
  • 团队纠正通过 Learning Loop 形成下次可复用规则。

AWS 原始方法论强调两条轴：AI Powered Execution with Human Oversight，以及 Dynamic Team Collaboration。AWS AI-DLC 方法论

#Superpowers 的目标

Superpowers 试图纠正 Coding Agent 的常见坏习惯：

  • 未理解需求就开始编码。
  • 未比较方案就采用第一个想法。
  • 计划过于抽象，执行者需要自行猜测。
  • 先写实现再补测试。
  • 遇到 Bug 反复猜测式修改。
  • 子 Agent 自报完成后直接相信。
  • 没有新鲜验证证据就宣称成功。
  • 在主分支直接修改，缺少隔离和安全收尾。

其哲学是 TDD、系统过程、降低复杂度和证据优先。Superpowers README

#五、控制流：确定性引擎与 Skill 纪律

这是两者最根本的技术差异。

#AIDLC：引擎决定“下一步是什么”

AIDLC 把以下判断交给确定性代码：

  • 新建还是恢复 Intent。
  • 当前 Scope 包含哪些 Stage。
  • 当前 Stage 是否满足输入依赖。
  • Gate 是否打开、通过或要求修改。
  • 哪些 Stage 被跳过。
  • Phase Boundary 是否可通过。
  • 当前处于哪个 Bolt。
  • 是否允许自主 Construction。
  • 失败后 retry、skip 或 abort。
  • 工作流何时完成。

Agent 的自由度集中在“怎样完成当前 Stage”，而不是“想不想执行下一 Stage”。

优势：

  • 不容易因为上下文压缩而忘记流程。
  • 恢复和审计更可靠。
  • 可以验证 Stage Graph 和状态一致性。
  • 适合长任务和多人协作。

代价：

  • 引擎、Hook、状态和目录较复杂。
  • 自定义 Stage 需要理解依赖和 Artifact Contract。
  • 流程变化需通过 Composer、Scope 或显式导航，临时自由度较低。

#Superpowers：Skill 决定“此时应遵守什么纪律”

Superpowers 通过 Skill 的名称、描述、触发条件和强制步骤影响 Agent：

text
“实现新功能” → brainstorming
“已有规格，要实施” → writing-plans
“出现失败” → systematic-debugging
“准备说完成” → verification-before-completion

它的强制力来自：

  • 入口 Skill 要求先检查相关 Skills。
  • 每个 Skill 写有明确 Iron Law。
  • Skill 之间显式引用前置/后置流程。
  • 实现 Task 后用独立 Reviewer 检查。

优势：

  • 结构简单，容易理解和局部采用。
  • 某个 Skill 可独立用于现有流程。
  • 不需要完整生命周期状态机。
  • 适合日常编码对话。

代价：

  • 本质上仍依赖 Agent 正确触发、读取和遵守 Skill。
  • 会话恢复更多依赖计划、Git 和 Agent 上下文。
  • 缺少统一的 Stage 状态和审计事件。
  • 多 Skill 同时命中时，可能发生优先级或流程解释问题。

#六、需求与设计：广度和深度不同

#AIDLC 的设计面更宽

AIDLC 在 Ideation 和 Inception 中可能覆盖：

  • Intent 和利益相关者。
  • 市场研究与 Build vs Buy。
  • 可行性、约束和 RAID。
  • Scope 和 Team Formation。
  • Rough/Refined Mockups。
  • Requirements、Stories 和 Personas。
  • Application Design、ADR、NFR。
  • Unit DAG 和 Delivery Plan。

它适合回答：

我们应该构建什么系统，它为什么值得做，它在组织和生产环境中怎样存在？

#Superpowers 的设计更靠近实现

brainstorming 主要：

  • 调查现有项目。
  • 每次提出一个澄清问题。
  • 比较 2～3 个方案。
  • 分段展示设计并由用户确认。
  • 保存设计文档。
  • 转入 writing-plans。

writing-plans 再将设计拆成：

  • 明确文件路径。
  • 每个文件的责任。
  • 失败测试。
  • 最小实现。
  • 验证命令。
  • 小而可执行的 Tasks。

它更适合回答：

这个已经确定要做的功能，应该怎样设计和可靠实现？

#关键判断

  • 需求尚不稳定、涉及多个利益相关者：AIDLC 更合适。
  • 产品方向已确定，只需技术设计：Superpowers 更高效。
  • 业务和技术都复杂：先 AIDLC Inception，再用 Superpowers 纪律实施。

#七、工作分解：Unit/Bolt 与 Task

#AIDLC

text
Intent
  └── Units of Work
        └── Bolt / Parallel Bolt Batch
              └── Functional/NFR/Infra/Code Stage

Unit 是可以形成设计、依赖和验收的交付单元；Bolt 是小时或天级的端到端切片。

#Superpowers

text
Approved Design
  └── Implementation Plan
        └── Task 1（约 2～5 分钟）
        └── Task 2
        └── Task 3
              ├── Test
              ├── Implement
              ├── Verify
              └── Review

Superpowers Task 更接近具体代码动作，例如：

text
Task 1：为 OrderCancellationPolicy 写失败单测
Task 2：实现最小领域规则
Task 3：为 Controller 写 MockMvc 失败测试
Task 4：实现 API 和异常映射

#映射关系

text
AIDLC Intent      ≈ 一个完整项目目标
AIDLC Unit        ≈ 一个可独立交付的子系统/能力
AIDLC Bolt        ≈ 一个可验证的端到端增量
Superpowers Plan  ≈ 一个 Bolt 或 Unit 的详细施工图
Superpowers Task  ≈ Bolt 内的单次工程动作

因此不要把一个 AIDLC Intent 直接压成一个 Superpowers Task，也不要为一个简单单测创建完整 AIDLC feature Intent。

#八、测试策略：覆盖规划与执行纪律

#AIDLC 的测试视角

AIDLC 将测试量和类型作为项目配置：

Test Strategy重点
Minimal每项需求最少验证，主要单元测试
Standard单元 + 集成，必要时 E2E/NFR
Comprehensive单元、集成、契约、E2E、安全、性能等

它解决的是：

这次 Intent 需要多大范围的验证投资？

#Superpowers 的测试视角

Superpowers 的 TDD Skill 有明确 Iron Law：

text
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST

要求：

  1. 先写测试。
  2. 亲眼看到它因预期原因失败。
  3. 写最小实现。
  4. 看到测试通过。
  5. Refactor 并保持通过。

如果先写了实现，规则要求删除后按测试重新实现。例外如 Throwaway Prototype、生成代码、配置文件，也需要向人类请求许可。test-driven-development

它解决的是：

每一次行为实现，是否真的由失败测试驱动？

#谁更强

  • 测试范围与风险配置：AIDLC 更强。
  • 测试先后顺序与 Red-Green 证据：Superpowers 更强。
  • 最佳组合：AIDLC 决定测试策略，Superpowers 约束每个可测试行为的实现顺序。

#潜在冲突

AIDLC 的 Code Generation Agent 可能一次生成实现和测试，但这不自动满足 Superpowers 的 TDD，因为没有证明测试先失败。若团队要求严格 TDD，应把以下规则写入 AIDLC Construction Memory：

text
每个行为必须先创建失败测试并记录失败原因；
未见预期失败不得创建生产实现；
修复后运行相关测试与全量回归；
完成声明必须附本轮命令输出。

这是组合建议，不是 AIDLC 官方默认行为。

#九、调试能力

#AIDLC

bugfix Scope 能缩短生命周期，通常保留 Reverse Engineering、Requirements、Code Generation 和 Build/Test。它善于：

  • 建立 Bug Intent。
  • 记录需求和修复标准。
  • 分析 Brownfield。
  • 保留状态与审计。
  • 为高风险 Bug 调高 Test Strategy。

但当前核心方法没有像 Superpowers 那样把“根因调查必须先于修复”写成独立而强硬的四阶段调试流程。

#Superpowers

systematic-debugging 明确规定：

text
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST

四阶段为：

  1. Root Cause Investigation。
  2. Pattern Analysis。
  3. Hypothesis and Testing。
  4. Implementation and Verification。

它要求读完整错误、稳定复现、检查最近变更、跨组件采集证据、向上追溯错误值来源，并一次只验证一个假设。systematic-debugging

#结论

对于“支付重复扣款”“偶发事务死锁”“测试污染”“CI 与本地不一致”等问题，Superpowers 的调试纪律明显更强。若 Bug 还涉及审计、合规、发布和事故复盘，则 AIDLC 提供更完整的外围治理。

#十、代码审查差异

#AIDLC 审查

  • 人类审核每个 Stage/Bolt 的产物。
  • Phase Boundary 检查 Artifact、Traceability 和一致性。
  • Reviewer Agent 可做架构或质量审查。
  • 审查对象包含需求、设计、代码、测试和运维产物。

#Superpowers 审查

每个 Task 完成后执行两级独立审查：

  1. Spec Compliance Review：是否完全符合需求，有无遗漏或过度实现。
  2. Code Quality Review：代码、测试、可维护性和工程质量。

只有规格审查通过，才进入质量审查。问题修复后 Reviewer 重新检查，不是一次性建议。subagent-driven-development

#结论

  • AIDLC 审查面更广，适合生命周期一致性。
  • Superpowers 审查粒度更细，适合阻止代码问题逐 Task 累积。
  • 两级审查对简单 Task 也可能产生明显 Token 和时间成本。

#十一、Human Gate 与自主性

#AIDLC 的放权曲线

text
前期每 Stage 互动与审批
→ Walking Skeleton 必须审批
→ 用户选择 remaining Bolts:
     gated / autonomous
→ 失败始终停止

这是一种按架构证据逐步放权的模型。

#Superpowers 的放权曲线

text
Brainstorming 中高互动
→ 用户批准设计
→ 用户批准计划/开始执行
→ subagent-driven-development 连续执行
→ 每 Task 由两个 Agent 审查
→ 仅在阻塞、关键歧义或全部完成时停下

官方 subagent-driven-development 明确要求不要在每个 Task 间打断人类，而是依赖 Reviewer 持续执行。subagent-driven-development

#风险差异

  • AIDLC：Human Gate 多，可能形成“审批疲劳”。
  • Superpowers：人类批准计划后自主度高，如果计划本身有系统性错误，会被忠实放大。
  • AIDLC 依靠 Skeleton 降低架构风险。
  • Superpowers 依靠细任务、TDD 和双 Reviewer 降低实现风险。

#十二、状态、恢复和审计

#AIDLC

  • 谁在什么时间批准了什么？
  • 当前会话应从哪里恢复？
  • 哪个 Artifact 支撑哪个下游决定？

#Superpowers

持久信息主要在：

  • Design Doc。
  • Implementation Plan。
  • Git Branch/Worktree。
  • Commits 和 Diff。
  • Tests。
  • Review 反馈。
  • Agent Todo/Plan。

它能很好回答“这次分支做了什么”，但通常不能像 AIDLC 那样提供统一的跨 Phase 事件账本和多个 Intent 注册表。

#结论

  • 单人、单分支、短周期：Superpowers 的状态通常足够。
  • 跨天、多团队、合规或多 Intent：AIDLC 更可靠。

#十三、团队知识与学习机制

#AIDLC

AIDLC 当前规则链：

text
org → team → project → phase → stage

Stage 执行中的解释、偏差、权衡和开放问题写入 Memory Diary，Gate 后经人确认才提升为 Project 或 Team Rule；规则在下一工作流生效。Rules and the Learning Loop

优势：

  • 规则有明确作用域。
  • 人类确认后才沉淀。
  • 可以跨 Intent 复用。
  • 避免同一纠正重复发生。

风险：

  • 规则会不断膨胀。
  • 错误纠正也可能被永久化。
  • Org、Team 和 Project 的严格叠加可能产生冗余。
  • 需要定期治理。

#Superpowers

Superpowers 的知识主要是：

  • 通用 Skills。
  • Skill 附带的参考和脚本。
  • 项目 AGENTS.md。
  • Design/Plan。

它没有与 AIDLC 等价的自动 Learning Loop。要沉淀团队纠正，需要人工更新 AGENTS.md、项目 Skill 或其他知识文件。

优势：

  • 模型简单。
  • 不容易自动积累大量规则。
  • 可通过修改 Skill 精确演进。

风险：

  • 本次纠正容易只留在聊天中。
  • 个人经验不一定形成团队制度。
  • 多项目作用域需要额外设计。

#十四、Git、Worktree 与并行

#AIDLC

  • Unit 依赖 DAG 决定 Bolt 顺序。
  • 无依赖 Bolt 可并行成 Batch。
  • Workshop/Swarm 支持多个参与者和 Worktree。
  • Audit 使用分片降低并行 Git 冲突。
  • Codex 下还要处理 Sandbox 对 .git 的保护。

适合按业务/架构边界并行。

#Superpowers

using-git-worktrees 明确：

  • 先检测是否已处于隔离环境。
  • 优先使用 Harness 原生 Worktree。
  • 没有原生能力再使用 Git Worktree。
  • 创建前确认用户意愿。
  • 验证 Worktree 目录被忽略。
  • 完成依赖安装并运行干净基线测试。

using-git-worktrees

适合按实现 Task 或独立计划并行。

#结论

  • Superpowers 的单分支隔离流程更直接、可立即复用。
  • AIDLC 的并行模型更理解 Unit 依赖和团队级记录。
  • 同时启用两者的 Worktree 创建逻辑可能重复创建或造成 Harness 无法管理的“幽灵状态”。

#十五、Operation 与生产治理

这是 AIDLC 对 Superpowers 最大的功能差异。

AIDLC Operation 包括：

  • Deployment Pipeline。
  • Environment Provisioning。
  • Deployment Execution。
  • Observability Setup。
  • Incident Response。
  • Performance Validation。
  • Feedback & Optimization。

Superpowers 在“分支如何结束”处完成：

  • 验证测试。
  • 选择 Merge、PR、Keep 或 Discard。
  • 清理 Worktree。

它不负责：

  • 环境供应。
  • 发布策略。
  • 生产 Smoke Test。
  • Dashboard、Alarm 和 SLO。
  • Incident Runbook。
  • 生产性能验证。
  • 成本和反馈闭环。

如果组织把“完成”定义为代码合并，Superpowers 足够；如果定义为“可运营的生产能力”，AIDLC 更匹配。

#十六、AIDLC 的优点

#1. 生命周期完整

从 Intent、市场和可行性一直覆盖到部署、观测和反馈，避免“代码写完即交付完成”。

#2. 流程可按风险裁剪

Scope 决定 Stage，Depth 决定产物深度，Test Strategy 决定测试投入；Bugfix 不必经过完整市场研究。

#3. 状态和审计强

每个 Intent 有独立状态、恢复点和追加式 Audit Trail，适合长任务、多人、监管和复盘。

#4. Traceability 完整

Requirements、Stories、Design、Units、Code、Tests 和 Operation Artifacts 有显式依赖，Phase Boundary 能检查孤立或缺失链接。

#5. Human-in-the-loop 是一等机制

Gate 不是临时提醒，而是状态机的一部分；AI 不能仅凭自己的输出推进关键阶段。

#6. Walking Skeleton 降低架构风险

先证明最小真实端到端链路，再允许剩余 Bolt 自主执行。

#7. 适合组织知识治理

Org、Team、Project 和 Phase 规则具有明确作用域，Learning Loop 可将纠正转成下一轮默认行为。

#8. 多角色覆盖广

Product、Architecture、Compliance、DevSecOps、Quality、Platform、Operations 等角色减少了只从编码视角优化的风险。

#十七、AIDLC 的缺点

#1. 仪式和产物较重

即使有 Scope 裁剪，完整 feature 仍可能运行 32 个 Stage。若团队不认真审查，最终只会生成大量 Markdown。

#2. 安装与运行复杂

当前多 Harness 实现涉及 .codex/、.agents/、aidlc/、Hooks、Bun、信任和 Sandbox 配置，学习成本显著高于单纯安装 Skills。

#3. Token、时间和审查成本高

多 Agent、丰富 Artifact、频繁 Gate 和 Comprehensive Depth 会增加费用，Human Gate 还可能造成审批疲劳。

#4. TDD 和调试纪律不够强硬

AIDLC 有 Build/Test 和测试策略，但默认不等于“每行生产行为都先看到失败测试”，也没有 Superpowers 同等级的根因调查 Iron Law。

#5. 版本表述存在迁移风险

官方最新可见 Release README 仍呈现三阶段 Rules 模型，而在线指南已描述五阶段、32 Stage 的新架构。安装方法、命令和目录不能混用。

#6. 官方实现带有 AWS-first 色彩

方法论本身可以跨平台，但当前 Agent 和 Operation 设计包含 AWS Platform、Bedrock 和 AWS 工具的默认路径。非 AWS 团队需要调整知识、Agent 和基础设施实践。

#7. 自定义需要理解框架模型

修改 Scope、Stage、Artifact Dependency、Sensor 和 Agent 比新增一条普通 Skill 更复杂。

#8. 形式正确不等于产品正确

完整状态、审计和文档只能证明流程发生过，不能自动证明需求、架构和代码是正确的。

#十八、Superpowers 的优点

#1. 实现纪律非常明确

设计、计划、TDD、调试、Review 和完成验证都有具体流程和禁止项，能直接纠正 Agent 的常见坏习惯。

#2. TDD 强度高

不是“有测试就行”，而是要求看到失败测试，再写最小实现，最后 Refactor。

#3. 调试方法成熟

先复现、读错误、检查变更、采集证据、比较模式、提出单一假设，避免猜测式修复。

#4. 双阶段 Reviewer

先审规格符合性，再审代码质量，能捕获“代码写得很好但做错需求”这一常见问题。

#5. Evidence over Claims

verification-before-completion 要求在当前回合运行完整验证命令，读取退出码和失败数后才能声明完成。verification-before-completion

#6. 可组合、可局部采用

只需使用 systematic-debugging 或 verification-before-completion，不必引入完整生命周期。

#7. Git 隔离清晰

Worktree 创建、基线测试、分支完成和清理都有专用 Skill。

#8. 学习和维护门槛相对较低

核心是 Markdown Skills 和少量辅助资源，个人开发者能较快理解并使用。

#十九、Superpowers 的缺点

#1. 生命周期覆盖不完整

缺少市场、可行性、组织 Scope、合规矩阵、部署、环境、可观测、事故和反馈闭环。

#2. 缺少确定性全局状态机

流程主要依赖 Agent 正确匹配和遵守 Skill。没有与 aidlc-state.md 和 Audit Trail 等价的全局控制面。

#3. 缺少多 Intent 和 Space 模型

适合围绕一个设计/计划/分支工作；多个团队、多个并行 Intent 和共享规则需要外部项目管理。

#4. 严格 TDD 并非所有工作都经济

UI 视觉探索、一次性迁移、生成代码、配置和 Throwaway PoC 可能不适合完整 Red-Green-Refactor。虽然 Skill 允许向人请求例外，但默认很严格。

#5. 细任务与双审查可能过度

2～5 分钟 Task 配上两次独立 Review，会增加大量 Agent 调用。对于简单、低风险、规格明确的改动，收益可能小于成本。

#6. 计划错误可能被高速放大

设计和计划一旦批准，Subagent 流程会持续执行。Reviewer 能发现局部不符，但未必能发现产品方向或架构假设本身错误。

#7. 没有内置 Learning Loop

一次有价值的纠正不会自动经过 Gate 提升为 Team/Project Rule，需要人工维护 AGENTS.md 或 Skills。

#8. NFR 和合规依赖外部补充

安全、性能、可靠性、隐私、成本和运维不是默认完整阶段，必须由需求、项目规则或额外 Skills 补充。

#二十三、组合使用的正确架构

#原则：只能有一个顶层 Conductor

错误组合：

text
$aidlc 决定下一 Stage
    ↕ 同时争夺控制
Superpowers brainstorming/writing-plans 决定下一 Skill

可能产生：

  • 两份设计。
  • 两份计划。
  • AIDLC Unit/Bolt 与 Superpowers Task 相互重复。
  • 两套审批门。
  • 两套 Worktree。
  • 两组 Subagent 同时修改相同文件。
  • 一个系统认为 Stage 完成，另一个认为尚未验证。

#推荐方案 A：AIDLC 主导

text
AIDLC
  ├── Ideation
  ├── Inception
  ├── Unit/Bolt Plan
  └── Construction 3.5
         ├── Superpowers TDD 纪律
         ├── Systematic Debugging
         ├── Spec Review
         ├── Code Quality Review
         └── Verification Before Completion
  └── AIDLC Operation

操作方式：

  1. $aidlc 是唯一决定下一 Stage 的入口。
  2. 不再启动 Superpowers 完整 Brainstorming → Plan 顶层流程。
  3. 将 TDD、Debug、Review、Verify 原则写入 AIDLC Construction Rules。
  4. 如 Harness 支持，可只显式调用对应 Superpowers 单项 Skill。
  5. Superpowers 产出的测试和 Review 结果作为当前 Bolt 证据。
  6. Gate 仍由 AIDLC 关闭。

适合：

  • 企业和团队项目。
  • 跨前后端、数据库、云和运维。
  • 需要审计和恢复。

#推荐方案 B：Superpowers 主导

text
人工/现有产品流程提供已批准需求
  ↓
Superpowers Brainstorming
  ↓
Design + Plan
  ↓
TDD + Subagents + Reviews
  ↓
Branch Finish
  ↓
团队现有 CI/CD 和运维流程

不启动 AIDLC Engine，只参考其方法补充：

  • NFR Checklist。
  • Walking Skeleton。
  • Operation Definition of Done。
  • 需求到测试的 Traceability。

适合：

  • 个人和小团队。
  • 现有公司已拥有成熟产品、发布和运维系统。
  • 只想提升编码 Agent 的工程质量。

#推荐方案 C：顺序交接

text
AIDLC 完成 Inception
→ 冻结 Requirements / Design / Units
→ Superpowers 将一个 Bolt 转成详细 Plan 并实现
→ 将验证证据回填 AIDLC
→ AIDLC 继续 Operation

此方案有边界风险：

  • AIDLC Construction 状态如何记录外部实现。
  • 两套 Artifact 如何避免漂移。
  • Git 和 Reviewer 结果如何回填。

它不是两项目官方共同定义的集成协议。采用前必须在团队规则中明确交接文件、完成条件和状态更新方式。

#二十五、Java 全栈示例

任务：

在 Spring Boot + React 的订单系统增加取消与异步退款。

#只用 AIDLC

优点：

  • 能覆盖需求、用户故事、架构、事务、Outbox、UI、部署和观测。
  • 能用 Walking Skeleton 先贯通浏览器 → API → PostgreSQL。
  • 能记录合规、审批和运维 Artifacts。

缺点：

  • Code Generation 可能一次生成较大变更。
  • 不保证每条业务规则都先看到失败测试。
  • 如果 Scope 选择 feature，流程可能较重。

#只用 Superpowers

优点：

  • 会先批准设计和详细计划。
  • 每条取消规则按 TDD 实现。
  • 每个 Task 经过规格和质量审查。
  • 遇到事务或幂等 Bug 会先查根因。

缺点：

  • 不会默认建立市场/利益相关者/Operation Artifacts。
  • 退款积压告警、SLO、Incident Runbook 需要在需求中主动补充。
  • 跨会话、多团队的统一审计较弱。

text

#二十六、落地建议

#个人 Java 开发者

先安装 Superpowers，重点使用：

  • brainstorming。
  • writing-plans。
  • test-driven-development。
  • systematic-debugging。
  • verification-before-completion。

当项目开始跨团队、跨环境、需要多个 Intent 或生产治理时，再评估 AIDLC。

#小型团队

#典型场景：2 人团队，每人主要负责一个项目

假设团队结构如下：

text
开发者 A ── 主要负责项目 A
开发者 B ── 主要负责项目 B

两人：
  ├── 偶尔协助对方排查问题
  ├── 在高风险变更和发布前互审
  ├── 共享 Java/Spring 工程规范
  └── 不需要每天共同开发同一个功能

这种团队的主要风险不是多人同时修改同一文件，而是：

  • 每个项目形成只有负责人知道的隐性知识。
  • 一人请假后，另一人难以接手。
  • 两个项目逐渐采用不同的构建、测试和发布习惯。
  • 没有足够人力逐个审批完整 AIDLC 的所有 Gate。
  • 项目负责人既实现又验收，容易出现自我确认偏差。

因此，推荐采用：

text
Superpowers 作为每个项目的默认开发 Inner Loop
          +
轻量共享 Harness 统一团队底线
          +
AIDLC 只用于新项目、重大功能和高风险发布

不推荐让两个项目的所有日常任务都运行完整 AIDLC feature Scope。两个人需要分别审批大量 Stage，容易产生仪式负担和形式化通过。

普通 Bugsystematic-debugging + TDD高风险 Bug 需要互审
小型重构Superpowers涉及公共接口时互审
新项目启动AIDLC mvp另一人审 Requirements、Skeleton、Release
大型生产功能AIDLC feature 或 Composer 裁剪三个关键 Gate 互审
安全补丁AIDLC security-patch + Superpowers Debug/TDD必须互审
基础设施/发布变更AIDLC infra 或发布 Checklist必须互审和验证回滚
一次性 PoCAIDLC poc 或 Brainstorming通常不需要逐步互审

#推荐的职责分配

每个项目设两个角色，但不要求两人共同完成所有操作：

角色人员责任
Project Owner项目主要负责人需求澄清、设计、实现、日常 Gate、发布准备
Peer Reviewer另一名开发者高风险设计、Walking Skeleton、关键 PR、发布和事故复盘

以项目 A 为例：

text
开发者 A：
  Owner
  ├── 维护项目 A 的 AGENTS.md
  ├── 执行 Brainstorming、Plan、TDD、Debug
  ├── 维护 ADR、测试和发布证据
  └── 负责日常 AIDLC Gate

开发者 B：
  Peer Reviewer
  ├── 审查关键需求和架构
  ├── 审查 API/Schema/安全/迁移变更
  ├── 验证 Walking Skeleton
  └── 在发布前进行独立检查

项目 B 的角色反转。

这样既保持明确所有权，也避免“项目完全属于一个人”。

#三层知识结构

两人不需要搭建复杂知识平台，但必须区分共享规则和项目事实。

#第一层：团队共享底线

建议放在共享模板仓库，或复制到每个项目的根 AGENTS.md：

  • 支持的 Java/JDK 和 Spring Boot 版本。
  • Maven/Gradle 标准命令。
  • 测试先行和完成前验证要求。
  • Checkstyle、SpotBugs、Sonar 或其他质量门。
  • API、异常、日志和 Trace ID 规范。
  • 密钥、权限、依赖漏洞和数据脱敏规则。
  • PR 与发布最低检查项。
  • 禁止在无验证证据时宣称完成。
#第二层：项目专属事实

保存在各项目自己的 AGENTS.md、ADR 或 AIDLC Knowledge：

  • 业务领域词汇。
  • 模块和包边界。
  • 数据库与消息 Schema。
  • 本地运行方式。
  • 特定测试数据。
  • 部署环境与回滚方式。
  • 项目已知限制。
#第三层：一次任务的短期上下文

保存在：

  • Issue。
  • Superpowers Design/Plan。
  • AIDLC Intent Artifacts。
  • PR 描述和测试证据。

不要把一次任务的全部讨论永久写进团队级 AGENTS.md。

不使用完整 AIDLC 时：

text

├── AGENTS.md
├── docs/
│   ├── adr/
│   └── superpowers/
│       ├── specs/
│       └── plans/
├── src/
├── pom.xml
└── .github/workflows/ 或其他 CI 配置

选择性启用 AIDLC 后：

text
project-a/
├── AGENTS.md
├── .agents/skills/
├── .codex/
├── aidlc/
│   └── spaces/default/
├── docs/
│   ├── adr/
│   └── superpowers/
└── ...

必须为每个项目分别保存领域知识、命令和部署约束，不要让项目 A 读取项目 B 的专属规则。

#日常工作流

#场景 1：一到两小时的小功能
text
Owner 明确验收条件
→ Superpowers Brainstorming（必要时简化）
→ 写失败测试
→ 最小实现
→ 运行相关测试
→ Agent Spec/Quality Review
→ 运行完整项目验证
→ 创建 PR
→ Peer 异步检查关键 Diff

不需要建立完整 AIDLC Intent，除非涉及高风险边界。

#场景 2：普通 Bug
text
稳定复现
→ Systematic Debugging 查根因
→ 写能复现 Bug 的失败测试
→ 最小修复
→ 相关回归 + 全量验证
→ 在 PR 中记录根因、影响和证据

出现以下情况时，另一人必须参与：

  • 生产事故。
  • 数据错误或丢失。
  • 权限和安全问题。
  • 并发、事务或幂等问题。
  • 修复需要绕开原架构。
  • 已经连续两次修复失败。
#场景 3：持续一周以上的功能

推荐使用轻量 AIDLC：

text
$aidlc compose "为当前功能保留需求分析、应用设计、
Unit/Bolt 规划、代码生成、构建测试和必要的 Operation；
跳过已由业务确认的市场研究和团队组建。"

由 Owner 处理日常 Stage，Peer 只参加三个关键 Gate：

  1. Requirements/Application Design Gate：确认没有方向错误。
  2. Walking Skeleton Gate：确认端到端架构真实可行。
  3. Release/Operation Gate：确认发布、回滚和观测准备完成。
#场景 4：新项目

使用 AIDLC mvp，但两人不必同时参加每个问题：

text
Owner：
  驱动 Intent、需求、设计和实现

Peer：
  审核 API/数据边界
  验证 Skeleton
  检查运行手册和接手资料

新项目完成 Walking Skeleton 后，应安排一次由 Peer 独立完成的“接手演练”：

  1. 只阅读仓库文档。
  2. 从零启动项目。
  3. 运行测试。
  4. 定位一个核心调用链。
  5. 完成一次非生产环境部署或 Smoke Test。

如果 Peer 无法完成，说明项目知识仍然只存在 Owner 脑中。

#哪些变更必须人工互审

不必规定所有 PR 都进行长时间同步评审。以下风险触发器更适合 2 人团队：

  • 对外 API 或事件 Schema。
  • 数据库迁移、数据修复脚本。
  • Spring Security、认证、授权和密钥。
  • 金额、账务、库存和幂等。
  • 跨服务事务或消息一致性。
  • 公共依赖和版本升级。
  • CI/CD、生产配置和基础设施。
  • 删除、批量更新或不可逆操作。
  • 性能关键路径。
  • Agent 生成的大范围重构。

低风险文档、测试补充和局部实现可以由 Owner + Agent Reviewer 完成，再由 Peer 抽查。

#推荐的人类检查点

为了避免另一人被频繁打断，可采用异步三检查点：

检查点Peer 重点检查目标时间
设计前范围、接口、数据、风险和非目标15～30 分钟
Skeleton 后真实链路、测试、错误处理和可观测性20～40 分钟
发布前Diff、迁移、回滚、告警和验证证据20～40 分钟

时间只是团队排期参考，不是硬性限制。关键是减少无价值的逐 Stage 同步等待，同时保留独立判断。

#建议的协作节奏

周期活动
每个任务Owner 执行 Superpowers Inner Loop
高风险 PRPeer 异步互审
每周一次30 分钟交换两个项目的进展、风险和设计变化
每个重大版本Peer 做一次运行/发布/回滚验证
每月一次清理共享规则、依赖版本和重复文档
每季度一次交换维护一个小任务，检验项目可接手性

#什么时候升级为完整 AIDLC

满足多个条件时，再从“Superpowers + 轻量文档”升级：

  • 一个功能持续两周以上。
  • 一个项目同时存在多个独立 Intent。
  • 两人开始共同修改同一项目。
  • 接入多个外部系统。
  • 出现合规、审计或正式审批要求。
  • 需求、设计、测试和发布信息开始分散。
  • 项目负责人休假时无法接手。
  • 发布需要复杂迁移、灰度、回滚和 SLO。
  • Agent 多次因上下文丢失重复分析。

#不建议的做法

  • 两个项目的每个小任务都运行 AIDLC feature。
  • 要求另一人参加所有 Stage Gate。
  • 用 Agent Review 完全取代人类高风险审查。
  • 两个项目共用一份包含业务细节的全局 AGENTS.md。
  • 同时让 AIDLC 和 Superpowers 创建 Worktree。
  • 把聊天记录当作项目文档。
  • 只有 Owner 能运行、测试或发布自己的项目。

text
默认：
  Superpowers
  ├── Brainstorming
  ├── Plan
  ├── TDD
  ├── Systematic Debugging
  ├── Agent Review
  └── Fresh Verification

共享：
  轻量 AGENTS.md 模板
  + CI 质量门
  + ADR
  + PR/发布 Checklist

选择性：
  AIDLC
  ├── 新项目用 mvp
  ├── 大功能用 compose/feature
  ├── 安全问题用 security-patch
  └── 基础设施用 infra

人类协作：
  各自拥有一个项目
  + 高风险变更互审
  + Requirements/Skeleton/Release 三检查点
  + 定期交叉接手演练

这能在不增加过多流程成本的情况下，兼顾个人效率、代码质量和项目可接手性。

#中大型团队

建议：

  1. AIDLC 管 Intent、Scope、Requirements、Architecture、Units、Operation。
  2. 把 Superpowers 的 TDD/Debug/Review/Verify 写入 Construction Rules。
  3. 统一 Artifact 和 Git 事实源。
  4. 设定 Gate Owner，避免所有人都以为别人会审。
  5. 测量每类 Scope 的平均 Token、等待时间和返工率。
  6. 每月治理 Learning Rules。

#受监管团队

建议以 AIDLC 为主，但不能只依赖其生成文档：

  • 人类签署风险与合规决定。
  • 测试证据进入可审计 CI。
  • 生产权限与职责分离。
  • Artifact 与真实代码/部署保持校验。
  • Superpowers 的新鲜验证原则用于每次完成声明。

#二十七、最终决策树

text
是否需要产品发现、多个利益相关者或完整生产运维？
├── 是 → AIDLC
│       └── 是否要求严格 TDD/调试/细粒度审查？
│           ├── 是 → AIDLC 主导 + Superpowers Inner Loop
│           └── 否 → AIDLC
│
└── 否 → 是否主要是代码实现、Bug 或重构？
        ├── 是 → Superpowers

                ├── 是 → Vibe/Brainstorming 或 AIDLC poc
