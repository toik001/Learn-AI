#OpenSpec + Superpowers + CI：Codex CLI 全栈实战教程

整理日期：2026-07-24
适用对象：以 Java 21、Spring Boot、TypeScript 前端和 GitLab 为主的小团队。
目标：把“让 AI 写代码”升级为一条有规格、有实现纪律、有机器证据的可复用交付链路。

#核心结论

推荐的职责分工只有一句话：OpenSpec 管“要改什么”，Superpowers 管“怎样可靠地改”，CI 管“改完是否真的成立”。Codex CLI 是执行这些约束的开发入口，人仍负责范围、架构、风险和最终合并决策。

text
需求或问题
   │
   ├─ 不确定：OpenSpec Explore + Superpowers Brainstorming
   │
   └─ 已确定：OpenSpec Propose
                 │
                 ▼
     proposal → specs → design → tasks
                 │ 人工确认
                 ▼
           OpenSpec Apply
                 │
                 ├─ Superpowers TDD
                 ├─ Superpowers Systematic Debugging
                 ├─ Superpowers Code Review
                 └─ Superpowers Verification
                 │
                 ▼
        本地验证 → CI → 人工 Review
                 │
                 ▼
          OpenSpec Archive

最关键的组合原则是：一个顶层真相源、多个局部能力。本方案以 OpenSpec 的 proposal/specs/design/tasks 为唯一计划，不再让 Superpowers 另起一套互相竞争的需求和任务清单；Superpowers 只承担设计讨论、TDD、调试、评审和完成前验证等实现内循环。

#三层职责与边界

层负责内容产物不应该替代
OpenSpec问题、范围、行为要求、技术设计、实施任务、变更状态openspec/specs/、openspec/changes/测试框架、代码质量工具和流水线
Superpowers脑暴、工作树、TDD、系统调试、代码评审、完成前验证实现过程、测试、评审发现和验证证据OpenSpec 的规格真相源
CI可重复运行的规格校验、编译、测试、静态检查、构建和安全门禁日志、报告、制品、通过或失败状态需求判断和人工验收
人优先级、边界、风险、架构取舍、数据迁移、发布与合并决策确认、审批和业务验收所有高影响决定都交给模型

OpenSpec 官方将 openspec/specs/ 定义为当前行为真相，将每次变更放在 openspec/changes/<change-id>/；归档时，delta spec 合并回主规格，变更目录带日期移入归档。OpenSpec Core Concepts

#环境与版本基线

  • Git 2.x，并已配置 GitLab SSH 或 HTTPS 凭据。
  • Java 21 LTS；Spring Boot 项目提交 Maven Wrapper，统一使用 ./mvnw。
  • Node.js 22 LTS。OpenSpec 当前要求 Node.js 20.19.0 或更高版本。
  • npm 10+；前端依赖和 OpenSpec CI 依赖都提交 lockfile。
  • GitLab Runner 能执行项目所需的容器镜像或 Shell 命令。

本页检索时的本机验证版本是 codex-cli 0.145.0。工具版本会继续变化，因此安装命令使用官方稳定入口，项目可复现性则依靠 lockfile、Wrapper 和 CI 镜像版本。

#Codex CLI 在项目中的基本用法

#交互式开发

bash
cd your-project
codex

# 也可以在启动时给出目标
codex "先读取 AGENTS.md 和 OpenSpec 状态，只汇报当前项目结构与可用技能，不修改文件"

Codex 会从项目根目录到当前工作目录逐层加载 AGENTS.md，越靠近当前目录的规则优先级越高。因此可在仓库根目录定义通用工程规则，在 backend/、frontend/ 下分别补充局部规则。AGENTS.md 官方说明

#非交互式任务与评审

bash
# 一次性只读分析
codex exec --sandbox read-only \
  "读取 AGENTS.md 和 openspec/，列出当前活动变更、风险和下一步，不修改文件"

# 评审本地所有未提交变更
codex review --uncommitted

# 以 main 为基线做 PR 风格评审
codex review --base main

# 评审一个提交
codex review --commit <sha>

codex exec 适合脚本化的单次任务，codex review 只输出按优先级排序的评审发现，不修改工作区。对于写代码任务仍建议使用交互会话，以便在规格、测试失败和高风险操作处停下来确认。Codex developer commands

#安装与初始化 OpenSpec

#开发机安装

bash
node --version
npm install -g @fission-ai/openspec@latest
openspec --version

cd your-project
openspec init --tools codex

# 升级 OpenSpec 后刷新项目里的技能
npm install -g @fission-ai/openspec@latest
openspec update

--tools codex 是可复现的非交互初始化方式。默认 core profile 会安装 propose、explore、apply、sync、archive 五类工作流。OpenSpec 生成的关键结构如下：

text
your-project/
├── AGENTS.md
├── .codex/
│   └── skills/
│       ├── openspec-propose/
│       ├── openspec-explore/
│       ├── openspec-apply-change/
│       ├── openspec-sync-specs/
│       └── openspec-archive-change/
└── openspec/
    ├── config.yaml
    ├── specs/                 # 当前系统行为真相
    └── changes/
        ├── <change-id>/
        │   ├── proposal.md    # 为什么改、范围是什么
        │   ├── specs/         # ADDED/MODIFIED/REMOVED 行为增量
        │   ├── design.md      # 技术方案
        │   └── tasks.md       # 可验证任务
        └── archive/

OpenSpec 本身以 Markdown 保存规格，这是该框架的工程数据格式；它与本知识库“学习页面只写 HTML”的约束不是一回事。应用仓库应把 openspec/ 和 .codex/skills/openspec-* 一起提交，让团队和 CI 共享同一份变更状态。

#Codex 中的正确调用方式

Codex 是 skills-only 集成。OpenSpec 不会为 Codex 生成 /opsx:propose 等斜杠命令；它生成项目级 .codex/skills/openspec-*。因此在 Codex 中应通过技能名或自然语言调用：

text
使用 $openspec-explore 探索“订单重复提交”的根因和候选方案，只分析，不创建变更，不写代码。

使用 $openspec-propose 为“订单取消”创建 change-id，
要求包含后端 API、状态机、数据库并发、前端交互、测试和回滚策略。

使用 $openspec-apply-change 实现 change-id=add-order-cancellation。
以 tasks.md 为唯一任务清单，一次只推进一个任务。

使用 $openspec-archive-change 归档 add-order-cancellation，
归档前先验证任务、测试、CI 和实现与规格一致。

如果 $ 自动补全中看不到技能，先检查 .codex/skills/openspec-* 是否存在，执行 openspec update，然后重启 Codex。OpenSpec 官方支持表明确写了 Codex 不生成命令文件。OpenSpec Supported Tools

#OpenSpec 终端检查命令

bash
openspec list
openspec show add-order-cancellation
openspec status --change add-order-cancellation
openspec validate add-order-cancellation
openspec validate --all --strict
openspec view

这些是终端中的检查命令；“提议和实现”发生在 Codex 会话中。不要把 $openspec-propose 当成 shell 命令执行。

#组合时只使用局部技能

场景推荐 Superpowers 能力与 OpenSpec 的连接点
需求仍模糊brainstorming结论写回 proposal/design，不另建长期计划
实现一个任务test-driven-development输入是 tasks.md 当前任务和 spec 场景
Bug 不明原因systematic-debugging根因和正确行为写回 change artifact
任务完成requesting-code-review按规格、任务和 diff 评审
声称完成前verification-before-completion运行本地验证并记录证据
分支收尾finishing-a-development-branchCI 绿灯、人确认后才合并和归档

Superpowers 在 Codex 中同样是技能，而不是 /brainstorming 斜杠命令。可直接说“使用 Superpowers 的 test-driven-development 技能完成当前 OpenSpec 任务”，或从技能补全中显式选择。其官方工作流强调 RED-GREEN-REFACTOR、系统调试、评审和证据优先。Superpowers Basic Workflow

#项目级 AGENTS.md

OpenSpec 和 Superpowers解决的是“工作方式”，项目自己的 AGENTS.md 则告诉 Codex 什么是本仓库的正确实现。下面是 Java 全栈项目可直接裁剪的基线：

markdown
# Project Instructions

## Stack
- Backend: Java 21, Spring Boot, Maven Wrapper
- Frontend: TypeScript, existing package manager and lockfile
- Database changes require forward migration and rollback notes

## Source of truth
- Behavioral truth: openspec/specs/
- Active change truth: openspec/changes/<change-id>/
- During implementation, tasks.md is the only task list.
- If code and artifacts diverge, stop and reconcile the artifacts first.

## Workflow
- Unknown problem: OpenSpec Explore; no production code.
- Known change: OpenSpec Propose; human reviews artifacts before Apply.
- During Apply, use Superpowers TDD/debug/review/verification skills as appropriate.
- Never archive before local verification, CI success, and human acceptance.

## Verification
- Backend: ./mvnw -B -ntp verify
- Frontend: cd frontend && npm ci && npm run lint && npm run test:ci && npm run build
- Specs: npx openspec validate --all --strict

## Safety
- Never commit secrets, tokens, local credentials, generated binaries, or production data.
- Do not change public API, database schema, auth, money, or permissions without explicit spec coverage.
- Preserve existing user changes; keep diffs scoped to the active change.

不要在 AGENTS.md 里重复几十页教程。它应该短、具体、可执行；格式化、静态检查和依赖策略等机械约束应尽量交给脚本和 CI。

#CI 作为确定性 Harness

这里的 Harness 是 AI 外部的执行环境和反馈装置：它把“完成”的定义变成机器命令，把失败日志反馈给 Codex，再进入下一轮修正。CI 不应只执行单元测试，还要覆盖规格结构、编译、静态检查、契约、集成和前端构建。

#固定 OpenSpec CI 版本

开发机可以全局安装最新版；CI 不要每次解析浮动的 latest。在项目根目录用精确版本写入 lockfile：

bash
npm install --save-dev --save-exact @fission-ai/openspec@latest
git add package.json package-lock.json

此命令执行当下会把具体版本写入 package.json 和 package-lock.json；之后 CI 使用 npm ci，不再随上游版本漂移。升级时由人显式执行并检查生成技能是否需要 openspec update。

#GitLab CI 示例

yaml
stages:
  - validate
  - test
  - build

spec-validate:
  stage: validate
  image: node:22-alpine
  script:
    - npm ci
    - npx openspec --no-color validate --all --strict

backend-verify:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  cache:
    key: maven-${CI_COMMIT_REF_SLUG}
    paths:
      - .m2/repository
  variables:
    MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  script:
    - ./mvnw -B -ntp verify
  artifacts:
    when: always
    reports:
      junit:
        - "**/target/surefire-reports/TEST-*.xml"
        - "**/target/failsafe-reports/TEST-*.xml"

frontend-verify:
  stage: test
  image: node:22-alpine
  before_script:
    - cd frontend
  script:
    - npm ci
    - npm run lint
    - npm run test:ci
    - npm run build
  artifacts:
    paths:
      - frontend/dist/

package-backend:
  stage: build
  image: maven:3.9-eclipse-temurin-21
  script:
    - ./mvnw -B -ntp -DskipTests package
  artifacts:
    paths:
      - "**/target/*.jar"
  needs:
    - backend-verify

示例中的镜像和脚本名应按仓库实际情况固定，例如前端可能使用 pnpm、Vitest 或 Playwright。数据库相关功能还应增加 Testcontainers 集成测试；接口变更增加 OpenAPI/契约检查；高风险项目再加 SAST、依赖和镜像扫描。

#门禁与完成定义

  1. openspec validate --all --strict 通过，变更规格结构完整。
  2. 新增或修改行为都有先失败后通过的自动化测试。
  3. Java verify、前端 lint/test/build、契约和迁移检查通过。
  4. codex review --base main 没有未处理的高优先级发现。
  5. 人工确认范围、用户体验、数据风险、可观测性和回滚方式。
  6. 合并后的默认分支 CI 通过，才执行 OpenSpec 归档或把归档放入同一合并请求。

Codex 的评审是有价值的第二意见，但不应该成为唯一的阻塞门禁。真正阻塞流水线的检查应尽可能确定、快速、可复现。

#统一日常操作模式

  1. 同步与基线：更新 main，确认工作区干净，运行现有验证。
  2. 识别工作类型：未知问题用 Explore；已知 bug/feature 用 Propose；极小机械修正可按团队规则走轻量路径。
  3. 一变更一分支：change-id 与分支名保持可追踪，例如 feature/add-order-cancellation。
  4. 人工审规格：重点审 proposal 的范围、spec 的 Given/When/Then、design 的边界和 tasks 的验收命令。
  5. 逐任务实现：一次只选一个 OpenSpec task，调用 Superpowers 的 TDD 或 systematic-debugging。
  6. 快速反馈：先跑最小相关测试，再跑模块测试，最后跑完整本地验证。
  7. 独立评审：让 Codex 根据 spec、tasks 和 diff 做评审；修复后重新验证。
  8. CI 证据：推送分支，由 GitLab CI 重新从干净环境验证。
  9. 合并与归档：人确认后合并；归档把 delta spec 变成当前真相。

#示例一：新项目启动

场景：启动一个“AI 学习计划”全栈系统，后端 Java 21 + Spring Boot，前端 TypeScript，第一条纵向切片是创建并查看学习计划。

#1. 初始化仓库和工具

bash
mkdir ai-study-planner
cd ai-study-planner
git init -b main

# 先创建后端、前端、Wrapper 和最小 README/AGENTS.md
# 再初始化 OpenSpec
openspec init --tools codex

# 固定 CI 使用的 OpenSpec 版本
npm install --save-dev --save-exact @fission-ai/openspec@latest

git add .
git commit -m "chore: initialize project harness"

初始化阶段只建立能跑通的工程骨架：后端健康检查、前端空壳、基础测试和 CI。不要一次要求 Codex 生成完整产品。

#2. 探索边界并创建首个变更

text
使用 $openspec-explore，并结合 Superpowers brainstorming，
探索 AI 学习计划系统的第一条最小纵向切片。

约束：
- Java 21 + Spring Boot + PostgreSQL；
- TypeScript 前端；
- 第一版不做模型训练，只通过模型 API 生成建议；
- 给出三种切片方案、推荐方案、暂不做事项和验收信号；
- 只探索，不创建文件，不写代码。

确认第一条切片后再输入：

text
使用 $openspec-propose 创建 change-id=bootstrap-study-plan-slice。

范围：
- POST /api/study-plans 创建计划；
- GET /api/study-plans/{id} 查询计划；
- PostgreSQL 持久化；
- 前端创建表单与详情页；
- 后端单元/集成测试、前端组件测试、OpenAPI 契约；
- 明确错误处理、可观测性和回滚方式。

不实现登录、支付、推荐系统和异步任务。
创建后停止，等我审 proposal/specs/design/tasks。

#3. 实现与收尾

text
使用 $openspec-apply-change 实现 bootstrap-study-plan-slice。
以 tasks.md 为唯一任务清单。
每个任务使用 Superpowers test-driven-development：
先写失败测试并展示 RED 证据，再做最小实现，最后重构。
每完成一个任务运行最小相关测试并更新 tasks.md。
遇到设计偏差先更新 OpenSpec artifact，不要静默扩大范围。
bash
npx openspec validate --all --strict
./mvnw -B -ntp verify
cd frontend && npm ci && npm run lint && npm run test:ci && npm run build
cd ..
codex review --base main
git push -u origin feature/bootstrap-study-plan-slice

CI 和人工验收完成后，使用 $openspec-archive-change 归档。首个项目切片完成的标准不是“页面看起来能开”，而是规格、后端、前端、数据库、测试和流水线共同闭环。

#示例二：Bugfix

场景：用户双击“提交订单”导致两笔订单。先找根因，再把正确行为变成回归规格和测试。

#1. 只诊断，不抢修

text
使用 $openspec-explore 和 Superpowers systematic-debugging，
诊断“相同用户快速双击提交会创建两笔订单”。

要求：
- 先稳定复现并定位请求、事务、唯一约束和前端按钮状态；
- 区分症状、近因和根因；
- 比较前端防抖、幂等键、数据库唯一约束三层方案；
- 不修改生产代码；
- 输出建议的正确行为和回归测试入口。

仅做前端禁用按钮通常不能覆盖重试、网络超时和多端并发；若业务语义要求幂等，应由服务端和数据库共同保证，前端只改善体验。

#2. 规格化正确行为

text
使用 $openspec-propose 创建 fix-duplicate-order-submit。
把正确行为写成 MODIFIED requirement：
GIVEN 同一用户和同一 Idempotency-Key，
WHEN 在有效期内并发提交相同订单，
THEN 只创建一笔订单，并返回同一订单标识。

design 必须覆盖唯一约束、事务边界、冲突响应、前端交互、
日志指标、兼容性和数据库迁移回滚。

审完规格后执行 Apply，并明确要求先写一个能稳定失败的并发集成测试。只有见过测试在旧代码上失败，才能证明它真的覆盖了缺陷。

#3. 验证矩阵

  • 同 key、同 payload、并发请求：只产生一个订单。
  • 同 key、不同 payload：返回明确冲突，不复用错误结果。
  • 不同 key：按两个独立请求处理。
  • 事务回滚后重试：不会留下半成品或永久占位。
  • 前端提交中禁用按钮，但后端测试不依赖此行为。
  • 数据库迁移可在测试环境执行，并有回滚或向前修复策略。

本地验证、codex review --base main、CI 和人工确认完成后再归档。OpenSpec 官方也建议 Bugfix 描述“正确行为”，而不是只写“修复 bug”。OpenSpec Bugfix Recipe

#示例三：新功能开发

场景：增加订单取消功能，涉及权限、状态机、库存释放、前端按钮、审计和并发。

#1. 创建可审规格

text
使用 $openspec-propose 创建 add-order-cancellation。

业务规则：
- 只有订单所有者或客服角色可取消；
- PAID 之前允许取消，SHIPPED 之后拒绝；
- 取消成功必须释放预占库存并写审计事件；
- 重复取消幂等；
- 前端根据状态显示按钮并呈现冲突原因。

要求 proposal 明确非目标；
spec 使用 Given/When/Then 覆盖成功、越权、状态冲突和重复请求；
design 说明状态机、并发控制、事务、API、事件、监控和回滚；
tasks 按数据库→领域→API→前端→可观测性→验证拆分。
完成 artifacts 后停止等待评审。

#2. 每个任务执行同一个 Loop

text
读取 add-order-cancellation 的当前 spec、design 和 tasks。
只执行第一个未完成任务。

使用 Superpowers test-driven-development：
1. 选出这个任务对应的一个可观察行为；
2. 写最小失败测试并运行；
3. 写最小生产代码使它通过；
4. 重构并运行相关测试；
5. 对照 spec 做自检；
6. 更新 tasks.md 和验证证据；
7. 停止，等待下一个任务。

任务粒度过大时先拆分，不要让一次 Codex turn 同时改数据库、领域、接口和整页前端。小步的价值是失败范围更小、上下文更聚焦、评审更具体。

#3. 全栈验收

  • 领域状态转换和权限规则有纯单元测试。
  • 数据库并发和事务用集成测试验证，而不是只 mock repository。
  • OpenAPI 契约、错误码和前端类型同步。
  • 前端按钮可见性、加载、成功和冲突状态有组件或端到端测试。
  • 日志不含敏感数据；指标能区分成功、越权、冲突和内部失败。
  • CI 从干净环境通过，人工走通关键路径和回滚策略。

#示例四：新功能探索

场景：想给学习系统增加 RAG 问答，但尚不确定向量库、切分策略、数据权限、成本和评测方式。此时目标不是“尽快写代码”，而是减少未知数。

#1. 无承诺模式

text
使用 $openspec-explore 和 Superpowers brainstorming，
探索“为学习资料增加 RAG 问答”。

先读取现有代码和规格，再回答：
- 用户问题和成功信号是什么；
- 数据来源、更新频率、租户隔离和删除要求是什么；
- pgvector、专用向量库、托管检索三种方案的取舍；
- Java/Spring AI 接入边界；
- chunk、embedding、rerank、引用和拒答策略；
- 离线评测集、线上指标、成本和延迟预算；
- 必须做的 spike 与可延期项。

只探索，不创建 OpenSpec change，不改生产代码。
最后给出推荐方案、反对理由、未知项和 go/no-go 条件。

Explore 官方定义为“不创建 artifact 的思考伙伴”。如果需要 spike，应把它放在独立临时分支或工作树中，明确“不进入生产”，并用实验问题、时间盒和退出条件约束。

#2. 探索必须有出口

结论下一步不要做
信息足够，值得做用 $openspec-propose 创建小范围 change把整份脑暴直接当实现任务
关键假设待验证创建时间盒 spike，产出数据和结论把实验代码偷偷演变成生产代码
收益不足或风险过高记录 no-go 原因和重新评估条件为了“已经研究过”而强行启动
范围过大拆成 ingestion、retrieval、answer、evaluation 等独立变更一个 change 包揽整个 AI 平台

当结论成熟后，新会话中创建 proposal，避免把长篇探索上下文全部带入实现阶段。OpenSpec 官方建议在不确定时先 Explore，再将已收敛的洞察转换为 Propose。OpenSpec Explore Recipe

#两人小团队推荐配置

两人且基本一人一个项目时，不需要设立流程管理员。每个项目只维护四类共享资产：简短 AGENTS.md、OpenSpec 目录、一个本地验证入口、GitLab CI。

  • 项目负责人拥有 change，负责 proposal/design/tasks 与代码一致。
  • 另一人只在 proposal/design 和合并请求两个关键点做轻量交叉评审。
  • 高风险变更（认证、权限、金额、删除、迁移、外部 API）必须交叉评审；低风险小修可异步。
  • 每月只复盘重复出现的问题，把能自动化的规则沉淀到测试、脚本或 CI；判断性经验才写入 AGENTS/skill。
  • 不要一开始自建庞大流程平台。先连续使用 4～6 周，留下真正反复出现的约束。

#常见失败与修正

失败方式原因修正
在 Codex 输入 /opsx:propose 无反应Codex 的 OpenSpec 集成是 skills-only使用 $openspec-propose 或自然语言点名技能
输入 /brainstorming 找不到Superpowers 在 Codex 中也是技能自然语言要求使用 brainstorming，或从技能补全选择
OpenSpec 与 Superpowers 各有一份计划两个顶层指挥流程竞争OpenSpec artifacts 是唯一计划，Superpowers 只做局部执行
AI 说“测试通过”但没有日志声明替代了证据运行明确命令，保留退出码、报告和 CI 链接
一条任务改几十个文件change 或 task 过大按可观察行为和架构边界拆分
CI 每次安装 latest上游更新导致不可复现开发机用 latest，项目 lockfile 固定 CI 版本
Bugfix 只改前端表现没有找到系统根因systematic debugging + 服务端/数据库回归测试
代码完成后才补规格规格失去约束作用先审 artifact；实现发现偏差时先同步 artifact
CI 里直接让 Codex 自动修代码权限、成本和非确定性扩大默认只跑确定性门禁；AI 修复在有审查的开发分支进行
