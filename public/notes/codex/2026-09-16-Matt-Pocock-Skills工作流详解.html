Matt Pocock Skills：整套工作流、原理与教程设计

阅读目标：先理解这套工作流怎样组织 AI 开发，再讨论如何制作适合 Java 开发者的使用教程与原理说明。

核验日期：2026-09-16。源码快照 959a8e9，提交时间 2026-09-15 UTC；该快照的 Claude 插件清单版本为 1.2.3。这里描述的是固定提交，不保证今后的安装结果与本文完全一致。

本次范围：本页提供介绍和路线导航；配套教程已生成独立练习环境、订单取消实战与原理说明。真实代码验证记录见实战页；示范提示词不代表已经执行过整套 Agent 会话。

核心结论 · 主线流程 · 技能地图 · 工作原理 · Java 案例 · 教程方案 · 参考资料

核心结论

  1. 研究对象是 Matt Pocock 的官方 mattpocock/skills。它把需求澄清、领域建模、任务拆分、测试和审查等工程做法写成可组合的 Agent Skills。主流程由人选择阶段，Agent 在阶段内部执行具体工作。官方 README
  2. 常见大需求路线：setup → grill-with-docs → to-spec → to-tickets → implement，其中实现阶段调用 tdd 和 code-review。小功能可在澄清后直接 implement；跨很多会话且尚不清晰的大项目，先走 wayfinder。ask-matt
  3. 值得学的是五种约束：先消除歧义；保持统一术语；按完整行为切任务；用真实反馈修正实现；把需求符合性与代码质量分开审查。
  4. 技能正文是给模型执行的操作规程。真正读文件、运行命令、访问 Issue、调用子代理的是宿主 Agent。执行效果仍取决于模型、工具权限、项目测试及人工决策。OpenAI：Skills 概念
  5. 教程应固定源码版本。当前实现与旧文章已有差别，包括命名、访谈节奏和 TDD 的重构时机。本文把源码事实、教学解释和个人建议分开标注。

主线流程：从模糊想法到可验证的代码

按需求大小选择路径
首次使用：setup-matt-pocock-skills
grill-with-docs：澄清目标、术语、边界和决策
小功能 → implement
跨会话需求 → to-spec → to-tickets → 逐任务 implement
实现内部：TDD 红 → 绿 → code-review → 处理发现的问题 → 验证

这是阅读导航，代表建议的阶段关系，并非输入第一条命令后自动串完全部阶段的脚本。当前路由技能 ask-matt 用于建议你选哪条路线。ask-matt

1. setup：让所有技能遵守项目的实际约定

setup-matt-pocock-skills 先检查仓库已有配置，再确定任务放在哪里、标签怎么映射、术语表和 ADR 怎么布局。当前有 GitHub、GitLab、本地 Markdown 模板；其他系统可以记录自定义操作方式。其输出包括项目规则中的入口指针，以及任务系统、领域文档、可选分诊标签的说明。setup-matt-pocock-skills

对 Java 开发者，可以类比为“为一组业务服务提供共享配置”：后面的技能不用各自猜测该调用哪个任务系统。但 setup 是提示词驱动的配置流程，不是具备事务回滚保证的安装程序。安装技能文件与运行项目 setup 是两个步骤。

2. grill-with-docs：把「我大概想要」变成共同理解

例如你说“给订单加取消功能”，Agent 需要弄清楚：取消与退款是否相同；哪些状态可取消；谁能操作；重复请求如何处理；支付与取消同时发生时谁成功。

当前 grill-with-docs 的正文非常短：组合 grilling 与 domain-modeling。前者推进决策树，后者核对代码与业务术语，并及时更新术语表和必要的 ADR。两者组合让访谈的结果能延续到后续会话。grill-with-docs domain-modeling

职责分工：项目已有状态枚举、数据库约束等事实由 Agent 查；取消政策、业务范围等决策由你定。当前访谈会给出推荐答案，但需要真实用户回答，不能让 Agent 自问自答充当需求确认。

3. to-spec：把讨论固化成可检查的规格

to-spec 从已有讨论形成问题说明、解决方案、用户故事、实现决策、测试决策和范围边界。原则上不再重新进行完整需求访谈，但当前正文要求核对测试所经过的公开接口，即测试切入点（seam）。随后将规格发布到已配置的任务系统。to-spec

这里的 Spec 也不能简单等同于“全部代码实现步骤”。它优先约定用户能得到什么、接口与状态如何表现、哪些情况不在本次范围。源码要求避免散布容易过期的具体文件路径和代码片段；原型中能精准表达决策的少量代码是例外。

4. to-tickets：把需求切成能交付的完整行为

垂直切片（vertical slice）的意思是：一个任务足以穿过必要的数据、后端、前端与测试层，交付一小段完整能力。后端项目没有前端时，可以用 API 与验收测试完成这一条路径，无需为了形式新增界面。

比如“用户取消一笔未支付订单并看见取消结果”比“先建全部表、再写全部 Service、最后补全部页面”更适合作为第一个实现任务。后者的每一层完成后仍难以验证真实使用效果。

每个任务写明验收条件和 Blocked by，大小以一个新的上下文窗口能够完成为目标。拆分先供你审阅，再写入任务系统。当前本地模式一任务一文件；宽范围机械重构则允许采用 expand–contract：先兼容新旧形式，再分批迁移，最后删除旧形式。to-tickets

5. implement：以一个行为为单位获取反馈

implement 从规格或任务出发，在约定好的 seam 上尽可能使用 tdd；过程中常做类型检查和单文件测试，最后执行全量测试，完成后调用 code-review。当前技能还包含提交到当前分支的指令。教程应事先明确分支与提交约定。implement

tdd 要求每个周期只处理一个切片：先证明测试能失败，再补足使它通过的代码。测试观察公开接口的行为，避免把内部类之间的调用次数、私有方法结构当成业务正确性的替代品。当前版本把重构安排到审查阶段。tdd

Java 适配建议：“类型检查”对应现有 Maven/Gradle 编译与静态检查；测试可以选业务接口测试、HTTP 集成测试或真实数据库集成测试，具体取决于验收行为。不要把 TypeScript 生态的命令机械换名后就当成完整 Java 教程。

6. code-review：把「做得对」与「做的是对的需求」分开

审查轴主要对照订单取消例子
Standards仓库编码约定与代码异味启发式命名不清、重复状态判断、为未要求的能力加入抽象。
Spec原始 Issue 或规格遗漏幂等行为；允许取消已发货订单；额外实现未授权的退款。

当前技能安排两个子代理分别审查，保留各轴报告；没有规格时，Spec 轴应明确跳过。这样可以减少“代码很整洁，因此需求肯定正确”的判断混淆，但不能保证两个模型完全独立或审查绝无遗漏。code-review

工作原理：文件为什么能改变 Agent 的开发方式

原理一：宿主加载技能，模型按规程选择工具

执行关系
用户请求 + 已有项目规则
发现技能 → 读取 SKILL.md → 按需读取参考文件
模型决定下一步 → 宿主执行文件、终端、Issue 或子代理工具
工具返回真实结果 → 对照完成条件 → 继续或进入下一阶段

OpenAI 文档说明，技能先通过名称和描述被发现，详细正文在需要时加载。它能够打包参考资料与脚本；如果需要网络数据与外部操作，则还需要宿主工具或 MCP 连接提供能力。OpenAI：Skills 概念 OpenAI：技能加载、安装与调用

Java 类比：SKILL.md 像操作规程，Agent 像能阅读规程的执行者，终端与 MCP 像能力接口，测试像结果校验。类比的边界在于：自然语言规程不会被 JVM 编译成确定性控制流，无法仅凭“写了必须”就保证每次照做。

原理二：把阶段入口与复用能力分开

人选择何时进行访谈、写规格或实现；这些入口复用底层能力。最直观的源码例子是 grill-with-docs 组合 grilling 与 domain-modeling。修正一处访谈规则，可以影响多个调用它的流程。grill-with-docs

作者通过手动入口控制流程推进，又用可自动选用的技能复用工程纪律。这里不要把每个技能理解为一个长期驻留的独立 Agent：通常是当前 Agent 切换操作规程，只有明确调度子代理时才创建其他执行上下文。

原理三：用持久产物接住会话中的决定

产物回答什么避免放入什么
CONTEXT.md业务术语各自是什么意思？当前源码明确规定它是术语表；不塞任务清单、实现设计和聊天记录。
ADR为什么在重要取舍中选这个方案？不为每个普通变量命名或容易反悔的小决定写 ADR。
Spec这次要交付什么，约束和范围是什么？不当成长期领域词典。
Ticket这一小段要做什么、怎样验收、依赖谁？不能只写“同上”或依赖上一会话的记忆。
Handoff下一会话从哪里继续，应该阅读哪些原始产物？已有文档以链接引用，避免复制成另一份真相。

这是外部化上下文：模型不会因生成文件自动获得永久记忆；新会话必须读取这些材料。术语表与 ADR 的职责来自 domain-modeling，交接文档的引用原则来自 handoff。

原理四：让错误尽早变成可见信号

规格限制“做什么”，测试证明某一行为发生，编译和静态检查发现机械错误，审查检查测试不容易表达的需求偏差与设计问题。这些反馈覆盖的错误类型不同。

例如把取消测试写成“断言内部 repository.save 调用过一次”，可能无法发现保存了错误状态。通过取消接口执行动作，再通过查询接口观察状态，能更直接地对照用户行为；涉及并发与事务时仍需相应环境下的专门验收。tdd Mock 使用原则

原理五：统一语言与深模块降低理解成本

统一语言：把“取消订单”和“退款”明确分开，规格、代码、测试就能沿用同一概念。它借鉴 DDD 的语言纪律，但使用这套技能不等于必须引入完整 DDD 架构。

深模块：调用者学习一个相对简单的接口，就能获得有意义的能力。比如取消订单模块在内部处理状态合法性、幂等与并发规则，调用方不需要自己按顺序编排一组脆弱的底层方法。这里的“深”是隐藏复杂性所带来的价值，不是多写代码、增加继承层级或建立巨大 Service。codebase-design

上下文设计：writing-for-agents 强调把规则放在一个权威位置，并通过条件明确的指针按需读取；它也讨论完成条件和人的记忆负担。这是作者的提示词设计方法，不能据此声称有通用、定量的成功率保证。writing-for-agents

用 Java 场景串起来：给订单增加取消能力

以下是建议的教学案例，不是上游自带的 Java 示例，也不是已经执行的实验。选择它是因为需求不大，却足以暴露术语、状态、幂等、并发、数据库与界面反馈的关系。

阶段你提供什么Agent 形成什么如何判断这一阶段完成
访谈“用户需要取消未支付订单”及业务取舍明确取消范围、角色、状态规则与重复请求结果取消与退款等歧义消失，关键决策有人作答
领域记录确认业务词义Order、Cancellation、Refund 的统一定义规格与现有代码使用相同含义；矛盾已被记录或解决
规格确认 API/行为与测试切入点成功、非法状态、越权、重复请求、并发冲突的验收约定能说明哪些情况必须支持，哪些暂不支持
任务拆分确认粒度与依赖每张任务有完整行为、验收条件和阻塞关系任务可以在新会话中独立读懂
实现已确认任务、可运行的工程环境逐行为测试与实现、真实执行结果失败用例先出现，再通过；约定范围内验证完成
审查明确比较基线、任务原文与编码标准Standards / Spec 两份发现重要问题处理完并再次验证，结果可追溯

一种候选拆分：①本人取消未支付订单并看到结果；②重复取消获得约定的幂等结果，依赖①；③已支付/已发货和非本人请求被拒绝，依赖①；④支付与取消并发时保持约定的一致性，依赖①及支付接口。每张任务覆盖必要的接口、数据和测试。授权保护也可并入①，具体以项目安全边界与部署节奏决定。

案例的教学重点：②和③都可能在①完成后开始，但“没有任务依赖”不代表文件没有冲突。是否并行、如何隔离分支与集成，需要另行设计，稳定版的 to-tickets 不会自动解决这些问题。

其他路线：什么情况下不用走完整主线

你当前的处境适合的入口关键区别

学习这套工作流时需要认识的边界

  1. 没有统一自动执行的强保证。规程可以约束模型行为，但权限、编译、测试和 CI 才能提供相应层面的机械检查。
  2. “整套”不等于每次全用。按需选择可以减少不必要的文档与访谈；对一个已明确的小修复完整走一轮大需求流程可能没有收益。
  3. 测试切入点要贴合项目。上游偏向少量、高层、行为可观察的 seam。这不等于 Java 项目一律禁止纯函数单元测试，也不等于所有测试都必须启动完整 Spring 容器。
  4. 源码存在值得教程验证的衔接问题。implement 写的是审查后提交，而 code-review 明确给出的比较命令是 git diff <fixed-point>...HEAD。按 Git 语义，它不会包括尚未提交的工作区改动。因此照抄默认流程可能漏审刚完成的代码；实操教程应明确审查已提交分支还是工作区/暂存区，并用实际 diff 核对覆盖范围。这是对两份源码的静态推断，尚未通过完整演示验证。implement code-review
  5. 清理上下文有信息损失。没有独立完整的任务与决策记录就清空会话，可能丢掉“为什么这样做”；上下文越长也不必然越好。
  6. 没有在本次调研中得到可支持定量结论的对照实验。可以说明其设计意图与适用场景，不能声称它比其他工作流快多少、少多少 Bug 或必然省 token。

配套教程与推荐阅读顺序

建议先形成两条互相链接的主线：一本可以照着操作的使用教程，以及一篇能解释选择理由的原理说明。以同一个 Java 案例贯穿，避免每个技能换一个项目，让读者看不到产物怎样衔接。以下课程已生成；示例以 HTML 代码块为唯一来源，可提取到独立目录运行。

材料主要内容验收标准
总览（本页）定位、主线、技能地图、原理概要与边界能根据任务大小说出应从哪个技能进入。
使用教程 · 环境与最小闭环固定技能版本、安装依赖、项目 setup、一个小功能用最少阶段完成一次真实测试与审查。
使用教程 · 完整需求实战订单取消需求访谈 → 规格 → 任务依赖 → 逐任务实现留下完整产物链，能够从全新会话接续任务。
工作流原理说明发现与加载、组合、决策树、文档职责、垂直切片、seam、反馈与审查能解释每个环节解决哪类失败，以及何时应该省略它。
进阶案例（第二阶段再做）故障诊断、架构改善、wayfinder、大项目上下文管理能处理需求尚不清晰或工程反馈不足的情况。

每个实操步骤统一包含：前置状态 → 可直接使用的中文请求 → Agent 应做什么 → 应产生什么文件/任务 → 人要决定什么 → 如何验证 → 常见偏差及恢复方式。模拟对话与真实运行记录必须明确区分。

制作顺序建议：①固定源码与工具版本；②准备一个可运行的 Spring Boot/Maven 示例仓库；③实际跑通一个最小任务；④记录输入、产物、测试和审查证据；⑤扩展成完整需求；⑥再用这些证据写原理章节。框架版本和依赖在教程实施时重新核验。

当前更推荐的范围：以 Codex 为主，保留 Claude Code 的调用差异说明；Java 后端为核心，用一个轻量界面展示最终行为。先做小功能，再覆盖完整需求，不必第一章就引入微服务、复杂前端、向量数据库或多 Agent 自动编排。

已采用的案例起点：先提供一个最小可运行的 Spring Boot 订单系统，再用这套工作流加入取消能力。依次阅读安装环境、完整实战、原理说明；基础版、单个失败测试版和完成版可分别提取。
