#Superpowers 详细介绍：Codex 的技能化软件开发方法

整理日期：2026-07-24
适用对象：使用 Codex CLI 或 Codex App 的 Java 全栈开发者
项目：obra/superpowers
当前资料基线：官方仓库 main 分支；最新可见发布说明为 v6.2.0（2026-07-23）

相关笔记：Codex 全栈开发最佳实践 · AIDLC 详细介绍 · AIDLC 与 Superpowers 差异分析

#核心结论

Superpowers 不是一个更强的模型，也不是单纯的提示词合集。它是一套安装到编码智能体中的“可组合 Skills + 强制开发流程”，目标是让智能体遵守一套可复现的软件工程方法：

text
先理解需求
→ 形成并批准设计
→ 编写可执行计划
→ 在隔离分支中按 TDD 实现
→ 每个任务独立审查
→ 系统化调试
→ 用新鲜证据验证
→ 决定合并、PR 或保留分支

项目将自己定义为“面向编码智能体的完整软件开发方法论”。官方插件描述覆盖规划、TDD、调试、并行执行、代码审查和分支收尾。Superpowers README

它最值得学习的地方不是某一个 Skill，而是把软件工程中的关键闸门强制串联：

  • 未批准设计，不进入实现。
  • 没有失败测试，不写生产代码。
  • 未调查根因，不提出修复。
  • 没有最新验证证据，不宣称完成。
  • Critical/Important 审查问题未解决，不进入下一任务或合并。

#一、Superpowers 解决什么问题

普通 Vibe Coding 很容易形成以下路径：

text
模糊需求 → 立即写代码 → 代码看起来合理 → 宣称完成

其中缺失了：

  • 对真实目标的澄清。
  • 方案比较和设计确认。
  • 对现有代码与约束的调查。
  • 可由其他执行者复现的计划。
  • 失败测试和回归保护。
  • 根因分析。
  • 独立代码审查。
  • 完成证据和安全的 Git 收尾。

Superpowers 将流程改为：

text
需求
  ↓
brainstorming
  ↓ 用户批准设计
writing-plans
  ↓
using-git-worktrees
  ↓
subagent-driven-development / executing-plans
  ├── test-driven-development
  ├── systematic-debugging
  ├── requesting-code-review
  └── verification-before-completion
  ↓
finishing-a-development-branch

这套方法尤其适合：

  • 需求包含多个步骤或多个模块。
  • Java 后端、前端、数据库和 API 契约需要共同修改。
  • Bug 已被尝试修复多次。
  • 重构必须保持现有行为。
  • 团队在意可审查性和长期维护。
  • 希望 Codex 长时间执行但不偏离计划。

#二、它与 Skill、Plugin、Harness 的关系

#1. Skill

每个 Skill 是一个有触发条件和操作规则的开发流程，例如：

  • brainstorming：从想法推导设计。
  • test-driven-development：执行 Red-Green-Refactor。
  • systematic-debugging：先调查根因再修复。
  • verification-before-completion：用命令输出证明完成。

Skill 不是知识文章，而是对 Agent 行为的约束。

#2. Plugin

Superpowers Plugin 把整套 Skills 打包并暴露给 Codex。其插件元数据将能力描述为规划、TDD、调试、协作和交付工作流，并把 skills/ 目录注册为技能来源。Codex plugin manifest

#3. Harness

Harness 是 Codex 工作的外部工程环境，例如：

  • AGENTS.md
  • Maven、npm、Docker 和 Playwright 命令
  • 测试、静态检查和 CI
  • Git 分支和 worktree
  • 子智能体与审查器
  • 文件、日志、接口契约和数据库
  • 沙箱、权限和审批规则

Superpowers 提供方法论和流程；项目 Harness 提供事实、命令和反馈。没有可靠测试和构建命令，Superpowers 也无法凭空证明软件正确。

#三、四项核心哲学

官方 README 总结了四项理念：

  1. Test-Driven Development：始终先写测试。
  2. Systematic over ad-hoc：使用系统过程，不靠猜测。
  3. Complexity reduction：把简单性作为主要目标。
  4. Evidence over claims：以证据代替口头完成声明。Superpowers philosophy

它们可以映射到 Java 全栈开发：

理念Java 全栈实践
TDDJUnit/MockMvc/Testcontainers/Vitest/Playwright 先描述行为
系统化先复现、查日志、跟踪请求与事务，再改代码
降低复杂度小的领域边界、明确接口、YAGNI、避免无关抽象
证据优先Maven/npm/浏览器/数据库验证结果，而非“应该可以”

#四、完整基础工作流

官方基础工作流包括七个阶段：Basic Workflow

#阶段 1：Brainstorming

Agent 在任何创造性工作前先理解项目，逐个澄清问题，比较 2～3 个方案，并分段提交设计供用户确认。

#阶段 2：Using Git Worktrees

设计批准后，进入隔离工作区。Agent 应先检测自己是否已经位于 worktree 或外部管理的隔离环境，再选择平台原生工具或 Git worktree。

#阶段 3：Writing Plans

把批准的设计拆成可执行计划。任务包含准确路径、接口、测试、命令和验证步骤。

#阶段 4：执行计划

两种选择：

  • subagent-driven-development：同一会话中，每个任务派发一个新实现子智能体，再由独立审查智能体检查。
  • executing-plans：在单独会话按计划顺序执行，遇到阻塞或歧义时停止。

#阶段 5：TDD

每个行为按 Red → Green → Refactor：

  1. 写失败测试。
  2. 亲眼看到它因预期原因失败。
  3. 写最小实现。
  4. 看到测试通过。
  5. 清理代码并保持测试通过。

#阶段 6：Code Review

任务结束、重大功能完成及合并前进行审查。Critical 和 Important 问题必须处理。

#阶段 7：Finish Branch

完整测试通过后，根据环境提供合并、创建 PR 或保留分支等选项，由用户决定集成方式。

#五、主要 Skills 详解

#1. using-superpowers

这是整个系统的路由入口。它要求 Agent 在回答、澄清、检查文件或执行动作之前先判断是否存在相关 Skill；只要有可能适用，就先调用 Skill。流程型 Skill 优先于实现型 Skill：

text
“实现功能” → brainstorming → 其他实现 Skill
“修复 Bug” → systematic-debugging → 领域 Skill

用户的直接要求和 AGENTS.md 高于 Superpowers Skill，Skill 又高于 Agent 的默认习惯。因此用户仍然拥有最高任务控制权。using-superpowers

实际影响：

  • Agent 不应在 Skill 检查前“先看一下文件”。
  • Agent 不应以“任务很简单”为由跳过流程。
  • Agent 需要读取当前版本的 Skill，不能凭记忆执行旧流程。
  • 在进入计划模式前，如果尚未完成设计，应先执行 brainstorming。

#2. brainstorming

触发场景：

  • 创建功能、组件、应用。
  • 添加能力。
  • 修改现有行为。
  • 任何需要设计判断的创造性工作。

当前工作流：

  1. 调查项目文件、文档和近期提交。
  2. 必要时及时提供视觉伴侣选项。
  3. 每次只问一个澄清问题。
  4. 提供 2～3 个方案、权衡与推荐。
  5. 分段展示设计并获取批准。
  6. 写入设计文档。
  7. 检查占位符、矛盾、范围和歧义。
  8. 请用户审阅最终设计文档。
  9. 转入 writing-plans。

默认设计文档路径：

text
docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md

设计应覆盖：

  • 架构与模块边界。
  • 组件职责。
  • 数据流。
  • 错误处理。
  • 测试策略。
  • 对现有代码的必要、相关改进。

它会阻止 Agent 在设计批准前写代码或搭脚手架；即使是小功能，也至少需要一个简短设计。brainstorming Skill

对 Java 全栈需求，建议设计阶段额外明确：

  • Spring Boot 模块与领域边界。
  • OpenAPI 请求和响应。
  • 事务、并发和幂等。
  • 数据迁移。
  • React 页面状态。
  • 权限与资源级授权。
  • 观测和发布策略。

#3. using-git-worktrees

目标是让实现与用户当前分支隔离。

关键顺序：

  1. 检查当前是否已处于隔离 worktree。
  2. 区分 worktree、submodule 和普通仓库。
  3. 已隔离时复用当前环境。
  4. 未隔离时先遵循用户偏好或取得同意。
  5. 优先使用当前平台原生 worktree 能力。
  6. 没有原生能力时再使用 git worktree。
  7. 初始化项目并确认测试基线。

它强调“不要和 Harness 对抗”：如果 Codex App 已经提供外部管理的 worktree，就不要再手动创建一个看不见的嵌套环境。using-git-worktrees

适合：

  • 大型功能。
  • 多任务计划。
  • 长时间执行。
  • 与用户现有未提交修改隔离。

不应自行强制：

  • 用户明确要求在当前分支修改。
  • 当前不是 Git 仓库。
  • 平台已在受管 detached HEAD 中运行。

#4. writing-plans

它假设执行计划的人：

  • 会编程。
  • 对当前仓库、工具和业务几乎没有上下文。
  • 可能不擅长设计测试。

计划默认写入：

text
docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md

计划要求：

  • 先检查范围是否包含多个独立系统。
  • 先确定文件结构和职责。
  • 每个任务产生可独立测试的交付。
  • 每一步约为一个 2～5 分钟动作。
  • 明确创建、修改和测试文件的路径。
  • 写明任务的 Consumes/Produces 接口。
  • 写出失败测试、执行命令、最小实现和提交步骤。
  • 采用 TDD、DRY、YAGNI 和频繁提交。

典型任务：

markdown
### Task 2: 订单取消应用服务

**Files**
- Create: `backend/src/main/java/.../CancelOrderService.java`
- Modify: `backend/src/main/java/.../OrderController.java`
- Test: `backend/src/test/java/.../CancelOrderServiceTest.java`

**Interfaces**
- Consumes: `OrderRepository.findById(OrderId)`
- Produces: `CancelOrderResult cancel(CancelOrderCommand)`

- [ ] 写“已发货订单不可取消”的失败测试
- [ ] 运行指定测试并确认因缺少规则失败
- [ ] 实现最小领域规则
- [ ] 再次运行测试并确认通过
- [ ] 运行订单模块测试
- [ ] 提交

当前 Skill 将“一个任务”定义为：带有自己的测试周期、值得独立审查的最小单元，而不是机械地把每个配置文件都拆成任务。writing-plans

#5. test-driven-development

这是最严格的 Skill 之一。

核心规则：

text
没有先看到失败测试，就不写生产代码。

适用：

  • 新功能。
  • Bug 修复。
  • 重构。
  • 行为变化。

可能的例外需要用户同意：

  • 一次性原型。
  • 生成代码。
  • 单纯配置文件。

为什么一定要先看到测试失败：

  • 证明测试确实能感知缺失行为。
  • 排除测试一开始就因为断言无效而“假绿”。
  • 确认失败原因是目标行为，而非环境错误。
  • 为后续回归提供可信基线。

完整周期：

text
RED
  写最小失败测试
  → 运行并确认失败原因
GREEN
  写最小生产代码
  → 运行并确认通过
REFACTOR
  清理命名、重复和结构
  → 再次运行并保持通过

Superpowers 的立场非常强：如果先写了生产代码，默认应删除并从测试重新实现。test-driven-development

在 Java 全栈项目中可分别应用：

层次推荐测试
Domain纯 JUnit，直接验证业务不变量
ApplicationJUnit + Fake/Mock 端口
WebMockMvc/WebTestClient
PersistenceTestcontainers + 真实数据库
Frontend logicVitest
UI componentTesting Library
User flowPlaywright

注意：不要为了遵守 TDD 而写只检查字符串、实现细节或 Mock 调用次数的脆弱测试。测试应保护可观察行为。

#6. subagent-driven-development

这是 Superpowers 的高自动化执行模式。

每个计划任务使用新的实现子智能体，避免它继承控制器会话中的全部历史。实现完成后，再派发任务审查者检查：

  1. 是否符合规格。
  2. 代码质量是否合格。

所有任务完成后，再进行一次整个分支的宽范围审查。

单任务循环：

text
提取任务 brief
→ 派发实现者
→ 实现者按 TDD 实现、测试、提交、自查
→ 生成 review package
→ 派发任务审查者
→ 规格与质量均通过？
    ├── 否：派发修复 → 重新审查
    └── 是：记录任务完成

它区分四种实现状态：

  • DONE
  • DONE_WITH_CONCERNS
  • NEEDS_CONTEXT
  • BLOCKED

不能对 BLOCKED 简单原样重试。应补充上下文、换更合适的模型、拆小任务，或将错误计划升级给用户。

v6.2.0 对 SDD 做了两项重要调整：

  • 按计划建立 .superpowers/sdd/<plan-basename>/ 工作区，避免不同计划之间的进度污染。
  • 修复轮次恢复原实现者，并设置五轮断路器，超出后由控制器判断。v6.2.0 release notes

它的优势：

  • 新上下文更聚焦。
  • 控制器保留全局计划和协调上下文。
  • 每个任务都经过独立审查。
  • 规格问题不会累积到最后。

它的成本：

  • 子智能体调用次数多。
  • 每个任务都有实现与审查开销。
  • 计划质量差时，会稳定地执行错误计划。
  • 高耦合任务不适合拆给独立子智能体。

官方 Skill 明确禁止同时并行派发多个会写同一工作区的实现者，以避免冲突；并行适合真正独立的问题，而不是同一功能的相互依赖任务。subagent-driven-development

#7. executing-plans

这是较简单的顺序计划执行模式：

  1. 加载并批判性审查计划。
  2. 有问题先告知用户。
  3. 创建任务清单。
  4. 按计划逐项执行并验证。
  5. 全部完成后进入分支收尾。

在下列情况必须停止：

  • 缺少依赖。
  • 测试失败且无法解决。
  • 指令含糊。
  • 计划有阻断性缺口。
  • 验证反复失败。

如果 Codex 环境提供子智能体，官方建议优先使用 subagent-driven-development；否则使用 executing-plans。executing-plans

#8. systematic-debugging

核心规则：

text
没有完成根因调查，不提出修复。

适用于：

  • 测试失败。
  • 生产 Bug。
  • 性能问题。
  • 构建失败。
  • 集成异常。
  • 多次修复仍未解决的问题。

四阶段方法：

#Phase 1：Root Cause Investigation

  • 完整阅读错误和堆栈。
  • 稳定复现。
  • 检查近期 diff、依赖和环境变化。
  • 在组件边界收集输入、输出、配置和状态。
  • 从错误位置向上追踪异常数据来源。

#Phase 2：Pattern Analysis

  • 找到仓库内相似的正常实现。
  • 完整理解参考实现。
  • 比较正常和异常路径的差异。

#Phase 3：Hypothesis and Testing

  • 一次提出一个明确假设。
  • 设计最小实验。
  • 根据实验结果确认或否定。
  • 不同时修改多个变量。

#Phase 4：Implementation

  • 创建能重现问题的失败测试。
  • 修复源头而非症状。
  • 运行验证。
  • 检查是否引入新问题。

对 Java 全栈故障，应特别检查边界：

text
浏览器
→ TypeScript Client
→ 网关/Controller
→ Service/Domain
→ Transaction
→ Repository/SQL
→ 消息或外部服务

在每个边界记录请求 ID、关键输入输出、状态和耗时，先确定在哪一层失真，再调查具体组件。systematic-debugging

#9. requesting-code-review

强制审查时点：

  • SDD 中每个任务完成后。
  • 重大功能完成后。
  • 合并到主分支前。

审查者不应获得整个会话历史，而应获得精确的：

  • 实现说明。
  • 计划或需求。
  • 基准 SHA。
  • 结束 SHA。
  • 相关 diff 或 review package。

问题分级：

  • Critical：立即修复，阻止继续。
  • Important：继续之前修复。
  • Minor：记录并在适当时处理。

审查者错误时可以反驳，但必须用代码、测试或明确技术理由证明，而不是因为“不想再改”。requesting-code-review

#10. verification-before-completion

核心规则：

text
没有本轮新鲜验证证据，不宣称完成、修复或通过。

验证闸门：

  1. Identify：什么命令能够证明这项声明？
  2. Run：完整执行该命令。
  3. Read：读取完整输出、退出码和失败数量。
  4. Verify：输出是否确实支持声明？
  5. Claim：只有这时才表述完成。

不同声明需要不同证据：

声明必要证据
测试通过测试命令显示 0 failures
构建成功构建命令 exit 0
Bug 已修复原始复现步骤或回归测试通过
回归测试有效Red-Green 过程得到验证
需求完成逐条对照计划和验收清单
子智能体已完成检查 diff 并独立运行验证

“lint 通过”不能证明“编译成功”，“子智能体说成功”不能证明任务成功，“以前跑过测试”也不是当前提交的证据。verification-before-completion

#11. finishing-a-development-branch

收尾顺序：

text
完整测试
→ 检测 Git/Worktree 环境
→ 确认基础分支
→ 展示集成选项
→ 执行用户选择
→ 验证合并结果
→ 安全清理

普通分支通常提供：

  1. 本地合并回基础分支。
  2. 推送并创建 PR。
  3. 保留当前分支，稍后处理。

在外部管理的 detached HEAD 环境中，不能假定本地合并能力；应提供创建新分支/PR或保留工作区的选项。删除完成成果不再作为普通菜单项，只在用户明确提出时处理。finishing-a-development-branch

#七、一个 Java 全栈实际示例

需求：

text
为订单系统增加“取消订单”功能。
前端使用 React + TypeScript，后端使用 Java 21 + Spring Boot，
数据库使用 PostgreSQL。

#1. Brainstorming 输出

需要澄清：

  • 哪些状态允许取消？
  • 谁可以取消？
  • 是否需要退款？
  • 是否存在并发发货？
  • 是否发送领域事件？
  • 是否允许重复请求？
  • UI 是列表直接取消还是详情页操作？

方案比较：

方案优点风险
同步事务内取消简单、即时反馈外部退款不适合长事务
订单取消 + Outbox 事件一致性好、适合异步退款组件更多
Saga/流程编排适合复杂跨服务流程对简单系统可能过度设计

设计文档：

text
docs/superpowers/specs/2026-07-24-order-cancellation-design.md

#2. Writing Plans 输出

可以拆为：

  1. 领域取消规则与单元测试。
  2. 应用服务、幂等与事务。
  3. 数据库状态/版本字段迁移。
  4. REST API 与错误映射。
  5. OpenAPI 和 TypeScript Client。
  6. 前端取消交互与状态。
  7. Testcontainers 集成测试。
  8. Playwright 用户流程。

#3. TDD 示例

后端 RED：

java
@Test
void shippedOrderCannotBeCancelled() {
    Order order = Order.shipped(anOrderId());

    assertThatThrownBy(() -> order.cancel(aCustomerId()))
        .isInstanceOf(OrderCannotBeCancelledException.class);
}

运行并确认因为领域规则尚不存在而失败，再写最小实现。

前端 RED：

ts
it("disables cancel while the request is pending", async () => {
  // arrange
  // click cancel
  // assert the action is disabled until request completes
});

#4. Systematic Debugging 示例

如果双击取消会返回 500：

  1. 浏览器确认是否发出两个请求。
  2. 检查后端请求 ID 和响应。
  3. 检查两个事务读取的订单版本。
  4. 查看唯一约束或乐观锁异常。
  5. 确认异常是否映射为幂等成功或 409。
  6. 用并发集成测试稳定复现。
  7. 修复源头，而不只是在前端添加 debounce。

#5. Verification 示例

bash
./mvnw -pl backend -Dtest=OrderCancellationTest test
./mvnw -pl backend verify
npm --prefix frontend run lint
npm --prefix frontend run typecheck
npm --prefix frontend test -- --run
npm --prefix frontend run build
npm --prefix e2e test

Agent 需要报告每条命令是否实际执行、退出码、测试数和未验证内容。

#八、Superpowers 与 Vibe Coding、Harness、Loop 的关系

模式Superpowers 的作用
Vibe Coding通过 brainstorming 给模糊想法增加设计闸门
Harness通过 Skills、worktree、计划、测试和审查组织 Codex
Loop通过 TDD、调试、review-fix-re-review 和验证形成闭环

Superpowers 更偏向“严谨工程”而非“完全自由的 Vibe Coding”。

适合保留纯 Vibe 的场景：

  • 一次性视觉探索。
  • 用于讨论的 throwaway prototype。
  • 快速验证库是否可行。

从 Vibe 切换到 Superpowers 完整流程的时点：

  • 原型方向得到认可。
  • 准备接真实 API、数据库或权限。
  • 开始要求兼容、测试、部署和维护。

可以明确告诉 Agent：

text
这一阶段是一次性原型，我批准跳过严格 TDD。
原型确认后，再用 brainstorming → plan → TDD 重新实现生产版本。

#九、优势、成本和局限

#优势

  • 减少 Agent 未理解需求就开始编码。
  • 设计和计划以文件形式沉淀。
  • TDD 和验证降低“看起来完成”的假成功。
  • 系统调试减少随机修改。
  • Worktree 保护用户当前分支。
  • 子智能体使用新鲜、有限上下文。
  • 规格审查与代码质量审查分离。
  • 关键决定保留人工批准权。

#成本

  • 小任务也可能产生设计和计划开销。
  • 严格 TDD 会增加早期步骤。
  • 多智能体审查增加时间、Token 和模型调用。
  • 需要 Git、稳定测试和清晰项目命令。
  • 流程可能与团队现有研发规范冲突。
  • 计划过细会变成低价值的机械清单。

#局限

  • 它无法判断错误的业务规则是否“真实正确”。
  • 测试本身可能错误或覆盖不完整。
  • 不替代架构师、安全负责人和产品负责人。
  • 不自动解决生产数据、权限和合规风险。
  • 高耦合任务不适合强行拆为独立子智能体任务。
  • 模型和 Skill 都可能犯错，最终 diff 和验证仍需检查。
  • 项目快速演进，安装方式和 Skill 细节需要以当前仓库为准。

#十、推荐的使用策略

#1. 不要一开始启用所有复杂性

第一阶段可重点使用：

  • brainstorming
  • writing-plans
  • test-driven-development
  • systematic-debugging
  • verification-before-completion

项目变大后再引入：

  • Git worktrees
  • subagent-driven-development
  • parallel agents
  • task review + whole-branch review

#2. 用 AGENTS.md 提供项目事实

Superpowers 告诉 Agent“应该按什么过程做”，AGENTS.md 应告诉它：

  • Java、Node、Maven/npm 版本。
  • 模块结构。
  • 构建和测试命令。
  • OpenAPI 路径。
  • 数据迁移规则。
  • 安全边界。
  • 发布和验收要求。

#3. 把测试命令做稳定

推荐项目提供：

text
./scripts/verify-fast.sh
./scripts/verify-full.sh

这样 verification-before-completion 能直接获得明确证据。

#4. 控制子智能体任务边界

好的任务：

  • 有精确输入、输出和文件范围。
  • 能独立运行测试。
  • 不与另一任务同时写相同文件。
  • 审查者可以独立判断是否符合规格。

差的任务：

  • “完成整个订单模块”。
  • 同时改变架构、API、数据库和前端。
  • 依赖尚未决定的产品规则。
  • 与多个并行任务共享大量可变状态。

#5. 保留人工闸门

以下操作不应因为 Superpowers 自动化而省略批准：

  • 破坏性数据库迁移。
  • 修改公开 API。
  • 部署生产。
  • 删除数据或分支。
  • 发送外部消息。
  • 改变权限模型。
  • 引入重要新依赖。
  • 合并到受保护分支。

#十一、常用提示词

#新功能

text
使用 Superpowers 工作流设计并实现该功能。
先执行 brainstorming，设计得到我批准后再写计划。

text
使用 systematic-debugging 调查这个问题。
先稳定复现和定位根因，不要直接猜修复方案。
确认根因后写失败回归测试，再做最小修复。
完成前使用 verification-before-completion 提供实际命令和结果。

计划必须包含准确文件路径、接口、TDD 步骤和验证命令。
我批准计划后，使用 subagent-driven-development 执行。

仍需限制修改范围，并在浏览器中验证。

#十二、排查 Superpowers 未生效

#现象：Agent 直接编码，没有 brainstorming

检查：

  1. Plugin 是否已安装并启用。
  2. 是否在安装后新建了会话。
  3. 当前任务是否明确被描述为新功能或行为修改。
  4. 是否有更高优先级用户指令要求跳过。
  5. 显式要求使用 superpowers:brainstorming。

#现象：没有使用子智能体

检查：

  1. Codex 是否启用 multi_agent。
  2. 当前环境是否提供子智能体工具。
  3. 任务是否已有详细计划。
  4. 任务之间是否足够独立。
  5. 并发槽位和平台政策是否允许。

#现象：流程太重

不要直接删除所有闸门，可先：

  • 缩小 brainstorming 设计篇幅。
  • 把需求拆小。
  • 对一次性原型明确批准 TDD 例外。
  • 使用顺序 executing-plans。
  • 只对高风险任务启用多阶段审查。
  • 将机械检查自动化到脚本和 CI。

#现象：计划和代码不一致

  • 停止实现。
  • 回到设计或计划进行修订。
  • 明确哪份文档是当前事实。
  • 重新生成受影响任务。
  • 不要让 Agent 私自选择违反计划或违反审查意见。

#十三、隐私与安全注意事项

仓库说明中提到：brainstorming 的可选视觉伴侣默认可能从 Prime Radiant 网站加载 Logo，并携带 Superpowers 版本信息；项目称不包含项目、提示或智能体详情。可通过下列环境变量禁用：

bash
SUPERPOWERS_DISABLE_TELEMETRY=1

它也声明遵循部分 Harness 的禁用遥测变量。企业或敏感项目应自行检查网络策略、插件代码和版本后再启用。Visual companion telemetry

还应遵循：

  • 不把生产密钥放进提示或测试。
  • 限制网络和文件权限。
  • 使用假数据或脱敏数据。
  • 检查 Plugin/Skill 更新带来的行为变化。
  • 在受管工作区遵循组织策略。

#易错点与局限

  1. 不要把旧版 .codex/INSTALL.md、superpowers-codex CLI 或手动 Skill 链接方式当作当前首选；当前 README 已指向 Codex 插件市场。
  2. Superpowers Skill 在 Codex 中主要通过原生技能发现和自动路由工作，不等同于一组固定斜杠命令。
  3. brainstorming 的强制设计批准会降低 one-shot 速度，这是它主动选择的质量权衡。
  4. subagent-driven-development 的价值依赖清晰计划、独立任务和可靠审查；不满足这些条件时可能更贵而非更快。
  5. “测试先行”不等于“测试必然正确”。仍需检查测试是否验证真实行为。
  6. Superpowers 的发布迭代较快，涉及安装、版本和工具映射时应重新查看官方仓库。

#下一步学习建议

  1. 安装后先用一个小型 Spring Boot 功能体验完整流程。
  2. 比较普通 Codex 与 Superpowers 在需求澄清、diff 大小和测试质量上的差异。
  3. 为项目补齐 AGENTS.md、verify-fast 和 verify-full。
  4. 用一个真实 Bug 练习 systematic-debugging。
  5. 最后再尝试 subagent-driven-development，观察任务拆分和审查成本。
