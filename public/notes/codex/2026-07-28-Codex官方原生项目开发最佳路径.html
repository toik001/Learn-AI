#Codex 官方原生项目开发最佳路径

适用场景：项目没有 AIDLC、OpenSpec、Superpowers、Spec Kit 等额外流程，希望直接使用 Codex 官方能力完成可靠开发。

资料范围：Codex 最新官方手册中的 Best practices、Prompting、Projects and chats、AGENTS.md、Approvals & security、CLI commands、Code review、Worktrees 与 Local environments。检索与整理日期：2026-07-28。

快速阅读： 核心结论 · 范围边界 · 默认闭环 · 任务决策 · Java 模板 · 提示词 · 检查单 · 参考资料

#核心结论

  1. 官方没有一条名为“Codex 项目开发工作流”的强制流程。OpenAI 官方把最佳实践分散在提示、计划、项目与 chat、AGENTS.md、权限、worktree、测试、diff 和 review 等能力中；本文给出的顺序是对这些官方建议的工程化综合。
  2. 默认最优路径是：准备成功跑道 → 明确一个结果 → 复杂任务先计划 → 小步实现 → 真实验证 → diff/review → 人工确认 → Git/PR。Codex 不是只负责写代码，而应读取仓库、执行项目命令、根据反馈修正并交付验证证据。
  3. 一个 chat 对应一个可独立验收的结果。同一问题继续留在原 chat；真正分叉的目标用新 chat 或 fork。不要用一个 chat 承载整个项目的所有需求。
  4. AGENTS.md 是最重要的持久项目接口。写入仓库布局、构建测试命令、工程约定、禁止事项和完成标准；当前任务细节仍放在提示词中。
  5. 复杂、模糊、跨模块任务先用 Plan mode；小而明确的修改直接执行。计划的价值是先读代码、发现约束和确定验证方案，而不是生产一份长文档。
  6. 完成必须有新鲜证据。至少检查 diff，并运行相关编译、测试、lint 或真实应用流程；再用 /review 或对应 review 界面建立第二视角。
  7. 权限默认收紧。从官方默认 sandbox/approval 开始，只为当前明确需要的目录、网络或命令扩大权限；不要把 --yolo 当作日常开发默认值。

#什么叫“官方原生路径”

本文的路径不依赖 AIDLC、OpenSpec、Superpowers 或其他外部工作流。它只依赖 Codex 官方表面、Git 和你的项目已经拥有的命令。

进入默认路径不作为前置条件说明
CLI、IDE 扩展、桌面 App 的 CodexAIDLC / BMAD产品生命周期治理不是完成一次代码任务的前置条件
AGENTS.md、Plan mode、sandbox、approvalOpenSpec / Spec Kit规格系统可在需求复杂后升级，但不是原生闭环必需
Local / Codex-managed worktree、HandoffSuperpowers / 第三方 Skillworktree 是 Codex App 官方隔离能力；Skill 属于后续复用层
/diff、/review、Git/PRMCP、hooks、scheduled tasks外部连接和自动化应在手动路径稳定后再增加
Maven、Gradle、npm、测试、浏览器、CI新建一套流程引擎项目的确定性反馈比额外流程名词更重要

延伸阅读：更宽泛的工程方法见Codex 全栈开发最佳实践；需要比较外部工作流时见AI 开发工作流选型与小团队沉淀指南。

#阶段一：让仓库成为“成功跑道”

  1. 从 Git 根目录启动 Codex；CLI 使用 codex 或 codex -C /path/to/repo，IDE 打开正确 workspace，桌面 App 选择正确 Local project。
  2. 检查当前分支和未提交修改；已有修改属于用户，除非任务要求，不覆盖、不重置、不混入无关重构。
  3. 确认项目的启动、快速验证和完整验证命令可运行。失败时先判断是基线问题还是本次改动。
  4. 密钥和本地配置保持在受控环境变量或忽略文件中，不放入提示、日志或提交。
# Java / Spring Boot 项目的最低可发现入口
./mvnw -q -DskipTests compile
./mvnw -q -Dtest=OrderServiceTest test
./mvnw verify

# Gradle 项目则对应
./gradlew compileJava
./gradlew test
./gradlew check

退出条件：Codex 能指出项目根目录、主要模块、快速检查与完整检查命令；如果基线失败，已经记录具体失败而不是假定代码可用。

#阶段二：用 AGENTS.md 固化持久规则

CLI 可使用 /init 生成起始 AGENTS.md，随后人工精简。官方建议它包含仓库布局、运行方式、构建测试命令、工程约定、PR 预期、限制和完成定义。规则越靠近当前目录优先级越高；根规则负责全局，子目录只写局部差异。

适合写入：Java/Node 版本、Maven/Gradle 命令、模块边界、迁移规则、测试要求、禁止修改区域、交付报告格式。不适合写入：本次需求、临时文件名、一次性验收细节、长篇架构史。

官方建议：保持短、准、可执行；当 Codex 重复犯同一种错误时再做复盘并添加规则，而不是预先写百科全书。

#阶段三：选择环境、隔离和权限

选择推荐场景注意事项
Local当前只有一个任务；需要复用已启动服务、IDE 或本地依赖先确认工作区状态，避免和人工同时改同一文件
Codex-managed worktreeCodex 后台执行、多个 chat 并行、希望隔离当前 checkout桌面 App 官方能力；Git 仓库才可用，默认 detached HEAD
Handoff 到 Local需要在惯用 IDE、本地服务或唯一设备环境中验证由 App 处理 Git 移交，不要在两个 worktree 同时 checkout 同一分支

权限从默认 Auto / workspace-write + on-request 起步。计划或审查阶段可切换只读；只有当前任务确实需要时才允许网络、额外目录或高风险命令。CLI 的 --dangerously-bypass-approvals-and-sandbox（--yolo）只适合外部已经硬化的隔离环境，不是普通项目默认值。

#阶段四：建立任务契约

官方 Best practices 建议提示至少覆盖四件事；本文把官方 Prompting 的 Output / Boundaries 适配为工程任务更常用的 Constraints / Done when：

  • Goal：最终要改变什么用户行为或工程结果。
  • Context：相关模块、文件、错误、截图、接口或复现步骤。
  • Constraints：兼容性、技术栈、安全边界和不能修改的内容。
  • Done when：必须通过的测试、真实行为、diff 范围和交付报告。

一个 chat 对应一个可独立验收的结果。继续修同一问题时保留原 chat 的上下文；当目标真正分叉时使用新 chat 或 /fork。CLI 可用 /status 检查当前工作目录、权限、模型和上下文状态。

#阶段五：复杂任务先 Plan mode

局部、低风险、验收明确的修改可直接执行。出现跨模块、架构选择、需求含糊、数据库迁移或高风险边界时，先使用 Plan mode；CLI 用 /plan，IDE / App 选择计划模式。

要求计划回答：

  1. 当前实现和问题证据是什么；涉及哪些文件、数据和调用链。
  2. 准备采取什么方案，为什么没有选择其他方案。
  3. 哪些契约必须保持，风险和失败回退是什么。
  4. 怎样验证每个步骤，以及最后用什么证据判断完成。

计划不是完成。计划确认后才进入写操作；如果调研发现任务范围和原目标明显不同，应先报告差异，不应悄悄扩大范围。

#阶段六：先检查或复现，再小步实现

  1. Observe：读取相关实现、测试和 Git 状态；Bug 先运行最小复现。
  2. Change：做能让一个验收条件成立的最小修改，不混入无关依赖升级或全库格式化。
  3. Check：立即运行最小相关检查，失败输出成为下一轮输入。
  4. Continue：在同一 chat 中继续，Codex 应简短报告进度、假设和阻塞。

让 Codex 直接操作仓库并运行命令，比让它只输出一大段“请复制以下代码”更符合编码智能体的价值。但外部写操作、生产变更、数据删除和向他人发送内容仍需要明确授权。

#阶段七：从最小相关检查到真实行为

层级Java 全栈示例证明什么
语法 / 编译./mvnw -DskipTests compile、TypeScript typecheck代码至少能被工具链接受
最小相关测试./mvnw -Dtest=OrderServiceTest test本次业务规则和回归点成立
模块 / 集成测试Spring Boot Test、Testcontainers、前端组件测试框架、数据库和模块组合没有破坏
完整检查./mvnw verify、前端生产构建、lint仓库质量门整体通过
真实行为启动服务、调用 API、浏览器验证关键流程用户可见行为和错误状态符合 Done when

“测试通过”必须说明实际运行了什么、退出码或结果是什么。环境缺失、网络受限或测试过慢时，明确列出未验证项；不要用“应该没问题”替代证据。

#阶段八：检查 diff，再建立第二视角

  1. CLI 使用 /diff，IDE / App 使用 diff pane；检查是否只改了授权范围、是否出现秘密、生成物、无关格式化或兼容性变化。
  2. CLI 使用 /review 审查未提交修改、指定 commit 或相对 base branch 的变化；也可以给出自定义关注点。
  3. 对每个 review 发现先核验再修复，不机械接受；修复后重跑受影响测试，并再次 review。
  4. 安全、数据迁移、支付、权限和不可逆动作不能只依赖模型 review，保留人类负责人确认。
/review Focus on:
- Java 并发与事务边界
- 越权访问和跨租户数据
- 数据库迁移的前向/回退兼容
- API 与前端类型是否漂移
- 测试是否真正覆盖失败路径

修复 Important / Critical 问题后：
1. 重跑相关验证；
2. 再运行 /review；
3. 输出仍存在的风险，而不是只说“已完成”。

#阶段九：人工确认后提交与 PR

桌面 App 提供 stage、revert、commit、push 和创建 Pull Request 的 Git 控件；CLI / IDE 可直接使用仓库惯用的 Git 命令。推荐顺序：

  1. 确认最终 diff、测试证据和未验证项。
  2. 按逻辑边界 stage，避免把用户未授权修改一起提交。
  3. 使用描述行为结果的 commit message。
  4. push 分支并创建 PR；PR 描述写目标、主要变化、验证命令、风险与回退。
  5. CI 失败时继续在同一任务上下文修复；新的独立需求开新 chat。

Codex 的 GitHub code review 可以作为 PR 上的额外检查，但它仍是评审工具，不替代项目 CI 和代码所有者审批。

#阶段十：只沉淀重复摩擦

任务结束后问三个问题：

  1. Codex 是否因为缺少稳定项目知识而走错路？如果是，把一条简洁规则写进相应层级的 AGENTS.md。
  2. 是否反复手工输入同一构建或验证命令？如果是，把它变成项目脚本或桌面 App local environment action。
  3. 这类任务是否已经多次稳定重复？只有此时才考虑 Skill、MCP、hook 或 scheduled task；它们是升级项，不是默认路径。

#Java 21 + Spring Boot 项目最小 AGENTS.md

下面是起点，不是需要原样复制的百科。命令必须替换为项目真实可运行的版本。

# Project guidance

## Stack and layout
- Java 21；Spring Boot；使用仓库自带 Maven Wrapper。
- `backend/` 是服务端，`frontend/` 是 TypeScript 前端。
- 数据库变更只通过 `backend/src/main/resources/db/migration/`。

## Working rules
- 修改前检查 `git status`，保留用户已有改动。
- 先阅读相邻实现和测试，遵循现有架构；不做无关重构。
- 不新增生产依赖、不改公开 API、不执行数据库破坏操作，除非任务明确授权。
- 密钥、token、生产数据不得进入代码、提示或日志。

## Verification
- 后端快速检查：`./mvnw -pl backend -DskipTests compile`
- 单测：`./mvnw -pl backend test`
- 完整检查：`./mvnw verify`
- 前端：`npm --prefix frontend test` 和 `npm --prefix frontend run build`
- UI 变化需启动应用，验证 loading、empty、error、success 和移动端。

## Done when
- 行为满足任务验收；相关测试与完整检查通过。
- 检查完整 diff，无无关文件、秘密或生成垃圾。
- 交付说明列出：改了什么、运行了什么、结果、未验证项与风险。

#三套直接可用的任务提示词

功能开发

Goal
在订单服务增加“取消待支付订单”，并在前端订单详情提供入口。

Context
- 后端：backend/order，现有 OrderApplicationService。
- 前端：frontend/src/features/orders。
- API 契约：docs/api/openapi.yaml。

Constraints
- Java 21 + Spring Boot，沿用现有事务和异常模型。
- 不改变已支付订单行为，不引入新生产依赖。
- 权限必须由后端强制，前端隐藏按钮不是授权。

Done when
- 待支付订单可取消；已支付/已取消订单返回稳定业务错误。
- 单元、API 集成和前端组件测试通过。
- 更新 OpenAPI 并验证前后端类型。
- 检查 diff，运行 review，报告命令、结果和未验证项。

这是跨前后端任务：先进入 Plan mode，检查实现后给出方案，再实现。

Bug 修复

Goal
修复并发提交时订单可能重复扣减库存的问题。

Context
- 复现：同时发送两个相同 idempotencyKey 的 POST /orders。
- 相关模块：OrderApplicationService、InventoryRepository。
- 当前失败日志：附在本消息后。

Constraints
- 先复现，不通过删除断言或串行化全部请求掩盖问题。
- 保持现有 API 兼容；不要修改无关模块。

Done when
- 新回归测试在修复前稳定失败、修复后稳定通过。
- 说明根因、并发边界和方案取舍。
- 运行相关测试及 `./mvnw verify`，检查 diff 和 review。

只读审查

只审查当前工作树，不编辑文件。

以 main 为基线，按严重度报告：
1. 正确性和回归；
2. 事务、并发和幂等；
3. 鉴权、租户隔离和敏感数据；
4. API / 数据库兼容；
5. 测试是否覆盖真实失败路径。

每个问题给出 file:line、影响、触发条件和建议修复。
如果没有问题，列出实际检查范围；不要只说 looks good。

#权限与安全基线

场景推荐权限原因
解释、调研、计划、reviewread-only没有必要产生文件修改
普通仓库开发workspace-write + on-request可自动编辑和运行仓库命令，越界或联网再审批

#交付检查单

  • 任务目标单一、可独立验收；没有把整个项目塞进一个 chat。
  • 当前目录、分支和用户已有改动已检查。
  • 持久规则来自正确层级的 AGENTS.md，临时约束在当前提示中。
  • 复杂任务已计划；小任务没有被不必要流程拖慢。
  • 实现范围与授权一致，没有无关重构、依赖升级或格式化。
  • 运行了最小相关检查，并按风险升级到模块、集成、全量和真实行为。
  • 使用 /diff 或 diff pane 检查完整变化。
  • 使用 /review 或等价 Codex review；问题修复后重跑验证。
  • 高风险业务、数据和外部动作经过人工确认。
  • 最终报告包含修改、命令、结果、未验证项、风险和建议下一步。

常见反模式

  • 只说“帮我把项目做完”，不给范围与 Done when。
  • 让 Codex 在错误目录启动，再靠提示描述真正项目。
  • 所有任务都先写长计划，或所有复杂任务都直接开写。
  • 不给测试命令，却要求 Codex 保证没有回归。
  • 只看最终回答，不看 diff、测试输出和真实应用行为。
  • 默认开放全磁盘、全网络或 --yolo。
  • 让多个 live task 同时编辑同一个 checkout。
  • 每次纠正同一个错误，却不更新 AGENTS.md、测试或项目脚本。
