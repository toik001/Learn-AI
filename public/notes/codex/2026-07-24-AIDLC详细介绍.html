#AIDLC 详细介绍：从 AI 辅助编码到可审计的软件交付生命周期

整理日期：2026-07-24
适用对象：以 Java、Spring Boot 为主的全栈开发者
本文范围：AWS 提出的 AI-DLC（AI-Driven Development Life Cycle）方法论及 awslabs/aidlc-workflows 官方实现
资料状态：官方最新可见 Tag 为 v0.1.8；在线指南已描述更新的五阶段、多 Harness 实现，二者存在版本差异

相关笔记：Codex 全栈开发最佳实践 · Superpowers 详细介绍 · AIDLC 与 Superpowers 差异分析

#核心结论

AI-DLC 不是一个模型，也不只是“先写规格再写代码”的提示词模板。它是一套以 AI 为执行中心、以人类为决策中心的软件开发生命周期方法：

text
人类提供目标和业务上下文
        ↓
AI 制定计划、识别不确定项并提出问题
        ↓
人类澄清、选择和批准
        ↓
AI 生成需求、设计、代码、测试与运维产物
        ↓
人类审查结果并决定继续、修改或停止
        ↓
状态、产物、决定和经验持久化

它试图解决两种常见极端：

  • AI 只做补全、文档、单测等局部辅助，整体流程仍然低效。
  • 只给一句需求就让 Agent 自主生成整个应用，人类失去关键决策和质量控制。

AWS 对其核心模式的描述是：AI 负责计划和执行，主动寻求澄清；人类负责关键判断与验证。这个循环在生命周期的每项活动中重复。AWS 方法论介绍

对于 Java 全栈团队，可把它理解为：

text
AI-DLC = 生命周期编排
       + 需求/设计/代码/测试/运维的结构化产物
       + Human-in-the-loop 审批门
       + 可恢复状态与审计日志
       + 面向项目持续演进的规则和知识

最重要的实践判断是：

  1. 它适合需要多阶段协作、可追踪性和生产交付的工作，不应强行套在每个一行修复上。
  2. Scope、Depth 和 Test Strategy 必须按风险调整，否则可能从“减少流程浪费”变成“自动制造文档”。
  3. 第一条端到端 Walking Skeleton 验证成功前，不宜开放后续 Bolt 的自主执行。
  4. AI 生成的计划、代码和验证结论仍需人审；官方仓库也明确提醒生成式 AI 会犯错，并需关注执行成本。官方仓库
  5. 在 Codex 中应把 AI-DLC 作为主编排器使用；若同时引入 Superpowers，应复用其 TDD、调试和验证纪律，不要让两个顶层工作流同时争夺流程控制。

#一、名称与范围辨析

#1. AI-DLC、AIDLC 和 aidlc

AWS 正式写法是 AI-DLC，全称 AI-Driven Development Life Cycle。项目目录、命令和状态文件普遍使用不带连字符的 aidlc，因此社区中也常写作 AIDLC。

本文介绍的是：

  • 方法论：AWS AI-DLC。
  • 开源实现：awslabs/aidlc-workflows。
  • Codex 接入：官方 dist/codex Harness 分发及 $aidlc Skills。

网络上还有使用 AIDLC 缩写的其他框架，例如把字母拆解为 Analyze、Ideate、Develop、Launch、Curate 的流程。它们不是本文所说的 AWS AI-DLC。

#2. 方法论与工具实现不是同一层

层次关注点是否绑定某个 Agent
AI-DLC 方法论AI 与人的职责、生命周期、协作仪式否
aidlc-workflows 核心Stage、Scope、Agent、规则、状态机、审计Harness-neutral
Harness 分发将核心映射为 Codex、Claude Code、Kiro 等原生能力是
项目实践Java 规范、测试命令、架构边界、发布约束由团队定义

当前在线指南说明，同一套核心可生成 Claude Code、Kiro CLI/IDE、Codex CLI 和 opencode 分发；方法论是“做什么”，Harness 分发是“在某个 Agent 环境里怎样运行”。AI-DLC Introduction

#二、为什么需要 AI-DLC

#1. 普通 Vibe Coding 的典型失控路径

text
一句模糊需求
→ Agent 立即改很多文件
→ 测试只覆盖快乐路径
→ 需求、设计和代码逐渐不一致
→ 新会话丢失上下文
→ “应该可以”替代了可验证证据

Vibe Coding 对原型和探索非常有效，但缺少以下机制时，不适合作为生产交付制度：

  • 需求到代码的追踪。
  • 不确定项和关键决策的显式确认。
  • 按风险决定流程深度。
  • 可恢复的长期状态。
  • 分阶段审批与审计。
  • 从本次纠正沉淀长期规则。

#2. 传统 SDLC 的另一端问题

传统流程又可能存在：

  • 长时间规划和会议。
  • 不同角色之间大量交接。
  • 需求、设计、测试文档手工同步。
  • 两周一个 Sprint，但反馈仍然过晚。
  • AI 只是被塞进原有流程的“高级补全工具”。

AI-DLC 的目标不是取消工程纪律，而是让 AI 承担产物生成、分析和执行，让人集中在目标、权衡、风险和验收上。AWS 将其概括为两个维度：

  1. AI Powered Execution with Human Oversight：AI 计划并执行，人类掌握关键决策。
  2. Dynamic Team Collaboration：跨职能成员围绕 AI 的问题和方案实时协作。

#三、核心心智模型

#1. 每项活动都执行同一个小循环

text
Plan → Clarify → Human Validate → Execute → Human Verify

它不是“需求批准一次，后面全自动”，而是把人类判断嵌入每个需要判断的节点。

#2. Small Mob, Broad Agents

当前实现强调“小型 Mob、宽能力 Agent”，而不是建立几十个极窄的专家：

  • 11 个领域 Agent。
  • 2 个只审查、不写主产物的 Reviewer。
  • 1 个 Adaptive Composer。
  • 合计 14 个 Persona。

领域 Agent 包括 Product、Design、Delivery、Architect、AWS Platform、Compliance、DevSecOps、Developer、Quality、Pipeline & Deploy、Operations。一个 Agent 跨多个阶段参与，以减少瀑布式交接和上下文损耗。Agents

“14 个 Agent”不等于每项任务都要并发启动 14 个子智能体。多数 Stage 是内联执行，只有适合独立协作的 Stage 才使用 subagent、pipeline 或 mob 拓扑。

#3. 确定性引擎与概率性执行分离

当前实现把“下一步应该做什么”与“这一步怎样做好”分开：

text
确定性 Orchestrator
  ├── 选择/确认 Scope
  ├── 判断下一 Stage
  ├── 检查依赖与 Gate
  ├── 维护状态和恢复点
  └── 决定完成或停止
            ↓
Conductor + Agent Persona
  ├── 读取 Stage 输入
  ├── 分析问题
  ├── 生成产物
  ├── 调用工具
  └── 提交人类审批

这样可减少纯提示词编排常见的跳步、重复、伪造进度和会话恢复失败。

#四、版本差异：为什么同时看到三阶段和五阶段

截至 2026-07-24，官方资料存在两套不同代际的表达。

官方资料面主要形态生命周期产物目录Codex 接入
最新可见 Tag v0.1.8 / 仓库 README 的 Rules 包Markdown Steering RulesInception、Construction、Operationsaidlc-docs/核心规则放入 AGENTS.md，细节放入 .aidlc-rule-details/
当前 GitHub Pages 指南 / 多 Harness 分发Skills + Agents + Hooks + TypeScript EngineInitialization、Ideation、Inception、Construction、Operation，共 32 Stageaidlc/spaces/....codex/ + .agents/skills/ + aidlc/ + 合并 AGENTS.md

三阶段是 AWS 最初方法论的主干：

  1. Inception：把业务意图变成需求、故事和 Unit of Work。
  2. Construction：形成架构、领域模型、代码和测试。
  3. Operations：以基础设施即代码、部署和运维完成交付。

五阶段实现是在主干前增加 Initialization、Ideation，并把阶段细化为可编排 Stage。它不是简单地否定三阶段，而是对工具执行模型的扩展。

使用建议：

  • 使用发布包时，严格跟随该 Tag 自带 README。
  • 使用源码中的 dist/codex 时，跟随同一 Commit 的指南。
  • 不要把 v0.1.8 的 AGENTS.md + .aidlc-rule-details 安装法，与新版 $aidlc + .codex + aidlc/spaces 运行法混装。
  • 团队项目应固定 Tag 或 Commit，并在升级前检查目录、状态和命令迁移。
  • 版本差异较大时，先在试验仓库运行 Doctor 和一条小型工作流。

#五、五阶段与 32 个 Stage

当前在线指南的完整生命周期如下。Phases and Stages

#Phase 0：Initialization

目的：初始化工作区、检测项目并创建状态。

Stage内容主要产物
0.1 Workspace Scaffold创建 Intent 记录目录aidlc/spaces/<space>/intents/...
0.2 Workspace Detection检测语言、框架、构建系统和项目类型workspace state
0.3 State Initialization生成 Scope 执行表、状态和审计目录aidlc-state.md、audit/

这三个 Stage 由确定性工具内联执行，不需要审批。

#Phase 1：Ideation

目的：判断项目是否值得做、约束是什么、范围多大、由谁参与。

Stage内容
1.1 Intent Capture & Framing捕获意图、利益相关者和成功目标
1.2 Market Research市场、竞品、Build vs Buy
1.3 Feasibility & Constraints技术可行性、约束、风险和依赖
1.4 Scope Definition范围、非目标、优先级
1.5 Team Formation需要的角色和 Mob 组合
1.6 Rough Mockups低保真界面和用户流
1.7 Approval & Handoff形成 Initiative Brief 并批准进入 Inception

Bugfix、Refactor 等 Scope 会跳过大部分 Ideation，避免小任务套完整产品立项流程。

#Phase 2：Inception

目的：把已批准的意图变成可实现、可测试、可排期的工程定义。

Stage内容Java 全栈对应物
2.1 Reverse EngineeringBrownfield 代码扫描与架构综合Maven 模块、Spring Bean、数据流、调用链
2.2 Practices Discovery发现团队已有实践并请人确认pom.xml、测试模式、CI、包结构
2.3 Requirements Analysis功能和约束需求requirements.md、验收条件
2.4 User Stories用户故事、角色和场景UI/API 端到端故事
2.5 Refined Mockups高保真原型和交互规格React/Vue 页面与状态
2.6 Application Design应用架构、ADR、接口与数据设计Spring 分层、REST、Kafka、PostgreSQL
2.7 Units Generation拆分 Unit of Work 和依赖 DAG后端、前端、迁移、集成测试单元
2.8 Delivery Planning生成 Bolt、人员、风险和外部依赖计划可交付切片和验证顺序

#Phase 3：Construction

目的：按可审查的端到端切片实现系统。

Stage内容执行频率
3.1 Functional Design业务逻辑和规则设计每个 Bolt，按需
3.2 NFR Requirements安全、性能、可靠性等非功能需求每个 Bolt，按需
3.3 NFR DesignNFR 的实现设计每个 Bolt，按需
3.4 Infrastructure Design基础设施和 IaC 设计每个 Bolt，按需
3.5 Code Generation代码与代码文档每个 Bolt
3.6 Build and Test全量构建和测试所有 Bolt 完成后一次
3.7 CI PipelineCI 配置和质量门最后按需执行

Construction 的关键单位是 Bolt：

  • 一个 Bolt 对应一个 Unit，或少量依赖紧密的 Units。
  • 每个 Bolt 运行 3.1～3.5 中属于它的步骤。
  • 没有依赖关系的 Bolt 可以并行成一个 Batch。
  • 3.6 和 3.7 在所有 Bolt 后统一执行。

#Walking Skeleton

第一个 Bolt 是 Walking Skeleton：用最小端到端功能证明技术架构真实可行。

它不应只是一个孤立 Controller、一个前端静态页，或 Mock 掉所有关键边界后宣称链路成立。它应尽可能贯通：

text
浏览器/客户端
→ API
→ 领域逻辑
→ 数据库或关键外部边界
→ 响应
→ 最小自动化验证

Walking Skeleton 必须经过人类 Gate。通过后，系统只询问一次：剩余 Bolt 是继续逐个审批，还是转为自主 Construction。选择会持久化到状态中。即使开启自主模式，任何 Bolt 失败仍应停止并让人选择 retry、skip 或 abort。

#Phase 4：Operation

目的：将“代码完成”延伸到“可部署、可观测、可恢复、可改进”。

Stage内容
4.1 Deployment PipelineCD、发布策略、回滚 Runbook
4.2 Environment Provisioning环境和基础设施准备
4.3 Deployment Execution部署、Smoke Test、健康检查
4.4 Observability SetupMetrics、Logs、Tracing、Dashboard、Alarm、SLO
4.5 Incident Response事件响应、升级矩阵和 Runbook
4.6 Performance Validation负载测试和 NFR 验证
4.7 Feedback & OptimizationSLO、成本、反馈和下一轮优化

Operation 的七个 Stage 都是条件执行。完成 4.7 后可结束 Intent，也可把反馈送回 Ideation 开启新循环。

#六、Scope、Depth 与 Test Strategy

AI-DLC 用三个互相独立的旋钮控制流程成本。

#1. Scope：哪些 Stage 要运行

ScopeStage 数默认深度默认测试适用场景
enterprise32/32ComprehensiveComprehensive受监管、强合规、完整生产交付
feature32/32StandardStandard普通生产功能，默认全流程
mvp22/32StandardStandardGreenfield MVP，暂不做后期运维
poc8/32MinimalMinimal快速验证技术可行性
bugfix7/32MinimalMinimal已知缺陷修复
refactor8/32MinimalMinimal保持行为的代码重构
infra13/32StandardStandard环境、IaC、部署和成本工作
security-patch10/32MinimalMinimalCVE 或安全漏洞修复
workshop25/32StandardMinimal培训和多人工作坊

Scope 不是项目大小标签，而是“这次 Intent 需要哪些生命周期活动”的路由表。官方实现还支持从自然语言关键词自动检测，以及通过 Adaptive Composer 生成满足依赖的最小自定义 Stage 集合。Scopes, Depth, and Test Strategy

#2. Depth：每个产物写多深

Depth特点建议
Minimal只保留核心决定和必要证据小 Bug、PoC、补丁
Standard完整但适度的需求、设计和理由大多数生产功能
Comprehensive完整合规矩阵、NFR、审计和详细论证监管或高风险系统

#3. Test Strategy：测试多少、覆盖哪些层

策略官方建议模型Java 全栈落地
Minimal每项需求至少一个测试，主要为单元测试JUnit 关键规则 + 最小 Smoke
Standard每组件约 5～8 个，单元 + 集成JUnit、Spring Boot Test、Testcontainers、关键 E2E
Comprehensive每组件约 10～15 个，覆盖所有所需类型再增加契约、安全、性能、故障和完整 E2E

这些数字是软指导，不是质量等式。关键支付、权限或数据一致性 Bug 即使文档采用 Minimal，也可能需要 Comprehensive 测试。

#七、关键术语

术语含义与传统概念的差异
Intent一次独立的生命周期工作比 Ticket 更完整，拥有状态、审计和产物
Unit of Work可设计和实现的业务/技术单元取代笼统的 Epic
Bolt一个短而密集的可交付切片取代以周计的 Sprint，通常以小时或天计
Walking Skeleton第一个最小端到端 Bolt先证明架构，再放大自主执行
Space一个团队的规则、知识和 Intents 世界多团队共享仓库时隔离方法和记录

当前实现允许一个 Workspace 有多个 Space，一个 Space 有多个并行 Intent。每个 Intent 有独立状态、审计和产物，用户通过游标切换，不再让新任务覆盖旧任务。Spaces and Intents

#八、状态、审计与 Learning Loop

#1. aidlc-state.md

每个 Intent 的状态文件是进度的单一事实源，记录 Scope、Depth、项目类型、待运行 Stage、当前 Agent、下一步和会话恢复点。

Stage 使用六态表示：

text
[ ] 未开始
[-] 执行中
[?] 等待人类审批
[R] 根据反馈修改中
[x] 完成
[S] 跳过

#2. Audit Trail

审计日志是追加式事件记录，当前指南定义 74 类事件，覆盖初始化、Scope、Stage、问题回答、Gate、Artifact、Subagent、错误和恢复。状态说明“现在在哪里”，审计解释“为什么走到这里”。State Tracking and Audit Trail

#3. Learning Loop

Learning Loop 把本次纠正变成下次默认规则：

text
Stage 记录 interpretation / deviation / tradeoff / open question
→ Gate 展示候选经验
→ 人类选择保留、修改或丢弃
→ 写入 project.md 或提升到 team.md
→ 下一次工作流编译时生效

当前规则链为：

text
org → team → project → phase → stage

规则严格叠加，冲突应在写入时处理，而不是运行中静默覆盖。新学习对下一次工作流生效，不应在当前工作流中途改变已经编译好的规则视图。Rules and the Learning Loop

#九、三种交互模式与审批门

模式方式适用场景
Guide MeAgent 逐项提出结构化问题初次使用、需求容易遗漏
Edit File用户直接编辑 Questions/Artifact已有明确规格或批量输入
Chat自由讨论，Agent 把结论写回文件需求探索和复杂权衡

三种模式最终都汇入 Questions File，使会话讨论转化为可追踪事实。每个非 Initialization Stage 通常以 Gate 收尾：

text
Approve → 更新状态并进入下一 Stage
Request Changes → 修订产物后重新提交

Gate 的价值不是多点一次按钮，而是明确责任边界：AI 不能把自己的输出当作人类验收，人类的批准应对应可阅读产物和可运行证据。Interaction Modes

#十、在 Codex 中怎样运行

#1. 当前多 Harness 版本

官方当前 Codex 指南要求：

  • 项目是 Git 仓库。
  • Codex CLI 版本满足该分发的最低要求。
  • 安装 Bun，用于 TypeScript 工具和 Hooks。
  • 从同一源码版本复制 .codex/、.agents/ 和 aidlc/。
  • 将分发中的 AGENTS.md 与项目现有文件合并。
  • 信任项目和 Hooks。
  • 合并/检查 .codex/config.toml。
  • 运行 Doctor 验证。

示意命令如下；路径必须替换为实际 AI-DLC 源码和项目目录：

bash
cp -r dist/codex/.codex/  your-project/.codex/
cp -r dist/codex/.agents/ your-project/.agents/
cp -r dist/codex/aidlc/   your-project/aidlc/

cd your-project
bun .codex/tools/aidlc-utility.ts doctor

AGENTS.md 必须人工合并，不能用 cp 直接覆盖。Codex 官方文档也把仓库级 Skill 放在 .agents/skills/，并支持用 $skill-name 显式调用。OpenAI：Build skills

AI-DLC 在 Codex 中的入口是：

text
$aidlc Build a REST API for inventory management
$aidlc feature
$aidlc-bugfix
$aidlc-code-generation
$aidlc --status
$aidlc --help

不要照抄 Claude Code 文档中的 /aidlc。Codex 使用 $aidlc，Stage Runner 也是 $aidlc-application-design 形式。AI-DLC on Codex CLI · Skills and Runner Commands

#2. v0.1.8 Rules 包

旧版发布包的 Codex 安装方式是：

  • 把 core-workflow.md 作为根 AGENTS.md。
  • 把细节规则复制到 .aidlc-rule-details/。
  • 以 “Using AI-DLC, ...” 触发。
  • 验证 Agent 能说明 Inception → Construction → Operations。

对于已经存在 AGENTS.md 的项目，这个命令具有覆盖风险。应先备份并合并，或直接选择当前 Skills/Hooks 分发；不要在当前学习仓库里直接执行 README 的覆盖命令。

#十一、Java 全栈示例：订单取消功能

已有系统：

  • Java 21、Spring Boot 3.x、Maven。
  • PostgreSQL。
  • Kafka/Outbox 发布订单事件。
  • React + TypeScript。
  • JUnit 5、Testcontainers、Playwright。

目标：

支持用户在未发货时取消订单，退款由异步流程处理，管理端可以查看取消原因。

#Step 1：选择 Scope

这是现有生产系统的新功能：

text
$aidlc feature Add order cancellation with async refund and admin visibility

若需求已由产品团队完整确认，可通过 Composer 或 Gate 跳过不增值的市场研究，而不应把整个任务错误改成 bugfix。

#Step 2：回答关键问题

  • 哪些订单状态可取消？
  • 取消请求是否幂等？
  • 退款失败是否影响订单取消事务？
  • 库存回补与订单取消如何保证一致性？
  • API 的错误码和并发冲突语义是什么？
  • 谁能取消订单？
  • 取消原因是否包含敏感信息？
  • 管理端需要实时更新还是最终一致？
  • SLO、吞吐量、审计保留期是什么？

#Step 3：形成 Unit of Work

text
U1 取消领域规则与状态机
U2 REST API、权限和幂等
U3 PostgreSQL 迁移与 Outbox 事件
U4 退款消费者与失败重试
U5 React 用户端和管理端
U6 可观测性、告警和运维 Runbook

依赖 DAG：

text
U1 → U2
U1 → U3 → U4
U2 → U5
U3 → U6
U4 → U6

#Step 4：Walking Skeleton

第一个 Bolt 贯通最小真实链路：

  1. 创建一条可取消测试订单。
  2. React 页面调用 POST /api/orders/{id}/cancellation。
  3. Spring Boot 校验最小领域规则。
  4. 在 PostgreSQL 事务中更新状态并写入 Outbox。
  5. 返回新的订单状态。
  6. 使用 Testcontainers 验证数据库结果。
  7. 使用 Playwright 验证用户能看到“已取消”。

Skeleton Gate 应审查：

  • API 契约是否稳定。
  • 事务边界是否正确。
  • 错误语义是否适合前端。
  • 测试是否真的经过数据库。
  • 是否证明前后端和数据层能共同工作。

通过后再决定是否让 U2～U6 自主执行。

#Step 5：测试纪律

层次建议验证
DomainJUnit 参数化测试覆盖状态转换和重复取消
RepositoryTestcontainers 验证乐观锁、Outbox 原子性
APIMockMvc/RestAssured 验证权限、幂等和错误码
Messaging契约测试验证事件 Schema 和兼容性
FrontendVitest 测状态，Playwright 测关键路径
NFR并发取消、重试、日志脱敏、Trace 关联
OperationSmoke Test、Dashboard、退款积压告警、回滚 Runbook

完成标准不是“代码已经生成”，而是需求能映射到设计、实现和测试，构建及 E2E 有最新证据，迁移可演进，关键失败可观测且可恢复。

#十二、与其他开发模式的关系

#1. 与 Vibe Coding

维度Vibe CodingAI-DLC
起点自然语言快速探索Intent + Scope
过程对话驱动、路径灵活Stage 和依赖驱动
人类控制依赖操作者主动审查内置 Gate
状态多依赖会话上下文持久状态与恢复点
产物代码优先需求、设计、代码、测试、运维全链路
最适合原型、学习、探索多阶段生产交付

AI-DLC 不是反对 Vibe，而是给 Vibe 加上 Harness、状态、检查点和证据。

#2. 与 Spec-Driven Development

SDD 强调先形成可执行规格，再让 Agent 依据规格实现，主要回答“要实现的行为和约束是什么”。AI-DLC 还覆盖是否值得做、走哪些阶段、怎样拆分、如何部署运营以及经验如何沉淀。

可以把 SDD 作为 AI-DLC Inception 和 Construction 的核心技术纪律，但 SDD 本身通常不提供完整 Operation、组织知识、审计和多 Intent 管理。

#3. 与 Superpowers

维度AI-DLCSuperpowers
主要范围端到端生命周期开发 Inner Loop
核心单位Intent、Stage、Unit、BoltDesign、Plan、Task、Skill
强项Scope、产物、审计、运维、Learning LoopTDD、系统调试、任务审查、完成前验证
人类控制每 Stage/Bolt Gate设计批准、计划与任务审查

推荐组合：

text
AI-DLC 负责 Outer Loop
  ├── Intent、需求、设计、Unit、Bolt、运维
  └── Gate、状态、审计、学习

Superpowers 的纪律用于 Inner Loop
  ├── Red-Green-Refactor
  ├── Systematic Debugging
  ├── Code Review
  └── Verification Before Completion

不要同时启动 $aidlc 和 Superpowers 的完整顶层编排器，让二者都决定下一步。应明确一个主 Conductor；另一个只提供局部实践。

#4. 与 Agile/Scrum

  • Unit of Work 类似更聚焦的 Epic。
  • Bolt 类似更短的 Sprint，但以端到端价值和快速验证为中心。
  • AI 生成并维护大量传统由人手工维护的产物。
  • 人类从分别生产文档和代码，转向共同回答关键问题并验证 AI 输出。
  • Scrum 可保留，但不应重复制造两套状态源和审批仪式。

#十三、适用场景与不适用场景

#适合

  • 跨后端、前端、数据库、消息和基础设施的功能。
  • Brownfield 大型系统，需要先理解架构和实践。
  • 金融、医疗、政企等强追踪或合规工作。
  • 多个团队共享知识和交付规则。
  • 需要跨会话或跨天持续执行。
  • 希望逐步提升 Agent 自主权，而不是一次性全放开。

#应缩小使用

  • 一次性脚本或明确的一行修复。
  • 纯探索性 Spike，结果可能全部丢弃。
  • 没有测试、构建和版本控制的临时目录。
  • 团队不愿审查产物，却希望 Gate 自动通过。
  • 只追求最快 Demo，不考虑生产维护。

这些场景可用 poc、bugfix 或单 Stage Runner，而不是强行运行 feature 的 32 个 Stage。

#十四、收益、成本与局限

#可能收益

  • 需求到生产的追踪更完整。
  • 新会话可以从状态和产物恢复。
  • 高风险决定不会被 Agent 静默替代。
  • Walking Skeleton 能更早暴露架构错误。
  • Scope 避免所有任务走同一流程。
  • Learning Loop 让团队纠正逐渐制度化。

AWS 博客列出的速度、创新、质量、市场响应和开发体验属于方法论提出方的预期收益，不应当作对所有团队都已独立验证的量化结论。

#成本与局限

  • 更多 Markdown、状态、审计和 Git 变更。
  • Gate 带来等待和审查成本。
  • 多 Agent 和 Comprehensive Depth 会增加 Token、时间和费用。
  • 团队需要维护规则、知识、模板和 Harness。
  • Agent 仍可能误读需求、代码或测试结果。
  • 形式上的可追踪不等于真实正确。
  • 并行 Bolt 可能在公共 Schema、模块和迁移上冲突。
  • 不同 Harness 的命令、Gate、Hooks 和沙箱行为并不完全相同。

#十五、Java 全栈团队最佳实践

  1. 从低风险试点开始：先运行一个 bugfix 或边界清楚的 feature，比较周期、返工、缺陷和人工审批成本。
  2. 固定版本：记录 AI-DLC Commit、Codex 最低版本、Bun 版本、安装和 Doctor 命令。
  3. 把 Java 事实放进团队知识：JDK/Spring 版本、Maven 命令、模块边界、REST/事件/Schema、事务、测试、可观测和回滚规则。
  4. 先验证 Skeleton，再扩大自治：真实构建、关键边界、最小 E2E、日志诊断和可审查 Diff 都通过后再选 autonomous。
  5. 测试策略与文档深度解耦：关键安全补丁可用 Depth=Minimal、Test Strategy=Comprehensive。
  6. 每个 Bolt 都要有新鲜证据：先运行相关编译和测试，最终再跑后端、前端、契约、E2E 和 NFR 全量验证。
  7. 控制并行边界：数据库迁移、公共 DTO/事件、根 pom.xml、全局路由和 Security 配置不宜无约束并行。
  8. 定期治理规则：合并重复项，删除过时项，保留日期、原因和作用域，不把每次偏好都提升为永久规范。

每个 Java Bolt 至少可以运行：

bash
./mvnw -q -DskipTests compile
./mvnw -q -Dtest=RelevantTest test

具体命令应以项目 AGENTS.md 和 CI 为准。

#十六、常见问题

#1. $aidlc 不存在

检查 .agents/skills/aidlc/、当前仓库根目录、SKILL.md、Codex 版本，并在必要时重启 Codex 以重新发现 Skill。

#2. /aidlc 在 Codex 中不能用

Codex 显式 Skill 使用 $aidlc；/aidlc 是 Claude Code/Kiro 文档常见写法。

#3. Doctor 报 Workspace Shell 缺失

新版除 .codex/ 和 .agents/ 外，还需要：

text
aidlc/spaces/default/memory/

#4. Hooks 没有运行

检查项目和 Hook Trust、Hook Manifest、用户配置、Git 仓库状态及 Sandbox 权限。

#5. Git/Worktree 被 Sandbox 拒绝

Codex 的 workspace-write 通常会保护 .git。交互会话需要审批；Headless/CI 应按官方模板配置最小必要 writable root，不能为了省事开放整个用户目录。

#6. 工作流太慢、问题太多

检查是否错误使用 feature/enterprise，是否应改为 bugfix、poc 或单 Stage Runner，能否降低 Depth，是否有可跳过 Stage，以及是否同时运行了两个顶层编排框架。

#7. Agent 一直修改，无法通过 Gate

回到 Questions/Requirements File，写出反例和期望结果，用测试或样例将验收条件可执行化；必要时重做 Application/Functional Design，不要继续让 Agent 猜。

#十七、推荐操作模板

#新生产功能

text
$aidlc feature

为现有 Spring Boot 订单系统增加订单取消能力。
必须覆盖 React 用户端、REST API、PostgreSQL、Outbox 事件、
异步退款、权限、幂等、可观测性和回滚。
先确认 Scope、Depth、Test Strategy 和 Walking Skeleton，
在 Skeleton Gate 通过前保持 gated 模式。

#关键 Bug

text
$aidlc-bugfix

修复并发支付回调导致订单重复记账的问题。
文档深度使用 Minimal，测试策略使用 Comprehensive。
先稳定复现并定位事务/幂等根因；没有失败测试不得修改生产代码。

#快速 PoC

text
$aidlc poc

验证 Spring AI 调用内部模型网关并完成最小 RAG 问答。
只验证认证、流式响应、向量检索和引用返回。
不建设生产级管理后台、扩缩容和完整告警。

具体可用参数以安装版本的 $aidlc --help 和同版本文档为准。

#十八、建议学习顺序

  1. 理解 Intent、Scope、Depth、Stage、Unit 和 Bolt。
  2. 用 bugfix 跑一次小型 Brownfield 工作流。
  3. 用 feature 跑一个 Walking Skeleton。
  4. 阅读 aidlc-state.md 和 Audit Trail，练习会话恢复。
  5. 将一条真实纠正通过 Learning Loop 提升为项目规则。
  6. 再研究 Adaptive Composer、并行 Bolt、Space 和团队知识。
  7. 最后考虑自定义 Scope、Agent、Sensor 或 Plugin。
