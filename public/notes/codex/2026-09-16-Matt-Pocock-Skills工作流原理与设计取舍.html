Matt Pocock Skills 工作流原理与设计取舍

总览 · 安装与环境 · 完整实战 · 原理说明

第 3 课：解释工作流为什么这样设计，以及什么情况下应该删减或调整。最好先运行一次前两课，再回来看原理。预计 40～60 分钟。

研究基线：Matt Pocock skills 固定提交 959a8e9；检索日期 2026-09-16。工程解释属于本文归纳；作者自己的提示词设计观点会单独标明。

核心结论

这套工作流通过一系列信息变换降低不确定性：需求对话变成决定，决定变成规格，规格变成可验收任务，任务变成代码与执行证据。每种产物承担不同责任，技能负责约束转换过程。

它依赖的是模型可读的规程、持久化上下文、宿主工具与工程反馈。测试、Git 和任务系统提供可观察结果；模型仍负责解释规则并选择动作，因此不存在仅靠安装 skills 就获得的确定性执行保证。

1. 执行时发生了什么

一次技能执行
用户目标 + 项目规则 + 技能目录
发现技能 → 加载正文 → 按条件读取参考文件
模型选择动作 → 宿主执行文件/终端/任务系统工具
读取反馈 → 对照完成条件 → 继续、提问或交付

在 Codex 中，技能名称、描述及路径用于发现，详细正文按需加载。模型选择技能不会自动安装数据库、获得 GitHub 权限或创建一个独立 Agent；这些取决于宿主提供的工具与实际调用。

Java 类比有帮助的部分类比的边界
操作规程与策略对象相同任务可以选择不同步骤和规则规程是自然语言，不具有 Java 方法调用那样的确定性语义
依赖注入技能依赖宿主提供终端、文件、Issue 等能力声明依赖不代表授权已经具备
持久化状态决定和任务可在后续会话重新读取文件存在不代表每次都会被正确加载，需要明确入口指针
断言与反馈循环编译、测试能拒绝某些错误结果测试只能验证已覆盖的行为，不能替人决定业务需求

2. 为什么分手动入口与可复用能力

主线阶段需要人理解自己正在做什么，所以 grill-with-docs、to-spec、to-tickets、implement 被设计为用户显式入口。grilling、domain-modeling、tdd 等则可由其他技能复用。

当前 grill-with-docs 正文就是调用访谈与领域建模两个能力。这种分解把“怎样问”与“怎样维护业务概念”放在各自的权威文件中。入口不必复制整套底层规则。

在 Codex 配置里，agents/openai.yaml 的 allow_implicit_invocation: false 控制语义匹配时的自动选用；显式调用仍可用。上游的调用分类是设计意图，具体保证还要以宿主的实现为准。不要据此推断所有宿主都完全隐藏手动技能的元数据。

3. 访谈怎样沿决策依赖推进

“支付后是否允许取消”决定了是否需要讨论退款与支付网关补偿。当前置问题未回答时，提前深挖退款接口会消耗时间并暗中带入范围假设。

当前 grilling 把可问的问题组织成 frontier：只询问前置决定已经明确的问题；一轮中可以有多个互不依赖的问题。回答后重新计算下一轮。

第一轮已知前提可以问暂时不用问
要加取消能力允许哪些状态？谁可以操作？未知是否涉及退款时，不先定退款重试队列
只取消 UNPAID重复请求怎样返回？与支付竞争谁成功？不继续设计已排除的退款流程
确定数据库控制终态现有事务和测试能否覆盖竞争？工程事实先读代码，不再要求用户猜

其作用是让隐藏假设显露。结束条件应是影响当前实现的关键决定已解决，而不是规定必须问满多少个问题。真实工程中要限制范围，避免把未来所有可能性都展开。

4. 产物怎样接住信息，又避免重复真相

产物主要回答变化节奏本课例子
术语表这个业务词是什么意思相对慢Cancellation 不包含退款
ADR为什么选这项长期设计有重要取舍时是否使用数据库锁管理订单迁移
Spec本次交付什么行为需求范围变化时取消、幂等、所有权、并发契约
Ticket这段工作怎样验收，受谁阻塞实现推进时完成本人取消与页面闭环
代码与测试系统实际上怎样运行频繁真实 HTTP 返回、最终状态与版本
交接记录下一会话从哪里继续会话/工具切换时引用任务路径与未解决问题

文档互相引用，避免把相同决定复制成多份。一条规则在 Spec、Ticket、测试和代码中可能有不同表示，但应能追溯到同一业务决定。需求变化时，需要检查这些表示是否仍一致。

上下文窗口是有限的工作区。保留访谈到拆任务的连续上下文，有助于保存决策理由；任务变得自包含后，可以为实现开启新会话。压缩和 handoff 都可能丢信息，应该在阶段边界执行，并带上原始产物的路径。

5. 垂直切片同时解决交付与上下文规模

“先做全部数据库，再做全部接口”能按技术层组织工作，却难以尽早看到完整用户行为。“取消一笔自己的订单”则能贯穿请求、权限、事务、数据库、响应与页面反馈。

从 Agent 的角度，一张自包含任务需要携带的上下文更可控；从人的角度，每张任务都有可检查的结果。两者相互支持。但大小不能只按代码行数衡量：一个跨数据库的字段重命名可能代码简单、影响范围却极大。

当前上游对宽范围重构给出例外：先扩展兼容新旧接口，再分批迁移，最后收缩删除旧接口。不要为了坚持“垂直切片”而让每一批都无法独立通过构建。

6. seam 与深模块怎样影响测试

Seam 是可以观察或替换行为的位置。本课选择 HTTP + H2，因为验收要求包括登录、CSRF、参数映射、事务、SQL 和状态竞争。只 mock Service 的控制器测试无法提供同等证据。

深模块的价值是把必要复杂性留在内部。调用方只需请求“取消自己的订单”，不必自己按顺序锁行、检查状态、改 version。本例 OrderService 已经把这些责任集中起来，因此增加功能主要是复用现有能力。

这不是要求所有 Java 程序减少类数，也不表示纯函数单元测试失去价值。如果风险是折扣计算，纯函数测试可能是更便宜、更精确的 seam；如果风险是数据库竞争，则需要真实并发环境。选择测试切入点应由验收风险决定。

7. 红绿循环与双轴审查提供不同证据

红灯首先证明测试能够拒绝缺失的行为；绿灯证明该实现满足这个断言。只看到一个一直为绿的测试，不能知道它是否真的能抓住目标错误。

本课 red 快照在真实认证、CSRF 和数据库环境中访问尚不存在的取消接口，得到 404；期望是 200。这比因依赖下载失败而无法启动更接近所要验证的需求缺口。

Standards 审查负责项目约定和设计判断；Spec 审查负责遗漏、错误和范围扩张。它们的职责不同，所以要分别报告。两个子代理能隔离部分上下文，但可能共享同一模型偏差，不能当成两位完全独立的人类专家。

当前上游把重构放入 review 阶段，这是该版本的策略。传统红绿重构仍是广泛使用的实践；教程保留版本事实，不把作者的一次流程调整推广为通用定义。

8. 两种「并发」不要混淆

维度本课怎样处理不能据此推断
业务请求并发两个 HTTP 请求竞争同一订单行锁，检查终态和 version通过 H2 测试不等于所有数据库、超时条件或分布式支付都正确
Agent 开发并发本课三张任务串行执行；原版审查可用双子代理任务没有阻塞依赖不代表两个 Agent 不会修改同一文件

如果以后采用并行实现，还需要分支或 worktree 隔离、集成顺序、契约检查与共享状态管理。正式主线的 to-tickets 只提供依赖信息，并不是完整调度引擎；实验区 implement-spec 的能力也不能默认算进稳定主线。

9. 上游规则、课程适配与真实约束

事项上游固定提交本课选择
实现后提交implement 包含提交到当前分支练习 AGENTS 明确先审查工作区，再按任务提交
审查差异code-review 默认比较固定点到 HEAD 的已提交差异提交前用 git diff HEAD 并读取未跟踪文件；最终分支审查再用三点式
产物格式默认 Markdown 术语表、ADR 和本地任务独立练习仓库沿用；本知识库只保存 HTML
测试纪律在事先确认的 seam 上逐行为推进确认 HTTP + H2；查询结果经接口断言，JDBC 仅准备夹具
范围可覆盖很多工程场景先完成一个单体中的取消闭环，进阶能力另开专题

这些适配应写成可检查的项目规则。若宿主或技能仍忽略它，明确指出具体文件与冲突，修正实际步骤。不要把“原版宣称可组合”理解为任意组合都没有衔接问题。

10. 什么时候用完整流程，什么时候缩短

任务建议路径原因
明确的单行为小修复直接 implement 或 tdd已有需求与测试 seam，可以快速获得反馈
普通新功能grill-with-docs → 需要时 to-spec/to-tickets → implement存在业务分歧或跨会话交付
大型且充满未知的项目wayfinder → to-spec → to-tickets → implement先解决影响路线的决策，再拆交付
难复现的 Bugdiagnosing-bugs先建立可识别目标故障的反馈，再讨论原因
频繁改动时架构阻力大improve-codebase-architecture → 选择候选 → 澄清与实施把改造投入集中在真实摩擦与常改区域

评估效果时记录：需求返工次数、第一次可运行结果的时间、测试发现的缺陷、审查遗漏、上下文恢复成本。比较前尽量控制任务难度、模型和工程环境；本课没有提供足以证明某个工具普遍更快的对照实验。

11. 自测与下一步

  1. 为什么表里已有 CANCELLED，不代表取消功能已经完成？
  2. 如果重复取消每次 version 都加 1，哪条验收失败？
  3. 为什么“先查状态再更新”在没有事务锁时可能出错？
  4. 为什么 git diff main...HEAD 会漏掉尚未提交的新文件？
  5. 什么材料齐全后，下一张任务可以在新会话实现？
  6. 如果要加入真实支付退款，哪些已排除的决定必须重新讨论？
核对思路

①状态只是数据能力，还缺入口、业务行为与验证；②幂等验收；③两个请求可同时读到旧状态并覆盖结果；④该命令比较提交，不包含工作区和新增文件；⑤规格、任务验收与依赖、领域术语、必要 ADR 和运行方式；⑥支付结果确认、退款时机、失败补偿、幂等键、状态机与审计。

下一次可以有意识引入一个“去掉事务”的缺陷，观察竞争测试是否抓到，再用 diagnosing-bugs 恢复。实验要在独立练习分支进行，并记录红灯证据；不要把一次偶然通过当成并发正确性的证明。
