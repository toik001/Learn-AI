#OpenSpec + Codex 原生：大型项目开发流程与 Superpowers 差异

目标：OpenSpec 负责需求整理、规格与变更历史；Codex 原生能力负责代码实现、测试、隔离、并行和审查。

问题背景：完整 Superpowers 任务可能运行十几小时，大量时间消耗在细粒度 TDD、失败后的系统化调试、逐任务双重审查和反复修复。

资料截至：2026-08-31。OpenSpec npm 最新版本核对为 1.11.0（发布于 2026-08-26）；Codex 能力以同期 OpenAI 官方文档为准。

快速阅读： 核心结论 · 职责分层 · 具体差异 · 耗时原因 · 推荐流程 · 大型项目边界 · 试点 · 参考资料

#核心结论

  1. 可以采用，而且比“完整 Superpowers 贯穿开发”更符合当前的效率目标。推荐模型是：OpenSpec 管外循环，Codex 原生管实现内循环，CI 管最终确定性门禁。
  2. OpenSpec 不能单独把控大型项目。它是需求与变更的 agreement layer，不是依赖图、构建系统、测试平台或执行调度器。大型项目的真正控制力来自：可验证规格、合理拆分、分层 AGENTS.md、契约测试、Worktree 隔离、CI 和人类风险门禁。
  3. 不要在同一个变更中同时启用两个实现编排器。规格确认后，不调用 Codex 中的 $openspec-apply-change，也不调用 Superpowers 的 writing-plans、subagent-driven-development、TDD 与逐任务 review 链；直接创建 Codex 原生任务并引用 OpenSpec 产物。
  4. 最大的时间节省来自减少审查频率，而不是减少测试。把“每个 2～5 分钟小任务都双重审查”改为“每个可验收批次测试一次、每个分支统一 review 一次”；保留高风险模块的专项审查。
  5. Codex 原生过程是能力集合，不是强制方法论。它提供 /plan、/goal、长期任务、子代理、Worktree、AGENTS.md 和 /review，但需要团队在仓库中定义何时使用、怎样验收和何时停止修复循环。
  6. 单仓库或 Monorepo 的可控性较高；多仓库应分阶段试点。OpenSpec Stores/Worksets 已能组织跨仓库规划，但官方仍标记为 beta；跨仓库依赖、发布顺序和契约兼容性仍应由显式计划、契约仓库与 CI 负责。

适合场景中大型长期项目、已有 CI、希望兼顾速度与规格治理高风险、陌生代码、测试薄弱、需要强教学或强过程约束的任务不必二选一：Superpowers 可保留为例外工具，而非默认总流程

#为什么 Superpowers 容易跑到十几小时

耗时通常不是一个步骤造成，而是多个正确但昂贵的局部纪律相乘：

  1. 计划被切得很细。一个跨模块功能可能被拆为几十个微任务。
  2. 每个微任务重新建立上下文。新子代理要读 spec、计划、相关代码和测试。
  3. 每个任务有两类审查。先核对规格，再看代码质量；发现问题后回到实现代理修复。
  4. 每个测试失败都进入完整调试纪律。对复杂回归很有价值，但第三方服务抖动、测试夹具、格式问题和简单编译错误也可能承担同样流程成本。
  5. 修复后重新验证和重新审查。如果测试基线不稳定或计划本身有偏差，循环次数会迅速放大。

所以换成 OpenSpec 并不会自动变快。如果仍使用 OpenSpec Apply 再叠加 Superpowers TDD、调试和逐任务 review，流程只会增加一层。真正的优化是把审查从“每个微任务”上移到“可验收批次和分支”，把调试强度与故障风险匹配。

#推荐流程：OpenSpec 规划，Codex 原生开发

#阶段一：OpenSpec 整理需求

  1. 需求不清晰时使用 $openspec-explore，只探索问题、用户价值、现状与方案，不写代码。
  2. 使用 $openspec-propose 创建一个 change；OpenSpec 1.x 默认产物链是 proposal → specs → design → tasks。
  3. 人工只检查四个关键点：范围与非目标、可观察行为场景、架构风险与回退、每项任务的验证证据。
  4. 运行 openspec validate <change> --strict；它验证产物结构，不等价于验证业务正确或代码正确。
  5. 把确认后的 change 提交到 Git，形成实现基线。实现中若需求发生变化，先更新 OpenSpec 产物，再继续代码。

#阶段二：Codex 原生执行

  1. 每个 change 使用一个分支或 Codex Worktree；不要让两个写任务同时修改同一组文件。
  2. 小 change 直接给 Codex 实现；多步骤 change 用 /goal，目标中写明 outcome、constraints 和 verification。需要先读代码确认路径时先用 /plan。
  3. Codex 读取 proposal、delta specs、design 和 tasks；tasks 是队列，specs 是行为契约，design 是技术边界。
  4. 按“接口/契约 → walking skeleton → 业务批次 → 集成”的顺序推进。每个批次完成后运行最小相关测试，而不是每改一行就跑全量回归。
  5. 只有读密集、互不依赖的探索、测试分析和审查交给子代理；写密集任务优先分 Worktree，并明确文件所有权。
/goal
实现 OpenSpec change：add-order-cancellation。

需求真相：
- openspec/changes/add-order-cancellation/proposal.md
- openspec/changes/add-order-cancellation/specs/**
- openspec/changes/add-order-cancellation/design.md
- openspec/changes/add-order-cancellation/tasks.md

执行约束：
- 使用 Codex 原生开发过程，不调用 $openspec-apply-change 或 Superpowers 实现技能。
- 遵守根目录和模块目录的 AGENTS.md。
- tasks.md 是唯一任务队列；每完成一个可验收批次，记录验证证据。
- 如果实现需要改变规格、公共契约或既定架构，停止并报告，不自行扩大范围。
- 测试失败先定位证据；连续两次修复仍失败时总结根因假设、已尝试项和下一决策。

完成标准：
- 所有任务完成；相关单元、模块和集成测试通过。
- 分支 diff 不含无关修改；完成一次独立 /review。
- 不归档 OpenSpec change，等待人工验收。

#阶段三：验证、审查和归档

  1. 批次验证：每个逻辑批次运行相关测试；共享契约、数据库迁移、权限和并发逻辑增加专项测试。
  2. 分支验证：运行模块或全量构建、静态检查和必要的真实流程。
  3. 统一审查：在逻辑功能完成后使用一次独立 /review，自定义要求同时检查 spec coverage、回归、兼容性和无关改动。
  4. 修复预算：普通问题最多两轮“修复 → 定向测试”；仍失败则停下来重新判断规格、设计或基线，而不是无上限自循环。
  5. 人工验收：确认关键行为、迁移和回退；随后同步主规格并归档 change。

#在 AGENTS.md 中固定单一指挥者

## Development workflow

- OpenSpec is the source of truth for product requirements and behavior changes.
- Use OpenSpec only for explore, propose, validate, sync, and archive.
- After a proposal is approved, implementation uses the native Codex workflow.
- Do not invoke OpenSpec apply or the full Superpowers implementation pipeline unless the user explicitly requests it.
- Read the active change's proposal, specs, design, and tasks before editing code.
- If code requires a requirement, contract, or architectural change, update the OpenSpec artifacts first.
- One active change owns one branch or worktree. Parallel writers must have non-overlapping file ownership.
- Run targeted checks per batch, the module suite before review, and the full required CI suite before completion.
- Request one independent branch review after the logical change is complete; use additional specialist reviews only for high-risk areas.
- After two unsuccessful repair cycles on the same failure, stop and report evidence instead of continuing an unbounded loop.

这段规则的价值是防止技能自动触发把实现重新带回完整 Superpowers 流程，也防止 OpenSpec 的 Apply 成为第二套执行状态机。

#大型项目能否把控：取决于八个条件

控制条件最低要求缺失后的表现
Change 大小一个 change 对应一个可独立验收的业务能力或兼容性变更巨型 change 超出上下文，tasks 变成愿望清单
领域边界规格按领域/能力组织，设计明确模块所有权和依赖方向Agent 在全库横向修改，review 无法判断影响面
行为可验证每项 requirement 有可观察 scenario；任务有明确验证命令或证据“代码写完”被误判为“需求完成”
稳定 Harness快速测试、模块测试、集成测试和 CI 命令可发现且可重复绝大多数时间被基线失败和不稳定回测吞噬
契约优先跨服务先明确 API、事件、Schema、兼容期与失败语义并行实现后在集成阶段集中返工
写隔离一个文件或模块同时只有一个写者；并行 change 使用 Worktree冲突、重复实现和互相覆盖
风险门禁权限、支付、数据删除、迁移和生产操作设置人工确认原生自主执行越快，错误放大越快
停止条件修复轮次、测试时间和任务范围都有升级阈值Agent 在同一失败上无限“回测—修复”

规模化原则：大型项目不是交给一个持续十几个小时的 chat，而是拆成“一个稳定 initiative/目标 → 多个边界清楚的 OpenSpec changes → 每个 change 一个 Codex 任务/Worktree → CI 汇合”。Codex 官方也建议只并行独立任务，并避免多个任务对同一来源同时写入。

#Superpowers 不必完全删除

建议从“默认总流程”降级为“按风险显式调用的专项工具”：

场景建议原因
普通 CRUD、清晰 UI、低风险重构OpenSpec + Codex 原生批次测试和分支 review 足够，逐任务双审查收益低
复杂线上 Bug、并发、数据一致性只显式调用 systematic-debugging根因纪律有价值，但不必启动完整设计和计划链
核心算法、结算、权限、安全边界按模块调用 TDD 和专项 reviewer错误代价高，额外验证开销合理
全新架构或团队没有共同方案OpenSpec Explore/Propose；必要时人工架构评审不要同时再生成一份 Superpowers spec 与 plan
测试体系很弱、团队刚开始使用 Agent短期保留更多 Superpowers 门禁确定性 Harness 尚不足，过程纪律能补位

#两周试点方案

  1. 选择样本：挑 3～5 个真实 change，至少包含一个跨模块功能、一个 Bugfix 和一个低风险需求；不要先拿最危险的生产迁移试验。
  2. 固定版本：团队和 CI 固定 OpenSpec 版本，不使用浮动 @latest 作为可重复基线；升级后再运行 openspec update。
  3. 固定路由：OpenSpec 只运行 explore/propose/validate/sync/archive；实现提示明确禁止 Apply 与完整 Superpowers。
  4. 固定审查频率：每个逻辑批次自测，分支完成后一次独立 review；只有安全、迁移或复杂并发再增加专项 review。
  5. 比较历史：用过去同规模的 Superpowers 任务作为基线，比较中位数，不用单个任务下结论。
指标怎样记录建议通过线

如果速度提升但回归缺陷增加，先补 Harness 和验收场景，不要立即回到完整 Superpowers；如果复杂故障仍长时间循环，则对该类任务恢复 systematic debugging，而不是恢复所有技能。

#最终选型

默认选型：OpenSpec 负责需求与规格，Codex 原生 Goal/Plan 负责开发，Worktree 负责隔离，AGENTS.md 固定完成标准，CI 提供确定性反馈，分支级 /review 建立第二视角。

不要采用：OpenSpec Propose → OpenSpec Apply → Superpowers TDD/逐任务子代理/双审查 → Codex Review。这会形成三层执行编排，是当前十几小时问题的高概率延续。

适用判断：只要项目已有可靠测试与 CI、能把 change 切到独立验收、公共契约清楚，这套组合足以把控大型单仓库或 Monorepo。多仓库、大规模数据库迁移、强合规或弱测试项目仍需要额外的发布编排、契约治理与人工门禁。
