#OpenSpec + Apply 与 Superpowers：大型项目执行流程对比

比较对象：OpenSpec 的 proposal/specs/design/tasks 加官方 openspec-apply-change 执行技能，对比完整 Superpowers 开发方法论。

资料截至：2026-08-31。OpenSpec npm 最新版本核对为 1.11.0；OpenSpec、Superpowers 和 Codex 能力均依据同期官方资料。

快速阅读： 核心结论 · 本质差异 · 具体对比 · 耗时模型 · 大型项目 · 推荐流程 · 试点指标 · 参考资料

#核心结论

  1. 如果只在这两个方案中选择，默认推荐 OpenSpec + Apply。它保留需求、设计、任务和进度的一致性，流程成本明显低于完整 Superpowers，更符合减少十几小时回测修复消耗的目标。
  2. OpenSpec Apply 是轻量任务执行协议，不是完整质量体系。它选择 change、读取 CLI 返回的上下文与任务、逐项实现并勾选完成；遇到歧义、超范围、设计问题或错误时暂停。它没有默认强制 TDD、系统化调试、逐任务双重评审、Worktree 或分支收尾。
  3. Superpowers 是工程方法论，不只是任务执行器。它把设计确认、隔离工作区、2～5 分钟实施计划、TDD、新子代理逐任务执行、规格/代码双审查、验证和分支收尾串成默认强制链。
  4. OpenSpec + Apply 能把控大型项目，但前提是质量门禁外置。必须由可验证任务、分层 AGENTS.md、稳定测试、契约检查、CI、分支级 /review 和人工风险审批补齐它没有强制规定的部分。
  5. 不要把完整 Superpowers 叠加到 Apply 后面。这样会同时维护 OpenSpec tasks、Superpowers plan 和多轮 review 状态，既重复规划又重复验证，十几小时问题大概率继续存在。
  6. 结合上一页的最终目标，首选仍是 OpenSpec + Codex 原生。若团队特别需要“严格按 tasks.md 前进、自动显示进度、遇阻立即停”的行为，再加入 Apply；Superpowers 只保留为高风险任务的专项技能。

#本质差异：任务驱动协议 vs. 工程方法论

OpenSpec + Apply
已确认 change → 读取上下文 → 按任务实现 → 勾选 → 遇阻暂停
Superpowers
设计确认 → Worktree → 微任务计划 → TDD → 子代理/批次执行 → 多轮 Review → 收尾
Apply 约束“做哪项任务、何时暂停”；Superpowers 还约束“怎样写、怎样测、怎样调试、怎样审查、怎样结束”。

OpenSpec 官方把自己定位为人与 AI 之间的 lightweight agreement layer。Apply 技能不是一个独立编译器或确定性执行引擎，实际修改代码的仍是所在工具中的 Agent；技能主要提供上下文加载、任务状态、范围边界和暂停规则。Superpowers 则主动改变整个开发生命周期，因此两者的固定成本和保障范围并不对称。

#为什么 Apply 通常更快

可以把一次 change 的墙钟时间粗略理解为：

OpenSpec + Apply
≈ 规格产物 + Σ(读取任务 + 实现 + 任务验证) + 分支验证/审查

完整 Superpowers
≈ 设计确认 + Worktree/基线 + 微任务计划
  + Σ(TDD 红绿循环 + 子代理上下文 + 实现 + 规格审查 + 代码审查 + 修复复审)
  + 完成验证 + 分支收尾

Apply 省下的是每个任务的流程固定成本，不是代码本身的复杂度。它仍可能运行很久，常见原因包括：

  • 一个 change 覆盖过多模块，tasks.md 实际上是整个项目计划；
  • 任务过粗，单个 checkbox 包含接口、数据库、前端、迁移和全量回归；
  • 任务验证都运行全量测试，且测试基线不稳定；
  • 实现中持续发现规格或设计缺口，反复暂停并修改 artifacts；
  • 仓库规则又自动触发完整 Superpowers，形成 Apply → TDD → 双 review 的嵌套链；
  • 外部服务、测试数据或环境存在非确定性，失败被误认为代码回归。

关键优化不是取消验证，而是调整验证层级：每个任务运行定向检查，每个逻辑批次运行模块套件，分支完成后统一运行全量 CI 和一次独立 review。

#OpenSpec + Apply 能否把控大型项目

答案是“能控制 change，但不能单独治理整个工程”。它擅长让一个变更从可审查规格稳定落到任务完成状态；它不替代依赖治理、架构守护、测试平台、发布编排和组织协作。

大型项目控制面Apply 已提供必须外部补齐
需求与范围proposal、行为 specs、design、tasks；超范围时暂停产品验收、跨团队依赖、优先级与变更授权
执行可追踪CLI 状态、任务进度、checkbox 持久化、可跨会话继续initiative → changes 的依赖图、里程碑和负责人
实现质量最小聚焦修改、任务必须可验证编码规范、架构规则、静态检查、覆盖率与专项测试
故障控制错误或 blocker 立即暂停，不静默猜测故障分类、重试预算、系统化调试触发条件和不稳定测试隔离
并行安全单个 Apply 循环天然偏顺序一 change 一 Worktree、文件所有权、契约优先和集成顺序
独立审查无默认独立 reviewer分支级 /review、高风险专项 reviewer、人工审批
交付与发布完成后建议 sync/archiveCI、制品、迁移、回滚、灰度、发布审批和可观测性

对于大型 Java/Spring 项目，建议把 change 限定为一个可独立验收的领域能力或兼容性变更。跨服务工作先固定 REST/OpenAPI、事件 Schema、数据库迁移和兼容窗口，再把各服务实现拆成不同 change 或非重叠任务；否则 Apply 只是把一个巨型任务列表顺序跑完，并没有真正降低集成风险。

#怎样选择

项目状态或任务类型推荐方式原因
已有稳定 CI、模块边界清楚、主要目标是降时延OpenSpec + Codex 原生最少编排层，允许 Codex 围绕 outcome 自主组织实现
希望严格消费 tasks、跨会话恢复并清楚显示进度OpenSpec + Apply任务状态单一，范围与暂停条件明确，成本仍较低
核心结算、权限、安全、并发一致性或测试体系薄弱OpenSpec + Apply，并显式增加 TDD/系统化调试/专项 review按风险补纪律，避免全项目承担完整 Superpowers 成本
新团队缺少共同开发方法，且可靠性优先于速度完整 Superpowers强制方法论可补足工程习惯和质量门禁的缺失
探索性原型或一次性低风险工具Codex 原生；必要时只写简化 OpenSpec完整 Apply 或 Superpowers 的固定成本可能超过任务本身

#推荐落地流程：轻量 Apply + 外部质量门禁

  1. 探索：需求模糊时运行 /opsx:explore，先确认用户价值、边界、依赖与高风险假设。
  2. 形成 change：运行 /opsx:propose，审查 proposal、delta specs、design 和 tasks；每项 task 必须包含具体验证证据。
  3. 规格校验：执行严格 validate。注意结构校验不证明业务或代码正确。
  4. 隔离：每个 change 使用独立分支或 Codex Worktree；并行 change 不共享写入文件。
  5. Apply：调用 $openspec-apply-change <change-name>。让 Apply 作为唯一实现任务状态机，不再生成 Superpowers implementation plan。
  6. 分层验证：每项任务跑定向检查；每组业务批次跑模块测试；全部任务完成后跑项目规定的 CI 套件。
  7. 独立审查：对整个分支执行一次 Codex /review，重点检查 specs coverage、回归、兼容性、迁移和无关改动。
  8. 验收归档：人工确认关键场景和风险项，再 sync/archive；不要仅凭 checkbox 全勾选就直接上线。

#AGENTS.md 规则样例

## OpenSpec apply workflow

- OpenSpec specs and the active change are the requirement source of truth.
- Use `$openspec-apply-change <change-name>` as the only implementation task runner.
- Do not invoke the full Superpowers planning or subagent-development pipeline unless the user explicitly requests it.
- One OpenSpec change owns one branch or worktree.
- Every task in tasks.md must name its verification command or observable evidence.
- Run targeted checks for each task, module tests per logical batch, and the required full CI suite before completion.
- Use TDD by default for behavior-heavy domain logic, bug regressions, security, money, concurrency, and migrations; it is optional for mechanical low-risk changes.
- If a failure repeats after two evidence-based repair attempts, stop and report the evidence, hypotheses, and decision needed.
- After all tasks pass, request one independent branch review against the OpenSpec specs.
- Do not sync or archive until CI, review, and human acceptance are complete.

Codex 官方说明 AGENTS.md 会在开始工作前加载，并支持从仓库根目录到当前目录的分层覆盖。因此可以在根目录规定通用 Apply 流程，再在支付、权限、数据库等模块目录追加更强的测试与审批规则。

#避免重新陷入十几小时：修复循环预算

失败类型第一次动作第二次仍失败升级方式
编译、格式、简单单测定位直接错误，最小修复，重跑定向检查检查任务理解、依赖与基线暂停 Apply，报告日志和假设
不稳定集成测试或外部服务区分产品失败与环境失败，保存可复现证据隔离 flaky test，不反复修改产品代码碰运气交给环境/测试平台负责人
复杂领域 Bug、并发、数据一致性显式调用 systematic-debugging，先做根因调查建立最小复现和回归测试架构或领域专家确认设计
规格与实现冲突停止写代码，更新 proposal/spec/design/tasks重新审查 change 范围产品/架构决策，不允许 Agent 自行简化需求
全量回归失败先确认是否由当前 diff 引入缩小到模块、测试类或提交若是历史基线问题，单独建 change 处理

#两周 A/B 试点

#最终判断

OpenSpec + Apply 的优势是“状态清楚、范围稳定、流程短”。它非常适合已经有成熟 Java 工程规范、测试和 CI 的中大型团队：OpenSpec 维护行为真相，Apply 消费任务，CI 和分支 review 承担确定性质量门禁。

Superpowers 的优势是“把正确的软件工程动作变成默认强制动作”。当团队测试薄弱、代码陌生、任务高风险或需要强教学时，它增加的时间通常值得；但把它作为所有 change 的默认实现链，会把规划、上下文、TDD、审查和修复成本重复放大。

针对当前目标：先以 OpenSpec + Codex 原生作为默认；若实际试点发现任务进度和范围容易漂移，再升级为 OpenSpec + Apply。不要直接回到完整 Superpowers，也不要把完整 Superpowers 叠在 Apply 之后。对高风险模块只显式启用 TDD、systematic-debugging 或专项 review。
