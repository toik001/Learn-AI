#Harness、Loop、Graph 与 Codex + Superpowers 开发模式

本文解决的问题：Harness、Loop、Graph 到底是不是互斥的开发流派？过去常见和 2026 年升温的 AI 开发模式是什么？在 Codex 中怎样落地？使用 Codex + Superpowers 开发项目时，哪些技能真的会创建子智能体？

核验范围：OpenAI、Anthropic、LangGraph、Microsoft Agent Framework、GitHub Spec Kit、ReAct 原论文、Superpowers 官方仓库，以及本机已安装的 Superpowers 6.2.0 技能正文。在线资料检索于 2026-08-07。

快速阅读： 核心结论 · 三层模型 · 模式演进 · Codex 实现 · Superpowers 组合 · 子智能体审计 · Java 项目建议 · 参考资料

#核心结论

  1. Harness、Loop、Graph 不在同一抽象层，不能三选一。Harness 是让智能体能可靠工作的环境、上下文、工具和护栏；Loop 是一次任务内部反复观察、行动和验证的运行机制；Graph 是多个步骤、角色或分支之间的显式编排结构。成熟系统通常三者叠加。
  2. “Agent 就是一个 Loop”仍然成立，但只写循环不等于可生产。ReAct 在 2022 年把推理与行动交错起来；生产系统还必须补上终止条件、权限、状态、重试、评测、可观测性和人工升级点，这些大多属于 Harness。
  3. Graph 的价值是可控，不是让系统看起来复杂。固定步骤、合规门禁、人工审批、可恢复长流程适合 Graph；开放式编码任务更适合模型驱动 Loop。能用普通函数或单智能体完成时，不应为了“多 Agent”增加图编排。
  4. 2025—2026 的主线从“提示模型写代码”转向“设计智能体工作的系统”。Spec-driven 把意图变成可执行工件，Ralph 把验收反馈写进长循环，Harness Engineering 把仓库、工具和质量信号做成智能体可读基础设施，Symphony 一类控制平面再把任务看板变成持续运行的 Agent Factory。
  5. 按本文的三层分析模型，Codex + Superpowers 是一个组合架构：Codex 提供执行 Harness 和原生 Agent Loop；Superpowers 的技能前置条件可映射为带门禁的开发 Graph；TDD、验证和审查形成嵌套 Loop；只有特定技能或明确指令才启用子智能体。这里的“Graph”是本文的结构化解释，不是 Superpowers 官方宣称的执行引擎。
  6. Superpowers 6.2.0 的普通项目主路径中，直接创建子智能体的核心技能有三个：subagent-driven-development、dispatching-parallel-agents、requesting-code-review。writing-skills 也会为压力测试创建子智能体，但它是编写 Skill 的元工作流，不是普通功能开发阶段。
  7. Brainstorming、Writing Plans、TDD、Systematic Debugging、Verification、Worktree 和 Finishing 本身不会创建子智能体。尤其是当前版本的规格与计划审查已经改为主智能体的 inline self-review；不要把“技能切换”“工具调用”或“自检”误算成子智能体。

专题课程：从概念到双层项目实战

本页用于模式总览。需要分别学习运行时审批 Agent 和 Codex 代码开发中的实际使用方法，可按以下顺序进入四篇专题课程：

  1. Harness：从运行时 Agent 到 Codex 开发环境
  2. Loop：从业务 Agent 循环到 Codex 开发闭环
  3. Graph：从审批状态编排到 Codex 开发流程
  4. Harness + Loop + Graph 双层整合实战

#先把三个词放回正确层级

Harness
环境 · 上下文 · 工具 · 护栏
Graph
步骤 · 分支 · 角色 · 门禁
Loop
观察 · 行动 · 反馈 · 终止
组合关系：Harness 包住整个系统；Graph 组织多个工作节点；每个 Agent/节点内部仍可能运行自己的 Loop。
概念主要回答最小组成优势主要风险
HarnessAgent 在什么环境里工作，怎样知道规则并取得真实反馈？指令、仓库知识、工具、权限、沙箱、测试、日志、状态、恢复让能力可重复、可验证、可治理文档腐化、工具不可读、护栏只有文字没有机械执行
LoopAgent 下一步做什么，何时继续或停止？目标、观察、决策、动作、反馈、终止条件适应未知步骤，能根据环境修正无限循环、错误累积、成本失控、伪完成
Graph多个步骤和角色怎样连接、分支、并发与恢复？State、Node、Edge、Router、Checkpoint路径可视、状态可持久化、容易加入 HITL 和合规门禁过度编排、共享状态冲突、图定义与实际行为漂移

LangGraph 的官方定义很直观：State 保存当前快照，Node 做工作，Edge 决定下一步；普通边、条件边和并行 super-step 共同组成可循环的工作流。Microsoft Agent Framework 也把 Agents / Harness / Workflows 分成三类能力，并明确建议：开放任务用 Agent，需要确定顺序和多组件协调时用 Workflow。

Harness 不只是“选了哪个 Agent 框架”

在测试领域，test harness 是驱动被测对象、提供夹具并收集结果的系统。Agent harness 延续同一思想：模型只是执行核心，Harness 负责把文件、工具、权限、状态、知识和质量信号变成模型可理解且可操作的接口。OpenAI 2026 年的 Harness Engineering 实践进一步把重点放在：

  • 仓库知识是版本化的 system of record，短 AGENTS.md 只做地图；
  • 应用、DOM、截图、日志、指标和 Trace 对 Codex 可见；
  • 架构边界、命名和质量要求由 lint、结构测试、CI 机械执行；
  • 失败不靠“再试一次”，而是把缺失能力补回工具、文档或护栏；
  • 人从逐行“in the loop”上移到设计和改进循环的“on the loop”。

Loop 至少要有三种停止

  • 成功停止：明确验收条件成立，并有新鲜测试或真实行为证据。
  • 预算停止：达到最大轮数、时间、Token、成本或重试上限。
  • 升级停止：权限不足、需求冲突、高风险判断或连续失败时交还人类。

Ralph Loop 的重点也不应被简化成“死循环调用 CLI”。其作者强调单进程、单仓库、每轮一个任务，通过观察失败域来改进循环；OpenAI 的 Harness Engineering 则把 PR 自审、Agent review、反馈修复和再验证视作一个持续到审查通过的循环。

Graph 分为确定图与模型动态拆图

  • 确定性 Workflow Graph：节点和边由代码预先定义，适合发布、审批、迁移和有严格审计要求的流程。
  • Orchestrator–Workers：中央模型根据当前输入动态拆任务，再聚合 Worker 结果；子任务数量和内容事先未知。
  • Manager / Handoff：Manager 保持控制并把专家当工具，或把对话控制权移交给另一 Agent。
  • Task DAG / Control Plane：任务、依赖、状态和重试存在看板或数据库中，多个工作区只领取未阻塞任务。

#从以前到近期升温的开发模式

趋势说明：下表中的“2026 升温”是本文根据 2026 年一手资料发布时间、官方工程实践和工具演进做出的趋势判断，不是行业标准分类或热度排行榜。

阶段 / 模式控制权典型结构今天怎样看
补全与单次生成人主导输入 → 模型 → 代码片段仍适合局部、低风险、上下文明确的工作；不是 Agent 系统
Chat / Pair Programming人逐轮主导人问 → AI 答 → 人复制/运行 → 再问交互直接，但人承担上下文搬运、运行和验证
Prompt Chaining / Routing代码主导固定链或分类后走专门路径最便宜、可预测；Anthropic 建议先从简单工作流开始
ReAct / Tool-use Loop（2022 起）模型决定下一动作Reason → Act → Observation → …现代编码 Agent 的基础运行形态；必须有环境反馈和停止条件
Graph Workflow代码与模型混合State + Nodes + Edges + Checkpoints适合持久状态、分支、并行、HITL 和确定性治理
Parallel / Orchestrator–Workers / Evaluator–Optimizer编排器主导并行分片、动态拆分、生成—评审循环提高覆盖和吞吐，但 Token、协调与共享写冲突明显增加
Spec-Driven / Intent-Driven规格约束实现Spec → Plan → Tasks → Implement把自然语言意图、验收和技术决策变成版本化中间工件
Ralph / Long-running Feedback Loop（本文判断：2026 升温）循环目标与反馈主导实现 → 测试/评审 → 修复 → 再验收适合验收可机器判断的长任务；必须限制轮数并可中断
Harness Engineering（本文判断：2026 升温）人设计环境，Agent 执行Agent-readable repo + tools + guardrails + evals优化对象从“一次 Prompt”转为整个成功系统，是当前最值得投入的一层
Agent Factory / Control Plane（本文判断：2026 升温）任务系统调度Issue board → DAG → isolated agents/workspaces → PRSymphony 类模式解决多会话管理；适合规模化团队，不是个人小改动起点

真正变化：优化对象上移

早期优化的是提示词和单次输出；随后优化 Agent 的工具循环；再后来优化 Graph 中的状态、分支和角色。Harness Engineering 把优化对象进一步上移到整个工程系统：仓库是否可导航、命令是否可运行、错误信息是否带修复上下文、测试能否证明完成、日志和 UI 是否可由 Agent 直接读取。

2026 年 OpenAI 发布的 Symphony 参考把这一思路再外扩一层：任务看板成为状态机和控制平面，每个开放任务对应独立 Agent workspace，依赖形成 DAG，只启动未阻塞任务，Codex App Server 提供可编程线程与事件接口。它代表的是管理 Agent 工作，不是一个更复杂的代码生成 Prompt。

Harness：把仓库变成 Agent 可工作的“成功跑道”

持久规则与导航AGENTS.md，就近目录覆盖短入口 + 指向架构、测试、领域和运行手册

相关基础可继续阅读Codex 官方原生项目开发最佳路径和Codex 全栈开发最佳实践。

Loop：Codex 主线程本身就是工具反馈循环

用户给出目标后，Codex 会检查仓库、选择工具、执行命令、读取结果、更新判断并继续，直到满足任务、遇到权限/信息阻塞或达到停止条件。这是模型驱动的动态 Loop。工程上应再叠加三个较小的可验证循环：

  1. 实现循环：写失败测试 → 观察失败 → 最小实现 → 观察通过 → 重构。
  2. 审查循环：生成 diff → reviewer 找问题 → implementer 修复 → scoped re-review。
  3. 交付循环：本地验证 → CI/真实应用反馈 → 修复 → 再验证 → 人工决定合并。
给 Codex 的 Loop 型任务契约

目标：修复订单重复扣库存，并保留现有 API。
反馈：先用并发回归测试稳定复现；每次改动后运行该测试。
成功停止：回归测试修复前失败、修复后连续通过，模块测试和 verify 通过。
预算停止：同一根因连续 3 轮未收敛时停止并报告证据。
升级停止：需要改变幂等语义、数据库约束或生产数据时先请求人工判断。

Graph：轻量用计划和技能，强确定性用外部编排器

Codex 原生适合模型动态决定下一步，并不是通用的持久化 Graph DSL。可以按确定性需求选择三档实现：

需求推荐实现说明
一次开发任务的阶段门禁Plan/Goal + Skill 前置条件 + checklistSuperpowers 就属于这一层；用说明文件表达状态机
一次会话内动态拆分Codex 原生 Subagents主 Agent spawn / steer / wait / synthesize；适合有限并行
固定 DAG、持久状态、跨天恢复、审批外部 Workflow Engine / LangGraph / Agent Framework / 自建 Java 状态机把 Codex CLI、SDK、MCP Server 或 App Server 当节点执行器
Issue 驱动的规模化 Agent FactorySymphony 思路：看板状态机 + 独立 workspace + Codex App Server任务系统拥有事实状态，Agent session 只是可替换执行实例

Codex 原生子智能体配置

当前 Codex Subagents 官方文档说明，本地 Codex 的 subagent workflow 默认启用；可以通过 [agents] 限制并发、默认模型和推理强度。只有当用户直接要求，或适用的 AGENTS.md/Skill 明确要求委派时，本地 Codex 才会创建子智能体。下面是一个保守的项目示例：

# .codex/config.toml
[agents]
enabled = true
max_concurrent_threads_per_session = 4
default_subagent_model = "gpt-5.6-terra"
default_subagent_reasoning_effort = "medium"

# .codex/agents/reviewer.toml
name = "reviewer"
description = "只读审查正确性、安全、并发和缺失测试。"
model = "gpt-5.6-terra"
model_reasoning_effort = "high"
sandbox_mode = "read-only"
developer_instructions = """
先给可复现的具体问题，引用文件和符号。
忽略纯风格偏好，优先正确性、安全、兼容性和测试缺口。
不要修改文件。
"""

版本提醒：本机 Superpowers 6.2.0 的 references/codex-tools.md 提示在 [features] 下设置 multi_agent = true。这不是失效配置：当前 Codex 配置参考仍把 features.multi_agent 列为稳定且默认开启的功能开关；同时，Subagents 配置在 [agents] 中提供 agents.enabled、并发上限、默认模型和推理强度等新一层控制。对当前版本而言，Superpowers 的开关通常是兼容且冗余的显式启用，而不是应删除的旧键。先检查当前会话是否已经暴露 subagent 工具，再按当前官方参考配置。

#Codex + Superpowers 实际用了哪些模式

分析口径：下面把 Superpowers 的条件式 Skill 工作流映射成 Harness、Graph 和 Loop，目的是解释控制关系；Superpowers 6.2.0 本身不是带持久状态、节点运行时和 checkpoint 的 Graph Engine。

层Codex + Superpowers 中的具体实现属于哪种模式
宿主执行层Codex 的文件、Shell、Git、浏览器、MCP、sandbox、approval、worktreeHarness
项目知识层AGENTS.md、仓库文档、测试命令、验证规则Harness
方法注入层Superpowers 的 SKILL.md、脚本、prompt template 和触发规则Harness + Policy
开发主流程Brainstorm → Spec → Plan → Implement → Review → Verify → FinishGated Graph / State Machine
任务内部TDD 的 Red–Green–Refactor，Debug 的证据—假设—验证Loop
审查修复Task review → Fix round → Scoped re-review，最多 5 轮Evaluator–Optimizer Loop
计划执行每个 Task 由新 implementer 完成，随后 reviewer 门禁，最后全分支 reviewSequential Multi-agent Graph
独立问题每个问题域一个 Agent，同时调查，主线程综合Parallel / Orchestrator–Workers

Superpowers 主状态机

  1. using-superpowers 先按任务语义路由到适用 Skill。
  2. 创意或行为变更先走 brainstorming，通过用户门禁后形成规格。
  3. writing-plans 把规格拆成带文件、接口、测试和提交步骤的任务。
  4. 用户选择 subagent-driven-development 或 inline executing-plans。
  5. 实现阶段按需嵌套 TDD、Systematic Debugging、Code Review 和 Verification。
  6. finishing-a-development-branch 在全量验证后让人决定合并、PR 或保留。

因此，把 Superpowers 只叫“Prompt 模板集合”会低估它。它更接近运行在 Codex Harness 之上的声明式流程策略：Skill 的前置条件和硬门禁构成 Graph，主智能体读取规则后负责推进状态。

#Superpowers 6.2.0 子智能体启用审计

以下结论来自本机已安装 superpowers/6.2.0/skills/*/SKILL.md 的逐项核对；它比只看旧博客或旧 README 更能回答“现在实际会不会 spawn”。

Skill会创建子智能体？创建什么关键边界
subagent-driven-development会，核心路径每 Task 一个新 implementer；每 Task 一个 reviewer；最终 whole-branch reviewer；必要时 fix agent / re-reviewer实现 Agent 明确禁止并行，逐 Task 串行推进，避免共享工作区冲突
dispatching-parallel-agents会，并行每个独立问题域一个 Agent只用于无共享状态、无顺序依赖的任务；返回后主 Agent 还要检查冲突和跑全量验证
requesting-code-review会，Reviewer一个通用 code reviewer，读取精确需求和 diff package审查结果仍需主 Agent 技术核验，不能盲信
writing-skills会，元工作流用 fresh-context subagent 运行压力场景，做 RED–GREEN–REFACTOR 式 Skill 测试仅在创建/修改 Skill 时出现，不属于普通项目功能开发
writing-plans本身不会无；只在交接时推荐 SDD计划 self-review 明确由当前 Agent inline 执行
executing-plans不会当前 Agent 按计划 inline 执行若 Harness 有 subagents，Skill 反而建议改用 SDD
brainstorming不会当前 Agent 与用户逐段确认并 inline self-review用户批准是门禁，不是子智能体评审
TDD / Debugging / Verification / Git Worktrees / Finishing不会自动创建当前 Agent 执行检查、命令和决策它们可能被子智能体使用，但 Skill 自身不等于 spawn

一次 SDD 到底会产生多少 Agent

设计划有 N 个 Task，且所有审查一次通过。Superpowers 6.2.0 的最低子智能体调用量大致是：

N 个 implementer
+ N 个 task reviewer（同时给 spec compliance 与 task quality 两个 verdict）
+ 1 个 final whole-branch reviewer
= 2N + 1 次基础子智能体任务

若审查失败，还会增加：
- rounds 1–3：恢复原 implementer 修复 + scoped re-review
- rounds 4–5：换更强的新 implementer + scoped re-review
- final review 有问题：一个统一 fix agent + 一次 scoped re-review

这里有两个重要判断：

  1. SDD 是顺序多 Agent，不是并行写代码。“一个 Task 一个新上下文”是为了减少 context pollution；Task 之间仍按计划依赖顺序执行。
  2. 子智能体不是免费增强。Codex 官方明确提醒每个子智能体都会独立做模型和工具工作，Token 消耗高于单 Agent。小改动用主 Agent + 测试 + review 往往更合适。

什么时候启用，什么时候不要启用

情况建议原因
多个目录的只读探索、不同资料源调研、不同维度审查并行 subagents独立、噪声大、结果可摘要，最符合官方建议
已有详细计划，Task 之间可按顺序独立验收Superpowers SDD新 implementer 上下文 + 每 Task reviewer 门禁
同一文件、同一数据库迁移、同一集成环境的并行写入不要并行共享可变状态、冲突和集成成本会抵消收益
一步可完成的小修、确定性命令、单一慢外部调用单 Agent / 普通代码子智能体不能缩短单链关键路径，只会增加成本
步骤必须固定、需要审计和跨天恢复外部 Graph / WorkflowCodex subagents 是模型驱动编排，不保证固定确定图
需求仍不清楚先 Brainstorm/Plan，不急着 spawn把含糊目标并行复制，只会更快地产生多份偏差

可直接使用的 Codex 提示词

# 只读并行探索
请用 3 个并行子智能体：
1. explorer 追踪订单取消调用链；
2. reviewer 检查事务、幂等和并发风险；
3. docs_researcher 核验 Spring 事务 API。
全部只读。等待三者完成后，由主智能体交叉核验并给出一份带文件证据的方案。

# Superpowers 顺序开发
使用 Superpowers 完成这个项目任务。先按 brainstorming 明确规格并让我确认，
再用 writing-plans 生成实施计划。计划批准后使用 subagent-driven-development：
每个 Task 一个 implementer，Task review 通过后再进入下一个 Task，最后做全分支 review。
不要并行编辑共享文件。

# 明确不启用子智能体
这是一个局部、单文件修复。由主智能体直接执行，不创建子智能体；
先写失败测试，做最小修复，运行相关测试并检查 diff。

#Java / Spring 项目的推荐落地

第一阶段：先让单 Agent Loop 可靠

  • 固定 Java LTS、Maven/Gradle Wrapper、模块构建和最小相关测试命令。
  • 把 Spring Boot 启动、Testcontainers、数据库迁移和前端开发服务做成可重复脚本。
  • 在 AGENTS.md 记录模块边界、事务、异常、鉴权和完成标准，但保持它是地图。
  • 让 API、日志、Actuator、OpenTelemetry、浏览器关键路径成为 Codex 可读取的反馈。
  • 为每个任务写 Goal、Constraints、Done when 和停止/升级条件。

第二阶段：再增加 Superpowers 门禁

  • 新功能先 Brainstorm → Spec → Plan；Bug 先 Systematic Debugging；所有改动走 TDD。
  • Task 粒度按可独立测试的领域行为拆，不按 Controller/Service/Repository 技术层机械拆。
  • 跨模块计划使用 SDD，但 implementer 串行；只读探索、测试分析和审查可并行。
  • 审查重点放在事务边界、幂等、并发、租户隔离、数据库/API 兼容和真实集成测试。

第三阶段：吞吐真正成为瓶颈后才做 Agent Factory

只有当团队已经有稳定测试、清晰任务、独立环境、可恢复 CI 和可靠 review packet，却仍被人工切换多个 Codex session 拖慢时，才值得引入看板状态机、任务 DAG、独立 workspace 和 App Server。否则，Agent Factory 只会把不稳定 Loop 放大。

项目规模推荐组合暂时不要
个人学习 / 小服务Codex 单 Agent Loop + AGENTS + 测试Graph 框架、常驻多 Agent
中型 Spring Boot 项目Codex Harness + Superpowers gated graph + 按需 SDD并行 Agent 改同一模块
大型 Monorepo领域化 Harness、worktree、只读并行探索、顺序 SDD、CI 门禁共享未隔离数据库和端口
受监管 / 固定业务流程Java Workflow/State Machine 负责确定图，Codex 作为受限节点让 LLM 自己决定审批和生产写入路径
高吞吐 Agent-first 团队Issue control plane + DAG + isolated workspace + App Server + observability在 Harness 未成熟前追求无人值守

#常见误区

  • “Harness、Loop、Graph 哪个更先进？”错误问题；它们解决不同层的问题。
  • “多 Agent 一定比单 Agent 强。”只有可独立分解且协调成本低时才成立。
  • “Graph 就是多 Agent。”Node 可以是普通函数；单 Agent 也能在 Graph 中运行。
  • “用了 Superpowers 就一定 spawn。”多数 Skill 只约束主 Agent；只有明确的委派 Skill 才会创建。
  • “Ralph 就是无限 while true。”没有验收、预算、升级和可恢复状态的循环只是失控重试。
  • “AGENTS.md 越长，Harness 越强。”OpenAI 的实践恰恰是短地图 + 结构化深层事实源 + 机械校验。
  • “文档写了规则就算护栏。”高价值规则最终应进入测试、lint、类型、schema、权限或 CI。
  • “Agent Factory 是下一步。”先把单任务成功率做高，再扩大并发；否则只是并行制造返工。

#一页选择检查单

  1. 任务能否由普通函数、一次模型调用或单 Agent 完成？能则停在最简单层。
  2. 步骤是否未知、需要根据工具反馈动态决定？需要则使用 Agent Loop。
  3. 是否有固定顺序、分支、审批、并行、持久状态？有则增加 Graph。
  4. Agent 是否能直接读取知识、运行项目、看到日志并验证结果？不能则先建设 Harness。
  5. 子任务是否真正独立、没有共享写状态？是才启用并行 subagents。
  6. 是否已有详细计划并希望隔离每个 Task 上下文？是则使用 Superpowers SDD。
  7. 成功、预算和人工升级三类停止条件是否都已定义？没有就不要启动长循环。
  8. 失败经验能否沉淀为规则、脚本、测试或可观测信号？能则回补 Harness，形成复利。
