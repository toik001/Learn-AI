#Codex 全栈开发最佳实践：Vibe Coding、Harness 与 Loop

整理日期：2026-07-24
主题：面向 Java 全栈开发者，建立从快速原型到可靠交付的 Codex 操作方法
资料范围：OpenAI 官方 Codex、Prompting 与 Cookbook 文档

延伸阅读：Codex 官方原生项目开发最佳路径 · Superpowers 详细介绍 · AIDLC 详细介绍 · AIDLC 与 Superpowers 差异分析

#核心结论

Codex 的正确用法不是“写一句提示词，然后接受生成结果”，而是把它当成一个能够读取代码、执行命令、修改文件和验证结果的工程协作者。

推荐采用三层工作方式：

层次解决的问题核心动作适用阶段
Vibe Coding快速把模糊想法变成可体验的软件描述目标、生成最小原型、观察、连续微调创意探索、UI 原型、技术验证
Harness Engineering让 Codex 在可控环境中稳定工作固化规则、脚本、测试、数据、验收标准和权限正式开发、团队协作、持续交付
Loop Engineering让实现根据真实反馈持续收敛Review → Repair → Validate → Feedback缺陷修复、重构、迁移、质量提升

三者不是互斥选择，而是一条成熟路径：

text
模糊想法
  ↓
Vibe Coding：尽快得到可以运行和体验的版本
  ↓
Harness：把隐含要求变成机器可执行的约束
  ↓
Loop：根据测试、浏览器、日志和评审反馈迭代
  ↓
可审查、可复现、可部署的全栈交付物

需要特别说明：Vibe Coding、Harness Engineering 和 Loop Engineering 在本文中是工程操作模式，不应都理解成 Codex 的固定按钮或斜杠命令。Codex 官方文档明确提供或讨论了相邻能力，例如 /plan、可用时的 /goal、/review、AGENTS.md、浏览器验证以及 Review/Repair/Validate 闭环。

#一、先建立正确的 Codex 心智模型

#1. Codex 是受约束的工程执行者

一个高质量 Codex 任务通常包含：

  1. 目标：最终要得到什么行为或交付物。
  2. 上下文：相关模块、入口、复现步骤、设计稿或接口契约。
  3. 边界：哪些 API、文件、数据库结构或用户行为不能改变。
  4. 验收：必须运行什么测试，如何证明任务完成。

OpenAI 的提示文档建议从结果开始描述，并根据需要补充 Goal、Context、Output 和 Boundaries；针对 Codex，还应指向相关代码或复现步骤，并明确如何验证修改。Prompting Codex

推荐提示词骨架：

text
目标：
实现/修复……

上下文：
- 后端模块：……
- 前端页面：……
- 接口契约：……
- 复现步骤：……

约束：
- 不修改……
- 保持向后兼容……
- 不引入新的生产依赖……

验收标准：
- 后端测试……
- 前端测试……
- 浏览器验证……
- 输出执行过的命令、结果和仍存在的风险。

#2. 让 Codex 对“完成”提供证据

“代码已经改完”不是完成。完成必须对应可检查的证据：

  • 文件和差异符合任务范围。
  • 编译、静态检查和相关测试通过。
  • 数据库迁移可以前进，必要时可以回退。
  • 前端真实运行并检查关键状态。
  • API 调用、错误处理和权限边界符合契约。
  • 没有把测试失败、未运行测试或环境问题描述成成功。

Codex Goals 的官方说明也强调证据式完成：完成审计应对照文件修改、执行命令、测试、基准结果、生成物或研究证据，而不是因为预算耗尽或代理停止就判定完成。Using Goals in Codex

#3. 根据任务规模选择工作模式

任务推荐方式
解释一段代码、修改一个局部函数直接对话，明确文件和输出
有明确复现步骤的 BugReproduce → Fix → Regression Test → Reproduce Again
跨模块需求、架构调整先 /plan，确认方案后再实现
长时间、多阶段目标先规划；可用时通过 /goal 保存线程级目标
UI 创意和产品原型Vibe Coding + 实时浏览器反馈
可重复维护任务Harness + Headless/Automation + Loop
合并或发布前检查测试流水线 + /review + 人工审查

官方文档建议多步骤任务可以先用 /plan 调研和提出方案；Goal Mode 可用时，再用 /goal 保存持续目标。/review 可用于本地工作树审查，并在修复后再次运行以确认问题已解决。Prompting Codex

#二、Vibe Coding：快速探索，但不要无证据交付

#1. 什么是可控的 Vibe Coding

Vibe Coding 的价值是降低“想法 → 可体验结果”的成本。它适合：

  • 从自然语言生成一个最小可用页面。
  • 根据截图实现 UI。
  • 快速试验交互、视觉风格或信息架构。
  • 验证一个 API、组件库或 AI 能力是否可行。
  • 在正式设计前创建可讨论的原型。

OpenAI 的概念验证指南推荐先形成视觉方向，再实现最小有用原型，并在浏览器中验证；第一版工作后，继续在同一上下文中提出范围明确的小修改。Get from idea to proof of concept

#2. 推荐的具体操作流程

#第一步：定义体验目标，而不是一次写完规格

text
为内部运营人员创建一个订单异常处理原型。

核心流程：
1. 查看异常订单列表。
2. 按异常类型筛选。
3. 打开订单详情。
4. 记录处理结果。

先实现可以体验的前端原型，使用 React + TypeScript。
数据先用本地 mock，不接真实后端。
必须包含 loading、empty、error 和 success 状态。

#第二步：让第一版尽快运行

要求 Codex：

  • 使用现有项目结构和组件库。
  • 只实现一个核心纵向流程。
  • 启动开发服务器。
  • 告知本地 URL 和具体路由。
  • 不在第一轮提前建设复杂权限、抽象层或通用平台。

#第三步：在浏览器中观察

不要只阅读 JSX、CSS 或截图。至少检查：

  • 首屏层级和主操作是否清晰。
  • 窄屏和宽屏布局。
  • 加载、空数据、错误、禁用和提交中状态。
  • 表单校验和错误提示。
  • 键盘导航、焦点和基础可访问性。
  • 控制台错误、网络失败和重复提交。

官方 Codex 文档对 UI 紧密迭代的建议是：保持开发服务器运行，使用小而具体的提示逐步修改，在浏览器中审查每次变化，并保存喜欢的版本。Iterate on UI with live updates

#第四步：一次只改变一个维度

推荐：

text
只修改订单详情抽屉：
- 提高关键信息的视觉层级；
- 把危险操作移到次要区域；
- 保持 API 和数据结构不变；
- 同时检查移动端。

不推荐：

text
让整个系统更高级、更现代，顺便优化代码和数据库。

#第五步：为满意版本建立检查点

  • 运行前端 lint、类型检查和构建。
  • 保存 Git commit 或至少检查完整 diff。
  • 记录确定下来的颜色、间距、组件和交互规范。
  • 把稳定规则写入 AGENTS.md、设计文档或测试。
  • 再进入真实后端和生产质量阶段。

#3. Vibe Coding 的退出条件

出现下列任一情况时，应从 Vibe 模式切换到 Harness 模式：

  • 开始接入真实用户、权限、支付或敏感数据。
  • API 和数据库结构需要长期维护。
  • 两个以上开发者需要协同。
  • 同类错误开始重复发生。
  • 每次改动都可能影响多个模块。
  • 需要部署、回滚、审计或服务等级保证。

#4. Vibe Coding 常见风险

风险典型表现控制方式
只看界面，不看行为页面漂亮但提交失败浏览器 + 网络请求 + E2E 验证
随意改变技术栈重写现有框架或引入大量依赖在提示和 AGENTS.md 中锁定栈与边界
生成假接口前端 mock 与真实 API 不一致OpenAPI/JSON Schema 作为契约
缺少异常状态只实现 happy path明确 loading/empty/error/permission 状态
不检查安全把鉴权放在前端、泄露密钥后端强制鉴权，密钥只来自安全配置
大批量改动UI、数据模型、架构同时变化小步修改、频繁 diff、检查点提交
“能运行”等于“可发布”无测试、无日志、无迁移策略进入 Harness 和 Loop 后再交付

#三、Harness Engineering：让 Codex 在“成功跑道”上工作

#1. Harness 的含义

本文中的 Harness，可以理解为包围 Codex 的工程执行环境：

text
项目规则 + 可发现的上下文 + 可重复命令 + 测试数据
+ 自动验证 + 浏览器/日志反馈 + 权限边界 + 审计记录

好的 Harness 不需要 Codex 猜测：

  • 项目怎么启动。
  • 哪些目录是后端、前端、契约和迁移。
  • 使用什么 Java、Node 和包管理器版本。
  • 最小相关测试和完整测试分别怎么运行。
  • 什么算破坏兼容性。
  • 哪些操作需要人工批准。
  • 完成后必须报告哪些证据。

#2. 推荐的全栈 Harness 结构

text
repo/
├── AGENTS.md
├── README.md
├── docs/
│   ├── architecture.md
│   ├── decisions/
│   └── api/openapi.yaml
├── backend/
│   ├── pom.xml
│   ├── src/main/
│   └── src/test/
├── frontend/
│   ├── package.json
│   ├── src/
│   └── tests/
├── e2e/
│   └── playwright/
├── db/
│   └── migration/
├── scripts/
│   ├── dev.sh
│   ├── verify-fast.sh
│   └── verify-full.sh
├── docker-compose.yml
└── .github/workflows/

目录名可以不同，关键是入口明确、命令稳定、失败信息可操作。

#3. 把长期规则写入 AGENTS.md

官方建议保持 AGENTS.md 简洁，用于每次都应遵循的构建/测试命令、评审预期、仓库约定和目录特定规则；反复发生的错误和 PR 反馈应沉淀进去，形成反馈闭环。AGENTS Guidance

适合 Java 全栈仓库的示例：

markdown
# Project instructions

## Stack
- Backend: Java 21, Spring Boot, Maven Wrapper.
- Frontend: React, TypeScript, npm.
- API contract: `docs/api/openapi.yaml`.
- Database migrations: Flyway; never edit an applied migration.

## Boundaries
- Preserve public API compatibility unless the task explicitly authorizes a breaking change.
- Never put authorization decisions only in the frontend.
- Never commit secrets, tokens, generated credentials, or local environment files.
- Keep unrelated user changes intact.

## Verification
- Backend focused test: `./mvnw -pl backend -Dtest=<TestName> test`
- Backend full test: `./mvnw -pl backend verify`
- Frontend: `npm --prefix frontend run lint`
- Frontend type check: `npm --prefix frontend run typecheck`
- Frontend test: `npm --prefix frontend test -- --run`
- Frontend build: `npm --prefix frontend run build`
- E2E: `npm --prefix e2e test`

## Delivery
- Report changed files, commands run, results, untested areas, and remaining risks.
- Do not claim success when a required check was skipped or failed.

不要把完整百科、长篇架构史或每次任务才需要的临时约束全部塞进 AGENTS.md。稳定规则放 AGENTS.md，详细说明放专门文档，可复用复杂流程做成 Skill，外部系统通过 MCP/连接器访问。

#4. 把验收标准做成机器可执行命令

Harness 的核心不是“更多文档”，而是“更好的反馈信号”。

建议至少提供两个入口：

bash
# 快速反馈：适合每次小改动
./scripts/verify-fast.sh

# 完整反馈：适合 PR 或交付前
./scripts/verify-full.sh

快速检查可以包含：

  • 修改模块的编译。
  • 相关单元测试。
  • 前端 lint 和类型检查。
  • OpenAPI 或 Schema 校验。

完整检查可以包含：

  • 后端全部测试和集成测试。
  • Testcontainers 数据库测试。
  • 前端测试与生产构建。
  • 端到端浏览器测试。
  • 数据库迁移验证。
  • 依赖、许可证和安全扫描。

脚本应满足：

  • 非零退出码表示失败。
  • 输出明确指出失败位置和修复方向。
  • 可在本地和 CI 中重复运行。
  • 不依赖某个开发者机器里的隐藏状态。
  • 不自动执行不可逆的生产操作。

#5. 为 Codex 提供最小但充分的上下文

优先提供：

  • 复现步骤和错误日志。
  • 相关入口文件与最近调用方。
  • OpenAPI、Schema、数据库迁移和领域规则。
  • 一两个符合团队风格的相邻实现。
  • 相关测试和测试数据。

避免：

  • 无差别附加整个文档库。
  • 把过期设计稿当成当前事实。
  • 同时提供互相冲突但不标注优先级的规则。
  • 在提示里粘贴密钥、生产数据或客户隐私信息。

#6. 把反复任务封装为 Skill 或自动化

当一个流程稳定并重复出现，例如：

  • 新增 Spring Boot CRUD 垂直切片。
  • 根据 OpenAPI 同步 Java DTO 与 TypeScript Client。
  • 排查线上接口慢查询。
  • 生成数据库迁移并做兼容性检查。
  • 发布前运行全栈验收。

就应把“使用时机、输入、步骤、命令、预期输出、失败处理”封装为可复用 Skill 或脚本，而不是每次重新描述。OpenAI 的 Codex 最佳实践也建议把重复工作转为 Skills，把稳定工作流自动化，并用 MCP 连接外部系统。Codex best practices

#四、Loop Engineering：用实际结果推动下一轮

#1. 标准闭环

OpenAI Cookbook 给出的迭代修复模式包含三个阶段：

  1. Review：只检查并输出结构化问题，不编辑。
  2. Repair：根据问题和上次验证反馈进行小范围修改。
  3. Validate：运行真正的检查，将剩余问题反馈给下一轮。

其关键不是“多执行几次”，而是每一轮都使用新的验证证据。Build iterative repair loops with Codex

text
Review
  ↓ findings
Repair
  ↓ changed artifact
Validate
  ↓ pass / remaining delta
┌───────────────┐
│ 未通过：进入下一轮 │
└───────┬───────┘
        └────────────→ Repair

#2. Java 全栈开发闭环

#Review

要求 Codex：

  • 读取需求、现有实现、测试和契约。
  • 找到最可能的根因或缺口。
  • 列出涉及的后端、前端和数据层。
  • 不立即重写代码。
  • 输出风险、假设和最小修复方向。

#Repair

要求 Codex：

  • 只修复当前有证据支持的问题。
  • 保持 API、数据库和用户行为边界。
  • 添加回归测试。
  • 避免顺手进行无关重构。
  • 保留用户已有修改。

#Validate

建议按成本从低到高运行：

  1. 编译、格式和静态检查。
  2. 最小相关单元测试。
  3. 模块测试和集成测试。
  4. 数据库迁移与真实依赖测试。
  5. 前端生产构建。
  6. 浏览器端到端流程。
  7. /review 或独立人工评审。

#Feedback

将失败转换为下一轮可操作输入：

json
{
  "passed": false,
  "failed_check": "OrderControllerIT.shouldRejectDuplicateSubmission",
  "evidence": "expected 409 but received 500",
  "remaining_delta": [
    "duplicate-key exception is not mapped to Conflict response",
    "frontend still allows repeated submission while request is pending"
  ]
}

下一轮只处理 remaining_delta，不要重新从模糊原始需求开始。

#3. Loop 的停止条件

生产闭环必须有显式停止条件：

  • 所有必需验证通过。
  • 达到最大尝试次数。
  • 连续两轮的剩余问题没有实质变化。
  • 修改开始扩大到未授权范围。
  • 需要产品、架构、安全或数据负责人判断。
  • 需要不可逆操作或生产权限。

OpenAI Cookbook 同样建议在验证通过、达到最大次数、剩余差异不再变化或需要人工评审时停止，并保留每轮的发现、修改、验证结果和剩余差异作为审计记录。Generalize to a continuous loop

#4. 一个可直接使用的闭环提示词

text
修复订单重复提交问题，使用 Review → Repair → Validate 闭环，最多 3 轮。

Review：
- 先复现问题；
- 检查前端按钮状态、后端幂等策略、事务和数据库唯一约束；
- 在确认根因前不要大规模修改。

Repair：
- 每轮只做解决当前证据所需的最小修改；
- 保持现有 API 兼容；
- 添加回归测试。

Validate：
- 运行最小相关测试；
- 运行 backend verify、frontend typecheck/build；
- 在浏览器中验证快速双击和网络重试；
- 每轮输出执行命令、结果和 remaining delta。

停止：
- 全部验收通过；
- 连续两轮没有收敛；
- 需要修改公开 API 或生产数据；
- 达到 3 轮。

#五、Java 全栈开发的重点注意事项

#1. 先守住契约，再分别实现前后端

对跨端需求，先明确：

  • URL、HTTP 方法和状态码。
  • 请求/响应字段、必填项、枚举和空值语义。
  • 分页、排序、过滤方式。
  • 错误结构和错误码。
  • 时间、时区、金额和精度。
  • 认证与授权规则。
  • 兼容策略和废弃周期。

推荐将 OpenAPI 或等价 Schema 作为单一契约来源。提示 Codex：

text
先更新并校验 OpenAPI，再实现 Spring Boot 接口和 TypeScript Client。
如果需求会造成破坏性变更，停止并说明影响，不要自行改变契约。

#2. 后端不要只验证 Controller

至少检查：

  • Controller：输入边界、状态码、序列化。
  • Application/Service：业务规则和用例编排。
  • Domain：不变量是否在可信边界内执行。
  • Repository：查询语义、锁、批量行为和 N+1。
  • Transaction：事务范围、重试、回滚和事件发布时机。
  • Database：索引、唯一约束、迁移和历史数据兼容。
  • Security：认证、资源级授权、越权访问和审计。
  • Observability：日志、指标、Trace 和关联 ID。

不要接受“前端隐藏按钮”作为授权方案；授权必须在服务端执行。

#3. 数据库迁移必须面向真实发布

要求 Codex检查：

  • 已应用的迁移不可直接修改。
  • 新旧应用版本并存时是否兼容。
  • 大表 DDL 是否会长时间锁表。
  • 新的非空字段如何回填。
  • 索引创建、数据清理和回滚策略。
  • 是否需要 expand → migrate → contract 分阶段发布。

#4. 前端必须覆盖非理想状态

每个数据页面至少考虑：

  • Initial/loading。
  • Empty。
  • Partial data。
  • Error/retry。
  • Unauthorized/forbidden。
  • Submitting/disabled。
  • Success feedback。
  • Stale data/conflict。

还应检查：

  • TypeScript 类型是否来自或对齐 API 契约。
  • 表单校验与后端规则是否一致。
  • 请求取消、竞态和重复提交。
  • 响应式布局。
  • 键盘、焦点、标签和颜色对比。
  • 浏览器控制台与网络错误。

#5. 测试应形成分层反馈

层次主要目的示例
单元测试快速验证业务规则JUnit、Mockito、Vitest
Slice/组件测试验证框架边界@WebMvcTest、React Testing Library
集成测试验证数据库和服务组合Spring Boot Test、Testcontainers
契约测试防止前后端或服务间漂移OpenAPI 校验、消费者契约
E2E验证真实用户路径Playwright
人工探索发现自动化未覆盖的体验问题浏览器、辅助技术、弱网

Codex 的默认验证顺序应是“最小相关测试 → 模块测试 → 全栈验收”，避免每个微小改动都先跑最慢的完整流水线，也避免只跑单测就宣称全栈功能完成。

#6. 启动真实应用做最后验证

对全栈功能，至少完成一次：

text
启动依赖 → 启动 Spring Boot → 启动前端
→ 打开浏览器 → 执行核心流程 → 检查网络、控制台与服务日志

截图只能提供视觉要求，无法表达 hover、校验、键盘操作等行为；官方 Codex 提示指南也要求用文字补足截图未显示的行为，并建议启动开发服务器进行验证。Prototype from a screenshot

#六、推荐的端到端操作模式

#模式 A：小型明确修改

text
Inspect → Edit → Focused Test → Diff Review → Report

适用：文案、局部校验、小函数、小组件。

#模式 B：Bug 修复

text
Reproduce → Locate Cause → Add Regression Test
→ Minimal Fix → Re-run Reproduction → Broader Checks

官方 Bug 修复示例强调提供可执行复现步骤、限制范围、要求最小修复和回归测试，并在修复后重新执行复现流程。Fix a bug with Codex

#模式 C：跨端功能

text
Clarify Acceptance Criteria
→ Define/Confirm API Contract
→ Plan Vertical Slice
→ Backend + Migration
→ Frontend Integration
→ Contract/Integration Tests
→ Browser E2E
→ Review

纵向切片应尽快贯通一个真实流程，避免先生成大量没有集成的 Controller、DTO、页面和假数据。

#模式 D：大型重构

text
/plan
→ Dependency and Behavior Baseline
→ Milestones with Stable Interfaces
→ Implement One Milestone
→ Tests and Review
→ Commit/Checkpoint
→ Next Milestone

不要让一次 Codex 任务同时承担“大规模移动文件、改变公开 API、替换框架、迁移数据、重做前端”的全部风险。

#模式 E：Vibe → Production

text
One-shot Prototype
→ Browser Feedback
→ Scoped Visual Iterations
→ Freeze UX Direction
→ Define API/Domain Contracts
→ Add Harness
→ Implement Real Vertical Slice
→ Closed-loop Validation
→ Security/Performance/Release Review

#模式 F：持续维护 Loop

text
Scheduled/Triggered Review
→ Structured Findings
→ Bounded Repair
→ Automated Validation
→ Audit Record
→ Auto-stop or Human Gate

适用于依赖升级、过期 API、文档代码样例、静态检查修复和有限范围的代码现代化。自动化范围越大，越需要严格的目录、命令、网络和审批边界。

#七、提示词与交互技巧

#1. 先说结果，少做微观遥控

应描述结果、关键上下文和不可违反的边界。除非流程本身是要求，否则不要把 Codex 限死在你预想的每个内部步骤中。官方提示指南也建议优先描述结果，让模型有空间搜索、比较和调整方案。Prompting overview

#2. 长任务需要计划和进度

要求：

  • 拆分任务。
  • 在关键工具操作前简短说明。
  • 维护 TODO 或验收清单。
  • 每次工具结果后检查是否仍满足目标。
  • 完成前做最终审计。

OpenAI 的编码提示建议为长时间 Agent 任务加入计划、持续性、关键操作说明和 TODO/量表，以降低遗漏。Prompt engineering: Coding

#3. 工作中及时 Steer，不必等它完成

Codex 工作过程中：

  • Steer：将新要求加入当前执行，用于纠正方向或补充关键信息。
  • Queue：把下一项要求排到之后，不干扰当前任务。

CLI 中，工作时按 Enter 可将消息 Steer 到当前 turn，Tab 可排队到下一 turn，具体以当前版本快捷键说明为准。Steering and queuing

#4. 明确“不要做什么”

高价值边界示例：

text
- 不改变公开 API。
- 不编辑已执行的 Flyway migration。
- 不升级无关依赖。
- 不覆盖工作区中已有的未提交修改。
- 不发送消息、不部署、不操作生产数据。
- 无法运行测试时必须明确说明，不能推测为通过。

#5. 用 /review 建立第二视角

交付前：

text
/review Focus on:
- correctness and edge cases
- authorization and data exposure
- transaction and concurrency risks
- API compatibility
- missing tests

修复评审问题后再次运行 /review。但模型评审不能替代高风险代码的人工审批。

#八、反模式清单

  • 只说“帮我完善一下”，不给目标和验收。
  • 把一个大型系统一次性交给 one-shot 生成。
  • 让 Codex 修改代码但不允许运行任何验证。
  • 只看 diff，不运行应用或复现用户流程。
  • 让前端类型、Java DTO 和 OpenAPI 分别手写并长期漂移。
  • 为了测试通过而删除测试或弱化断言。
  • 自动循环没有最大次数、收敛判断和人工闸门。
  • 把生产密钥、客户数据或访问令牌放进提示词或仓库。
  • 将所有规则塞进根 AGENTS.md，导致指令冗长冲突。
  • 每次纠正 Codex，却不把重复问题沉淀为规则、测试或脚本。
  • 在一个修改中混入无关格式化、依赖升级和架构重构。
  • 因为 Codex 报告“完成”就跳过 Git diff、测试结果和浏览器检查。

#九、个人推荐的最小落地方案

针对 Java + Spring Boot + TypeScript 全栈项目，先完成以下六件事：

  1. 根目录维护简洁的 AGENTS.md。
  2. 固化 verify-fast 和 verify-full 两套命令。
  3. 用 OpenAPI 管理前后端契约。
  4. 为数据库和外部依赖建立可重复的集成测试环境。
  5. 用 Playwright 覆盖最关键的 3～5 条用户路径。
  6. 所有 Codex 任务都要求报告：改了什么、跑了什么、结果如何、什么没验证。

之后再逐步增加：

  • 目录级 AGENTS.md。
  • 复用 Skills。
  • MCP 外部系统连接。
  • /review 质量门。
  • 自动化维护 Loop。
  • 基于真实失败案例持续增强 Harness。

#十、可复制的全栈任务模板

text
你正在维护一个 Java 21 + Spring Boot + React/TypeScript 项目。

目标：
[描述用户可以观察到的最终行为]

范围：
- backend: [模块/路径]
- frontend: [模块/路径]
- contract: [OpenAPI/Schema 路径]
- database: [迁移路径]

约束：
- 保持现有公开 API 向后兼容；
- 不修改已应用迁移；
- 不升级无关依赖；
- 不覆盖已有未提交改动；
- 鉴权必须由后端执行；
- 不使用真实密钥或生产数据。

工作方式：
1. 先检查 AGENTS.md、相关实现、测试和契约。
2. 若涉及多个模块，先给出简洁计划和验收矩阵。
3. 优先实现最小完整纵向切片。
4. 使用 Review → Repair → Validate 闭环。
5. 每轮只处理有证据支持的 remaining delta。

验收：
- 运行最小相关测试；
- 运行后端 verify；
- 运行前端 lint、typecheck、test、build；
- 验证 OpenAPI/Schema；
- 启动应用并在浏览器验证核心流程及错误状态；
- 检查最终 diff；
- 输出变更文件、执行命令、结果、未验证项和剩余风险。

停止条件：
- 所有验收通过；
- 连续两轮没有收敛；
- 需要破坏性 API/数据库修改；
- 需要生产权限或人工业务决策。

#易错点与局限

  1. Codex 的功能、命令和界面会演进，/plan、/goal、快捷键和具体入口应以当前产品界面与官方文档为准。
  2. Vibe Coding 可以快速发现产品方向，但不能代替领域建模、安全设计、容量规划和发布治理。
  3. Harness 的质量决定了自动 Loop 的上限；测试或验收标准错误，循环会稳定地产生错误结果。
  4. 模型评审和自动测试都有盲区，高风险权限、支付、隐私、迁移和生产操作需要人工审批。
  5. 并非所有任务都适合自动循环。结果难以客观验证、修改不可逆或反馈周期很长时，应缩小范围并增加人工闸门。

#下一步学习建议

  1. 使用本文模板完成一个 Spring Boot + React 的最小纵向功能。
  2. 为当前仓库补充 verify-fast 和 verify-full。
  3. 选择一个真实 Bug，实践三轮以内的 Review/Repair/Validate。
  4. 将重复发生的一个 Codex 错误沉淀为 AGENTS.md 规则和自动测试。
  5. 为一个前端页面建立“浏览器观察 → 小步修改 → 再验证”的 Vibe Coding 流程。
