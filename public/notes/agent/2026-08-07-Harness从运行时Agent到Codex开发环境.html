Harness：从运行时 Agent 到 Codex 开发环境

一句话：Harness 不是模型，也不是某个框架；它是围绕模型建立的“成功环境”，把上下文、工具、权限、状态、反馈、评测和恢复变成可执行约束。

双场景：第一部分开发企业智能审批 Agent；第二部分说明在 Codex 开发普通软件时怎样建设仓库 Harness。审批示例使用 Java 25，并分别给出无 Agent 框架与 Spring AI 2.0.0 的实现。

快速阅读： 核心结论 · 概念模型 · 审批 Agent · Codex 开发 · 线上应用 · 练习 · 资料

核心结论

  1. 能力不等于可靠性。模型能调用工具，只说明它具备行动能力；能否在正确租户、正确权限、正确数据版本上行动，由 Harness 决定。
  2. Harness 的输出是证据链。每次运行应能回答：加载了什么规则、调用了什么工具、为何允许、花费多少、怎样验证、失败后如何恢复。
  3. 文字规则必须有机械护栏。“不要越权”需要落实为服务端鉴权；“必须测试”需要落实为命令、CI 和失败即阻断。
  4. 业务 Agent 与编码 Agent 的 Harness 同构但不共享状态。审批 Agent 的状态是 case、证据和授权；Codex 的状态是仓库、diff、测试和任务进度。
  5. 先做 Harness，再谈长 Loop 和复杂 Graph。缺少真实反馈与权限边界时，循环越长、编排越复杂，错误只会扩散得更远。

概念模型

目标、规则与完成定义业务政策、项目约束、风险等级、成功标准
状态与上下文最小相关事实、版本、身份、预算，不等于全部聊天历史
模型与决策适配器可替换、可评测；只产生建议或动作意图
工具与外部系统结构化参数、最小权限、超时、幂等、结果校验
反馈、评测与观测测试、规则结果、日志、指标、Trace、人工意见
安全、审计与恢复底座鉴权、审批、版本、checkpoint、回滚与事件记录

读图：模型只是中间一层。上层限制它为什么行动，下层决定行动能否发生并提供可验证反馈。

何时需要显式建设 Harness

  • 模型会读取私有数据、调用外部工具或产生副作用；
  • 任务超过一次调用，需要重试、持久化或人工接管；
  • 结果必须被测试、审计、复现或满足 SLO；
  • 多个团队、Agent 或环境必须遵守一致的开发规则。

一次性的只读摘要可以使用轻量 Harness；不要为了展示“Agent 架构”给简单函数套上数据库、队列和复杂权限系统。

第一部分：智能审批 Agent 开发

无 Agent 框架
ApprovalService
ModelPort + ToolRegistry
PolicyGate + AuditSink
Spring AI
ApprovalService
ChatClient + ToolCallback
同一 PolicyGate + AuditSink

两条轨道只替换 AI 适配层。业务状态、鉴权、最终批准权和执行副作用不能随着框架切换。

从零开发与接入现有项目

  1. 列出输入数据、允许读取的系统、可能产生的副作用和必须人工批准的动作。
  2. 定义结构化 ApprovalProposal，让模型只返回建议、理由、证据引用和下一步，不返回“已批准”。
  3. 把模型、工具、政策门禁、审计、时钟和预算做成端口，先用 fake 实现跑通正常与拒绝路径。
  4. 在工具内部根据认证主体重新鉴权；模型参数中的 tenant、user、role 一律不可信。
  5. 接入真实模型前先建立契约测试、注入攻击样本和操作审计；接入后再做离线评测与 shadow 流量。

无框架实现：Java 25 端口与硬门禁

public record ApprovalContext(
        String tenantId, String requesterId, long caseVersion,
        java.util.Set<String> roles) {}

public record ApprovalProposal(
        Decision recommendation,
        java.util.List<String> evidenceIds,
        java.util.List<String> missingFields,
        String rationale) {}

public interface ModelPort {
    ApprovalProposal propose(ApprovalContext context, EvidenceBundle evidence);
}

public interface ApprovalTool<I, O> {
    String name();
    O execute(ApprovalContext trustedContext, I input);
}

public interface PolicyGate {
    GateResult authorize(ApprovalContext context, ProposedAction action);
}

public interface AuditSink {
    void append(AuditEvent event);
}

关键点是 ApprovalContext 来自认证态和数据库，而不是模型生成；PolicyGate 在每次工具动作之前运行。

public final class ApprovalHarness {
    private final ModelPort model;
    private final PolicyGate policy;
    private final EvidenceService evidence;
    private final AuditSink audit;

    public ApprovalProposal propose(ApprovalContext context, java.util.UUID caseId) {
        var snapshot = evidence.loadAuthorized(context, caseId);
        var proposal = model.propose(context, snapshot);
        var result = policy.authorize(context, ProposedAction.publish(proposal));
        audit.append(AuditEvent.of(context, caseId, snapshot.hash(), proposal, result));
        if (!result.allowed()) throw new SecurityException(result.reasonCode());
        return proposal; // 只是提案，不写最终审批决定
    }
}

Spring AI 实现：替换 AI 适配器

Spring AI 2.0.0 的 ChatClient 可映射 Java 实体，并通过 ToolCallingAdvisor 管理工具调用；官方也提供用户控制工具执行的模式。高风险审批更适合关闭不透明的自动执行，或让工具本身强制门禁。

@Component
final class SpringAiProposalModel implements ModelPort {
    private final ChatClient chatClient;

    SpringAiProposalModel(ChatClient.Builder builder, ApprovalReadTools tools) {
        this.chatClient = builder
                .defaultSystem("""
                    你是审批提案助手。只能基于工具返回的证据提出建议；
                    不得声称已批准，不得请求或执行写操作。
                    """)
                .defaultTools(tools)
                .build();
    }

    @Override
    public ApprovalProposal propose(ApprovalContext context, EvidenceBundle evidence) {
        return chatClient.prompt()
                .user(u -> u.text("caseVersion={version}; evidence={evidence}")
                        .param("version", context.caseVersion())
                        .param("evidence", evidence.safeProjection()))
                .call()
                .entity(ApprovalProposal.class, spec -> spec.validateSchema());
    }
}

不要默认记录完整 Prompt/Completion。Spring AI 的 Observability 默认不导出这些高基数且可能敏感的内容，生产环境应优先记录模板版本、模型、Token、耗时、工具名、停止原因和脱敏 traceId。

第二部分：代码开发过程中的使用

在 Codex 中，Harness 不是一个开关，而是一组互补表面。官方 Customization 文档明确：AGENTS.md 负责持久项目指导，Skills 封装可复用流程，MCP 连接外部工具与上下文，Subagents 处理可独立委派工作；项目 .codex/config.toml、Hooks、sandbox 和 approval 提供执行约束。

Codex 表面项目中怎么用不要放什么验证方法
AGENTS.md仓库地图、常用命令、边界、完成定义几千行百科和易过期细节让 Codex复述已加载规则
Skills发布、迁移、文档、评测等重复流程只适用一次的任务背景用触发/不触发提示测试
MCP / AppsIssue、文档、日志、设计、业务系统无授权的任意写接口检查工具权限与审计事件
Sandbox / approval限制写目录、网络与高风险命令把文字警告当权限系统在只读/自动模式分别演练
Hooks + CI格式、结构、安全和发布门禁模型可忽略的“建议检查”制造违规并观察失败
Worktree一项任务一个隔离工作区多个 Agent 同写同一分支确认分支、基线与差异范围

Codex 仓库 Harness 最小模板

# AGENTS.md
## Repository map
- `approval-domain/`: 纯 Java 领域模型，不依赖 Spring AI
- `approval-ai/`: ModelPort 与 Spring AI 适配器
- `approval-app/`: HTTP、持久化、鉴权和审计

## Commands
- Fast check: `./mvnw -pl approval-domain test`
- Full check: `./mvnw verify`

## Guardrails
- 模型不得写最终审批状态；任何副作用都经过 PolicyGate。
- 先写失败测试，再做最小实现；完成声明必须附新鲜测试输出。
- 不提交密钥、生产数据或未经脱敏的 Prompt/Completion。
# .codex/config.toml（项目被信任后才加载）
sandbox_mode = "workspace-write"
approval_policy = "on-request"

[sandbox_workspace_write]
network_access = false

[[hooks.PreToolUse]]
[[hooks.PreToolUse.hooks]]
command = 'python3 .codex/hooks/check_policy.py'

开发操作：先让 Codex 读取仓库并报告现实状态，再给 Goal、Context、Constraints、Done when；为功能创建隔离 worktree；让测试、浏览器行为和日志成为真实反馈；最后用 /review 或专用 reviewer 检查明确范围的 diff。

线上应用、观测与验收

指标审批 AgentCodex 开发 Harness告警信号
权限工具拒绝率、越权尝试approval 请求与拒绝高风险动作未触发门禁
质量结构化输出通过率、证据覆盖率测试通过率、review 返工率无证据完成、schema 错误激增
成本每 case Token/模型/工具次数每任务轮数与耗时预算消耗异常、工具风暴
恢复checkpoint 恢复率、幂等冲突worktree/commit 可恢复性重复副作用或无法重放

上线顺序建议：fake 工具的契约测试 → 脱敏数据离线评测 → 只读 shadow → 人工确认的辅助决策 → 只对低风险动作开放受控自动化。Harness 的版本应与模型、Prompt、工具 schema 和政策版本一起记录。

失败模式与边界

  • 巨型指令文件：把 AGENTS.md 或 system prompt 当百科，导致重要约束被稀释。修复：短地图、深文档、机械检查。
  • 工具信任模型身份：模型传入 tenantId 后直接查询。修复：从认证态注入并在服务端授权。
  • 只记最终文本：无法解释提案来自哪版证据。修复：记录 caseVersion、evidence hash、模型/提示/工具/策略版本。
  • 观测泄密：把合同、个人信息和 Prompt 全量写日志。修复：默认不记录正文，分级脱敏与最短保留。
  • Harness 过度建设：简单只读任务也上队列、Graph 和多 Agent。修复：从普通函数/单次调用开始。

练习与验收

  1. 为审批 Agent 写一个 fake ModelPort，证明无权限角色无法发布提案，且审计事件仍被记录。
  2. 为现有 Java 项目写不超过 100 行的 AGENTS.md，只保留地图、命令、边界与 Done when。
  3. 故意让工具返回超时和脏 schema，验证系统会拒绝、重试或升级，而不是继续猜测。

验收标准：能画出六层 Harness；能指出 Prompt 规则和服务端护栏的区别；能在不改领域测试的情况下替换无框架模型端口与 Spring AI 适配器；能让 Codex 从仓库获得新鲜测试、日志或浏览器证据。
