Graph：从审批状态编排到 Codex 开发流程

一句话：Graph 把多个步骤的状态、执行单元和转换关系显式化，适合分支、并发、循环、人工等待和故障恢复；它的价值是可控与可恢复，不是让系统显得高级。

双场景：审批 Agent 使用 Java 25 无框架状态机与 Spring AI 模型节点；代码开发部分用 Graph 分析 Codex 的规格—计划—实现—审查—验证流程，不声称 Codex 内置了通用 Graph 引擎。

快速阅读： 核心结论 · 概念模型 · 审批 Agent · Codex 开发 · 线上应用 · 资料

核心结论

  1. Graph = State + Node + Edge + Router + Checkpoint。节点完成工作，边决定可达路径，路由根据状态选边，checkpoint 让长流程能恢复。
  2. Graph 不等于 DAG。审批补件和 review—fix 都可能回到前一节点；允许环时必须设计循环上限和状态单调性。
  3. 模型只是节点实现之一。规则、数据库事务、人工审批、外部 API 和普通 Java 函数同样可以是节点，且常常更可靠。
  4. 状态必须可版本化。只持久化“当前节点”不够；还要保存业务版本、节点输入输出、等待请求、幂等动作与图定义版本。
  5. Codex 开发 Graph 是工程抽象。AGENTS.md、Skills、任务计划、subagent、review 和 CI 能形成阶段与门禁，但官方未把它们统一命名为 Graph。

元素职责设计问题常见错误
State流程的可恢复事实哪些字段可合并？谁能写？如何版本迁移？把完整聊天当 State
Node纯计算、模型、工具或人工任务输入输出和副作用边界是什么？一个节点承担全部业务
Edge合法转换是否允许环、并发、取消和补偿？任何节点都能跳任何节点
Router根据状态选下一条边模型建议还是确定性规则最终决定？用自然语言替代硬规则
Checkpoint保存状态与待处理请求何时保存、怎样恢复、如何防重复？只保存节点名

选择 Graph、Loop 还是普通函数

场景首选理由
一次校验或纯计算普通函数最简单、可测试、无需持久状态
下一步取决于未知工具结果有界 Loop模型动态选择动作，直到可验证停止
固定分支、并行、人工等待、长事务Graph / Workflow路径显式，状态可持久化与恢复
复杂生产 Agent三者组合Graph 管流程，节点内 Loop 处理局部未知，普通函数实现硬规则

Spring AI 负责模型节点，不替代 BPMN/状态机、规则服务、人工任务或数据库事务。

从业务流程到可执行 Graph

  1. 从业务事实画状态转换表，而不是从“需要几个 Agent”开始；标出终态、等待态和禁止回退的状态。
  2. 将规则节点、模型节点、人工节点与副作用节点分开；每个节点定义输入、输出、错误和幂等语义。
  3. 为并行分支定义 merge/reducer，避免多个节点写同一字段产生最后写入获胜。
  4. 在外部调用前后 checkpoint；恢复时读取图版本和业务版本，重新校验待执行动作。
  5. 用状态迁移测试覆盖所有边，再做节点契约、并发、恢复和补偿测试。

无框架实现：Java 25 状态机

public enum ApprovalStage {
    SUBMITTED, VALIDATING, ANALYZING, NEEDS_INFO,
    PENDING_APPROVAL, APPROVED, REJECTED,
    EXECUTING, COMPLETED, FAILED
}

public record ApprovalState(
        java.util.UUID caseId,
        long caseVersion,
        ApprovalStage stage,
        java.util.Map<String, Evidence> evidence,
        ApprovalProposal proposal,
        java.util.Set<String> pendingApproverRoles,
        int revision) {}

@FunctionalInterface
public interface ApprovalNode {
    NodeResult apply(ApprovalState state);
}
public final class ApprovalGraph {
    private final java.util.Map<ApprovalStage, ApprovalNode> nodes;
    private final TransitionPolicy transitions;
    private final CheckpointRepository checkpoints;

    public ApprovalState step(ApprovalState current) {
        var result = nodes.get(current.stage()).apply(current);
        var next = transitions.reduce(current, result);
        transitions.requireLegal(current.stage(), next.stage());
        checkpoints.saveIfVersionMatches(current.revision(), next);
        return next;
    }

    public ApprovalState resume(java.util.UUID caseId) {
        var saved = checkpoints.load(caseId);
        return transitions.revalidateAgainstCurrentPolicy(saved);
    }
}

节点不直接跳转；它返回事实，由 TransitionPolicy 统一决定合法状态。乐观锁避免两个恢复任务同时推进同一 case。

Spring AI 实现：模型作为受限节点

@Component
final class ProposalNode implements ApprovalNode {
    private final ChatClient client;

    @Override
    public NodeResult apply(ApprovalState state) {
        var proposal = client.prompt()
                .system("基于给定证据生成提案；不得批准，不得发起写操作。")
                .user(stateProjection(state))
                .call()
                .entity(ApprovalProposal.class, spec -> spec.validateSchema());
        return NodeResult.fact("proposal.generated", proposal);
    }
}

// Router 仍由确定性代码拥有
ApprovalStage route(ApprovalState state) {
    if (state.proposal().hasPolicyConflict()) return ApprovalStage.REJECTED;
    if (!state.proposal().missingFields().isEmpty()) return ApprovalStage.NEEDS_INFO;
    return ApprovalStage.PENDING_APPROVAL;
}

若采用 LangGraph4j 等库，可以把 StateGraph、条件边、线程、checkpoint 和并行节点映射到上述概念；但业务授权和迁移策略仍需项目自己设计。

这是本文对工程流程的 Graph 化表达；Codex 提供计划、subagent、review、worktree、Hooks 等能力，但并未把这条图发布为固定 SDLC。

怎样把 Codex 任务组织成 Graph

  1. Node：每个节点产生一个可独立审查的工件，例如规格、测试、一个模块改动或 review 报告。
  2. Edge：只有验证通过才能进入交付；review 发现回到对应实现节点，而不是重做全部工作。
  3. Parallel：只并行互不依赖、写集不重叠的任务，如文档核验与只读代码审计；共享状态修改保持串行。
  4. Human gate：需求取舍、破坏性迁移、权限扩张、外部发布和合并决策由人确认。
  5. Checkpoint：用 Git commit、版本化计划、测试输出和决策记录保存阶段结果，不能只靠聊天上下文。
Task graph: approval-idempotency

T1 复现重复执行并添加失败测试
  └── T2 实现数据库原子 claim
        ├── T3 增加恢复任务与结果查询
        └── T4 更新审计事件与指标
              └── T5 review（正确性 / 安全 / 测试）
                    ├── finding → 返回对应 T2/T3/T4
                    └── clean → T6 full verify
                                  └── 人工决定提交与发布

并行规则：T3 与 T4 只有在接口冻结且写集不重叠时才能并行。
给 Codex 的 Graph 节点契约

Node: T2 数据库原子 claim
Consumes: 失败的并发回归测试、ExecutionRepository 接口
Produces: claim(idempotencyKey, proposalHash) 的唯一语义
Allowed files: approval-app persistence package + migration + scoped tests
Done when: 并发测试通过；重复 key 返回同一 executionId；无先查后写
Next: 只在 review 与最小相关验证通过后开放 T3/T4

Codex 官方 Subagents 文档建议优先把读多写少、独立的探索/测试/日志分析并行化，并对多个 Agent 同时写代码保持谨慎。子 Agent 继承权限模式；并行不会自动解决共享状态冲突。

Microsoft Agent Framework 官方说明 checkpoint 可用于长流程恢复、暂停/继续、审计与迁移，并将待处理人工请求一起保存。无论采用哪个框架，都要测试“在每个节点前后崩溃”的恢复行为。

失败模式与边界

  • 过度编排：三步固定逻辑也建图。修复：先用普通函数，出现持久等待、复杂分支或恢复需求再升级。
  • Graph 只在白板：图与代码真实路径漂移。修复：由同一状态转换定义生成可视化或结构测试。
  • 共享 State 无 reducer：并行节点互相覆盖。修复：字段所有权、幂等 merge 和确定性汇聚。
  • 恢复即重跑：重复扣款或重复创建订单。修复：checkpoint + 幂等结果查询 + 补偿。
  • 把 Codex 工作流当官方固定 Graph：忽略不同任务的必要简化。修复：明确这是项目方法，按风险删减节点。

练习与验收

  1. 为审批状态机列出所有合法边，写参数化测试证明非法跳转全部失败。
  2. 模拟 ANALYZING 节点完成后进程崩溃，验证恢复不会重复调用已成功的预算工具。
  3. 把一个大型 Codex 任务画成 DAG，标注哪些任务可并行、哪些有共享写集、哪些必须人工确认。

验收标准：能区分 Graph、DAG、Loop 与普通函数；能解释 checkpoint 不只是当前节点；能把模型限制在适合的节点；能说明 Codex 开发 Graph 是工程映射而不是官方内置执行引擎。
