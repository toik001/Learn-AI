#多 Agent 协作与编排

多 Agent 不是“多建几个模型客户端”。它是一种用额外调用、状态协调和故障面，换取角色边界、工具最小权限或上下文隔离的架构选择。若这些隔离不能相对单 Agent 基线产生可测净收益，就不应拆分。

本文使用 Java 21、Spring AI 2.0.0 与 Spring Boot 4.0.x / 4.1.x，保持模型供应商中立。整理日期与官方资料检索日期：2026-07-27。

#核心结论

  • 先跑单 Agent 基线，再决定是否拆分。固定同一数据集、模型、工具结果与预算，记录任务质量、端到端延迟、token、工具调用、失败率和运维复杂度；多 Agent 必须在目标指标上有可重复收益，且收益高于新增成本与故障面。
  • 只有隔离带来净收益才拆。不同角色需要互斥权限、长上下文彼此污染、专用提示和评测标准明显不同，或独立分支确能并行降时延时，拆分才有工程理由。“让它们讨论”本身不是理由。
  • Coordinator 必须是显式业务组件。它消费上一课的 ExecutionPlan / PlanStep，负责确定性路由、deadline、取消、去重、版本合并、冲突升级、部分失败策略和审计；不能把这些责任隐藏在自然语言群聊里。
  • 角色隔离要落实为能力隔离。每个角色拥有独立系统策略、输入视图、RoleToolSet 和服务身份；Agent 之间只传经过校验的 AgentHandoff，不共享 API key、数据库密码、完整会话或任意工具目录。
  • 共享状态必须版本化。每次 handoff 携带 correlation ID、来源、证据引用、期望版本、deadline 和幂等键；合并使用乐观锁、稳定排序和领域冲突规则。版本过期或语义冲突时停止合并，不能用“最后写入者获胜”掩盖错误。
  • 审批是独立控制面。action 角色只能产出工单提案，不能持有写入工具；统一 ApprovalService 绑定认证主体、提案哈希和版本，人工批准后才由受控写入端执行，并记录拒绝、过期与重复审批。
  • 多个 ChatClient 不会自动形成多 Agent runtime。Spring AI 2.0.0 的 ChatClient 是模型交互入口，Advisor 是请求链增强机制，Tool Calling 提供工具声明与循环能力；路由、持久共享状态、Coordinator、审批、恢复和失败传播仍由应用 Bean 与基础设施实现。Spring AI ChatClient

本课消费上一课的 ExecutionPlan、PlanStep、步骤 deadline 与幂等要求：只有计划中已通过校验的步骤才允许被 Coordinator 派发。多角色输出仍是不可信输入，不能改写授权、审批、预算或共享状态版本。

#先建立单 Agent 基线

把“一个受限 Agent + 同一组只读工具 + 独立审批服务”作为对照组。先冻结代表性工单集、模型版本、提示版本、工具夹具、超时和成本口径，至少重复运行到置信区间稳定；不要用一个成功演示替代基线。下表中的 B_* 是你需要实测并登记的值，不是本文虚构的行业数字。

基线指标单 Agent 记录值一致口径拆分后的放行条件
任务质量B_quality正确分类、引用支持率、提案可接受率；盲评并保留失败类别预注册的主质量指标显著改善，且安全指标不退化
端到端延迟B_p50 / B_p95从 intake 到最终答复 / 待审批状态，含队列、模型、工具与合并目标分位数满足 SLA；不能只报告可并行子步骤耗时
tokenB_input / B_output汇总所有模型调用、重试、评审和摘要，不只看最后一次增量成本低于业务收益或风险降低的预算上限
工具调用B_tool_calls总次数、重复次数、拒绝次数和每类工具分布重复与无效调用不增加；角色越权调用为零
失败率B_failure超时、部分失败、冲突、解析失败、人工拒绝和不可恢复失败分别统计端到端成功率改善，或关键风险失败显著降低
运维复杂度B_opsBean / 队列 / 状态表 / 告警 / 值班手册 / 恢复步骤数量与人时新增组件有明确 owner、SLO、Runbook，净收益覆盖长期运维成本

拆分决策门

  1. 角色边界：是否存在互相不应拥有的权限或不同责任人？若所有角色都需要同一工具和数据，拆分可能只是换名字。
  2. 上下文隔离：是否有证据表明分离知识域能减少干扰、泄露或 token，而不是通过输入裁剪就能解决？
  3. 并行价值：分支是否真正独立，且 p95 延迟节省大于派发、排队、合并和冲突成本？
  4. 可评测性：每个角色是否有独立可判定的契约与测试 oracle？若只能由另一个模型“觉得不错”，故障会被转移而非消除。
  5. 净收益：在同一回归集上进行单 Agent / 多 Agent A/B；任何主指标未达门槛、审批风险上升或总成本超预算，都保留单 Agent。

#角色与工具隔离

角色不是 system prompt 里的称谓，而是服务端可强制执行的能力边界。每个角色使用独立 ChatClient / Service Bean、独立工具回调集合和最小输入投影；每个实际 ToolCallback.call 必须在调用 delegate 之前，用服务器绑定的受信 current AgentRole 和 RoleToolSet 校验 callback 的真实名称。角色不能来自模型参数、Prompt、ToolContext 或结果自报。Spring AI 官方提醒，builder 的 defaultTools 会对由该 builder 构建的客户端请求共享，配置不慎可能让工具在不该出现时可用，因此不要复用一个已附带宽权限工具的 client 再“靠提示词限制”。Spring AI Tool Calling

显式 handoff，而不是转发聊天记录

AgentHandoff 至少包含 handoff ID、受信 tenant / principal、correlation ID、plan / step ID、from / to、输入 schema 版本、最小数据引用、证据 provenance、期望共享状态版本、deadline、幂等键和预算切片。Coordinator 必须在派发前把完整不可变 handoff 追加到持久 HandoffLedger，结果只携带 handoff ID；接收和合并端从 ledger 反查原件，先验证身份、角色、schema、版本、deadline 与数据范围，再解析内容。不接受自然语言要求扩大工具或跳过审批。

  • Provenance：区分用户输入、模型推断、知识文档、工具 Observation 和人工决定；保存源 ID、版本、时间与内容哈希，不把模型生成的 URI 当来源。
  • Correlation：一次入口请求使用稳定 correlation ID；每个计划步骤、handoff、模型调用和工具调用另有独立 ID，Trace 与审计通过父子关系连接，而不是复用成一个模糊 ID。
  • 无共享密钥：工具适配器在服务器端以各自 workload identity / secret reference 调用后端。Agent 只看到工具 schema 与脱敏结果；handoff、Prompt、共享状态和 Trace 都不得携带明文密钥。
  • 最小披露：knowledge 不需要用户完整联系方式，status 不需要对话历史，action 不需要原始 runbook 全文。每个投影在服务端构造并执行字段 allowlist。

#共享状态与冲突

共享状态不是多个 Agent 可同时改写的一张 Map。Coordinator 读取不可变快照 SharedStateVersion(runId, version)，分支只返回带 expectedVersion 的补丁 / 结果；合并端不能相信结果自报上下文，而要按 handoff ID 从持久 HandoffLedger 读取派发前登记的不可变原件，验证完整绑定后再进行 compare-and-set。成功后版本严格加一，失败则重新读取并按策略决定重算、人工裁决或终止。

冲突检测方式确定性处理禁止做法
陈旧版本result.expectedVersion != currentVersion拒绝合并；只读且输入未变时可重新派发，否则转人工 / 新计划版本直接覆盖新状态
重复派发 / 重放同一 (runId, stepId, idempotencyKey) 已有终态返回已存结果；处理中则附着观察，不再启动第二次调用因为超时未知就盲目重做写操作
字段级语义冲突不同来源对同一受保护字段给出不兼容值按领域优先级或新鲜度规则裁决；无规则则标记 conflict 并停止 action最后写入者获胜或让模型自由选择
确定性重放差异相同输入 / 版本的归一化结果哈希不同保留两份 provenance，标为 non-deterministic，按风险转评审 / 人工隐藏差异只保留最新文本
部分成功并行分支中一部分成功，一部分超时 / 失败由步骤策略声明 required / optional；required 失败终止，optional 失败输出明确缺口把缺失结果当空字符串继续建单

确定性合并顺序

  1. 按固定角色优先级，再按 handoff ID 排序，禁止依赖线程完成先后。
  2. 按 result 的 handoff ID 从持久 ledger 读取原始不可变 handoff；缺失、重复 ID 或未登记结果立即拒绝。
  3. 验证 handoff 的 tenant / principal、from / to、run / plan / step / correlation、schema、expectedVersion 和 deadline 都与当前 MergeContext 一致。
  4. 验证结果 provenance 至少保留 handoff 的全部输入来源；结果自报工具名只做防御性复核，不能补做或替代执行前授权。
  5. 先合并互不相交字段；同字段使用代码化领域规则，例如实时状态只能由 STATUS 写，runbook 引用只能由 KNOWLEDGE 写。
  6. 任何未知字段、来源缺失、版本陈旧或无法裁决的冲突都使合并失败；不调用 action。
  7. 用期望版本 compare-and-set 原子保存新快照与审计事件；CAS 失败时绝不原地重试同一补丁。

#Java 21：协调器与版本化契约

下面是供应商中立的核心契约。集合在构造时复制为不可变值；角色工具集拒绝越权；handoff 显式携带版本、来源、deadline 与幂等键。Executor 只用于说明并行执行机制，不承担业务编排、持久化或审批。

import java.time.Instant;
import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Set;
import java.util.UUID;
import java.util.concurrent.CompletionStage;
import java.util.concurrent.Executor;

enum AgentRole {
    COORDINATOR, TRIAGE, KNOWLEDGE, STATUS, ACTION, REVIEWER
}

record RoleToolSet(AgentRole role, Set<String> allowedToolNames) {
    RoleToolSet {
        Objects.requireNonNull(role);
        allowedToolNames = Set.copyOf(allowedToolNames);
    }

    void requireAllowed(AgentRole trustedRole, String toolName) {
        if (role != trustedRole || !allowedToolNames.contains(toolName)) {
            throw new SecurityException(trustedRole + " cannot call " + toolName);
        }
    }
}

interface RoleToolCatalog {
    RoleToolSet forRole(AgentRole role);
}

record SharedStateVersion(UUID runId, long value) {
    SharedStateVersion {
        Objects.requireNonNull(runId);
        if (value < 0) throw new IllegalArgumentException("negative version");
    }

    SharedStateVersion next() {
        return new SharedStateVersion(runId, Math.addExact(value, 1));
    }
}

record Provenance(
        String sourceType,
        String sourceId,
        String sourceVersion,
        String contentHash) {}

record AgentHandoff(
        UUID handoffId,
        String tenantId,
        String principalId,
        String correlationId,
        String planId,
        String planStepId,
        AgentRole from,
        AgentRole to,
        int schemaVersion,
        Map<String, String> inputRefs,
        List<Provenance> provenance,
        SharedStateVersion expectedVersion,
        Instant deadline,
        String idempotencyKey) {
    AgentHandoff {
        Objects.requireNonNull(handoffId);
        Objects.requireNonNull(tenantId);
        Objects.requireNonNull(principalId);
        Objects.requireNonNull(correlationId);
        Objects.requireNonNull(planId);
        Objects.requireNonNull(planStepId);
        Objects.requireNonNull(from);
        Objects.requireNonNull(to);
        if (schemaVersion != 1) throw new IllegalArgumentException("unsupported schema");
        inputRefs = Map.copyOf(inputRefs);

    }

final class StateConflictException extends RuntimeException {
    StateConflictException(String message) {
        super(message);
    }
}

final class HandoffValidationException extends RuntimeException {
    HandoffValidationException(String message) {
        super(message);
    }

final class DeterministicMerger {
    private static final Comparator<AgentResult> ORDER =
            Comparator.comparing((AgentResult r) -> r.role().ordinal())
                    .thenComparing(r -> r.handoffId().toString());

    private final Map<AgentRole, RoleToolSet> toolSets;
    private final VersionedStateStore stateStore;
    private final HandoffLedger handoffLedger;

    DeterministicMerger(
            Map<AgentRole, RoleToolSet> toolSets,
            VersionedStateStore stateStore,
            HandoffLedger handoffLedger) {
        this.toolSets = Map.copyOf(toolSets);
        this.stateStore = stateStore;
        this.handoffLedger = handoffLedger;
    }

    SharedStateVersion merge(
            MergeContext context,
            List<AgentResult> unorderedResults) {
        var expected = context.expectedVersion();
        var current = stateStore.current(expected.runId());
        if (!current.equals(expected)) {
            throw new StateConflictException("stale shared-state version");
        }

        var ordered = unorderedResults.stream().sorted(ORDER).toList();
        var patch = new java.util.LinkedHashMap<String, String>();
        var provenance = new java.util.ArrayList<Provenance>();
        var seenHandoffs = new java.util.HashSet<UUID>();

        for (var result : ordered) {
            if (!seenHandoffs.add(result.handoffId())) {
                throw new HandoffValidationException("duplicate handoff result");
            }
            var handoff = handoffLedger.require(result.handoffId());
            validateBinding(context, handoff, result);

            // 防御性复核结果摘要；真正授权已在 callback delegate.call 前完成。
            result.reportedToolsUsed().forEach(toolName ->
                    toolSets.get(result.role())
                            .requireAllowed(result.role(), toolName));
            result.patch().forEach((key, value) -> {
                var previous = patch.putIfAbsent(key, value);
                if (previous != null && !previous.equals(value)) {
                    throw new StateConflictException("conflict at " + key);
                }
            });
            provenance.addAll(result.provenance());
        }

        var update = expected.next();
        if (!stateStore.compareAndSet(expected, update, patch, provenance)) {
            throw new StateConflictException("concurrent merge won");
        }
        return update;
    }

    private static void validateBinding(
            MergeContext context,
            AgentHandoff handoff,
            AgentResult result) {
        boolean invalid =
                !handoff.tenantId().equals(context.tenantId())
                || !handoff.principalId().equals(context.principalId())
                || !handoff.correlationId().equals(context.correlationId())
                || !handoff.planId().equals(context.planId())
                || !handoff.planStepId().equals(context.planStepId())
                || !handoff.expectedVersion().runId()
                        .equals(context.expectedVersion().runId())
                || !handoff.expectedVersion().equals(context.expectedVersion())
                || !result.expectedVersion().equals(handoff.expectedVersion())
                || handoff.from() != AgentRole.COORDINATOR
                || handoff.to() != result.role()
                || !context.expectedRoles().contains(result.role())
                || handoff.schemaVersion() != 1
                || !context.mergeTime().isBefore(handoff.deadline())
                || !result.provenance().containsAll(handoff.provenance());
        if (invalid) {
            throw new HandoffValidationException("result is not bound to handoff");
        }
    }
}

final class ParallelDispatcher {
    private final Executor executor; // 有界、可观测、由应用管理

    ParallelDispatcher(Executor executor) {
        this.executor = executor;
    }

    // 仅示意并行机制：业务 Coordinator 仍负责 deadline、预算、去重、
    // Future 取消、持久化 attempt、required/optional 分支与失败传播。
    CompletionStage<List<AgentResult>> readInParallel(
            AgentHandoff knowledge,
            AgentHandoff status,
            RoleRunner runner) {
        var knowledgeFuture = runner.run(knowledge, executor);
        var statusFuture = runner.run(status, executor);
        return knowledgeFuture.thenCombine(
                statusFuture,
                (knowledgeResult, statusResult) ->
                        List.of(knowledgeResult, statusResult));
    }
}

边界提醒：上面的 thenCombine 只组合两个完成结果，不会替你完成可靠取消、持久恢复或 exactly-once。Coordinator 必须给两个分支同一个绝对 deadline；任一 required 分支超时后取消尚未开始的任务，并让运行中的工具通过显式取消 token / HTTP deadline 尽快停止。外部副作用仍按幂等契约实现，不能宣称分布式 exactly-once。

工具执行前策略门

ToolCallback 同时承载工具定义和执行逻辑；因此包装器必须透传 definition / metadata，但在两种 call 重载进入 delegate 前共享同一 authorize()。Spring AI 2.0.0 的 DefaultToolCallingManager 只捕获 ToolExecutionException 并交给 ToolExecutionExceptionProcessor，所以自定义 callback 不能直接抛普通 SecurityException。拒绝时先用真实角色和 callback name 写安全审计，再用真实 ToolDefinition 与不含输入、租户、凭证或内部策略细节的固定 cause 构造框架异常；always-throw processor 随后向调用方重抛，不生成可发送给模型的普通工具错误。delegate 调用次数保持为 0。结果里的 reportedToolsUsed 只供合并端做防御性复核，绝不能充当执行授权或证明某工具真的执行过。ToolExecutionException 2.0.0 API

interface SecurityAudit {
    void toolDenied(AgentRole trustedRole, String toolName);
}

final class PolicyEnforcingToolCallback implements ToolCallback {
    private static final String SAFE_DENIAL_MESSAGE =
            "Tool execution denied by server policy";

    private final AgentRole trustedRole; // 由服务器 role Bean 固定，不读模型输入
    private final RoleToolSet toolSet;
    private final SecurityAudit audit;
    private final ToolCallback delegate;

    PolicyEnforcingToolCallback(
            AgentRole trustedRole,
            RoleToolSet toolSet,
            SecurityAudit audit,
            ToolCallback delegate) {
        this.trustedRole = Objects.requireNonNull(trustedRole);
        this.toolSet = Objects.requireNonNull(toolSet);
        this.audit = Objects.requireNonNull(audit);
        this.delegate = Objects.requireNonNull(delegate);
    }

    static ToolCallback[] wrap(
            AgentRole trustedRole,
            RoleToolSet toolSet,
            SecurityAudit audit,
            ToolCallback[] delegates) {
        return java.util.Arrays.stream(delegates)
                .map(delegate -> new PolicyEnforcingToolCallback(
                        trustedRole, toolSet, audit, delegate))
                .toArray(ToolCallback[]::new);
    }

    @Override
    public ToolDefinition getToolDefinition() {
        return delegate.getToolDefinition();
    }

    @Override
    public ToolMetadata getToolMetadata() {
        return delegate.getToolMetadata();
    }

    @Override
    public String call(String toolInput) {
        authorize();
        return delegate.call(toolInput);
    }

    @Override
    public String call(String toolInput, ToolContext toolContext) {
        authorize();
        return delegate.call(toolInput, toolContext);
    }

    private void authorize() {
        ToolDefinition toolDefinition = delegate.getToolDefinition();
        String toolName = toolDefinition.name();
        try {
            toolSet.requireAllowed(trustedRole, toolName);
        }
        catch (SecurityException denied) {
            audit.toolDenied(trustedRole, toolName);
            // 不把原异常串入 cause：其 message 可能含角色、工具或策略细节。
            throw new ToolExecutionException(
                    toolDefinition,
                    new SecurityException(SAFE_DENIAL_MESSAGE));
        }
    }
}

#失败传播与审批

故障要沿结构化状态传播，而不是拼进下一段 Prompt 后“请自行判断”。每个分支返回 SUCCESS、PARTIAL、TIMED_OUT、CANCELLED、CONFLICT、POLICY_DENIED 或 FAILED_FINAL，同时保留公开摘要和私有诊断引用。Coordinator 根据计划中预声明的 required / optional 策略决定继续、降级或终止。

事件传播与取消共享状态 / 副作用用户可见结果
重复执行dispatch claim 命中已完成记录时返回原结果；运行中则附着观察不再次调用角色；审批和建单使用独立幂等键同一状态与外部对象 ID
knowledge 超时，status 成功取消 knowledge 的下游调用；若知识为 required，取消尚未开始的 action可保存 status 证据，但不伪造 knowledge 空结果明确缺少知识证据，部分答复或转人工
status 超时，knowledge 成功不无限等待；到总 deadline 后传播 TIMED_OUT只读结果可审计；依赖实时状态的提案不得生成提供带引用 runbook，并标明无法确认实时状态
版本冲突停止合并并取消以旧快照为输入的后续节点CAS 不写入；保存冲突双方 provenance重新读取后重算，或说明需人工裁决
角色越权执行前由 allowlist 拒绝，标记 POLICY_DENIED工具未运行；安全审计告警，不能换角色重试绕过安全失败，不暴露工具目录或策略细节
Coordinator 重启从持久 dispatch / state / deadline 恢复；先查询外部调用状态未确认副作用不盲重放；过期 run 转恢复 / 人工队列继续原 run 或给出可追踪的升级编号
审批拒绝 / 过期取消写入路径，不返回 action 继续游说提案保持不可变；记录决定、审批人、版本和理由REJECTED / EXPIRED，可由人工创建新提案版本

统一审批服务不能被角色绕过

  1. action 产生不可变 TicketProposal；服务器重新校验字段、风险、tenant、主体权限与当前共享状态版本，并计算 canonical hash。
  2. ApprovalService.submit 以 (runId, proposalVersion, proposalHash) 幂等创建审批请求；模型不能生成“已批准”状态。
  3. 人工界面展示最小必要证据、实时状态、知识引用、预期副作用和可撤销性；审批决定绑定已认证审批人、时效和具体 hash，提案变化即旧审批失效。
  4. 批准后只有 ApprovalService 内部受控的 TicketWriter 能执行 ticket.create；写入使用外部系统支持的幂等键，并保存 ticket ID。triage / knowledge / status / action / reviewer 均不注入该 writer。
  5. 未知结果、网络超时或服务重启时先按幂等键查询工单系统；确认未创建前才允许受控重试。审批拒绝、过期、版本冲突或主体权限变化都安全停止。

#企业服务台案例

请求：“华东订单服务持续超时，按运行手册排查；如果需要，请帮我提工单。”入口已经从认证态得到 tenant、principal 与允许服务范围，不能从用户正文接受 tenant 替换。

  1. Intake：生成 correlation ID 和请求幂等键；加载上一课已校验的 ExecutionPlan，其中知识 / 状态步骤为并行只读，action 依赖两者合并，ticket write 依赖人工审批。
  2. Triage：只查看脱敏描述和 taxonomy，分类为 ORDER_LATENCY，输出 service / region 缺失检查与路由标签；不能检索或建单。
  3. Knowledge：在 tenant、ACL 和固定知识版本内检索 runbook，返回带文档 ID、标题、版本、URI 的步骤；遇到提示注入文本时仍按数据处理。
  4. Status：使用只读服务身份读取受控 service ID 的当前健康、最近告警和观测时间；不接受模型提供任意 URL，也不能重启服务。
  5. Merge：Coordinator 验证两个结果都基于同一 SharedStateVersion，按 KNOWLEDGE → STATUS 稳定顺序合并；若 runbook 说“服务正常”而实时状态说“异常”，保留时间与来源，不将其视为可覆盖同一字段。
  6. Action：只基于已校验摘要提出优先级、标题、影响范围和证据引用，调用草稿字段校验；无法满足证据要求时返回“缺证”，不创建工单。
  7. Approval：统一服务展示提案 hash、实时影响与 runbook 引用，等待有权限的人批准。拒绝即终止；批准后由内部 TicketWriter 以幂等键创建一次工单。
  8. Final / audit：返回排查建议、实时状态、引用和 PENDING_APPROVAL / ticket ID；审计关联 plan、step、handoff、模型 / 工具调用、版本、审批与成本。

#评测与测试

多 Agent 的测试 oracle 是业务状态、授权决定、外部副作用和来源链，而不是“几个角色说得像不像”。同一固定数据集必须同时跑单 Agent 对照；汇总所有角色与重试的 token、延迟和工具次数。

场景夹具 / 注入必须断言禁止结果
重复派发相同 run / step / idempotencyKey 并发到达两次只有一个 dispatch claim 和一次角色 / 工具执行；第二请求取得同一终态重复 action、审批或工单
陈旧合并版本分支返回 version 7，存储已是 version 8CAS 拒绝、后续 action 未调用、冲突审计包含两个版本覆盖 version 8 或静默丢弃
伪造 handoff结果携带从未 append 到 HandoffLedger 的随机 handoff ID，或重复提交同一 IDrequire / duplicate 检查在读取 patch 前拒绝；CAS、action 与工具调用均为 0从结果字段猜测 handoff，或接受未登记来源
过期 handoffledger 原件的 deadline 等于或早于 MergeContext.mergeTime绑定校验返回 HandoffValidationException；保留超时审计且不合并因为角色已返回成功就忽略 deadline

生产评测指标

  • 端到端：任务成功率、引用支持率、提案接受率、安全失败率、p50 / p95 / p99、总 token、总模型与工具调用、单位成功任务成本。
  • 角色级：triage 路由准确率、knowledge 召回 / 引用正确性、status 新鲜度、action schema / policy 通过率；角色指标不能替代端到端指标。
  • 协作级：重复派发率、handoff schema 失败率、陈旧版本率、冲突率、取消成功率、部分成功率、重启恢复时间、审批等待与拒绝率。
  • 比较纪律：固定模型与工具夹具，报告置信区间和失败分层；并行拓扑报告 wall-clock 与累计 compute 两种成本，不能把并行隐藏成“免费”。

#练习与验收

动手练习

  1. 基线卡：选择 30～50 个脱敏服务台请求，为单 Agent 记录六类基线指标；预注册一个主质量指标、一个安全门、p95 与单位成功成本上限。
  2. 拓扑 ADR：分别为主管—执行者、流水线、并行专员、评审者写“采用 / 不采用”理由。至少删除一个没有角色、权限或上下文隔离收益的 Agent。
  3. 契约实现：实现本课 records、DispatchLedger 与内存 CAS store；用两个完成顺序相反的并行结果证明合并输出相同。
  4. 故障注入：注入重复派发、version stale、字段冲突、角色越权、分支超时、Coordinator 重启与审批拒绝，验证没有重复副作用且终态可解释。
  5. Spring 切片：用一个 provider-neutral ChatModel 测试替身构造三类 ChatClient Bean，验证每个请求只获得该角色工具；Coordinator 和 ApprovalService 用真实内存实现，不用模型 mock 代替业务断言。
  6. A/B 复验：用同一数据集比较单 Agent 与候选多 Agent，若净收益门未通过，提交“保留单 Agent”的结论和证据。

验收标准

  • 能解释为什么“多个 ChatClient”不等于多 Agent runtime，并指出业务 Coordinator、状态库、dispatch ledger、审批与恢复的 owner。
  • 有完整单 Agent 基线，涵盖质量、延迟、token、工具调用、失败率和运维复杂度；拆分决策有可重复的净收益证据。
  • 能根据依赖、并行性、角色权限和评审信号在四种拓扑中选择，且能说明何时固定工作流更合适。
  • PolicyEnforcingToolCallback 使用服务器固定角色与实际 callback name，在 delegate 前执行 RoleToolSet；越权时 delegate 计数为 0、产生安全审计，并以真实 ToolDefinition 和固定安全 cause 抛出 ToolExecutionException。always-throw processor 向调用方重抛，不能生成给模型继续推理的工具错误。任意角色都看不到共享密钥，action 没有 ticket.create。
  • AgentHandoff 包含 tenant / principal、correlation / plan / step / handoff ID、from / to、schema、provenance、expected version、deadline 和 idempotency key，并在派发前不可变写入 HandoffLedger；伪造、过期、错 run / 上下文或来源断链的结果被拒绝。
  • 并行结果按稳定顺序合并并使用 CAS；字段冲突、版本冲突和重复派发有确定性测试，不能依赖线程完成顺序。
  • 超时能向子任务和后续节点传播取消；required / optional 部分失败规则显式，重启后从持久记录恢复而不盲重放。
  • 所有建单都经过统一 ApprovalService 与人工决定；拒绝、过期、提案变更和未知写入结果均安全停止。
  • 外链安全、标题锚点唯一、图示有等价文字说明，Java 泛型与 Lambda 符号已正确转义。
