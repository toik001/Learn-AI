Harness + Loop + Graph 双层整合实战

项目：构建“28 万元 SaaS 续费”企业智能审批 Agent。它读取申请、合同和制度，核验预算与合规，生成有证据的提案；确定性规则负责硬门禁，授权人负责最终决定，执行器在有效批准后创建采购订单。

双层：第一层是线上运行时 Agent 的 Harness/Loop/Graph；第二层是使用 Codex 开发这个 Java 25 + Spring Boot + Spring AI 项目时的 Harness/Loop/Graph。两层目标相连，但身份、状态、权限和恢复机制完全独立。

快速阅读： 结论 · 双层模型 · 审批项目 · Codex 开发 · 上线运行 · 验收 · 资料

核心结论

  1. 成熟 Agent 通常三者叠加，不是三选一。Harness 包住系统，Graph 组织步骤，Loop 在需要动态探索的节点内运行。
  2. 审批权永远不属于模型。模型输出 ApprovalProposal；规则和授权人输出 ApprovalDecision；执行器只消费绑定 proposalHash 的有效批准。
  3. 先做无框架核心，再接 Spring AI。领域状态、规则、工具权限、幂等和测试先用普通 Java 25 固化，Spring AI 仅作为模型/工具适配器。
  4. 用 Codex 开发时同样需要三层。仓库与工具构成 Harness；检查—编辑—测试—审查形成 Loop；规格—计划—任务—验证—交付形成开发 Graph。
  5. 上线采用渐进授权。从离线评测到 shadow、辅助决策，再到低风险自动化；任何高风险写动作保留人工门禁和回滚开关。

概念模型：两套三层结构

第一层：运行时 Agent
Harness：身份、工具、规则、审计
Graph：收件、核验、会签、执行
Loop：发现证据缺口并收敛
第二层：编码 Agent
Harness：仓库、AGENTS.md、工具、CI
Graph：规格、计划、实现、验证
Loop：检查、编辑、测试、review

编码 Agent 可以开发运行时 Agent，但绝不能继承审批用户身份、生产凭据或业务授权；生产写工具不应暴露给开发 Harness。

API / Identity / Tenant认证主体、caseId、caseVersion、请求幂等键
Approval GraphSUBMITTED → ANALYZING → NEEDS_INFO / PENDING_APPROVAL → EXECUTING
Bounded Agent Loop只在材料理解、证据补全和提案节点内动态调用只读工具
Deterministic ControlsPolicyGate、人工会签、职责分离、幂等执行器
Harness ServicesPostgreSQL、对象存储、审计、指标、Trace、评测集、恢复任务

组合原则：模型节点可以建议下一步，Graph 控制合法路径，Harness 决定哪些工具和数据真正可用。

第一部分：智能审批 Agent 开发

1. 先定义责任，不先选框架

能力模型/Agent规则/应用人类
材料理解抽取字段、指出冲突与缺失schema、文件 ACL、来源 hash处理低置信或矛盾材料
制度适用检索并解释相关条款版本、生效日、主体过滤解释制度歧义
预算/重复总结工具结果精确查询和计算批准例外
最终决定只能生成提案硬规则与路由授权人批准或拒绝
创建订单不能直接执行有效批准、幂等、最小写权限高风险时二次确认

教学业务规则：金额超过 20 万需要经理、财务与法务会签；涉及个人数据必须提供 DPA；报价上涨超过 10% 需要议价说明。这些阈值只是示例，真实规则必须由企业流程 Owner、财务、法务和合规确认并版本化。

3. 领域状态、提案和批准分离

public record ApprovalProposal(
        java.util.UUID proposalId,
        java.util.UUID caseId,
        long caseVersion,
        Recommendation recommendation,
        java.util.List<EvidenceRef> evidence,
        java.util.List<String> missingFields,
        String policyVersion,
        String proposalHash) {}

public record ApprovalDecision(
        java.util.UUID decisionId,
        java.util.UUID proposalId,
        String proposalHash,
        String approverId,
        String approverRole,
        Decision value,
        java.time.Instant decidedAt) {}

public record ExecutionCommand(
        java.util.UUID caseId,
        String proposalHash,
        String idempotencyKey) {}

材料、金额、供应商或拟执行动作变化时 caseVersion 增加并生成新的 proposalHash；旧批准自动失效。执行器校验批准集合、proposalHash、策略版本、职责分离和幂等键。

无框架实现：组合 Harness、Graph 与 Loop

public final class ApprovalApplicationService {
    private final ApprovalGraph graph;
    private final ApprovalLoopRunner evidenceLoop;
    private final PolicyGate policy;
    private final ExecutionPort execution;

    public ApprovalState advance(Principal principal, java.util.UUID caseId) {
        var state = graph.loadAuthorized(principal, caseId);
        return switch (state.stage()) {
            case ANALYZING -> graph.persist(evidenceLoop.run(state, LoopBudget.standard()));
            case PENDING_APPROVAL -> graph.waitForHuman(state);
            case APPROVED -> {
                policy.requireExecutable(principal, state);
                var receipt = execution.executeOnce(toCommand(state));
                yield graph.complete(state, receipt);
            }
            default -> graph.step(state);
        };
    }
}

这段代码展示所有权：Graph 决定合法状态，Loop 只处理 ANALYZING 的局部未知，PolicyGate 在副作用前重新鉴权，ExecutionPort 保证幂等。

Spring AI 实现：仅替换模型节点

@Configuration
class ApprovalAiConfiguration {
    @Bean
    ModelPort proposalModel(ChatClient.Builder builder, ApprovalReadTools tools) {
        var client = builder
                .defaultSystem("只生成带证据引用的审批提案；不得批准或执行。")
                .defaultTools(tools)
                .defaultAdvisors(new PolicyContextAdvisor())
                .build();
        return (context, evidence) -> client.prompt()
                .user(ApprovalPrompt.render(context, evidence))
                .call()
                .entity(ApprovalProposal.class, spec -> spec.validateSchema());
    }
}

final class ApprovalReadTools {
    @Tool(description = "读取认证主体有权查看的预算快照")
    BudgetSnapshot budget(String costCenter) {
        var principal = TrustedPrincipal.current(); // 不使用模型传入的 tenant
        return budgetService.readAuthorized(principal, costCenter);
    }
}

如果需要观察每次工具迭代或在调用间插入政策检查，应关闭 per-call 自动工具执行并使用用户控制模式。无论哪种模式，写工具都必须自行鉴权、校验有效批准并记录审计。

POST /api/approval-cases/{id}/documents  # 上传材料，version + 1
POST /api/approval-cases/{id}/analyze    # 启动/恢复 Graph
GET  /api/approval-cases/{id}            # 查询状态与脱敏证据
POST /api/approval-proposals/{id}/decisions # 授权人决定，绑定 proposalHash
POST /api/approval-cases/{id}/execute    # 校验批准后幂等执行

主路径：提交 → 硬校验 → 并行取证 → 缺 DPA → NEEDS_INFO
      → 补件/version+1 → 重新取证 → 三方会签 → APPROVED
      → 原子 claim → ERP 创建一次订单 → COMPLETED

第二部分：代码开发过程中的使用——用 Codex 开发这个项目

1. 先把仓库变成可工作的 Harness

# AGENTS.md（保持简短，作为地图）
## Architecture
- `approval-domain` 不依赖 Spring、模型或外部系统。
- 模型只能生成 ApprovalProposal；最终决定来自规则或授权人。
- 所有写操作经过 PolicyGate，并绑定 proposalHash 与 idempotencyKey。

## Commands
- Domain: `./mvnw -pl approval-domain,approval-usecase test`
- Integration: `./mvnw -pl approval-adapter-persistence verify`
- Full: `./mvnw verify`

## Workflow
- 先读规格与相关测试；先失败测试、后最小实现。
- 完成声明包含实际运行的命令与输出摘要。
- 需求冲突、权限扩张、破坏性迁移和外部发布必须停下询问。

再补齐一条命令启动本地 PostgreSQL/fake model、种子数据、架构测试、日志/Trace 查询和最小 UI/API 场景。OpenAI 的 Harness Engineering 实践强调让仓库知识成为 system of record，并让应用、日志、指标和 UI 对 Codex 可读。

T6 交付全部工件E2E、SLO、runbookreview、全量 verify、人工批准

3. 每个节点内部使用 Codex Loop

Goal:
实现 approval_execution 的原子幂等 claim，消除并发重复订单。

Context:
读取 AGENTS.md、ExecutionPort、现有迁移和并发测试；先报告当前语义。

Constraints:
- Java 25；先添加稳定失败的并发测试。
- 使用数据库唯一键/事务，不使用 JVM 本地锁，不做先查后写。
- 不修改 HTTP API、审批规则或无关模块。

Done when:
- 20 个并发请求只产生一个 executionId，其余返回同一结果。
- 超时恢复先查询既有执行，不能再次创建订单。
- scoped test、模块 verify、全量 verify 和 review 全部通过。

Stop:
需要选择数据库方言、删除数据或修改生产权限时停止并请求决定。

Codex 的小 Loop 是：Inspect → 预测失败 → Test red → 最小 Edit → Test green → 扩大验证 → Review → 修复 → 用新鲜证据 Stop。连续两轮失败信号不变时，不应继续随机改动，而应报告假设、证据和阻塞。

4. Review 与人工门禁

  • 正确性 reviewer：状态迁移、并发、事务、幂等、版本绑定；
  • 安全 reviewer：租户隔离、Prompt Injection、工具权限、日志隐私、密钥；
  • 测试 reviewer：正常、补件、拒绝、超时、取消、恢复、重复请求和脏数据；
  • 人工决定：业务规则阈值、破坏性迁移、权限扩张、生产发布和最终合并。

Codex Subagents 适合并行只读审计、测试运行或独立模块探索；存在共享文件、数据库迁移顺序或接口未冻结时保持串行。子 Agent 继承 sandbox/permission，不能用并行绕过审批。

线上应用、评测、部署与运行手册

测试与评测金字塔

层级验证内容代表用例发布门槛
纯 Java 单元规则、状态、停止、hash旧 proposalHash 不可执行全量确定性通过
契约/集成工具 ACL、schema、DB、幂等并发重复执行、租户越权零越权、零重复副作用
离线 AI eval抽取、证据、建议、拒答缺 DPA、条款冲突、注入文本按风险分层阈值并与基线比较
Graph 恢复每节点前后崩溃人工等待恢复、工具已成功但响应丢失无丢状态、无重复动作
shadow / E2E真实分布、延迟、成本、人工分歧不写业务系统的旁路运行满足 SLO 才扩大流量

部署与安全

Ingress / SSO
  → approval-api（无模型密钥）
  → approval-worker（Graph + bounded Loop）
      → policy-service（确定性规则）
      → PostgreSQL（case/checkpoint/audit/outbox）
      → read-tool gateway（预算/制度/合同，租户 ACL）
      → model gateway（限额、版本、脱敏、熔断）
  → approval-executor（独立身份，只接受有效批准）
      → ERP / SRM

隔离原则：模型 Worker 没有 ERP 写凭据；执行器不接收自由文本 Prompt；
所有跨边界消息使用结构化 schema、proposalHash 和 idempotencyKey。

Prompt Injection 防御不能只写在 system prompt：外部文档一律作为不可信数据；工具白名单和参数校验在服务端；模型不能修改权限、策略或工具定义；敏感写操作要求授权并保留 kill switch。

灰度、SLO 与告警

阶段权限观察指标退出条件
离线fake/脱敏数据准确率、证据覆盖、拒答、安全回归集与对抗集达标
shadow生产只读，不展示建议延迟、成本、路径、人工结果差异无数据泄露和越权
辅助决策展示提案，全部人工批准采用率、override、升级率稳定周期内满足阈值
低风险自动化仅白名单动作重复副作用、恢复、投诉任何安全事件立即回退

示例 SLO：API P95 < 2s（不含人工等待）；Graph checkpoint 成功率 ≥ 99.99%；工具越权成功数 = 0；重复外部订单数 = 0；每个运行必须有 stop_reason、模型/Prompt/工具/策略版本和 traceId。阈值需由企业按风险重新确认。

故障运行手册

  1. 模型异常：关闭 AI 节点，保留普通工作流；将 case 升级人工，不猜测结果。
  2. 工具超时：按错误类型退避；写动作先查幂等结果；超过预算进入死信/人工队列。
  3. 策略版本错误：冻结执行器，回滚策略，按 caseVersion 重放受影响提案。
  4. Prompt/数据泄露：撤销凭据、停止日志导出、保全审计、通知安全团队并修复 Harness。
  5. Graph 卡住：检查等待请求、checkpoint 与图版本；禁止手工直接改最终状态，使用受审计恢复命令。

失败模式与分层定位

症状真正层次错误修法正确修法
模型读不到制度Harness反复改 Prompt修 ACL、索引、工具返回和可观测性
不断重复同一查询Loop提高模型温度动作 fingerprint、no-progress 停止
补件后旧批准仍可执行Graph/领域让模型提醒caseVersion + proposalHash 强绑定
Codex 多次改错开发 Harness/Loop追加“认真一点”补复现、测试、日志、范围和停止条件
并行 Agent 冲突开发 Graph更多并行冻结接口、拆写集、显式依赖或串行

练习与验收

  1. 只实现 approval-domain 和 fake ModelPort，完成正常、缺件、拒绝、超时、取消和旧批准失效测试。
  2. 让 Codex 按本页任务契约实现幂等执行，保存 red/green 输出与 review 发现。
  3. 接入 Spring AI 后重跑同一领域测试，证明框架替换没有改变授权与状态语义。
  4. 执行故障演练：模型不可用、预算 API 超时、checkpoint 后崩溃、ERP 成功但响应丢失、恶意合同提示注入。

最终验收：能从代码和日志重建任一提案的证据链；任何模型输出都不能直接成为最终批准；每条写路径都有鉴权、proposalHash、幂等与审计；Graph 可从 checkpoint 恢复；Loop 有三类停止；Codex 开发任务用实际验证输出证明完成。
