#企业智能审批与公司主子 Agent 落地实战

案例：员工提交 28 万元的 SaaS 续费采购申请，系统需要核对材料、制度、预算、供应商与数据合规，再完成经理、财务和法务审批。

技术立场：Agent 只生成提案；最终决定由规则引擎或授权审批人完成。BPMN/工作流引擎拥有流程状态，业务系统拥有真实数据，Agent 没有“替公司签字”的权限。

整理与一手资料检索日期：2026-07-28。

#核心结论

  1. 智能审批不是让模型直接批准。LLM 适合处理非结构化材料、制度解释、证据汇总与异常说明；金额阈值、预算占用、职责分离、审批路由和最终写入必须由确定性代码、规则引擎和授权人控制。
  2. 主 Agent 是协调器，不是“超级 Agent”。它创建审批 case、选择所需子 Agent、合并结构化证据和生成提案，但不持有 ERP、付款、合同签署或账户授权的宽权限。
  3. 子 Agent 按业务能力和权限边界拆分。材料理解、制度检索、财务核验与合规风险分别只看到完成任务所需的最小数据，并只拥有只读或提案类工具。
  4. BPMN、DMN 与 Agent 各有所有权。BPMN 管等待、超时、补件、会签和升级；DMN/规则服务计算硬规则与路由；Agent 负责不确定信息的理解和建议，不能用 Prompt 代替企业制度。
  5. 每个建议都必须可追溯。提案携带来源、版本、事实时间、规则版本和 proposalHash；任何材料或金额变化都会使旧审批失效。
  6. 先做“辅助审批”，再做低风险自动化。早期所有结果由人确认；成熟后也只能由确定性规则自动处理明确定义的低风险场景，模型意见不能单独触发自动批准。

#业务场景与目标

传统企业审批的主要成本并不只是“点同意”，而是材料反复补充、制度难查、系统数据分散、不同审批人判断口径不一。智能审批的目标应定义为缩短准备与判断时间，而不是取消问责。

当前痛点Agent 适合做什么确定性系统必须做什么成功指标
发票、合同、报价单字段不一致抽取、对齐、指出冲突与缺失文件防病毒、格式校验、主数据核验首次材料完整率
制度分散且难检索检索适用条款并给出引用制度版本、ACL、生效日期和规则发布引用支持率、错误条款率
预算和历史交易散落在系统中解释异常及形成摘要预算余额、重复报销、供应商和订单查询误报率、漏报率
审批人花时间重新整理材料生成带证据的审批提案和风险摘要身份、路由、会签、时限、最终决定人均审批时长、补件轮次
审计难还原当时依据生成结构化解释不可变事件、版本、审批人、执行结果审计证据完整率

不适用：规则已经完全稳定、输入全部结构化且没有解释需求时，普通 BPMN + DMN 更简单；决定会造成重大法律、财务或人身影响且无法提供有效人类复核时，不应让生成式 Agent参与决定。

#采购审批实例：28 万元 SaaS 续费

输入：某业务部门申请续费一套 SaaS，含申请单、供应商报价、上一年度合同和安全问卷。成本中心预算充足，但本次报价比去年高 12%，申请材料没有新的数据处理协议（DPA）。

教学假设：所有金额阈值、角色、制度编号和 DPA 路由均为教学假设，不是通用法规或行业标准。实际项目必须由本企业流程 Owner、财务、法务、合规与适用法律共同确定，并以版本化 BPMN/DMN 发布。

时点系统/角色动作结果为什么可审计
T0 提交BPMN 创建 case，绑定 requester、tenant、成本中心和文件引用COLLECTING主体来自认证态，原文件只读留存
T1 硬校验Schema + DMN 检查金额、品类、职责分离金额超过 20 万，需要经理 + 财务 + 法务规则版本 PROC-2026.07 和命中行可还原
T2 并行取证状态进入 ANALYZING；材料、制度、财务、合规四个子 Agent 只读执行预算足够；涨价 12%；DPA 缺失；示例制度要求处理个人数据必须有 DPA每项含 caseVersion、sourceRef、版本、观察时间和摘要 hash
T3 首次提案主 Agent 合并证据，规则服务决定路由进入 NEEDS_INFO，要求补 DPA 和涨价说明不是模型直接拒绝；提案 hash 冻结当时证据
T4 补件申请人上传 DPA 与议价说明，caseVersion 递增并重新进入 ANALYZING旧提案失效，重新取证并生成新 proposalHash任何材料、金额、供应商或拟执行动作变化都会使旧审批失效
T5 会签状态进入 PENDING_APPROVAL；经理、财务、法务分别完成 BPMN 用户任务三方批准后进入 APPROVED；法务意见绑定 DPA 版本审批人、角色、时间、MFA 强度、认证上下文和提案 hash 被记录
T6 执行状态进入 EXECUTING；采购执行器校验有效审批并调用 SRM/ERP通过原子 claim 和 idempotencyKey 创建一次采购订单，成功后进入 COMPLETED超时后由恢复任务按同一幂等键查询，不盲目重复创建

如果预算查询超时，结果应为 ESCALATE 或等待重试，而不是让模型根据历史语境猜测“预算应该够”。如果报价单与申请金额冲突，则固定进入 REQUEST_INFO；如果供应商命中硬性制裁规则，则确定性规则返回拒绝原因码，并由合规负责人复核。

何时值得设公司主 Agent：只有当多个部门能力需要共享统一入口、case ID、身份传播、预算、状态和审计时才值得。若单个场景只调用一个知识库和一个业务 API，优先使用单 Agent 或固定工作流。

#领域状态与数据设计

不要把聊天记录当审批数据库。流程状态必须可查询、可并发控制、可恢复；模型上下文只加载当前步骤所需的投影。

create table approval_case (
  case_id uuid primary key,
  tenant_id varchar(64) not null,
  requester_id varchar(128) not null,
  process_instance_id varchar(128) not null unique,
  current_state varchar(32) not null,
  current_version bigint not null,
  created_at timestamp with time zone not null,
  unique (tenant_id, case_id)
);

-- 每次材料、金额、供应商或拟执行动作变化都追加版本，不覆盖旧快照。
create table approval_case_version (
  case_id uuid not null references approval_case(case_id),
  case_version bigint not null,
  snapshot_hash varchar(64) not null,
  created_at timestamp with time zone not null,
  primary key (case_id, case_version)
);

create table approval_evidence (
  case_id uuid not null,
  case_version bigint not null,
  evidence_id uuid primary key,
  evidence_type varchar(48) not null,
  source_ref varchar(256) not null,
  source_version varchar(96) not null,
  observed_at timestamp with time zone not null,
  content_hash varchar(64) not null,
  conclusion_code varchar(64) not null,
  foreign key (case_id, case_version)
    references approval_case_version(case_id, case_version)
);

create table approval_proposal (
  proposal_id uuid primary key,
  case_id uuid not null,
  case_version bigint not null,
  recommendation varchar(32) not null,
  policy_version varchar(64) not null,
  proposal_hash varchar(64) not null unique,
  status varchar(32) not null,
  unique (proposal_id, proposal_hash),
  foreign key (case_id, case_version)
    references approval_case_version(case_id, case_version)
);

create table approval_decision (
  decision_id uuid primary key,
  proposal_id uuid not null,
  proposal_hash varchar(64) not null,
  approver_id varchar(128) not null,
  approver_role varchar(64) not null,
  auth_context_ref varchar(256) not null,
  mfa_strength varchar(32) not null,
  decision varchar(24) not null,
  decided_at timestamp with time zone not null,
  unique (proposal_id, approver_id, approver_role),
  foreign key (proposal_id, proposal_hash)
    references approval_proposal(proposal_id, proposal_hash)
);

-- claim 必须在一个事务中依赖唯一键原子创建；禁止“先查后写”。
create table approval_execution (
  execution_id uuid primary key,
  tenant_id varchar(64) not null,
  case_id uuid not null,
  proposal_id uuid not null,
  proposal_hash varchar(64) not null,
  idempotency_key varchar(128) not null,
  status varchar(32) not null,
  external_ref varchar(256),
  claimed_at timestamp with time zone not null,
  completed_at timestamp with time zone,
  unique (tenant_id, idempotency_key),
  foreign key (tenant_id, case_id)
    references approval_case(tenant_id, case_id),
  foreign key (proposal_id, proposal_hash)
    references approval_proposal(proposal_id, proposal_hash)
);

-- 仅追加事件；数据库写角色不得 UPDATE/DELETE，内容正文放受限证据库。
create table approval_audit_event (
  event_id uuid primary key,
  case_id uuid not null references approval_case(case_id),
  sequence_no bigint not null,
  event_type varchar(64) not null,
  actor_ref varchar(128) not null,
  auth_context_ref varchar(256),
  proposal_hash varchar(64),
  policy_version varchar(64),
  outcome_code varchar(64) not null,
  external_ref varchar(256),
  previous_hash varchar(64),
  event_hash varchar(64) not null,
  occurred_at timestamp with time zone not null,
  unique (case_id, sequence_no)
);

COLLECTING创建 case 或补件ANALYZING / CANCELLED必填结构字段有效；每次变化追加 caseVersion

ESCALATED超预算、硬门或无法自动恢复COLLECTING / PENDING_APPROVAL / REJECTED / CANCELLED由明确的人工角色接管

REJECTED授权人或硬门复核后拒绝终态保留原因码与证据，不执行写操作

COMPLETED外部回执已持久化终态执行结果和审计 hash 链完整
CANCELLED申请人撤回或流程管理员取消终态未执行外部副作用

#Java 21：领域契约

Agent handoff 不传完整对话，而传版本化、最小化、可验证的记录。以下是应用领域类型，不是 Spring AI 框架类型。

import java.time.Instant;
import java.util.List;
import java.util.Objects;
import java.util.Set;
import java.util.UUID;

enum Recommendation { APPROVE, REJECT, REQUEST_INFO, ESCALATE }
enum EvidenceKind { DOCUMENT, POLICY, BUDGET, VENDOR, COMPLIANCE }
enum ApprovalCaseState {
    COLLECTING,
    ANALYZING,
    NEEDS_INFO,
    ANALYSIS_RETRYABLE,
    NEEDS_REVIEW,
    PENDING_APPROVAL,
    ESCALATED,
    APPROVED,
    REJECTED,
    EXECUTING,
    EXECUTION_UNKNOWN,
    COMPLETED,
    CANCELLED
}

record ApprovalCaseRef(
        UUID caseId,
        String tenantId,
        long caseVersion,
        ApprovalCaseState state,
        String requesterId,
        String processInstanceId) {}

record EvidenceRef(
        UUID evidenceId,
        long caseVersion,
        EvidenceKind kind,
        String sourceRef,
        String sourceVersion,
        Instant observedAt,
        String contentHash,
        String conclusionCode,
        Set<String> reasonCodes) {
    EvidenceRef {
        reasonCodes = Set.copyOf(reasonCodes);
    }
}

record ApprovalProposal(
        UUID proposalId,
        ApprovalCaseRef caseRef,
        Recommendation recommendation,
        List<EvidenceRef> evidence,
        Set<String> missingEvidence,
        String policyVersion,
        String proposalHash) {
    ApprovalProposal {
        evidence = List.copyOf(evidence);
        missingEvidence = Set.copyOf(missingEvidence);
        Objects.requireNonNull(policyVersion);
        Objects.requireNonNull(proposalHash);
    }
}

proposalHash 必须由服务器对 canonical proposal（case、版本、金额、对象、证据 ID/版本、规则版本和拟执行动作）计算，模型只能看到计算后的值，不能自己提供可信 hash。

#Spring AI：独立角色与工具白名单

Spring AI 的 Tool Calling 中，模型只能提出工具请求，客户端应用负责解析、执行并返回结果，这是生产权限边界。当前 2.0 文档以 ToolCallback 表达工具，并支持由 ChatClient 与 Tool Calling Advisor 管理调用循环；需要条件控制时也可以由应用掌控执行循环。2.0 已推荐使用能接收 ToolCallback、provider 或 @Tool 对象的 defaultTools(...)；旧 defaultToolCallbacks(...) 已弃用。Spring AI Tool Calling · Spring AI ChatClient · ChatClient.Builder 2.0 API

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.tool.ToolCallback;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

enum ApprovalAgentRole { DOCUMENT, POLICY, FINANCE, COMPLIANCE }

interface GuardedToolCatalog {
    ToolCallback[] callbacksFor(ApprovalAgentRole role);
}

@Configuration
class ApprovalAgentConfiguration {

    private ChatClient roleClient(
            ChatClient.Builder builder,
            String systemPolicy,
            ApprovalAgentRole role,
            GuardedToolCatalog tools) {
        return builder
                .defaultSystem(systemPolicy)
                .defaultTools(tools.callbacksFor(role))
                .build();
    }

    @Bean("documentApprovalAgent")
    ChatClient documentAgent(ChatClient.Builder builder, GuardedToolCatalog tools) {
        return roleClient(builder,
                "只抽取申请材料并返回 DocumentEvidence；不得给出批准结论。",
                ApprovalAgentRole.DOCUMENT, tools);
    }

    @Bean("policyApprovalAgent")
    ChatClient policyAgent(ChatClient.Builder builder, GuardedToolCatalog tools) {
        return roleClient(builder,
                "只检索当前主体可见且在申请日有效的制度；每项结论必须引用版本。",
                ApprovalAgentRole.POLICY, tools);
    }

    @Bean("financeApprovalAgent")
    ChatClient financeAgent(ChatClient.Builder builder, GuardedToolCatalog tools) {
        return roleClient(builder,
                "只使用预算和历史交易只读工具；不得修改预算或创建付款。",
                ApprovalAgentRole.FINANCE, tools);
    }

    @Bean("complianceApprovalAgent")
    ChatClient complianceAgent(ChatClient.Builder builder, GuardedToolCatalog tools) {
        return roleClient(builder,
                "只返回供应商与数据合规证据；硬门由规则服务和授权人决定。",
                ApprovalAgentRole.COMPLIANCE, tools);
    }
}

工具目录要求：role 来自服务器固定 Bean，而不是 Prompt 或工具参数；每个 callback 在 delegate 前重新检查 principal、tenant、role、action、resource 和 deadline。不要创建一个携带全公司工具的共享 ChatClient 再依靠 system prompt 限制角色。执行器不能作为任何 Agent 的工具暴露，只能消费工作流发出的受信命令。

#确定性 Coordinator 与审批写入门

多 Agent 的真正 owner 是普通 Spring Application Service。它决定运行哪些角色、如何合并、何时停止和什么时候创建人类任务；模型不能递归生成无限子 Agent。

import java.util.List;
import java.util.UUID;

interface EvidenceAgent {
    EvidenceRef analyze(ApprovalCaseRef caseRef);
}

interface ApprovalRules {
    RuleDecision evaluate(ApprovalCaseRef caseRef, List<EvidenceRef> evidence);
}

record RuleDecision(
        Recommendation recommendation,
        String policyVersion,
        List<String> requiredApproverRoles,
        List<String> missingEvidence) {}

interface ProposalFactory {
    ApprovalProposal create(
            ApprovalCaseRef caseRef,
            List<EvidenceRef> evidence,
            RuleDecision decision);
}

interface ApprovalWorkflow {
    void requestInformation(UUID caseId, long expectedVersion, List<String> missing);
    void createHumanTasks(ApprovalProposal proposal, List<String> approverRoles);
    void escalate(UUID caseId, long expectedVersion, String reasonCode);
}

final class IntelligentApprovalCoordinator {
    private final List<EvidenceAgent> readOnlyAgents;
    private final ApprovalRules rules;
    private final ProposalFactory proposals;
    private final ApprovalWorkflow workflow;

    IntelligentApprovalCoordinator(
            List<EvidenceAgent> readOnlyAgents,
            ApprovalRules rules,
            ProposalFactory proposals,
            ApprovalWorkflow workflow) {
        this.readOnlyAgents = List.copyOf(readOnlyAgents);
        this.rules = rules;
        this.proposals = proposals;
        this.workflow = workflow;
    }

    ApprovalProposal analyze(ApprovalCaseRef caseRef) {
        List<EvidenceRef> evidence = readOnlyAgents.stream()
                .map(agent -> agent.analyze(caseRef))
                .toList();
        RuleDecision decision = rules.evaluate(caseRef, evidence);
        ApprovalProposal proposal = proposals.create(caseRef, evidence, decision);

        switch (decision.recommendation()) {
            case REQUEST_INFO -> workflow.requestInformation(
                    caseRef.caseId(), caseRef.caseVersion(), decision.missingEvidence());
            case ESCALATE -> workflow.escalate(
                    caseRef.caseId(), caseRef.caseVersion(), "RULE_ESCALATION");
            case APPROVE, REJECT -> workflow.createHumanTasks(
                    proposal, decision.requiredApproverRoles());
        }
        return proposal; // 返回提案，不执行采购或付款。
    }
}

并行边界：为了让控制流一眼可读，上述教学骨架按固定顺序执行四个只读 Agent。生产实现可以在有界线程池中并行，但必须传播同一 deadline、取消信号与预算；合并前按角色检查“每个必需角色恰好一个结果”，并按稳定顺序排序证据。任何写工具和审批任务都不能并行越过合并门。

import java.util.Optional;

record ApprovedExecution(
        String tenantId,
        UUID caseId,
        UUID proposalId,
        String proposalHash,
        String approvalRef,
        String idempotencyKey) {}

interface ApprovalVerifier {
    void requireCurrentAndFullyApproved(ApprovedExecution command);
}

interface ProcurementWriter {
    // 目标系统必须原生接受并兑现 command.idempotencyKey()。
    String createPurchaseOrder(ApprovedExecution command);
}

interface ProcurementRecoveryReader {
    // 只供 EXECUTION_UNKNOWN 恢复任务查询，不能用于执行路径的“先查后写”。
    Optional<String> lookupByIdempotencyKey(
            String tenantId, String idempotencyKey);
}

sealed interface ExecutionClaim
        permits AcquiredExecution, CompletedExecution, InProgressExecution {}
record AcquiredExecution(UUID executionId) implements ExecutionClaim {}
record CompletedExecution(UUID executionId, String externalRef)
        implements ExecutionClaim {}
record InProgressExecution(UUID executionId) implements ExecutionClaim {}

interface ApprovalExecutionStore {
    // 在一个事务内 INSERT；(tenantId, idempotencyKey) 唯一冲突时返回已有 claim。
    ExecutionClaim claim(ApprovedExecution command);
    void complete(UUID executionId, String externalRef);
}

final class ApprovedProcurementExecutor {
    private final ApprovalVerifier verifier;
    private final ApprovalExecutionStore executions;
    private final ProcurementWriter writer;

    ApprovedProcurementExecutor(
            ApprovalVerifier verifier,
            ApprovalExecutionStore executions,
            ProcurementWriter writer) {
        this.verifier = Objects.requireNonNull(verifier);
        this.executions = Objects.requireNonNull(executions);
        this.writer = Objects.requireNonNull(writer);
    }

    String execute(ApprovedExecution command) {
        verifier.requireCurrentAndFullyApproved(command);
        return switch (executions.claim(command)) {
            case CompletedExecution completed -> completed.externalRef();
            case InProgressExecution inProgress ->
                    throw new IllegalStateException(
                            "execution already in progress: " + inProgress.executionId());
            case AcquiredExecution acquired -> {
                String externalRef = writer.createPurchaseOrder(command);
                executions.complete(acquired.executionId(), externalRef);
                yield externalRef;
            }
        };
    }
}

ApprovalExecutionStore.claim 必须通过数据库唯一约束原子获得执行权，不能用“先查后写”。ProcurementWriter 还必须把同一个幂等键传给目标系统；如果进程在目标写入后、complete 前崩溃，恢复任务将状态置为 EXECUTION_UNKNOWN，使用同一幂等键查询目标系统并补录回执，不能直接再次调用 create。

#分阶段落地路线

阶段 0：流程与数据基线（2～4 周）

盘点审批类型、规则、系统记录、审批角色和历史样本；先修复身份、状态、幂等和审计。Agent 只做离线影子分析。

阶段 1：材料与制度助手（4～6 周）

上线抽取、缺件提醒、制度引用和风险摘要；所有提案由审批人确认，不开放写工具。建立人工修正回流数据集。

阶段 2：主/子 Agent 辅助审批（6～10 周）

加入 Coordinator、领域子 Agent、结构化 evidence 和 proposalHash；BPMN/DMN 决定补件与会签，运行红队和故障演练。

阶段 3：低风险自动化

只对制度明确、数据完整、可逆且由确定性规则允许的场景自动流转；Agent 提供证据但不是自动批准条件。持续抽样复核并支持一键回退到人工。

MVP 选择建议：先选材料量大、规则相对清晰、每月样本足够、最终动作可逆的采购预审或费用报销补件，不从付款、员工处分、重大合同签署等高风险决定开始。

#实施检查单

  • 业务 Owner、流程 Owner、规则 Owner、模型 Owner、数据 Owner 和最终问责人已明确。
  • BPMN/DMN 基线能在没有模型时完成审批；模型故障不会阻塞核心业务。
  • 主 Agent 没有超级权限；每个子 Agent 的输入投影、工具白名单、预算和 SLO 已版本化。
  • 规则、知识和实时数据被区分；来源、版本、生效日期和观察时间随证据保存。
  • 模型输出经过 closed schema 校验，不能直接成为流程变量、SQL、脚本或最终审批状态。
  • 所有人工决定绑定已认证审批人、角色、proposalHash、策略版本和有效期。
  • 高风险执行器不向 Agent 暴露，使用最小权限 workload identity 与 idempotencyKey。
  • 越权、注入、跨 tenant、重复执行、陈旧提案、工具超时和模型不可用均有回归测试。
  • 指标同时覆盖质量、安全、流程、成本和人工负担，不只看“AI 采纳率”。
  • 灰度、停止、人工接管、回滚和审计取证流程已经演练。

常见反模式

  • 把整个公司所有工具挂到一个主 Agent，形成新的超级管理员。
  • 用四个不同 system prompt 就声称建立了多 Agent 系统，却没有 Coordinator、状态、权限和失败传播。
  • 让模型从制度文本中直接决定金额阈值和审批人，无法版本化或回放。
  • 把“模型置信度 95%”当作批准权限或真实概率。
  • 只保存最终自然语言摘要，不保存原材料引用、证据版本、规则命中和审批决定。
  • 把人工确认变成默认勾选或无证据的形式步骤。
