Loop：从业务 Agent 循环到 Codex 开发闭环

一句话：Loop 是 Agent 反复“观察 → 决策 → 行动 → 验证”的运行机制；生产级 Loop 的核心不是能转，而是有可靠反馈、有限预算、幂等动作和明确停止。

双场景：审批 Agent 运行时 Loop 使用 Java 25 无框架与 Spring AI 两条实现；代码开发部分只说明 Codex 的检查—编辑—测试—审查闭环。

快速阅读： 核心结论 · 概念模型 · 审批 Agent · Codex 开发 · 线上应用 · 资料

核心结论

  1. Loop 解决未知步骤，不替代确定流程。当下一步要依据最新观察动态选择时使用 Loop；固定审批顺序更适合普通代码或 Graph。
  2. 每轮必须改变知识或环境。如果连续两轮既没有新证据、状态变化也没有错误收敛，继续调用模型只是成本放大。
  3. 停止条件是业务契约。至少同时设计成功停止、预算停止和升级停止，且成功必须由外部证据证明。
  4. 重试与重复执行不同。只对可恢复错误重试；任何写动作需要幂等键、结果查询或补偿，不能“超时就再点一次”。
  5. Codex 的高质量开发也来自嵌套 Loop。外层是任务闭环，内层是 TDD、review—fix 和运行行为验证闭环。

概念模型

1. 目标与状态
2. Observe
3. Decide
4. Validate
5. Act
6. Record
7. Verify
8. Stop / Continue
每轮都检查：授权 · 剩余轮数 · 时间 · Token · 成本 · 重复动作 · 人工升级

Loop 不应把隐藏思维过程存入业务库；持久化的是结构化状态、动作、Observation、预算和停止原因。

停止类型判定者审批 Agent 示例Codex 示例
SUCCESS可执行验收器证据齐全且提案 schema/政策校验通过目标测试与真实行为验证通过
BUDGET_EXHAUSTEDLoop 控制器轮数、Token、时间或成本达到上限反复修改无收敛，达到尝试上限
ESCALATE风险/异常策略高金额、制度冲突、权限不足、连续失败需求冲突、破坏性动作、环境不可用
REJECTED确定性规则硬性合规规则不允许Hook、CI 或安全策略拒绝变更
CANCELLED用户或上游系统申请撤回或 case 版本变化用户中断、任务被新指令替换

何时使用与何时不用

  • 适合：证据需要逐步发现、工具结果会改变下一步、错误可通过反馈修正、完成条件可验证。
  • 不适合：固定表单校验、确定性规则计算、一次数据库事务、严格顺序且无动态决策的工作流。
  • 边界：Loop 可以运行在 Graph 节点内，但不能自行绕过 Graph 的人工门禁或业务状态机。

第一部分：智能审批 Agent 开发

运行时审批 Loop
读 case 与证据缺口
选择只读工具
校验证据与提案
编码时 Codex Loop
检查代码与测试
最小修改
测试、审查与修复

两种 Loop 的反馈源不同：审批来自业务系统和规则，编码来自仓库、测试、应用行为和 review。

从零开发步骤

  1. 定义不可变输入和可变 LoopState，包括 caseVersion、证据、已执行动作、剩余预算与停止原因。
  2. 将模型输出限制为 NextAction，先过 schema、权限、重复动作和风险校验，再执行工具。
  3. 为错误分类：瞬时错误可退避重试；永久错误立即失败；权限/高风险错误升级人工。
  4. 每轮追加结构化事件；caseVersion 变化时取消旧循环，禁止把旧批准应用到新材料。
  5. 先用脚本化 fake 决策器覆盖所有停止路径，再接入模型。

无框架实现：Java 25 有界 Loop

public sealed interface NextAction {
    record QueryEvidence(String tool, java.util.Map<String, Object> args)
            implements NextAction {}
    record Propose(ApprovalProposal proposal) implements NextAction {}
    record Escalate(String reasonCode) implements NextAction {}
}

public record LoopBudget(int maxRounds, java.time.Duration timeout, long maxTokens) {}

public record LoopState(
        java.util.UUID caseId,
        long caseVersion,
        int round,
        java.util.List<Evidence> evidence,
        java.util.Set<String> actionFingerprints,
        StopReason stopReason) {
    boolean stopped() { return stopReason != null; }
}
public final class ApprovalLoopRunner {
    public LoopState run(LoopState initial, LoopBudget budget) {
        var state = initial;
        var deadline = clock.instant().plus(budget.timeout());
        while (!state.stopped()) {
            if (state.round() >= budget.maxRounds() || clock.instant().isAfter(deadline))
                return stop(state, StopReason.BUDGET_EXHAUSTED);

            var action = decision.next(project(state));
            var gate = policy.validate(action, state);
            if (gate.requiresHuman()) return stop(state, StopReason.ESCALATE);
            if (!gate.allowed()) return stop(state, StopReason.REJECTED);

            var fingerprint = fingerprint(action);
            if (state.actionFingerprints().contains(fingerprint))
                return stop(state, StopReason.NO_PROGRESS);

            var observation = tools.executeIdempotently(action, fingerprint);
            state = reducer.apply(state, action, observation);
            state = verifier.success(state)
                    ? stop(state, StopReason.SUCCESS)
                    : incrementRound(state);
        }
        return state;
    }
}

真实实现还要在每次工具调用前重新读取取消状态和 caseVersion；写工具应在业务数据库中原子 claim 幂等键，而不是先查后写。

第二部分：代码开发过程中的使用

Codex 接到目标后，本身会在工具反馈中迭代。但开发者仍需设计外层任务契约和内层验证 Loop，避免“不断改直到看起来差不多”。

Loop输入反馈停止
需求收敛Goal、Context、Constraints仓库现实、用户回答范围与 Done when 无歧义
TDD一个行为失败测试与通过测试红—绿—重构完成
调试可复现症状最小实验、日志、Trace根因被证据支持且回归通过
Review—fix明确 diff 范围优先级发现与复审无阻塞发现或升级人工
交付完成定义全量验证、CI、运行行为证据齐全并由人决定合并

可直接使用的 Codex Loop 任务契约

Goal:
修复并发提交造成的审批重复执行，不改变现有 HTTP API。

Context:
- 先读取 AGENTS.md、approval-app 的幂等实现和现有并发测试。
- 真实完成证据来自测试与数据库唯一约束，不来自代码推断。

Constraints:
- 先添加能稳定复现的失败测试。
- 不修改无关模块；不删除现有迁移；不放宽权限。
- 每次写操作必须携带 idempotencyKey。

Done when:
- 新测试先失败后通过；相关模块测试和全量 verify 通过。
- review 无阻塞发现；说明根因、修改、证据和剩余风险。

Stop / escalate:
- 连续两次修改没有改变失败信号时停止并报告假设。
- 需要生产凭据、破坏性迁移或业务规则选择时请求人工。
# 每个实现任务的小循环
1. Inspect：读取最小相关代码、测试和规则。
2. Predict：写下预期失败信号。
3. Test red：运行最小测试并确认失败原因正确。
4. Edit：做最小修改。
5. Test green：重跑最小测试，再扩大验证范围。
6. Review：检查 diff、权限、边界和未覆盖路径。
7. Stop：用新鲜输出证明 Done when，或明确升级。

长任务应在里程碑后压缩上下文并保留版本化计划、决策和测试命令；不要依赖模型“记得之前发生过什么”。Codex 的 /review 可按基线分支、未提交修改或指定 commit 运行独立审查。

线上应用、指标与故障恢复

指标意义建议告警处置
round_count循环长度P95 突增或触顶检查反馈质量、工具错误与任务拆分
no_progress_rate重复动作/无新证据连续两轮无变化停止并升级，不盲目重试
stop_reason为何结束预算/升级比例异常按原因修复 Harness 或策略
tool_retry_count外部依赖稳定性同工具重试激增熔断、退避、查询已有结果
human_override_rate提案与授权人分歧特定政策/模型版本突变切回旧版本并重放评测集

恢复时读取持久化状态与最新 caseVersion，重新计算剩余预算并查询幂等动作结果；不要从自然语言聊天尾部猜测“上次执行到哪里”。

失败模式与边界

  • 无限 Loop：没有轮数、时间或预算上限。修复：控制器外部硬限制。
  • 伪完成：模型说“完成”就停止。修复：独立 verifier 检查规则、测试或真实系统状态。
  • 所有错误都重试：权限拒绝和 schema 不兼容也反复调用。修复：瞬时、永久、高风险错误分类。
  • 重复副作用：超时后再次创建订单。修复：幂等 claim、结果查询、补偿和审计。
  • Codex 大循环：一次提示要求完成几十项共享修改。修复：按可验收任务拆分，用 Graph 管依赖、用 Loop 做节点内部收敛。

练习与验收

  1. 给 ApprovalLoopRunner 写五个测试，分别触发 SUCCESS、BUDGET_EXHAUSTED、ESCALATE、NO_PROGRESS 和 CANCELLED。
  2. 把一个模糊 Codex 请求重写为 Goal/Context/Constraints/Done when/Stop，并为每个 Done when 指定命令或行为证据。
  3. 模拟工具超时但实际已成功，验证重试前先通过幂等键查询结果。

验收标准：能解释为什么停止条件属于业务契约；能把 Loop 状态与聊天历史分开；能说清 Spring AI 自动工具循环和用户控制循环的选型；能用新鲜测试输出而不是模型自述结束 Codex 任务。
