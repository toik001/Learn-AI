#Java Agent 生产部署、可观测性与故障恢复

把 Agent 上线，不是把一次 ChatClient.call() 放进 Controller，而是把不可预测的多步执行约束成可寻址、可暂停、可审计、可恢复且不会重复制造副作用的业务运行。

本文使用 Java 21、Spring AI 2.0.0 与 Spring Boot 4.0.x / 4.1.x，保持模型供应商中立。整理日期与官方资料检索日期：2026-07-27。

#核心结论

  • 运行（run）是第一等业务资源。长任务必须先持久化 AgentRun 和命令，再返回 202 Accepted；实例重启后，新 worker 能从检查点继续，而不是依赖原 JVM 的线程、内存或聊天上下文。
  • 投递通常是至少一次，副作用必须做到“效果至多一次”。队列可能重复、HTTP 客户端会重发、worker 会在提交前后崩溃。入口幂等、步骤幂等、写工具幂等和 transactional outbox 共同把重复投递变成可安全吸收的事实。
  • 重试是分类决策，不是通用注解。只重试瞬态且幂等的调用；认证、授权、参数、配额硬上限、策略拒绝和确定性数据冲突直接失败。超时不会自动取消下游，必须传播绝对 deadline，并为迟到结果设计隔离与对账。
  • 恢复不是“重新发原 Prompt”。从结构化检查点生成新恢复命令，用当前身份、当前策略、当前数据版本和当前审批重新决策；写操作不得继承旧授权，批准内容或目标变化时必须重新审批。
  • 三类基础设施职责不同。Spring AI / Spring Boot / Micrometer 提供模型、工具、向量库与应用的观测集成；队列、幂等账本、持久状态、outbox、恢复队列、重放策略和人工操作台都是业务拥有的基础设施，不能归因于框架。
  • 内容最小化必须覆盖 VectorStore Trace。Spring AI 2.0.0 的 Prompt / completion 日志与工具参数 / 结果 observation 默认关闭；但默认 DefaultVectorStoreObservationConvention 会把查询正文和 metadata filter 加入高基数 Trace 属性。生产环境除保持内容日志开关为 false 外，还必须在实际 VectorStore builder 上接入只允许安全属性的自定义 convention。
  • 可观测性服务于决策，而不是“多打日志”。必须能回答哪个阶段慢、哪类依赖失败、队列是否积压、运行是否卡住、预算如何消耗、恢复是否成功；metric 标签必须有界，requestId、runId、原始 tenantId 和用户 ID 不能成为无界标签。

#同步、异步与持久状态机

同步适用：一次模型调用或一次只读工具、预计在网关 deadline 内完成、没有人工等待、可安全取消，并且失败可直接返回。即使同步执行，也先创建可审计 run，传播 deadline，客户端断开后停止不必要工作。

异步适用：多步骤、写操作、审批、长 RAG、不可预测模型延迟、需要排队 / 限流 / checkpoint 或跨实例恢复。POST /agent-runs 返回 202 Accepted、Location: /agent-runs/{runId} 与稳定状态摘要；客户端轮询 GET，或订阅经过授权的 Webhook / SSE / 消息事件。事件投递本身也需序列号、幂等和断线续传，不能把 SSE 连接当状态库。

等价文字说明：入口事务写入 ACCEPTED run 和 outbox，发布后为 QUEUED；worker 以 lease 领取并用版本 CAS 切换 RUNNING。审批等待不占 worker；批准或重试到期重新排队。成功、取消和不可恢复失败进入终态。需要人工判断的失败进入 RECOVERY_REQUIRED；授权恢复以旧 run 和 checkpoint 为来源创建新 attempt，历史 run 保持不可变。任何陈旧 worker 的 checkpoint CAS 都会失败，避免双执行者覆盖状态。

状态与检查点纪律

  • 检查点只保存结构化、版本化且最小化的数据：已完成 step、输出引用、知识快照版本、工具效果 ID、预算余额、下一动作；不保存可直接重放的原始 Prompt、Bearer token 或审批令牌。
  • lease 到期只表示任务可被其他 worker 认领，不证明旧下游已取消；所有工具效果必须用 (runId, stepId, effectId) 幂等并能对账。
  • 取消是持久意图。Runtime 在步骤边界检查取消标志，并向支持取消的下游传播；不可取消写入必须等待对账后再标记终态。
  • 状态转移、outbox 和效果账本尽量同库同事务；跨系统无法原子提交时，使用明确的 pending / confirmed / unknown 状态与补偿，不伪装成分布式强一致。

#超时、重试、熔断与背压

入口生成一个绝对 deadline，各层只能缩短不能延长：stepTimeout = min(stepPolicy, remainingDeadline - cleanupMargin)。连接、读取、模型、工具、数据库、队列可见性和人工等待分别配置上限；人工等待通常暂停活动执行预算，但仍受审批有效期和 run 最长保留期约束。Resilience4j 可装饰调用，但业务分类必须先于装饰器配置。Resilience4j 官方文档

失败是否自动重试前提与动作
模型 429 / 瞬态 5xx / 网络抖动是，有限次读取 Retry-After，指数退避 + full jitter，服从 deadline / token / 成本预算；跨供应商降级需显式质量策略
只读工具 408 / 429 / 5xx是，有限次工具确定为幂等；每次尝试计入预算；超时后迟到结果不得覆盖新检查点
写工具超时 / 连接中断不直接重发先用业务 effect key 查询结果；对方支持同一幂等键才可重试，否则进入 UNKNOWN 并对账 / 补偿
400 / Schema / 参数校验否修正模型输出或终止；同一 payload 重试没有意义
401 / 403 / 策略拒绝 / 审批过期否fail closed；刷新认证也不能自动继承旧审批，交给用户或操作员重新授权
知识版本冲突 / 乐观锁冲突条件性重新读取并重新规划；不得用重试覆盖他人更新
模型拒答 / 幻觉 / 低置信通常否这是语义结果而非基础设施瞬态错误；诚实降级或转人工，避免“多问几次直到碰巧成功”
毒消息 / 确定性代码错误否达到小次数阈值后隔离到恢复队列，避免热循环

韧性组件的组合边界

  • RateLimiter：按模型 / 工具配额和公平性限制到达率；tenant 配额在业务层执行，不能把原始 tenant 作为指标标签。
  • Bulkhead：模型、RAG、每类工具使用独立并发舱和连接池；一个慢工单系统不能耗尽全部 worker。虚拟线程降低线程占用，不会消除连接、内存、token 或下游容量上限。
  • CircuitBreaker：按依赖 + 操作类别划分，统计技术失败 / 慢调用；OPEN 快速失败，HALF_OPEN 只放少量探针。业务拒绝、404“未找到”和策略拒绝不应计为依赖故障。
  • Retry：放在整体 deadline 和 bulkhead 纪律内，限制总尝试；不要形成 SDK、HTTP、业务和队列四层乘法重试。记录 original attempt 与 retry attempt。
  • Backpressure：入口按全局 / tenant / 风险层配额拒绝或延迟；监控 queue depth、oldest age 和 consumption rate。高水位时停止低优先级接收、降低并发或返回 429 / 503 + 重试建议，而不是无限扩容内存队列。
  • Recovery queue：它是业务基础设施，保存 runRef、stepRef、checkpointRef、错误分类、attempt、策略 / 数据版本和安全证据引用；不是日志桶，也不是 Spring AI / Actuator / Resilience4j 自动提供的能力。

#可观测性：安全关联、指标和 Trace

Spring Boot 将 observability 概括为日志、指标和 Trace 三柱，并通过 Micrometer Observation 连接指标与 Trace；注入 ObservationRegistry 可创建业务 observation。Micrometer Tracing 是 tracer facade，注册 tracing ObservationHandler 后，一次 Observation 会对应创建、启动、停止并上报 span。Spring Boot Observability · Micrometer Tracing

关联字段与基数

信号安全字段禁止 / 限制
结构化日志requestId、runId、traceId、受控 tenantRef、step、attempt、outcomeCode、duration日志受访问控制与保留期约束；tenant 采用内部 pseudonymous ref。禁止 Prompt、检索正文、工具内容、token、审批凭证和原始异常响应
Metric 低基数标签operation、dependencyClass、riskTier、outcome、retryable、model family（有界时）requestId、runId、user、原始 tenant、ticket ID、完整模型名 / URL 不得进入标签；除非 tenant 集合有严格上限与容量评审
Trace 高基数属性必要时使用 runRef、stepRef、requestId；错误码、版本和安全资源引用高基数仍有成本和隐私风险；采样不等于脱敏。tenantId 仅在合规允许且受控映射时进入 Trace，不默认采集用户 ID
审计主体引用、tenantRef、策略 / 审批版本、动作、资源、decision、effectId、前后摘要审计与调试日志分离、append-only；不把完整业务内容当“为了审计必须保存”

业务指标与告警

  • 运行：agent.run.active gauge、agent.run.completed counter、端到端 / 活动执行 timer，按有界 outcome / riskTier 分组；等待审批与执行时间分开。
  • 步骤：step / tool / model / retrieval duration、error、timeout、retry、circuit-open；工具名只在严格 allowlist 且数量有界时成为标签。
  • 队列：depth、oldest-message-age、enqueue / dequeue rate、processing lease expiry、recovery queue inflow / age；只看 depth 会漏掉“小队列中的超老消息”。
  • 预算：token、模型调用、工具调用、成本和 deadline 消耗；同时记录成功与失败成本。告警优先使用 burn rate、队列年龄、失败分类和恢复积压。
  • 饱和度：worker active / configured、bulkhead available、连接池、限流等待、heap / GC。active 与 completed 必须同时看，只有 completed 会漏掉卡住调用。

VectorStore Trace：默认泄露面与自定义清洗

Spring AI v2.0.0 源码显示，DefaultVectorStoreObservationConvention.getHighCardinalityKeyValues 会依次加入 collection、dimension、field、metadata filter、namespace、query content、similarity metric / threshold 与 top-k；其中 metadataFilter(...) 直接序列化 filter expression，queryContent(...) 直接复制查询正文。Micrometer 的高基数键不进入 metric，却会进入 Trace，因此“metric 标签安全”不能推出“span 无敏感内容”。v2.0.0 默认 convention 源码

spring.ai.vectorstore.observations.log-query-response=false 的作用仅是阻止自动配置注册 VectorStoreQueryResponseObservationHandler，从而不把返回文档正文写入日志；它不会删除默认 convention 已生成的 db.vector.query.content 或 db.vector.query.filter span attributes。v2.0.0 默认 convention 不导出 response document / ID 高基数键，但 VectorStoreObservationContext 仍持有 query response，任何自定义 handler 都必须经过安全审查。v2.0.0 响应日志自动配置源码

下面采用空的高基数 allowlist：继承默认低基数的 spring.ai.kind、db.system、db.operation.name 指标 / Trace 属性，但不导出 query、filter、collection、namespace、field、response 内容或文档 ID。若以后确需 top-k 等数值属性，也必须逐项加入、做隐私与基数评审，不能调用 super.getHighCardinalityKeyValues(context) 后再期望靠日志开关清洗。

import io.micrometer.common.KeyValues;
import org.springframework.ai.vectorstore.observation
        .DefaultVectorStoreObservationConvention;
import org.springframework.ai.vectorstore.observation
        .VectorStoreObservationContext;

final class SafeVectorStoreObservationConvention
        extends DefaultVectorStoreObservationConvention {

    @Override
    public KeyValues getHighCardinalityKeyValues(
            VectorStoreObservationContext context) {
        // Fail closed：不调用 super。明确排除：
        // db.vector.query.content / db.vector.query.filter
        // db.collection.name / db.namespace / db.vector.field_name
        // query response content / document IDs / metadata。
        return KeyValues.empty();
    }
}

必须在实际 provider builder 上接线

v2.0.0 的通用 VectorStore.Builder / AbstractVectorStoreBuilder 提供 observationRegistry(...) 与 customObservationConvention(...)，构造出的 AbstractObservationVectorStore 才会使用该 convention。只声明一个 VectorStoreObservationConvention Spring Bean 不足以证明它已接入；官方 observation auto-configuration 只管理响应日志 handler，没有把任意 convention Bean 全局塞入所有 provider。每个选定 provider 必须在自己的 @Bean VectorStore 工厂中使用其官方 builder，或使用该 provider 经源码核验的等效 customizer。VectorStore.Builder v2.0.0 源码 · AbstractVectorStoreBuilder v2.0.0 源码

import io.micrometer.observation.ObservationRegistry;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.ai.vectorstore.observation
        .VectorStoreObservationConvention;

final class SafeVectorStoreWiring {
    private SafeVectorStoreWiring() {}

    // 在所选 provider 的 @Bean VectorStore 工厂内调用；
    // B 是该 provider 官方 builder 的真实类型，不虚构统一 provider API。
    static <B extends VectorStore.Builder<B>> VectorStore build(
            B providerBuilder,
            ObservationRegistry registry,
            VectorStoreObservationConvention safeConvention) {
        return providerBuilder
                .observationRegistry(registry)
                .customObservationConvention(safeConvention)
                .build();
    }
}

Trace 父子关系

同步链路采用 HTTP server → agent.run → step → ChatClient / Advisor → ChatModel | VectorStore | tool。异步链路以 API span 创建 queue producer span；consumer 提取传播上下文并创建 consumer / run attempt span。若任务等待数小时或由人工恢复，不强行保持超长父 span：新的 attempt 使用 span link 指向原 trace，并通过持久 runId / attempt 关联。必须对 worker 线程 / reactive / 消息边界验证上下文传播；Spring Boot 文档特别指出自定义异步执行器需配置 context propagation，不能假设 ThreadLocal 自动穿越所有边界。

#幂等与一致性

幂等键必须有明确作用域与过期策略。推荐入口唯一键为 (tenantRef, operation, idempotencyKey)，账本同时存 canonical request fingerprint、runId、状态和首次响应。相同 key + 相同 fingerprint 返回已有 run；相同 key + 不同 fingerprint 返回 409 Conflict，绝不能把两个请求合并。

层级唯一约束原子边界冲突处理
API 请求tenant + operation + client key幂等账本 + AgentRun + outbox 同事务指纹不同返回 409；不启动第二个 run
队列命令commandId / run attemptinbox 去重 + 状态 CAS + 新 outbox已处理则 ack；处理中由 lease / version 判定
步骤runId + attempt + stepId + inputVersioncheckpoint + step outcome读取既有结果；版本变更须重新规划
外部副作用稳定 effectId / provider idempotency key本地 effect ledger + 远端幂等 API / 对账UNKNOWN 不盲重发；查询、确认、补偿或人工处理
事件发布outbox eventId业务写 + outbox 同事务；relay 可重复发布消费者 inbox 去重；不要假设 broker exactly-once 等于业务 exactly-once

Outbox 的价值：避免“数据库提交成功但消息未发”和“消息发出但数据库回滚”的双写窗口。relay 仍可能重复发布，所以消费者去重不可省。审计与写副作用的关系必须按风险定义：高风险动作若要求审计先存在，则审计 append 不可用时 fail closed；若远端已写而本地确认失败，则进入 UNKNOWN / RECOVERY_REQUIRED 做对账，不能返回“失败”后静默重试。

#故障恢复与安全重放

恢复队列只接收已经停止自动重试、具备持久证据并需要业务判断的 run。操作员先分类：可从检查点继续、需要重新规划、需要补偿 / 对账、需要用户重新提交、或永久拒绝。任何“重放”都创建新的 RecoveryCommand 与 attempt，保留原失败链路。

  1. 重新认证操作员：校验 operator、tenant scope、职责分离和恢复动作权限；队列可见不等于可执行。
  2. 重新读取当前事实：读取最新 run / checkpoint version、知识快照、外部 effect 状态和业务对象 ETag；不信任恢复请求自带的状态。
  3. 重新执行当前策略：ReplayPolicy.authorize 使用当前 policy version、工具 allowlist、预算、数据保留与风险规则；旧的 ALLOW 只作为历史证据。
  4. 重新校验审批：所有写操作要求当前、未过期且绑定准确 action、resource、arguments digest、data version 与 policy version 的审批。内容、目标、版本、风险任何变化都使旧审批失效。
  5. 核对幂等与副作用：先查 effect ledger 和远端状态。已完成则只修复本地确认；UNKNOWN 先对账；只有已证明未执行且远端支持幂等时才发起写。
  6. 从结构化边界恢复：使用 checkpoint 与受控引用重新构造上下文；不盲目重放原始 Prompt、工具 arguments、检索正文或曾获授权的写调用。
  7. 创建新 attempt 并审计：记录 sourceRunId、sourceCheckpointVersion、operatorRef、reasonCode、policy decision、approvalRef 和新 runId；原 run 不改写。

Fail closed：找不到策略版本、数据版本过旧、审批过期、指纹不一致、状态 CAS 冲突、effect 状态 UNKNOWN 且无法对账、审计不可用，均不得自动执行写操作。允许的降级是只读诊断、向用户解释和转人工，而不是跳过检查。

record IdempotencyKey(
        String tenantRef,
        String operation,
        String clientKey,
        String requestFingerprint) {
    IdempotencyKey {
        tenantRef = requireToken(tenantRef, "tenantRef");
        operation = requireToken(operation, "operation");
        clientKey = requireToken(clientKey, "clientKey");

final class RunTransitions {
    private static final Map<RunStatus, Set<RunStatus>> ALLOWED =
            allowedTransitions();

    static AgentRun move(
            AgentRun current,
            RunStatus next,
            long expectedVersion,
            Instant now,
            Optional<String> checkpointRef,
            Optional<String> outcomeCode) {
        if (current.version() != expectedVersion) {
            throw new StaleRunVersionException(current.runId());
        }
        if (!ALLOWED.getOrDefault(current.status(), Set.of()).contains(next)) {
            throw new IllegalRunTransitionException(
                    current.status(), next);
        }
        return new AgentRun(
                current.runId(),
                current.tenantRef(),
                current.principalRef(),
                next,
                current.attempt(),
                current.version() + 1,
                current.deadline(),
                now,
                current.policyVersion(),
                current.inputRef(),
                checkpointRef,
                outcomeCode);
    }

    private static Map<RunStatus, Set<RunStatus>> allowedTransitions() {
        var result = new EnumMap<RunStatus, Set<RunStatus>>(
                RunStatus.class);
        result.put(RunStatus.ACCEPTED, Set.of(RunStatus.QUEUED));
        result.put(
                RunStatus.QUEUED,
                Set.of(RunStatus.RUNNING, RunStatus.CANCELLED));
        result.put(
                RunStatus.RUNNING,
                Set.of(
                        RunStatus.WAITING_APPROVAL,
                        RunStatus.RETRY_SCHEDULED,
                        RunStatus.SUCCEEDED,
                        RunStatus.FAILED,
                        RunStatus.CANCELLED,
                        RunStatus.RECOVERY_REQUIRED));
        result.put(
                RunStatus.WAITING_APPROVAL,
                Set.of(
                        RunStatus.QUEUED,
                        RunStatus.CANCELLED,
                        RunStatus.RECOVERY_REQUIRED));
        result.put(
                RunStatus.RETRY_SCHEDULED,
                Set.of(RunStatus.QUEUED, RunStatus.CANCELLED));
        result.put(
                RunStatus.FAILED,
                Set.of(RunStatus.RECOVERY_REQUIRED));
        return Map.copyOf(result);
    }
}

enum ReplayEffect { ALLOW_READ_ONLY, REQUIRE_APPROVAL, DENY }

record ReplayDecision(
        ReplayEffect effect,
        String reasonCode,
        String policyVersion) {
    boolean permitsWrite() {
        return effect == ReplayEffect.REQUIRE_APPROVAL;
    }
}

interface ReplayPolicy {
    ReplayDecision authorize(
            TrustedOperator operator,
            AgentRun source,
            RecoveryCommand command,
            CurrentResourceSnapshot resources,
            ExternalEffectState effects,
            Optional<BoundApproval> approval);
}

final class RecoveryService {
    private final AgentRunRepository runs;
    private final CheckpointRepository checkpoints;
    private final ReplayPolicy policy;
    private final EffectLedger effects;
    private final RecoveryQueue recoveryQueue;
    private final AuditStore audit;

    UUID recover(TrustedOperator operator, RecoveryCommand command) {
        AgentRun source =
                runs.requireVersion(
                        command.sourceRunId(), command.expectedRunVersion());
        Checkpoint checkpoint =
                checkpoints.requireVersion(
                        command.checkpointRef(),
                        command.expectedCheckpointVersion());
        CurrentResourceSnapshot resources =
                loadCurrentResources(source, checkpoint);
        ExternalEffectState effectState =
                effects.reconcile(source.runId(), checkpoint.stepId());
        Optional<BoundApproval> approval =
                loadCurrentApproval(command.approvalRef());

        ReplayDecision decision =
                policy.authorize(
                        operator,
                        source,
                        command,
                        resources,
                        effectState,
                        approval);
        audit.appendRecoveryDecision(source, command, decision);
        if (decision.effect() == ReplayEffect.DENY) {
            throw new RecoveryDeniedException(decision.reasonCode());
        }
        if (checkpoint.nextStepWrites()
                && (!decision.permitsWrite()
                    || approval.isEmpty()
                    || !approval.get().matchesCurrent(
                            resources, command.currentPolicyVersion()))) {
            throw new RecoveryDeniedException(
                    "CURRENT_BOUND_APPROVAL_REQUIRED");
        }
        if (effectState == ExternalEffectState.UNKNOWN) {
            throw new RecoveryDeniedException(
                    "EXTERNAL_EFFECT_RECONCILIATION_REQUIRED");
        }

        UUID newRunId =
                runs.createRecoveryAttempt(
                        source,
                        checkpoint.safeReference(),
                        command.currentPolicyVersion());
        recoveryQueue.enqueueAuthorized(newRunId, command.commandId());
        return newRunId;
    }

    private CurrentResourceSnapshot loadCurrentResources(
            AgentRun source, Checkpoint checkpoint) {
        throw new UnsupportedOperationException("application implementation");
    }

    private Optional<BoundApproval> loadCurrentApproval(
            Optional<String> approvalRef) {
        throw new UnsupportedOperationException("application implementation");
    }
}

关键性质：ReplayPolicy.authorize 的输入来自服务器重新读取的 current snapshots，而非模型或命令自报；即使策略返回 REQUIRE_APPROVAL，代码仍检查审批是否绑定当前资源和策略。UNKNOWN 外部效果阻止重放。真实实现应将“创建 recovery attempt + outbox”置于一个事务，而不是先创建 run 再调用不可靠 broker。

final class AgentRunService {
    private final RunUnitOfWork unitOfWork;
    private final ObservationRegistry observations;

    AgentRunService(
            RunUnitOfWork unitOfWork,
            ObservationRegistry observations) {
        this.unitOfWork = unitOfWork;
        this.observations = observations;
    }

    RunAccepted accept(
            TrustedRequestContext context,
            String clientKey,
            StartAgentRequest request) {
        IdempotencyKey key =
                new IdempotencyKey(
                        context.tenantRef(),
                        "START_AGENT_RUN",
                        clientKey,
                        canonicalFingerprint(request));

        return Observation
                .createNotStarted("agent.run.accept", observations)
                // 只用有界枚举做低基数标签；不放 tenant / run / user。
                .lowCardinalityKeyValue(
                        "agent.operation", "start")
                .lowCardinalityKeyValue(
                        "agent.risk_tier",
                        request.allowsWrite() ? "write" : "read_only")
                .observe(() ->
                        unitOfWork.createRunAndOutboxAtomically(
                                context, key, request, Instant.now()));
    }

    RunView readAuthorized(
            TrustedRequestContext context, UUID runId) {
        return unitOfWork.readAuthorized(context, runId);
    }

    private String canonicalFingerprint(StartAgentRequest request) {
        throw new UnsupportedOperationException("canonical JSON + SHA-256");
    }
}

边界说明：RunUnitOfWork 在一个业务事务中处理幂等唯一约束、创建 run 与 outbox；Controller 不直接把请求交给模型。relay、broker、worker lease、checkpoint repository、恢复队列与重放操作台仍是业务基础设施。ObservationRegistry 只观测业务边界；Spring AI 会自动为 ChatClient、Advisor、ChatModel、tool 和 VectorStore 产生其官方 observations，不必再套同名 observation 造成重复计时。

    }
}

日志只记录固定错误码与受限诊断引用。禁止在 catch 中直接记录 exception.getMessage()，因为 SDK 异常可能包含请求、响应或 URL 参数；先经错误分类器提取 provider-neutral code，把原始证据加密放入受限事故存储并设置短 TTL。

#企业服务台案例：最终生产状态

  1. 用户以租户身份提交“诊断支付 API 失败”；API 从认证态获得 principal / tenant，校验客户端幂等键，创建异步 diagnostic run，返回 202 与 Location。
  2. outbox relay 投递命令；worker 从 QUEUED run 领取 lease。第一检查点记录输入引用、策略版本、预算和知识快照，不保存原始 Prompt。
  3. Runtime 只给 triage 角色暴露服务状态、工单查询等只读工具；每次调用重新做 tenant / 对象级授权。模型 429 遵循 Retry-After 与有限退避，工具池与模型池用独立 bulkhead。
  4. RAG 按 tenant ACL、文档版本和有效期检索 runbook，答案必须带文档 ID、标题、版本与 URI；向量库故障时停止“凭记忆猜答案”，返回诊断待恢复或转人工。
  5. 诊断完成后保存 checkpoint、引用、step outcome 与 outbox。若需建单，只生成结构化提案；用户审批绑定 ticket fields digest、目标系统、资源版本、策略版本和有效期。
  6. 执行写入前重新授权并检查审批；用 effectId 调用支持幂等的建单 API。本地状态与远端结果不确定时进入 UNKNOWN 并对账，不盲重试。
  7. 审计链记录主体引用、策略决定、审批引用、effectId 和 outcome；Trace 连接 API、队列、Runtime、RAG、模型和工具；指标只用有界 operation / outcome / riskTier。
  8. 实例重启后新 worker 从最后 confirmed checkpoint 继续。毒消息、过期审批或冲突写入进入恢复队列；操作员只能通过 RecoveryCommand 和当前 ReplayPolicy 发起新 attempt。

#练习与验收

练习

  1. 入口幂等：用 Spring Boot + 数据库实现 POST /agent-runs。并发发送 20 个相同 key / 指纹请求，再发送一个相同 key / 不同指纹请求。
  2. 可恢复 worker：实现 lease、状态 CAS 和三个 checkpoint，在“远端写成功、本地提交前”注入进程退出，并通过 effectId 对账。
  3. 韧性实验：为模型、只读工具和向量库建立独立 bulkhead / circuit breaker；模拟 429、慢调用和 5xx，证明总尝试受 deadline / 预算限制且没有乘法重试。
  4. 安全遥测：接入 Actuator、ObservationRegistry 和 Spring AI observations；用不同 canary 放入 Prompt、工具参数 / 结果、VectorStore query / filter、返回文档正文 / ID 与异常。先证明默认 VectorStore convention 的 span 扫描 RED，再在生产实际 builder 接入安全 convention，扫描 logs、metrics、spans 要求零泄露。
  5. 安全恢复：实现 RecoveryCommand 与 ReplayPolicy，测试过期审批、撤销权限、资源版本冲突、UNKNOWN effect 和当前合法只读恢复。

验收标准

  • 同步路径只承载短只读动作；多步 / 写 / 审批均返回 202 + Location，并能通过 GET 或授权事件读取持久状态。
  • 相同幂等 key + 指纹只产生 1 个 run / outbox / 外部效果；不同指纹稳定返回 409。进程重启和消息重复测试均通过。
  • 状态机拒绝非法转移与陈旧 version；终态不原地重开，恢复创建带 sourceRunId 的新 attempt。
  • 429 / 5xx、超时、circuit open、bulkhead full、queue high-water 都有确定 outcome；总尝试、deadline、token、工具与成本预算有硬上限。
  • 故障矩阵十类场景均有自动化或演练证据；部分写入没有重复副作用，毒消息不会热循环。
  • Dashboard 同时展示 active / completed、queue oldest age、step / model / tool / RAG latency-error、budget 与 recovery age；metric 中不存在 run / user / 原始 tenant 等无界标签。
  • Spring AI 2.0.0 的 ChatClient、Advisor、ChatModel、tool、VectorStore observations 可见，trace 父子 / link 关系正确，异步边界上下文传播经过测试。
  • Prompt / completion 日志与工具 arguments / result observation 开关保持关闭；spring.ai.tools.observations.include-content=false。VectorStore 的 log-query-response=false 仅承担响应日志控制，生产 bean 另接安全 convention；query / filter / response text / document ID canary 在 logs、metrics、spans 中均为零。
  • 恢复时重新认证、读取当前状态、执行当前策略并重新校验审批 / 幂等；过期审批、撤权、冲突或 UNKNOWN effect 的写 delegate 调用数为 0。
  • 团队能明确指出：Spring AI / Boot / Micrometer 提供观测集成；队列、run 状态、幂等、outbox、recovery queue 和 replay policy 是业务基础设施。
