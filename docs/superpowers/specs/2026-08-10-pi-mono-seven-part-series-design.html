pi-mono 七篇专题设计说明

目标与读者

围绕当前由 Earendil Works 维护的开源 Pi Agent Harness（现仓库 earendil-works/pi，历史仓库名 badlogic/pi-mono），为具备软件开发经验、正在学习 AI 编码 Agent 的读者创建七篇递进式中文专题。专题同时回答三个问题：Pi 为什么这样设计、怎样有效使用与扩展、它相对主流编码 Agent 适合什么场景。

内容深度采用“原理与实践各半”。读者完成专题后，应能解释 Pi 的模块边界和运行路径，独立完成安装与日常使用，理解 Extension、工具、Prompt、Skill、SDK 与 RPC 的扩展边界，并能在 Pi、Claude Code、Codex CLI、OpenCode、Aider、Goose 之间做有依据的选择。

采用的内容方案

采用七篇渐进式专题，而不是五篇浓缩版或九篇参考手册版。七篇可以让每个页面拥有单一职责，同时把专题规模控制在一次可验证的交付内：

  1. 专题总览与学习路线；
  2. 设计理念、定位与边界；
  3. Monorepo 模块架构、Agent Loop、事件与会话；
  4. 安装、配置、模型接入和日常使用；
  5. Extension、自定义工具、Prompt、Skill、SDK 与 RPC；
  6. 与 Claude Code、Codex CLI、OpenCode、Aider、Goose 的统一维度对比；
  7. 面向不同开发者与团队的选型建议和实践路线。

不把 Provider、Session、RPC 或 Web UI 继续拆成独立文章，以免内容碎片化；这些主题分别放入架构、使用或扩展页。不把通用 Agent 应用框架纳入主对比，因为本专题比较的是面向软件开发任务的编码 Agent，而不是用于构建业务 Agent 的通用运行时。

七篇页面边界

  1. 总览：解释 Pi 是什么、不是什么、适合谁，说明 badlogic/pi-mono、Mario Zechner、Earendil Works 与当前 Pi 的关系，给出七篇阅读顺序、项目能力地图、五分钟判断和专题术语表。只提供鸟瞰，不重复后续页面的完整教程。
  2. 设计理念：解释极简核心、组合优于内置、终端优先、模型中立、透明可控和扩展优先等理念，并分析每项理念带来的收益、成本与适用边界。明确区分作者的公开表述、仓库可观察事实和本文分析。
  3. 源码架构：说明当前根 README 列出的 pi-telemetry、pi-ai、pi-agent-core、pi-coding-agent、pi-tui 的职责和依赖；对 pi-web-ui 等旧清单内容只作为历史变化说明，不把它们写成当前核心清单；追踪一次用户请求从输入、上下文组装、模型流式调用、工具执行、事件发送到会话持久化的完整路径；解释关键 TypeScript 类型、异步流与 Node.js 进程边界。
  4. 使用教程：覆盖运行环境、安装方式、认证与 API Key、Provider/模型选择、项目上下文、会话管理、高频命令、常见配置、排错和可验证练习。命令以官方当前文档为准；需要外部账号或付费额度的步骤明确写出前置条件。
  5. 扩展开发：分别讲清 Extension、自定义工具、Prompt Template、Skill、SDK 和 RPC 的职责、选择条件及最小示例。示例使用项目原生的 TypeScript/JavaScript，并说明通过 SDK、子进程或 RPC 嵌入其他系统时的通用工程边界。
  6. 竞品对比：对 Pi、Claude Code、Codex CLI、OpenCode、Aider、Goose 采用同一组维度和同一检索时间截面，比较许可证、模型/Provider、核心交互、扩展机制、自动化与无头模式、会话与上下文、生态成熟度、主要优势、限制和典型团队。避免用单一分数制造虚假精确性。
  7. 选型与实践：面向个人学习、日常编码、小型团队、自动化流水线和自定义 Agent Harness 给出情景化建议、决策树、风险清单、渐进练习和验收标准，并把建议链接回前六篇的事实依据。

统一页面结构与导航

七篇均写入 public/notes/coding-agent/，文件名使用日期 2026-08-10 与简洁中文关键词。每篇至少包含语义化 header、nav、main、article，并在 head 提供 description、study-category 和 study-date 元数据。

每页都包含“核心结论”和“参考资料”，并按主题加入实践、示例、误区或检查清单。页内目录使用稳定唯一的标题 ID；七篇通过显式专题导航互链，站点生成器继续维护全站侧栏、上一篇/下一篇和清单。共享样式与脚本复用 public/assets/style.css 和 public/assets/app.js，不新增第三方前端依赖或远程资源。

图表与示例设计

  • 总览页使用能力地图和学习路线表，帮助读者先定位再深入。
  • 理念页使用“理念—机制—收益—代价”表，避免只写抽象口号。
  • 架构页使用 HTML/CSS 模块依赖图、请求时序图和事件流表；图形必须带文字说明，在移动端和暗色主题下可读。
  • 使用页提供可复制命令、预期结果、验证步骤和常见错误，不展示无法从官方资料确认的参数。
  • 扩展页对每种扩展点给出“何时用、依赖什么、最小结构、怎样验证、何时不要用”，代码放入转义正确的 <pre><code>。
  • 竞品页使用统一对比表和场景矩阵；对易变化能力标明检索日期，不把营销描述当作实测结论。
  • 选型页使用纯 HTML/CSS 决策树和分阶段练习路线，不依赖 Mermaid 或外部脚本。

资料与事实核验

资料检索日期为 2026-08-10。Pi 的当前事实优先取自 earendil-works/pi 官方仓库、pi.dev、各 package README、变更记录和 RFC；项目迁移事实同时核验 pi.dev 的 2026-05-07 官方公告与对应 release。旧的 badlogic/pi-mono URL、@mariozechner/* scope 和 0.73.1 以前的资料只作为历史背景。竞品事实优先取自各自官方文档、官方代码仓库、许可证和发布说明。关键版本、功能、许可证与扩展边界由一手来源确认，必要时交叉核验仓库代码或发布记录。

页面必须区分三类信息：“官方说明”表示来源直接陈述，“仓库观察”表示从公开结构或代码推导出的可复核事实，“选型建议”表示基于前两类事实的分析判断。无法验证的行为标记为待验证；未实际运行外部认证、付费模型或云端服务时，不声称完成端到端实测。

比较方法

主对比对象固定为 Claude Code、Codex CLI、OpenCode、Aider 与 Goose。所有项目使用同一信息截面和以下维度：

  • 产品/项目定位与主要交互界面；
  • 开源状态、许可证与可自托管边界；
  • 模型及 Provider 支持方式；
  • 工具、插件、Hook、Skill、MCP 或其他扩展机制；
  • 会话、上下文、项目指令和代码编辑策略；
  • 无头模式、SDK、CI 与自动化集成能力；
  • 成熟度、生态、主要优势、限制和适用团队。

不做没有可复现实验支撑的性能排行榜，不用 GitHub Star 直接代表质量，也不把“支持某种扩展协议”等同于扩展体验完全一致。若官方能力在不同套餐或登录方式下有差异，页面必须说明前提。

技术语境与集成边界

源码与扩展示例保持 Pi 原生的 TypeScript、JavaScript 和 Node.js 技术语境。架构页直接解释联合类型、异步迭代器、事件流、包边界与进程模型，不为特定后端语言增加专门类比。

扩展与选型页说明通过 SDK、子进程或 RPC 集成 Pi 时的通用工程约束，包括协议版本、超时、取消、日志、并发、密钥隔离与进程生命周期；本次交付不创建某种语言或框架的完整集成工程。

测试与生成策略

  • 新增专题契约测试，断言恰好七篇目标页面存在，元数据、核心结论、参考资料和专题导航完整。
  • 断言关键页面包含预定项目/package 名、对比对象和 SDK/RPC 集成边界，防止页面标题存在但内容缺失。
  • 复用现有站点测试与 scripts/verify-site.mjs 检查相对链接、标题 ID、外链安全属性、共享资源和 HTML 结构。
  • 运行 node scripts/build-html-index.mjs 重建根目录 index.html、文档侧栏、上一篇/下一篇和 public/manifest.json。
  • 重跑生成器后检查 git diff --exit-code -- index.html public，确认生成结果幂等。

验收标准

  • 恰好新增七篇 pi-mono 学习页面，职责与本设计一致并形成可连续阅读的专题。
  • 设计理念、完整使用方法、扩展开发与五个竞品对比均有独立且足够深入的内容。
  • 架构页正确覆盖当前仓库根 README 的核心 package，并用可追踪的请求/事件路径解释协作关系；旧 package 只在迁移历史中出现。
  • 使用与扩展示例包含环境、前置条件、步骤、预期结果、验证方法和常见失败边界。
  • 竞品结论来自同一时间截面的一手资料；事实、观察和建议有清晰标签。
  • 读者能够理解 TypeScript/Node.js 示例，并判断 Extension、SDK、子进程和 RPC 方案各自适用的集成场景。
  • 站内链接适配 GitHub Pages 的 /Learn-AI/ 子路径，外链带 target="_blank" 与 rel="noopener noreferrer"。
  • 索引生成器、脚本语法检查、全部现有测试、新增专题测试、站点验证和生成器幂等检查全部通过。
