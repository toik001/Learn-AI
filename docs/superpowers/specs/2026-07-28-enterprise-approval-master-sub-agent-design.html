企业智能审批与公司主子 Agent 落地实战设计

目标

在 Agent 开发学习分类中新增一篇独立实战页，以采购/费用智能审批为贯穿案例，讲清企业主 Agent、领域子 Agent、确定性工作流、规则引擎、人工审批和业务系统之间的生产边界，并提供 Java 21 + Spring AI 的可迁移实现骨架。

方案选择

  1. 只扩写现有多 Agent 页面：内容分散，难以形成完整企业案例，不采用。
  2. 新增独立实战页并与现有课程互链：采用。既能完整呈现落地闭环，也能复用已有多 Agent、安全和生产部署课程。
  3. 直接创建可运行审批项目：超出本次“场景说明”的范围，不采用。

核心架构决定

  • BPMN/工作流引擎拥有流程状态、等待、超时、升级和人工任务；DMN/规则服务拥有硬规则与路由；Agent 不替代二者。
  • 主 Agent 是受限协调器，不是超级管理员：负责理解目标、建立 case、分派子任务、合并证据和生成审批提案，无最终批准权。
  • 子 Agent 按业务能力和工具权限拆分：材料理解、制度检索、预算核验、供应商/合规风险；它们返回版本化结构化证据，不互相转发完整聊天。
  • 最终审批由业务授权人或确定性规则完成。Agent 只能建议 APPROVE、REJECT、REQUEST_INFO 或 ESCALATE，不能直接写入最终审批结果。
  • 执行 ERP/财务/采购系统副作用前再次鉴权，绑定提案 hash、审批人、策略版本、幂等键和审计事件。

页面结构

  1. 核心结论、场景假设、价值与不适用边界。
  2. 八步智能审批闭环图和公司主/子 Agent 组织拓扑图。
  3. 采购申请案例逐步演示，包括正常、补件、拒绝和升级路径。
  4. 主 Agent、四类子 Agent、规则引擎、工作流和审批人的职责/工具/禁区矩阵。
  5. 公司级实际应用场景：采购、报销、合同、入职、IT 服务、销售报价。
  6. 领域契约、状态机、数据表和 Java 21 记录类型。
  7. Spring AI 多 ChatClient、角色工具和确定性 Coordinator 代码骨架。
  8. 权限、审计、Prompt Injection、失败恢复、幂等、预算与可观测性。
  9. MVP → 辅助决策 → 低风险自动化三阶段上线计划和验收指标。
  10. 常见反模式、实施检查单、参考资料和相关课程链接。

内容边界

  • 不声称多 Agent 一定优于单 Agent；页面必须给出拆分门槛和单 Agent/固定工作流替代方案。
  • 不把模型置信度当作授权，不把自然语言制度文本当作唯一规则源。
  • 不展示可绕过权限的通用“执行任意审批”工具。
  • Spring AI 示例使用官方 ChatClient、ToolCallback/@Tool 能力，但明确业务 Coordinator、BPMN/DMN、审批和持久状态由应用基础设施拥有。
  • Camunda 仅作为 BPMN/DMN 实现示例，架构保持工作流引擎中立。

验证标准

  • 页面满足项目 HTML 元数据、语义标签、核心结论、参考资料、稳定标题 ID 和共享资源要求。
  • 至少两张可访问图、五张决策/职责表、四段 Java/配置/数据示例。
  • 明确出现“Agent 只生成提案，最终决定由规则/授权人完成”等关键边界。
  • 主目录、多 Agent 课程、安全课程与新页面双向可达。
  • 官方外链来自 Spring AI、Camunda、NIST 等一手来源，记录检索日期 2026-07-28。
  • 索引生成、分类导航、目录、站内链接、锚点、脚本语法和现有回归测试全部通过。

自审结果

未发现占位符、互相矛盾或多义要求。本设计限定为一篇生产落地实战页及必要的导航/样式/测试修改，不扩展为完整审批产品。用户已授权所有人工判断采用最佳建议并直接确认，因此选择方案二并进入实施计划。
