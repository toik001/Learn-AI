Harness、Loop、Graph 与企业审批 Agent 四篇课程设计

目标

把 Harness、Loop、Graph 从容易混淆的术语拆成三篇可独立阅读的学习页，再用一篇企业智能审批 Agent 实战将三者组合起来。读者以 Java 全栈开发者为主；课程同时解释原理、实际开发方法和生产上线约束，而不只罗列框架 API。

采用的内容方案

采用“递进课程 + 同一审批案例 + 双轨实现”。Harness、Loop、Graph 三篇分别建立概念边界，并持续映射到同一个企业审批场景；整合篇给出端到端项目方法。每篇的实现部分分为两条轨道：

  1. 无 Agent 框架：使用 Java 21、Spring Boot、普通接口与状态机展示最小机制，帮助读者看见概念本体。
  2. Spring AI：使用 Spring AI 官方能力完成模型调用、工具调用、结构化输出、顾问链和可观测性集成，同时保持领域状态、权限、重试和审批责任归属于应用。

不采用纯框架教程，因为它会把 Harness、Loop、Graph 错误等同于特定 API；也不采用只做一个长项目页的方案，因为三种概念将难以独立检索和复习。

四篇页面边界

  1. Harness：解释模型外围的上下文、工具、权限、沙箱、结构化契约、测试、评测、日志、指标、Trace、恢复和安全护栏。审批案例聚焦“让提案 Agent 在受控环境中可靠工作”。
  2. Loop：解释 Observe–Decide–Act–Verify、成功/预算/升级三类停止、重试与退避、幂等、上下文压缩、失败分类和人工接管。审批案例聚焦“材料缺失—补件—重试—升级”的动态闭环。
  3. Graph：解释 State、Node、Edge、Router、Checkpoint、并行汇聚、循环边与人工节点，区分确定性工作流图和模型动态拆分。审批案例聚焦“收件—并行核验—规则路由—会签—执行”的可恢复状态图。
  4. 整合实战：从需求分析、风险分级、架构、领域模型、接口契约、两条实现轨道、测试评测、灰度上线到运维复盘，构建企业智能审批 Agent。明确模型只生成有证据的建议，确定性规则负责硬门禁，授权人完成高风险决策，受限执行器实施副作用。

图表设计

  • Harness 页：分层架构图、一次审批请求时序图、能力与线上风险矩阵。
  • Loop 页：循环结构图、停止与升级决策图、重试/成本/故障对照表。
  • Graph 页：审批状态图、并行核验与汇聚图、Graph 与普通函数/Loop 的选型表。
  • 整合页：Harness 包裹 Graph、节点内部运行 Loop 的组合图；端到端部署图；分阶段上线与 SLO 表。

图形优先使用语义化 HTML/CSS，保证无外部脚本、暗色主题和移动端下仍可阅读；每张图提供可访问文本说明。比较关系使用 HTML 表格，不依赖远程图床。

项目开发方法

  1. 先识别必须确定性的业务规则、风险等级和人工审批点，再决定哪里允许模型参与。
  2. 先实现无框架版本的领域接口、状态、工具边界和验收测试，再接入 Spring AI 适配器。
  3. 将提示、模型、工具和策略版本化；将审批事实、证据与执行记录持久化，不把聊天历史当业务数据库。
  4. 用契约测试、场景测试、离线评测、对抗测试和线上观测覆盖正确性、安全、成本与恢复能力。
  5. 按 shadow、辅助决策、低风险自动化三个阶段上线，高风险写操作始终要求授权和幂等保护。

代码与框架边界

  • Java 版本为 21，构建与依赖片段采用 Maven；示例保持可迁移，不承诺仓库内生成完整可运行产品。
  • 无框架轨道展示 ModelClient、Tool、AgentState、LoopRunner、ApprovalGraph 等普通 Java 抽象。
  • Spring AI 轨道映射到 ChatClient、结构化实体映射、@Tool/ToolCallback、Advisor、Observation 与模型可替换配置。
  • Spring AI 不拥有审批业务状态、最终授权和外部系统副作用；这些由数据库、规则组件、工作流/应用服务和受限执行器负责。
  • 不引入另一套 Agent 框架作为主实现；LangGraph、OpenAI Agents SDK 等只用于官方概念或行业实现对照。
