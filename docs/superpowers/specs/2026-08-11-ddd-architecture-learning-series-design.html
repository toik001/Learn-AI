DDD 架构七篇学习专题设计说明

目标与读者

为具备 Java 与 Spring 基础、希望系统掌握领域驱动设计（Domain-Driven Design，DDD）的开发者创建七篇递进式中文学习页面。专题既解释 DDD 的基础概念、战略设计与战术设计，也比较经典四层架构、六边形架构、洋葱架构和整洁架构的依赖逻辑，并通过订单领域的 Java 21 代码片段展示如何落地。

读者完成专题后，应能区分问题空间与解决方案空间，使用统一语言讨论业务，通过子域和限界上下文划分模型边界，使用实体、值对象、聚合、仓储、领域服务和领域事件表达模型，并能根据场景选择分层方式。读者还应理解 DDD 与微服务、CQRS、事件溯源之间是可组合但非强制绑定的关系。

采用的内容方案

采用七篇渐进式专题。相较五篇浓缩版，七篇能够给战略设计、战术设计和分层架构各自独立的讲解空间；相较九篇参考手册版，七篇保留清晰主线，避免初学者在事件风暴、CQRS 和事件溯源等扩展主题中失去重点。

  1. DDD 总览与学习路线；
  2. 基础概念与统一语言；
  3. 战略设计：子域、限界上下文与上下文映射；
  4. 战术设计：实体、值对象、聚合、仓储与领域服务；
  5. DDD 分层架构：经典四层、六边形、洋葱与整洁架构；
  6. 订单领域 Java 实践：领域模型、用例、端口适配器、事件与测试；
  7. 落地方法：事件风暴、CQRS、模块化单体、微服务边界、误区与演进。

七篇形成“理解语言 → 划分边界 → 构建模型 → 组织依赖 → Java 实践 → 生产演进”的学习路径。

七篇页面边界

  1. 总览与学习路线：建立 DDD 全景图，解释战略设计、战术设计与架构模式之间的关系，给出七篇阅读顺序、前置知识、术语入口和学习验收标准。只提供鸟瞰，不重复后续页面的完整推导。
  2. 基础概念与统一语言：解释领域、领域模型、统一语言、模型驱动设计、问题空间与解决方案空间；说明模型不是数据库表的映射，统一语言也不是静态术语表。通过订单场景展示业务对话、代码命名和模型反馈如何互相校正。
  3. 战略设计：讲解核心域、支撑域、通用域、子域、限界上下文和上下文映射。覆盖 Partnership、Shared Kernel、Customer/Supplier、Conformist、Anti-Corruption Layer、Open Host Service 与 Published Language 等主要关系，并说明组织边界、模型边界和部署边界并不天然相等。
  4. 战术设计：讲解实体、值对象、聚合、聚合根、领域服务、领域事件、仓储、工厂和规约。重点解释身份、不可变性、不变量、一致性边界、事务边界和跨聚合协作；避免把每个数据库表都建成聚合，也避免把全部逻辑塞入 Service。
  5. 分层与架构模式：对比传统三层、DDD 经典四层、六边形架构、洋葱架构和整洁架构。统一从核心目标、依赖方向、典型目录、输入输出边界、框架位置、优点、成本、适用场景和常见误用分析。明确四种 DDD 友好架构并非互斥产品：它们使用不同术语强调“业务核心不依赖外部技术细节”的共同原则。
  6. Java 订单领域实践：以 Java 21 和 Spring Boot 工程语境展示订单聚合、订单项、Money 值对象、创建订单用例、仓储端口、数据库适配器、领域事件和单元测试。代码片段能够按页面说明组合运行，但本次不创建独立 Spring Boot 工程，不展开数据库迁移、认证、部署等外围配置。
  7. 落地、演进与误区：讲解事件风暴如何发现领域事件与边界，比较模块化单体和微服务，说明 CQRS、最终一致性和事件溯源的采用条件。给出从事务脚本到领域模型的渐进路线，并分析贫血模型、过度建模、聚合过大、跨聚合强事务、按数据库表拆服务和把包名当架构等常见问题。

贯穿案例与代码边界

订单/交易场景贯穿七篇。战略设计阶段区分订单、支付、库存和商品目录等限界上下文；战术设计阶段聚焦订单上下文内部模型；Java 实践阶段实现“创建订单”主用例，并以“订单已创建”领域事件展示边界内状态变化和边界外协作。

代码使用 Java 21，优先采用不可变值对象、record、显式构造器和领域行为方法。领域模型不依赖 Spring、JPA 或 Web 类型；应用层表达用例和事务边界；端口表达领域或应用需要的能力；适配器负责 HTTP、持久化和消息设施。Spring 注解只出现在组合根或外围适配器示例中。

示例必须包含正常路径与至少一个不变量失败测试，例如拒绝空订单或非正数金额。代码块使用正确转义的 <pre><code>，标明 Java 版本、所属层和预期行为。

图片与视觉语言

用户已在视觉预览中选择“A · 工程蓝图”。专题图片统一使用精确中文标签、节点、分组、连接线和箭头，不使用装饰性照片或难以核验的生成式文字。图片以仓库内 SVG 文件保存到 public/assets/ddd/，通过相对路径嵌入知识页面。

计划制作至少九张图片：

  • 总览页：DDD 全景图、七篇学习路线图；
  • 基础概念页：统一语言反馈循环图；
  • 战略设计页：子域与限界上下文关系图、上下文映射图；
  • 战术设计页：聚合一致性边界图、战术构件关系图；
  • 分层架构页：四种架构对比图、依赖方向图；
  • Java 实践页：创建订单用例调用链与领域事件流图；
  • 落地演进页：模块化单体到微服务的演进决策图。

“至少九张”允许一个 SVG 同时承担紧密相关的双面板比较，但七篇每篇必须至少嵌入一张核心图。每张图使用 <figure>、非空 alt 和 <figcaption>，正文提供等价文字说明。颜色只辅助分类，边框、标签、位置和线型承担主要语义；图片在桌面、手机、浅色和深色环境中保持可读。所有图片均为本专题自行绘制，不复制书籍或网站图片。

统一页面结构与导航

七篇页面写入 public/notes/architecture/，文件名使用日期 2026-08-11 与简洁中文关键词。分类元数据统一为“软件架构与 DDD”。页面复用 public/assets/style.css 和 public/assets/app.js，不新增第三方前端依赖或远程资源。

每篇至少包含语义化 header、nav、main 和 article，并在 head 提供 description、study-category 与 study-date。每页保留“核心结论”和“参考资料”，按主题加入概念解释、Java 对照、示例、误区、练习或验收清单。标题使用稳定唯一 ID，七篇通过显式专题导航互链；站点生成器继续维护分类侧栏、上一篇/下一篇、根入口和清单。

资料调研与事实边界

资料检索截面固定为 2026-08-11。优先使用 DDD Community、领域驱动设计作者公开资料、Martin Fowler、Microsoft Architecture Center、相关模式作者页面和权威书籍公开页面。基础定义与模式来源尽量交叉核验；易受解释影响的术语明确标注语境。

页面区分三类内容：“来源定义”表示资料直接陈述，“工程解释”表示为 Java 开发者提供的概念转译，“实践建议”表示根据场景给出的取舍。不会把某个框架的目录结构写成 DDD 标准，也不会把微服务、CQRS、事件溯源或六边形架构描述成实施 DDD 的强制前提。外部资料链接使用 target="_blank" 与 rel="noopener noreferrer"，关键结论在正文附近标注来源。

分层比较方法

分层架构页面使用同一维度比较传统三层、经典四层、六边形、洋葱和整洁架构：

  • 要解决的主要问题与核心隐喻；
  • 业务规则位于何处以及编译期依赖指向；
  • 输入、输出、持久化和框架分别位于何处；
  • 典型 Java 包结构与接口归属；
  • 测试隔离、替换技术设施和演进边界；
  • 引入成本、适用复杂度与常见误用。

比较不使用主观总分。选择建议基于业务复杂度、变化频率、团队规模、技术生命周期、测试要求和外部系统数量，避免把层数越多等同于架构越成熟。

测试与生成策略

  • 新增 DDD 七篇专题契约测试，断言目标页面存在，元数据、核心结论、参考资料和专题互链完整。
  • 断言战略设计、战术设计、分层比较、Java 实践和落地演进页面包含约定关键概念，避免只有标题而缺少核心内容。
  • 断言七篇每篇至少存在一个 <figure>、本地 SVG 图片、非空替代文本和图注，并验证图片文件存在。
  • 复用现有站点测试与 scripts/verify-site.mjs 检查语义结构、元数据、相对链接、标题 ID、外链安全属性、共享资源和 GitHub Pages 子路径。
  • 运行 node scripts/build-html-index.mjs 更新根目录 index.html、分类侧栏、上一篇/下一篇和 public/manifest.json。
  • 重跑生成器并检查 git diff --exit-code -- index.html public，确认生成结果幂等；最后运行 git diff --check。

验收标准

  • 恰好新增七篇 DDD 学习页面，职责与本设计一致并可按推荐顺序连续阅读。
  • 读者能够解释战略设计与战术设计的区别，并把订单、支付、库存和商品目录划分为有依据的模型边界。
  • 读者能够从统一维度比较经典四层、六边形、洋葱和整洁架构，并理解它们共同的依赖原则与术语差异。
  • Java 实践包含订单聚合、值对象、应用用例、仓储端口、适配器、领域事件和单元测试，并保持领域模型独立于 Spring/JPA/Web。
  • 七篇每篇至少一张工程蓝图图片，合计至少九张；图片使用本地相对路径，标签准确，并具有替代文本、图注和正文等价说明。
  • 每篇都有核心结论、参考资料、资料检索日期、专题导航和稳定标题 ID。
  • 索引生成器、脚本语法检查、全部既有测试、新增专题测试、站点验证和生成器幂等检查全部通过。

自审结果

占位符扫描通过，页面、内容数量与实施边界均已确定。七篇职责互不冲突：总览负责导航，基础页建立语言，战略页划分模型边界，战术页构建边界内部模型，架构页组织依赖，Java 页落实主用例，演进页处理团队和系统规模变化。订单案例贯穿但不扩展为独立工程；图片固定为可精确标注的本地 SVG；资料检索、页面生成和验证均有明确边界。范围足以形成一次完整、可测试的交付，不包含无关的数据库、认证或部署实现。
